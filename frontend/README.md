# frontend_2027

律师的作业台 —— 新一代前端。

现有 `frontend/` 本质是 Django Admin 的 React 复刻（菜单按数据表切），所以它必然长得像后台。
`frontend_2027` 是一次**换轴**：导航按「律师的动作」切，不按数据表切。技术栈沿用，不换。

## 定位

| | |
|---|---|
| 使用者 | 单人律师 |
| 切入点 | 材料预处理 + 办案 |
| 长期目标 | all-in-one（逐步替代现有 frontend） |
| 与现有 frontend 的关系 | 并行存在，共用同一套 `/api/v1`，逐步迁移 |

单人使用意味着**不做**：权限体系、多角色、协作与审批流。评价标准只有一条 —— 顺不顺手。

## 顶层导航（两个入口）

品牌名：**法穿 AI Copilot**（不是「作业台 2027」）。

| 入口 | 回答的问题 |
|---|---|
| **材料预处理** | 这批材料是什么？要拆成几份？ |
| **办案** | 这个案子现在到哪一步了？ |

两条入口是一条线的前后两段：**材料预处理 = 案子还不存在时的材料；办案 = 案子立起来之后的活。**
一个是准备，一个是正事。

**两个入口都必须是「动作」，不能是「实体」。** 这是这块导航唯一容易走偏的地方：

- 第一个入口原叫「接案」，已改名 —— 导航是竖排的，`接案 / 案件` 只差一个字，扫读极易看混；
  而且大部分案件都会接，用「接不接」定义整块功能是错的。
- 第二个入口原叫「案件」，也已改名 —— 它是四个入口里**唯一的名词**，
  而其余入口都是动作。名词当菜单名 = 数据表名当菜单名，正是这套导航要避开的。
  「办案」和「材料预处理」同轴，构成「准备 → 开干」的递进；而且律师说的是「去办案」，
  没人说「去案件」。

**「待办」和「检索」已删**（2026-09-12）。理由：都是「跨入口的辅助能力」，不该占顶层位置 ——
待办的内容其实就是办案列表的一个排序，检索是任何页面都该有的能力。
顶层只留真正互斥、且都是主战场的入口。

**当事人、合同不再有独立菜单** —— 它们从「办案」进入。

## 原型制作规范（硬性）

高保真原型必须满足下面三条。第一版原型就是因为全部违反了才不合格（自创蓝色配色、零交互、写完不检查）。

**一、配色只能来自设计系统，不许自创。**
唯一来源是 `frontend/src/index.css` 的「v4 Zinc Monochrome Design System」：

| 用途 | 变量 | 值 |
|---|---|---|
| 页面底 | `--background` | `#fafafa` |
| 卡片 | `--card` | `#ffffff` |
| 主色（近黑，**不是蓝**） | `--primary` | `#18181b` |
| 边框 | `--border` | `#e4e4e7` |
| 次要文字 | `--text-secondary` | `#71717a` |
| 侧边栏（始终深色） | `--sidebar` | `#18181b` |
| 状态色 | `--status-{green,yellow,red,blue,purple}` + `-bg` | 见 index.css |
| 圆角基准 | `--radius` | `8px`（lg = +4，xl = +8） |

自创配色是原型「不像这个产品」的头号原因。

**二、必须做视觉自检。**
写完用 Playwright 截图，**自己看过一遍再改**：

```bash
backend/.venv/bin/python your_shot_script.py   # 用 backend venv，chromium 已有缓存
```

不要一次写完就交付。「美观」是迭代出来的 —— 第一版截出来发现顶栏是空的、标签用了 4 种颜色、
拖入区过于松散，改完第二版才达标。

**三、交互要真跑。**
标签切换、拖拽反馈、hover、状态流转，用真 JS 实现，不做静态图。

**技术选择**：单文件 HTML + 手写 CSS（无构建、无 CDN、双击可看）。
刻意不用 Tailwind CDN —— 预览环境有 CSP 白名单限制，CDN 可能加载不到。

## 手势约定：浏览优先（2026-09-12 改）

原先把「选页」绑在最贵的手势上：单击就选中、↑↓ 也是挪选择而不是滚动。
但选页是**为跨源合并服务的低频操作**（连续几页成一份用**切两刀**就够了），
却占了单击、拖选文字、↑↓ 三个最高频的手势。**手势的价格要匹配操作的频率。**

实测出来的三条误触路径，改完前后对比：

| 操作 | 改之前 | 改之后 |
|---|---|---|
| 单击页面 | 选中 1 页 | 什么也不做 |
| 在页面上拖着选字 | **也选中了 1 页** | 只选字，不选页 |
| 按 ↓ 想往下滚一点 | **跳一整页 + 选中**（110 → 1434） | 小幅滚动（3107 → 3147） |

**现在的规则**：

| 手势 | 作用 |
|---|---|
| 点击页面 | 什么也不做（有选中时则散开选择） |
| **⌘ / Ctrl + 点击** | 选中 / 取消这一页 |
| **⌘ / Ctrl + ⇧ + 点击** | 从上一次选中处到这一页的区间 |
| 工具栏「选页」开关 | 进入选页模式：此时点即选中、⇧+点 选区间，Esc 退出 |
| **↑↓ / PageUp / PageDown** | 原生滚动（不再被拦） |
| **⌘ / Ctrl + ↑↓** | 用键盘挪选择 |
| `S` | 把选中的页合成一份 |
| `Esc` | 先清选择，再退模式，最后才关阅读器 |

配套改动：

- **拖拽判定**：mousedown 后移动超过 4px 就不算点击。用 `downActive` 门控 ——
  松开手指之后的鼠标移动不会被算进下一次点击（否则第二次点击永远失效）。
- **拖拽后不碰焦点**：`focus()` 会把用户刚选中的文字清掉，所以拖拽分支直接 return。
- **`.rd-flow` 加了 `tabindex="0"` 并在打开时聚焦** —— 不然浏览器不知道该滚谁。
  注意 `.rd` 有 `visibility` 过渡，刚加 `on` 时聚焦不进去，所以过渡结束要补一次 focus。
- **选择条按钮跟着选区换词**：跨了不同源文件就叫「合并为一份材料」，
  没有则叫「独立成一份材料」—— 动词不一样，别让人猜。

## 窄屏适配（2026-09-12 补）

阅读器一开始是 **268 / flex / 296 三栏固定宽**，宽屏好用，窄屏直接把中间那片页面挤没。
现在改成**侧栏逐级收成抽屉，中间永远占满**：

| 视口宽 | 布局 |
|---|---|
| ≥ 1280 | 三栏常驻（左栏 268 / 中栏 flex / 右栏 296） |
| 1100–1280 | 三栏常驻，侧栏收窄（232 / 256） |
| < 1100 | **右栏收成抽屉**，工具栏出现「信息」按钮 |
| < 860 | **左栏也收成抽屉**，工具栏出现「材料」按钮 |
| < 620 | 品牌名收成「法」字块、卡片单列、按钮只留图标 |

几个要点：

- **抽屉定位在 `.rd-main` 内**（`.rd-main{position:relative}`），不是整个 `.rd` ——
  这样顶栏始终可见可用，不会连「归案」按钮一起被盖住。
- 抽屉打开时有半透明遮罩，点遮罩关闭；两个抽屉互斥（开一个自动关另一个）。
- **进入框选取字模式会自动关掉抽屉** —— 要框选就得看得见页面，右栏挡着就没法用。
- 窗口变宽（> 1100）时自动清掉抽屉状态，否则遮罩会残留。
- 卡片墙的 `minmax(300px, 1fr)` 换成 `minmax(min(300px, 100%), 1fr)`，
  容器比 300px 还窄时不再横向溢出。

**验证**：1500 / 1280 / 1100 / 1024 / 860 / 768 / 620 / 390 八档宽度，
卡片墙与阅读器**均无横向溢出**，抽屉按钮按档位正确出现，0 JS 错误。

## 阶段一：先做一版「零 AI」的

整条办案链路（拆分 / 识别 / 建案 / 出文书）的**后端已经全部就绪**，
唯一没有落脚点的是链路最前面那一步：**案件还不存在时的材料**。

所以阶段一要新建一个实体 —— **材料包**：可收任意格式材料、有「待判断」状态、
判断后分流为「接 → 建档」或「不接 → 归档留痕」。

但**第一版不引入任何 AI**，全部人工完成。理由：

1. **AI 会掩盖信息架构的缺陷。** 归案要是得连点 5 下，人工版这个痛是实打实的；
   AI 版会变成「机器猜对了，我只点 1 下」，于是流程本身有多难用，永远发现不了。
2. **人工版能验证 AI 到底有没有必要。** 万一这界面一个月只用 3 次、人工 20 分钟也能接受，
   这块 AI 根本不该做。这个结论只有先做人工版才拿得到。
3. **骨架先定死，AI 才不会反过来绑架产品结构。** 骨架没定就上 AI，
   设计会不自觉迁就「AI 能算什么」。先跑通人工版 = 状态机被钉死。

**关键手法：删功能，不删位置。** 右栏不从界面上拿掉，改由人工填 ——
将来 AI 上线只是换一个填充器，右栏位置和字段结构都不动，界面零改动。

### 被删掉的机器判断（14 号相对 13 号）

**只删「机器替你下判断」的部分，「人工干活」的部分一个都不能少。**

| 位置 | 13 号（目标态） | 14 号（第一版） |
|---|---|---|
| 初始分段 | 机器先分好，标 `confidence` | 每个源文件默认整份一段，人工切 |
| 段头 | 置信度胶囊「待核对 · 58%」 | 「未归类」提醒，点掉即消 |
| 右栏 | AI 侧栏：建议接案 + 抽出的要素 | 材料信息便签，默认只记委托人 + 对方当事人 |
| 归案 | 「AI 已按案号与当事人匹配」 | 搜索框，人工自己找案号 / 当事人 |
| 建合同 | 「AI 已抽出要素，将据此生成合同」 | 就地展开委托人 / 对方 / 标的额让你填 |
| 列表卡片 | 委托人 / 标的额（机器抽的） | 人工标出来的材料类型（如「身份证 · 借条 · 银行流水」） |
| 驱动信号 | 哪些要**核对** | 哪些**没干完** |

### 右栏是便签，不是表单（2026-09-12 定）

原设计把它做成了带「必填」的表单，这是错的。三条归案路里**两条一条信息都不用填**：

| 出口 | 需要的信息 |
|---|---|
| 追加到已有案件 | 无 —— 案件信息早就有了 |
| 新建案件 · 挂已有合同 | 无 —— 合同也是现成的 |
| 新建案件 · 先建合同 | 委托人 / 对方当事人 / 标的额 |

**唯一真正需要信息的时刻是「先建合同」，所以就地在那里补 —— 不把人赶回右栏。**

由此确定：

1. **没有任何必填。** 全空也能一路走完。预处理阶段的任务只有一件事：看清材料、切开、归类。
2. **默认只记两项**：`委托人` + `对方当事人`。这两项是后续无论走哪条路都最常用到的。
3. **其余字段从字段库里自己加**，加错了能删：标的额 / 关键日期 / 事项·案由 / 业务类型 /
   管辖法院 / 案号 / 备注。字段库按 `FIELD_LIB` 定义。
4. **不要「案件类型」这个字段名。** 它把非诉排除了 —— 非诉没有案由，可能是「专项法律顾问」。
   要区分诉讼 / 非诉，用「业务类型」；要说具体事项，用自由文本的「事项 / 案由」。
5. **「对方当事人」可以没有、也可以有多个。** 非诉常常没有对方；诉讼可能连带被告两三个。
   所以是可选字段，多个用、分隔。
6. **在归案面板里补填过的东西，提交时自动记回右栏** —— 填一次就够了，不让人抄第二遍。
7. **「标来源」保留。** 便签上唯一"硬"的功能：点一下再点某一页，就能把这项绑回原文。

### 框选取字（2026-09-12 加）

标来源的时候不止记「第 N 页」，还能**在页面上拖一个框，调本地 RapidOCR 把那块的字取出来**，
填进字段。已实现于 14 号原型。

**为什么这不违反「第一版零 AI」**：RapidOCR 干的是「像素 → 字符」，是机械转换，不是判断。
框哪里、取到的字对不对、要不要采纳，全在人手里。它比「AI 自动抽字段」更可靠 ——
因为结果是人框出来、人确认过的，不存在"机器猜错而你没看"。

**两种拿法，一个入口**：

| 操作 | 结果 |
|---|---|
| 只点一下某一页 | 只记「第 N 页」，不取字 |
| 在页面上按住拖一个框 | 调 OCR 取那块的字 → 结果进面板 → 人确认/修改后填进字段 |

**交互细节**：

- 进入标来源模式后，工具栏下方出现琥珀色提示条写明这两种用法，光标变十字
- 拖框时实时画琥珀虚框；松手后虚框变斜纹 +「识别中…」
- 结果面板标 `RapidOCR` 徽标 + 来源页 + 去向字段，输入框里是识别结果，**可以直接改**
- 三个出口：`重框`（保持字段不变）/ `取消`（什么都不记）/ `填入「委托人」`
- **框可以反复调**：拖框内部平移整块，拖八个手柄（四角 + 四边中点）改大小，hover 才显手柄
  - 面板还开着时调框 → 只更新面板里的识别结果，不动字段
  - 采纳之后调绿框 → 按新框重新识别并写回字段
  - 理由：**框就是「我要这部分」的表达，改了框就是换了内容**，没必要让人重框一遍
- 采纳后页面上留一个**绿色虚线框**在原位，hover 显示「字段名：值」
- 矩形坐标**归一化存 0–1**（`srcRef.rect = {x,y,w,h}`），换分辨率/纸宽都不变形
- 只记页码的字段，页面上用琥珀色整页描边（`.rp.mark`）区分

**页面上得有真字**：14 号把原来的灰条占位换成了真实文字（借条正文、银行流水明细、
身份证/微信/转账的卡片内容）。不这么做，框选就成了对着空白拖框 —— 功能无法自证。
其中关键片段标了 `data-ocr`，**框到哪个就识别出哪个，框大了就多识别几段**，
和真 OCR 返回多个文字块的行为一致。

**取字模式下的两条硬约束**（都踩过坑）：

1. **不能顺手把页选中。** 取字模式本质上和「页选择」是两套交互，混在一起会让只点一下的人
   莫名进入多选态。所以取字模式下 `togglePageAt` 直接 return，进入模式时还会清空已有的页选择。
2. **不能顺手把页面文字选上。** 拖框如果不拦，浏览器会把页面文字选成蓝色高亮，
   看起来像「选到了页面本身」。修法是在 `.rd.picking .rd-flow` 上加 `user-select:none`
   （**注意选择器**：`picking` 类挂在 `.rd` 上，不是 `.rd-flow` 上，写成 `.rd-flow.picking` 是空的）。

另外，面板开着时再拖一个新框，必须**先清掉旧的框元素**，否则旧框会变成孤儿留在页面上
（`document.querySelectorAll('.rp .selrect').forEach(el => el.remove())`）。

### 材料包是个实体：能命名，也能继续收材料（2026-09-12 加）

材料包不是一次性的「收件箱」——收进来的那一刻只是个开始，后面还会陆续来东西。
所以它必须有名字，也必须能追加。

**新建（三条入口，走同一条路）**：

| 入口 | 场景 |
|---|---|
| **拖文件到桌面** | 习惯拖的人 |
| **点顶部「新建材料包」** | 习惯点的人（走真实的文件选择） |
| **点列表里的虚线槽** | 同上，虚线槽同时是拖拽的落点提示 |

三条入口都调同一个 `createBundle(files)` —— **区别只是触发方式，行为完全一致**。
建完停在列表，卡片落在第一位并高亮 2 秒，**不自动进阅读器**
（列表是「待处理队列」，一次可能建好几个包；自动跳转会打断批量收材料的节奏）。

**取消文件选择 = 什么都不做，不建空包。** 材料包就是「一批材料」，没有材料就没有包 ——
不做空状态，就不会有列表里一堆空卡片的问题。（将来若真的需要「先把包建好再慢慢收」，
再加"预留包"这个概念，而不是让新建按钮产生空包。）

**命名**（两个入口，改的是同一个值）：

- 卡片墙上 hover 卡片标题旁的铅笔
- 阅读器顶栏标题旁的铅笔

**追加材料**（两个入口）：

- 阅读器工具栏的 `+ 追加材料`（走真实的文件选择）
- **把文件直接拖进阅读器** —— 出现「松手即追加到「XXX」」的琥珀色遮罩，松手即入

**拖放的靶子是整个阅读器，不只是中间那片页面。** 拖到「+ 追加材料」按钮上、拖到左栏材料清单上、
拖到右侧材料信息栏上，都算追加 —— 三个地方都是"这个材料包的地盘"。
拖拽进行时 `+ 追加材料` 按钮会被点亮（琥珀边框 + 淡黄底），明确告诉人"松手就是这儿"。
（按钮的 `title` 也写明「点这里选文件，或把文件直接拖到这儿」。）

**追加之后**：

- 新源文件按上传顺序接在左栏末尾，并**高亮 2 秒**（提示"这几份是新来的"）
- 每份新源文件生成一整段，类型空着 —— 和新建材料包时的初始状态一样
- 顶部进度、左栏统计、主区页数全部更新
- **卡片墙上那张卡同步更新**：页数、进度条、状态胶囊、"N 份未归类"
  （这个同步是双向的 —— 在阅读器里归类几段再回到列表，卡片的进度就是对的）
- **已有的拆分和归类一个都不动** —— 追加是在既有基础上继续，不是重新开始

**每个材料包各存各的材料。** `MATS` / `SEGS` 在打开某个包时被指向它的
`d.mats` / `d.segList`（引用赋值），之后的 `push` / `splice` 都是原地改，两边自动同步。
所以新建的包点开就是自己的文件，在 A 包归类几段切到 B 再切回来，状态还在。
注意 `d.segs` 是**段的数量**（卡片进度用），段的数组叫 `d.segList`，别搞混。

**一处原型的妥协**（真机交给后端）：页数是猜的 —— 图片算 1 页，其他按 `file.size` 估 1–9 页。
真机由后端解析后返回真实页数。

### 一个顺带修掉的键盘隐患

全局快捷键（`↑↓` 选页、`S` 切分、`空格`/`Esc` 收起、`Enter` 打开材料包）原本会**穿透输入框**。
后果很实在：在段名输入框里敲个 `s` 会触发切分；在材料包名输入框里按 `Esc` 会关掉整个阅读器；
在 OCR 结果框里按方向键会翻页。

修法是一道总守卫，放在全局 keydown 的第一行：

```js
if (e.target && e.target.closest && e.target.closest('input, textarea, select')) return;
```

### 后端要补的第三处：框选 OCR 接口

```text
POST /api/v1/material-bundles/{id}/ocr
body: { material_id, page, rect?: {x, y, w, h} }   # 归一化 0–1；省略 rect 则整页
resp: { blocks: [ { text, box: {x, y, w, h}, score } ] }
```

**实现建议：不要「按 rect 裁图再 OCR」，而是「整页 OCR 一次，用 rect 过滤文字块」。**

理由（`backend/apps/automation/services/ocr/ocr_service.py` 已经具备条件）：

1. `OCRService.recognize_with_boxes(image_path)` **本来就返回文字块 + 坐标**，不用新造轮子
2. 一次识别，多个字段复用 —— 同一页框 5 个字段只跑一次 OCR，而不是跑 5 次
3. 文字块是 OCR 的自然输出粒度，不会把字切一半（裁图再识别就可能切到字的中缝）
4. 顺带能让前端把**所有**识别出的文字块都画出来 —— 人点一下就能选中，
   根本不用精确拖框，拖框只是"我懒得点"时的模糊输入

> 注意 `recognize_with_boxes` 目前带 `# pragma: no cover`，可能从未被实际调用过，动手前先跑通。
> 返回的 box 是图像像素坐标，要用页面尺寸归一化后再和前端传来的 rect 做交叠判断。

### 画布缩放（2026-09-12 加，替掉了「纸宽四档」）

原来的「纸宽」四档（960 / 720 / 520 / 340）有个硬伤：**它是 `max-width`，小屏下完全失效** ——
容器比它窄时 `width:100%` 说了算，所以屏幕一小，点纸宽根本不动。
而且它只有"缩"，没有"放"。

现在换成工具栏上的 **`− 100% +`** 画布缩放：

| 操作 | 效果 |
|---|---|
| `−` / `+` | 在 35/45/55/70/85/100/120/140/165/200/250/300% 之间走 |
| 点中间百分比 | 回到 100%（= 适应宽度） |
| 到两端 | 对应按钮置灰 |

**100% 的定义是「适应宽度」**：单页先铺满可用宽，再受 960px 上限约束。
所以在 900px 窗口里 100% 就是 644px 的页，在 2560px 屏上 100% 是 960px 的页。

**三个值由 `applyZoom()` 一起算出来**（都设在 `.rd` 上）：

- `--pgw` 页宽 = `min(960, 可用宽 ÷ 列数) × 缩放`
- `--roww` 行宽 = `页宽 × 列数 + 间距 × (列数-1)`
- `--ptz` 字号 = `12.5 × 页宽 ÷ 960` ← **字号跟页宽等比，缩小时看起来就是"整张纸变小了"，版式一点不变**

**放大超过视口宽时靠左对齐**（`.rd.zwide`）—— 居中的话左边那截会永远滚不到。
实测：1500px 屏放到 140% → 页宽 1277 > 936，横向可滚 341px；
而 **2560px 屏放到 140% → 页宽 1344 < 1996，不产生滚动** ——
大屏放大是"充分利用宽度"，小屏放大才需要滚，两种情况都对。

> 为什么不直接用 CSS `zoom`：试过了，**`zoom` 下 `width:100%` 永远"填满容器"**，
> 所以放大永远不会溢出（实测 140% 时页宽还是 936）。缩小有效、放大无效。
> 改成 JS 算尺寸后两种都精确。

**`--cols` 不能声明在 `.rd-flow` 上** —— 那会遮蔽 `applyZoom` 设在 `.rd` 上的值
（自定义属性是继承的，但自身声明优先）。曾经因为这个，列数按钮完全失效。

### 并排列数（2026-09-12 加）

单页是默认，也是「像 PDF 一样读」的形态。但**屏幕宽到放得下两个原尺寸的页时，单页就是浪费**
（外接大屏上中栏能到 1996px，单页 960 空掉一半）。

**关键区分：否决过的是「把页缩小强行并排」，不是「并排」本身。**
13 号方案里写过「多页横向并排 = 缩略图墙逻辑，违反阅读顺序」—— 那是对的，
因为页被缩小就读不清。但如果每页仍是原尺寸、只是屏幕放得下两个，
那就没有读不清的问题，只剩一次横向扫视 —— **2 列就是翻开的书。**

**做法**：

- 工具栏「列数：N」按钮，点击递增，到当前窗口上限后再点回到 1
- **上限按可用宽度算**：`floor((可用宽 + 18) ÷ (360 + 18))`，即每列至少 360px
- **宽度不够就置灰并说明原因**（"并排至少要有 738px"），点了没反应比置灰更困惑
- 窗口变小时自动把列数夹回上限

**结构上的两个必要改动**（否则多列会散架）：

1. **段头必须横跨整行。** 段现在是容器（`.seg`）—— 段头（`.sh`）占满一行，
   段内的页在 `.sgrid` 里按列排。段头宽度 = `pgw × 列数 + 间距 × (列数-1)`。
   段头只占一格的话，段的边界就看不清了。
2. **切缝挪进了页格里。** 它原来是两页之间的独立元素，在 grid 里会占掉一格导致错位。
   现在每个页格是 `.cell`（切缝在上、页在下），**每段的第一个页格放一个等高的占位条**
   保证各页顶对齐。单列时切缝正好落在两页之间，和多列完全一致 ——
   而且语义反而更准了：它就是「在这页之前切开」。

**验证**：2560px 下能切到 5 列（列宽 385px），同一段内的页确实并排（top 相同）、
段头横跨整行 1996px；700px 下按钮正确置灰。多列下 ⌘+选页、框选取字、
`S` 独立成段、点切缝切开全部正常。

## 办案页（`prototype/16-办案.html`，2026-09-12）

第二个入口。**它回答的是「我手上这些案子，各自卡在哪一步」** ——
和材料预处理的根本区别：材料预处理是个**队列**（处理完就消失），
办案是**进行中的承诺**（有外部期限，有对方在等）。

### 列表：卡片的第一信息是「下一步」

```
│ 李某 涉嫌危险驾驶                    09-13 还有 1 天   ← 案件名（主，可两行）
│ [刑事] (2026)粤0106刑初312号                          ← 类型 · 案号（弱）
│ → 会见（已批捕，48 小时内）                            ← 下一步（动作，次主）
│ 委托人 李某                                4 份材料  ← 元信息（最弱），贴底
```

**如果卡片只显示当事人 / 标的额 / 类型，那就是一张档案卡，不是作业台。**

> **类型用后端 `SimpleCaseType` 的真实枚举**（民事 / 行政 / 刑事 / 申请执行 / 破产），
> 不自己编。**已知缺口：没有「非诉 / 常年顾问」这一档** —— 候选集非诉业务会被迫错标成
> 民事，需要反馈后端加枚举。
>
> 案件名允许两行（`-webkit-line-clamp:2`）。「某某贸易 不服市场监管处罚」单行会被截成
> 「某某贸易 不服市场监管...」，**分不清是哪个案**。

- **左侧 3px 竖条 = 紧迫度**：案件卡片没有缩略图，靠这条竖条给一个视觉锚点，扫一眼就知道哪些急。
  灰 → 琥珀 → 橙 → 红 = `>21 天 / ≤21 天 / ≤7 天 / 已过期。
- **「下一步」不用灰底方块**（第一版是个 39px 的灰块塞一行字，很丑。改成普通一行，靠位置和字号表达它是次主信息。
- **层次只有四行**。`grid-auto-rows:1fr` + `.cmeta{margin-top:auto}` 让所有卡片等高、元信息贴底。

刻意的取舍：**没有缩略图**。材料包卡片有纸张堆叠图（"刚收进来的实物"），案件卡片是"已在办的事"，靠左侧紧迫度竖条 + 文字层次就够了。

**三种视图**（顶部切换，都是同一个列表，只是排序/分组不同）：

| 视图 | 什么时候用 |
|---|---|
| **按紧急度**（默认） | 日常。有临近事项的排前面 —— **打开办案页就等于看到了待办** |
| **按类型** | 想知道"我手上几个刑事" —— 分组头 + 组内按名排序 |
| **按当事人** | 老客户 / 顾问单位：折叠分组，展开就是他名下全部案子 |

后两个是同一套分组机制（`keyOf()` + `.grphead`），按紧急度**不分组** ——
分组会打断紧急度的阅读顺序。

### 详情：材料 + 案件信息 / 事项

- **中间是材料**，复用材料预处理阅读器的全部能力（段头 / 切缝 / 缩放 / 列数 / 拖放追加）。
  左栏**按批次分组**（"第 1 批 · 3/12 收"）—— 谁发的、什么时候来的，这条线不能断
- **右栏 = 案件信息 + 下一步 + 备注**。事项列表分「未完成 / 已完成」，
  **已完成的那组就是轻量时间线**，不单开时间线模块

### 几个已经定下的判断

- **「下一步」不新建实体**：直接给 `reminders.Reminder` 加"完成"状态即可，
  它已经有 content + due_at + 8 种类型。律师的"下一步"九成本来就带期限。
- **文书不单开模块**：起诉状 / 答辩状 / 代理词本质就是一类材料，走材料的段类型。
  文书**生成**是 AI 的活（第二版），文书**存放**现在就有。
- **阶段：原型里不画**（2026-09-12 用户纠正）。后端 `Case.current_stage` 字段确实存在，
  枚举 18 个（一审 / 二审 / 执行 / 劳动仲裁 / 行政复议 / 侦查 / 审查起诉 / 死刑复核 …），
  **但库里没数据**。我原来编的三套「诉讼 / 仲裁 / 非诉」阶段体系跟后端对不上，已作废。
  将来真要用，模型仍是 **A 字段为主**（点一下推进），侧栏挂「前序 / 后续案件」链接兜住
  `previous_case` 案件链 —— 不把它做成主视图，否则界面变成"我在链上第几环"，理解成本高。
- **通则：原型里出现的每个字段都要能指回后端真实字段、且有数据。**
  没数据支撑的 UI 不画 —— 画了就是给自己造返工。
- **不开「当事人」「合同」独立页面**：那等于回到按数据表切导航。
  跨案件视角用列表的「按当事人」视图兜住；合同只在案件侧栏显示摘要 + 到期日。
- **利冲比对第一版不做**，但**每个案子都要把「对方当事人」记全** ——
  利冲的难点从来不是检索，是历史数据够不够全。

### 原型的取舍

- **新建案件**是直接加一个空白案件并打开（顶栏铅笔改名、右栏填信息），
  没有做"从合同出发"的表单 —— 那是下一步。
- **框选取字**在办案页**没有接入口**（右栏换成了案件信息，没有"标来源"按钮）。
  代码还在，需要时接上即可。
- **材料内容是示例**：只有借条那一套写实文案，其余按文件名生成占位页，
  且明确标注为示例 —— 原型不编造真实案情。
- 数据全是假的，但**字段名按后端实际模型来**（`Case` / `CaseParty` / `Reminder` / `Contract`），
  将来对接不改名。
