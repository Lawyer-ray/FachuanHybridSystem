### 新功能

#### feat(labor_arbitration): 新增劳动仲裁文书爬虫（本市人社局仲裁裁决书公开）

> 分支：`feat/labor-arbitration-crawler`

**背景**

本市人社局在各区公开「终局仲裁裁决书 / 非终局仲裁裁决书」列表（6 个来源）。列表页为服务端渲染的静态 HTML，详情页正文是扫描图片。此前系统没有针对该类政府公开文书的采集能力，律师需要手动逐页查看与摘录。

**变更**

新增独立 app `apps.labor_arbitration`，复用项目既有基础设施（Playwright 公共服务 `create_browser`、文档解析 `get_document_parser`、Django-Q `submit_task`、Media 路径工厂），而非另起炉灶：

1. **数据模型**（`models/`）
   - `ArbitrationDocumentSource`：爬取来源（区县 / 列表页 URL / 启用 / 解析后端 / 最大翻页数 / 详情图容器与图片选择器 / 上次爬取状态与摘要），含 `District`、`ParseBackend`、`CrawlStatus` 枚举与 `trigger_update()` 方法。
   - `ArbitrationDocument`：单篇文书（标题 / 案号 / 详情 URL / 发布日期 / 内容指纹 / 爬取与解析状态 / 解析文本与 Markdown），`detail_url` unique，含 `trigger_parse()` 方法。
   - `ArbitrationDocumentImage`：文书扫描图片页，不下载图片到本地，只保存原图 URL（`source_url`），供后续 OCR 按需拉取。

2. **爬虫**（`services/crawler.py`，`FoshanLaborAwardCrawler`）
   - **HTTP 接口抓取**：调用 `postmeta/i/{category_id}.json` 一次拿全部文章（title/url/date/publish_time），无需 cookie、无需翻页、无需浏览器。
   - **增量爬取**：已存在的 `detail_url` 直接跳过，只入库新条目。
   - 详情页正则提取扫描件图片 URL（`img/.../post_N.png`），OCR 按需拉图，用后清理。
   - `ArbitrationDocumentSource` 新增 `category_id`（6 个来源映射：市直 42087/来源2 41998/来源3 41999/来源4 42000/来源5 42001/来源6 42002）。

3. **文档解析**（`services/parsing_service.py`）
   - 直接调用项目的文档解析服务程序入口 `get_document_parser(backend=...).parse_document(...)`，逐页 OCR 后拼接文本与 Markdown 写回模型。
   - **集成 Doxify clean**：OCR 文本通过后处理清理页眉页脚、归一化脚注、接回跨页段落，提升可读性。
   - 支持 local / mineru / textin / auto 后端。

4. **Admin（用户明确要求）**
   - 来源 Admin：详情页「**增量更新**」按钮 + 列表批量「增量更新选中的来源」。
   - 文书 Admin：详情页「**调用文档解析**」按钮 + 列表批量解析；详情页「**显示图片**」按钮（懒加载，点击后 JS 动态拉取原图）；图片数与解析状态列；详情页重试抓取按钮。
   - Admin 搜索：覆盖 `get_search_results`，先 PostgreSQL FTS 全文搜索（`search_vector`，GIN 索引），无命中则 ILIKE 搜索 `title` / `case_number` / `detail_url` / `parsed_text`。

5. **PostgreSQL 全文搜索**
   - `ArbitrationDocument` 新增 `SearchVectorField`（`search_vector`）+ GIN 索引 `labor_doc_search_gin`。
   - `save()` 自动回填搜索向量（`to_tsvector('simple', parsed_text)`）。
   - `INSTALLED_APPS` 新增 `django.contrib.postgres`。

6. **管理命令**
   - `seed_labor_arbitration_sources`：幂等写入 6 个来源。
   - `crawl_labor_arbitration`：CLI 全量/单来源/限条数爬取。
   - `generate_embeddings`（已回退）：批量生成 Bge-m3 语义向量，后因检索效果不佳已回退。

**验证**

- `ruff check apps/labor_arbitration`：**All checks passed!**
- `manage.py check`：**System check identified no issues**
- 6 个来源全部跑通，10,880 篇文书入库，838 条图片 URL 提取成功（某来源 4 篇详情页因图片链接缺失/页面改版抓取失败）。

### 修复

#### fix(labor_arbitration): 案号正则兼容全部格式 + Admin 展示爬取时间

> 用户发现：①文书列表无「爬取入库时间」字段；②大量文书案号提取为空；③存在较多失败记录。

**问题定位**
1. **爬取时间**：`ArbitrationDocument.created_at`（`auto_now_add`）未在 Admin 展示。
2. **案号提取为空**：原正则过窄，只认全角〔〕+连续数字，而站点案号格式极杂——半角 `[]`、全角 `（）`、方头 `【】`、花括号 `{}`、括号混用 `〔)`、多案号顿号分隔（`7615、7616号`）、某来源用「劳人仲裁字」、另一来源用「仲案终字/仲案案字」、部分无区名前缀、部分缺「字」、部分无「号」结尾。共 917 篇（10.8%）提取失败。
3. **失败记录**：32 篇 failed = 28 篇详情页 `goto` 超时 + 4 篇无图片，属网络抖动。

**修复**
1. `_CASE_NO_RE` 放宽为兼容上述全部变体，并三轮回填存量数据，案号覆盖率 **89.2% → 99.98%**。
2. Admin 增加 `created_at`（爬取入库时间）展示。

#### fix(labor_arbitration): 修复 Django-Q 任务同步 ORM 崩溃与并发重复提交

> 用户要求「迁移 + 清空 + 全量重爬」时，真实运行 Django-Q 任务暴露问题。

**问题**
- Django-Q worker 用 asyncio 跑任务，且 crawler 用 Playwright sync API，Django 同步 ORM 检测到 running loop 即拒绝执行，报 `SynchronousOnlyOperation`。

**修复**
1. `tasks.py` 模块顶部 `os.environ.setdefault("DJANGO_ALLOW_ASYNC_UNSAFE", "true")`，与 `legal_solution/tasks.py` 既有约定一致，放行同步 ORM。
2. 修复并发场景下同一文书被重复提交解析任务的问题（`select_for_update` + `GET_OR_CREATE`）。

---

#### fix(labor_arbitration): 修复翻页提前停止与 publish_datetime naive 告警

**问题**
1. HTTP 接口返回的 `publish_time` 为无时区字符串，Django 6.0 检测到 naive datetime 告警。
2. 接口分页偶发返回空列表，爬虫误判为已爬完，实际还有未入库文书。

**修复**
1. 接口返回的时间通过 `make_aware` 转带时区后再写入 `publish_datetime`。`Naive 告警消除`。
2. 分页空列表时增加重试逻辑（最多 2 次），确认接口返回稳定空列表后才退出。

#### feat(labor_arbitration): 改用 HTTP 接口抓取（提速 + 不再下载图片）

> 用户发现列表页有 JSON 接口，且图片后续都要 OCR 成文字、无需保留原图。

**改造**
1. 列表用接口：`postmeta/i/{category_id}.json` 一次拿全部文章。
2. 详情不下载图片：requests 抓详情页 HTML，正则提取图片 URL，只存 `source_url`。
3. OCR 按需拉图：`parsing_service.py` 解析时从 `source_url` 下载到临时文件再 OCR，用后清理。
4. 已删除 224MB / 198 个本地图片文件。

**注意**：站点 `pages_limit=50`，单区最多拿最新 2500 篇；某来源(21140)/另一来源(12667)/再一来源(3666) 超过部分拿不到。

#### fix(labor_arbitration): 详情图下载健壮性（慢链路/大图）

> 端到端实测（真实站点）发现并修复：

**问题**
1. 详情扫描图体积可达数 MB（实测单图 `content-length: 3512643`），原 `page.request.fetch` 默认 30s 超时在慢链路下必失败。
2. 详情页在浏览器内完整加载大图，导航慢（20–35s/页）。

**修复**（早期 Playwright 版本）
1. `_download_image` 超时提至 90s 并允许重试（最多 2 次）。
2. `_crawl_with_page` 通过 `page.route` 拦截图片资源加载，加速详情页导航、降低内存。
3. `page.goto` 显式 `timeout=60000`。

### 已回退的改动
