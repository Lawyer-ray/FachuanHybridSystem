# v27.11.9 后端 · 一张网文书下载链路稳固性修复

## 后端

### 修复

- **一张网（zxfw.court.gov.cn）文书下载三级降级名存实亡**（任务 313 事故，2026-10-27）：纯 API 模式（`requires_browser=False`）下任务链路从不创建浏览器，直接 API 一失败，「Playwright 拦截」「页面点击」两级降级全部因 `self.page is None` 直接报错退出。现直接 API 失败且 Playwright 可用时**按需懒创建浏览器上下文**（反检测）再走降级策略，自建资源在 `finally` 中关闭（dispatcher 共享的上下文不动），不再留浏览器泄漏。
- **直接 API 列表接口偶发 30s 超时直接判死**：实测法院服务端对**新生成送达**的首次 `getWsListBySdbhNew` 请求可能超 30s（签收确认同秒即返，列表接口 2 分钟后 <1s），单次 30s 硬超时无重试过于脆弱。现增加**运行内重试**（3 次尝试、3s/8s 退避，单次仍 30s 超时；业务码错误不重试），大多数瞬态慢响应不再落入浏览器降级。
- **文书下载成功但落库必失败**：`getWsListBySdbhNew` 响应已不含 `dt_cjsj` 字段（实测仅 8 个字段），而落库校验仍将其列为必填——每次直接 API 下载 2/2 成功、`db_save_result` 却 0/2 全败，审计记录静默丢失。现 `dt_cjsj` 不再强制，缺失/空值/非字符串一律回落当前时间（与既有「解析失败用当前时间」一致），结构性字段（下载链接、唯一键等）仍严格校验。
- **任务级与 SMS 级双层重试并发，重复下载同一送达**：任务失败先落 `FAILED` 触发状态钩子，外层 `execute_scraper_task` 随即将任务翻回 `PENDING` 排程自重试——SMS 侧失败处理器与该翻回存在竞态，两边各排一个 60s 重试，实发同一送达被并发下载两次（重复建任务 314、重复打法院 API）。现两层去重：
  - 失败处理器重新拉取任务最新状态，任务已回 `PENDING`/`RUNNING`（任务级自重试已接管）时不再排 SMS 级重试，短信状态不动；
  - 创建下载任务前对**同短信同 URL 的活跃任务**（pending/running/waiting_for_captcha，含任务级自重试翻回的）去重复用，兜住竞态窗口，不再新建重复任务。
- 直接 API / 拦截失败的日志消息现携带异常类型与详情（原先只进 `extra`，控制台日志完全看不到失败原因，排查超时全靠猜时间差）。
