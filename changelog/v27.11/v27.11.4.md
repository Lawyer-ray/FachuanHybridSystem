# v27.11.4 — AI 直改真正就地落笔（不再整页刷新）+ 旧画布不再覆盖 AI 修订

用户反馈（承接 v27.11.3 之后仍在复现）：

1. 「AI 改完之后还是会强制刷新，体验很差」——v27.11.3 加了就地落笔通道，但**实际每次仍降级重载**；
2. 「AI 说改好了，关掉编辑器再打开又变回旧文」——落盘的修订被编辑器旧画布静默覆盖（数据丢失）。

## 排查结论：三个叠加的根因

### 根因一：插件改动从未真正生效（整页刷新的主因）

DS 对插件目录走 nginx `gzip_static`，**优先下发 `plugin.js.gz`**。而：

- `gzip -k` 不覆盖已存在的 `.gz`；
- `docker cp plugin.js` 也不会顺手重压；
- 更糟的是这些 `.gz` 曾被**提交进仓库**，于是 git 里「源文件新、`.gz` 旧」，任何机器部署都拿到旧插件。

结果：`plugin.js` 已是 17243 字节，实际下发的 `Content-Length` 仍是旧值 **3899**；
而 `docker exec grep 新代码 plugin.js` **能搜到**——极具误导性，让人以为已经生效。

于是 `apply-revision` 永远停在最脆的「精确子串匹配」那一层。合同正文被排版、拼写检查、
修订边界切成十几个 run 并夹带空格/全角差异，精确匹配命中率很低，**失败即降级换 key 重建画布**。

### 根因二：插件定位只有一层，太脆

`__find` 只有 `doc.Search(anchor)`。改为**四层降级**（逐层收窄，找到才落笔，绝不错位改字）：

| 层 | 手段 | 治什么 |
|---|---|---|
| 1 | `doc.Search(raw)` | 干净原文 |
| 2 | 逐元素 `GetText` 包含 | 跨 run 但同段 |
| 3 | 归一化包含（去空白/零宽、NFKC 全半角折叠） | 空格多余/丢失、全角标点 |
| 4 | 取开头 40 字再匹配 | 原文尾部被模型顺手改写 |

实测红线：**`ApiRange` 没有 `SetStart`/`SetEnd`**（`typeof` 均为 `undefined`），真实 API 是
`SetStartPos` / `SetEndPos`。照着想当然写会让归一化层**恒假且不报错**，一路落到最后失败。

### 根因三：AI 落盘后，编辑器旧画布会把它整篇盖掉

`status=2/6` 交回来的是**编辑器内存里的画布**，不是磁盘文件。AI 直改走后端直接改 docx，
磁盘变了、画布还是旧的；旧画布一回写，AI 刚落的 `w:ins`/`w:del` 就被整篇静默覆盖。

## 改动

### 插件（`deploy/onlyoffice/plugins/fachuan-rewrite/plugin.js`）

- `__find` 四层降级 + `__norm` / `__selectRange`（用真实的 `SetStartPos`/`SetEndPos`）；
- `COMMAND_TIMEOUT_MS = 8000`（归一化层要遍历全部元素，原来 3s 会把正在成功的定位误报成超时）。

### 前端（`use-live-rewrite-apply.ts`）

- `APPLY_TIMEOUT_MS` 6000 → 10000，**必须大于插件超时**：否则插件还没给结论，前端就先超时降级，
  白白多一次画布重建。

### 后端（`apps/onlyoffice`）

- 新增两个字段（迁移 `0002` / `0003`），职责必须分离：
  - `external_write_seq`：文档现在第几代（文档级计数器，bump 时 +1）；
  - `canvas_seq`：这份画布**按第几代签发**（快照，只在换 key/回写成功时登记）；
- `bump_external_write()` 落盘后只抬 `external_write_seq`；
- `stale_canvas_reason()` 回写前比对 `external_write_seq > canvas_seq`，命中则
  **丢弃本次保存并 `return True`**（必须应答成功：DS 重试交回的仍是同一份旧画布，
  `error 1` 只会无限循环）。

#### 评审抓到的缺陷（已修）：守卫曾是死代码

第一版用「文档级 `max(external_write_seq)`」比「会话自己的 `external_write_seq`」，
而 `bump_external_write` 的 `UPDATE ... F(...)+1` 把**同一行**这个字段也抬了，
于是两边永远相等、判据恒假——线上守卫从未生效，AI 修订照样被旧画布覆盖。

当时单测拿的是**未刷新的内存对象**（还是 bump 前的值）所以一直是绿的；DS 回调
实际走 `load_session_by_key()` 从库重取，取到的已是抬过的值。修复后单测**一律经
`load_session_by_key()` 取会话**，并额外断言 `refresh_from_db()` 后同样判过期。

另注：换 key 会把该行 `document_key` 改写，老 key 在库里已不存在 →
回调直接 fail-closed `{"error": 1}`。两道防线叠加，不互相替代。

### 部署（`.gitignore` / README）

- **`deploy/onlyoffice/plugins/*/*.gz` 不再入库**：DS 启动时 `documentserver-static-gzip.sh`
  会对插件目录跑 `gzip -kf9`（`-f` 强制覆盖），`.gz` 本来就是它自己生成的产物；
  入库只会带来「源文件新、`.gz` 旧」的静默故障。README 相应章节已改写并记录两个坑。

## 验证

- **真机（DS 9.4.0.1）**：仅修 `.gz` 同步即可观察下发 `Content-Length` 3899 → 17243；
  部署目录 `plugin.js.gz` 与 `plugin.js` 解压后逐字节一致。
- **逐层定位**：带多余空格 / 首尾空格的原文由 `ok:false` 转为 `{ok:true, how:'normalized'}`；
  文档里确实不存在的文本仍正确失败（不瞎改位置）。
- **端到端（无重载）**：探针统计 `DocEditor` 构造次数，`editors` 0 → 0，回执
  `applied{ok:true, how:'normalized'}` → 就地落笔，画布未重建。
- **单测**：后端 `tests/ci/unit/onlyoffice/` 全套 **42 passed**（`test_stale_canvas_guard.py` 10 项，
  含「生产路径 `load_session_by_key` 必须命中」「计数器涨而快照不涨」两条专项回归）；
  前端 `use-rewrite-refresh.dom.test.ts` 8 项，锁死「就地成功不推进 nonce / 失败才推进」的决策。
- **数据丢失防线实测**：`bump` 后经 `load_session_by_key`（生产路径）取会话，
  `stale_canvas_reason` 返回拦截文案（修复前返回空串）；重开换新 key 后恢复可保存。
