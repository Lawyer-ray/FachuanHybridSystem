# v27.13.3 · 修复收件箱附件预览/下载 401

收件箱抽屉里的「预览」「下载」对任何账号都失败，包括用自己的账号下载自己的
一张网材料。用户最初怀疑是权限配置问题，实际与权限无关——是前端取文件的
方式不对。

## 前端

#### 修复

- **附件预览/下载改用一次性下载票据**（`use-attachment-opener`）。

  原实现是裸 `<a href>` 直接指向 `/api/v1/inbox/messages/{id}/attachments/{i}/{preview,download}`。
  但本应用的 JWT 存在 localStorage，**只有经 ky 发出的请求才带 `Authorization` 头**；
  浏览器导航（`<a href>` / `window.open`）带不上它。后端 `JWTOrSessionAuth`
  也刻意不接受 `?token=<JWT>`——安全审计 2026Q4 M-2 明确记录：完整 JWT 落入
  nginx access log、浏览器历史、Referer 与中间代理日志，拿到即等于拿到身份
  （有效期 2 小时且可换 refresh）。

  两条路径都断，所以请求必然是未认证的 401。

  正确路径是后端为 `<a>` / `<img>` / `<iframe>` 这类带不上请求头的场景准备的
  **短时一次性下载票据**：已认证端点 `POST /api/v1/download-ticket` 换 `?ticket=`
  （票据只含 user_id、默认 60 秒、单次使用），再当普通链接打开。办案模块的
  文档预览/下载一直是这么做的（`lib/download-ticket` + `lib/download`），
  收件箱抽屉当初没接上这一套。

- **交互**：`<a href>` 改 `<button>`，换票期间按钮显示 spinner 并禁用，
  避免「点下去像没反应」以及重复点击消耗票据。

- **修正 `attachmentUrl` 的误导性注释**：原文声称「鉴权靠 cookie/session」，
  但本应用登录只下发 JWT，从不下发 session cookie——这条错误注释正是当初
  误判可以裸用 `<a href>` 的原因，已改写为明确的 warning。

#### 测试

新增 3 例回归测试（`InboxView.dom.test.tsx`）：

- 预览：断言先调 `withDownloadTicket`（入参是 preview 端点），再把带 `ticket=`
  的 URL 交给 `window.open`；
- 下载：同上，断言交给 `downloadUrl` 的 URL 含票据；
- 断言抽屉里不再出现任何 `a[href*="/attachments/"]`——裸链一旦回归立刻失败。

此前该抽屉的附件按钮完全没有测试覆盖，这是本 bug 能潜伏下来的直接原因。

#### 验证

对本地后端（:8002）用真实测试账号（id=2）与其可见消息 484
（真实判决书 PDF，176654 字节）实测：

| 请求方式 | 结果 |
|---|---|
| 无鉴权（旧 `<a href>` 行为） | **401** |
| `Authorization: Bearer`（ky 正常路径） | 200 |
| `?ticket=`（本次修复路径） | **200**，176654 字节 |

同时验证票据单次使用：同一张票据重复兑现返回 401；`download` 端点返回
`application/pdf` + 正确 `Content-Disposition` 文件名。
