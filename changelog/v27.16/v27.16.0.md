# v27.16.0 · 发票待认领（邮件自动解析 + 首页确认绑定）

> 分支 `feature/invoice-module`。本文只记本次发票功能链；同分支上并行会话的非诉页
> 样式修复见 `v27.15.0` / `v27.15.1`。

## 背景

律所财务开好票后通过邮件发给律师。此前拿到发票只有一条路：**手工拖进项目详情页**，
系统识别、改名、落到合同文件夹。问题在入口——律师得先知道"财务发过票给我"，
再去邮箱翻、下载、拖拽。票发过来没人提，就一直躺着。

本版把它接成一条线：**邮件进来 → 自动识别 → 首页提醒 → 点一下确认 → 落到项目**。

真实样本（本次实现的验证数据）：财务邮件附件
`dzfp_<20位号码>_<购买方>_<项目号>-<开票人>.pdf`，
票面 ¥2,400.00，备注栏 `<项目号>-<委托人>与<对方公司>合同纠纷`。

## 后端

### 新功能

#### `InvoiceIntake` 待认领发票模型

与到账待认领（`PaymentIntake`）同构的过程态表，记录"财务发了这张票、还没确认归哪个项目"。

| 字段组 | 内容 |
|---|---|
| 来源 | `inbox_message`（PROTECT）、`part_index`、`attachment_path`、`original_filename` |
| 票面事实 | `invoice_number`、`invoice_date`、`total_amount`、`buyer_name`、`remark`、`project_code` |
| 系统建议 | `suggested_contract`、`suggested_payment`、`match_snapshot`（不可变快照） |
| 人工裁定 | `status`、`confirmed_contract`、`confirmed_payment`、`confirmed_by/at`、`invoice`、`decision_note` |

状态机只有三态：`pending → confirmed / rejected`，`reopen` 可回退。

**不落任何税号/身份证/统一社会信用代码**：发票购买方税号是自然人身份证号，
对匹配零价值、纯隐私负债。购买方名称也只存脱敏后的本体（`张三（个人）` → `张三`）。

`Invoice` 新增 `folder_subpath`：记录镜像到合同文件夹的相对落点，撤销时据此
**确定性**删除副本（按文件名搜索会误删同名票）。

迁移 `0053_invoice_intake`：`AddField` + `CreateModel` 两项，无删列、无回填。

#### 发票解析：文件名优先，PDF 兜底

- `invoice_filename.py`：从数电票附件名抽号码 / 购买方 / 项目号
  （`dzfp_<20位号码>_<购买方>_<项目号>-<开票人>.pdf`）。纯函数，抽不到给空串，
  绝不让一个解析失败挡住整批邮件同步。
- `InvoiceParser` 增强：从 PDF 备注栏抽律所项目号与案由原文。备注栏在 pdfplumber
  文本里被表格切成孤立「备」「注」两行，因此**按内容定位**而非行号硬编码。

**踩到的两个真坑**（均已加回归测试锁死）：

| 坑 | 症状 | 处理 |
|---|---|---|
| `\b` 在中文/下划线旁失效 | 号码前后紧贴 `_`（`dzfp_264420…_张三`）、项目号后接汉字，`\b` 不命中，真实样本抽不出任何东西 | 改用 `(?<![0-9A-Za-z])` / `(?<!\d)` 断言 |
| 开票日期被当成发票号 | `发票_某公司_20260623开具.pdf` 里 `20260623` 符合 8 位旧版号码形态，被当成号码 → **污染去重键**，同一张票重发就多一条待认领 | 8 位候选若形如 `YYYYMMDD`（19xx–20xx）判为日期，跳过 |

#### 匹配器 `invoice_match.py`：S1–S4 四级信号

发票的证据强度比到账邮件高一个量级，因此**不是**照搬到账那套"只排序不预选"：

| 级 | 信号 | 强度 |
|---|---|---|
| **S1** | 备注/文件名里的律所项目号 → `Contract.law_firm_oa_case_number`（字段有唯一约束） | **确定性 1.0** |
| S2 | 备注案由文字 vs 合同名相似度 | 0.7 |
| S3 | 购买方名称命中委托人 | 0.5 |
| S4 | 金额 + 日期 → 在已定合同下定位收款 | 不单独构成候选 |

**S1 命中即预选**，与到账侧"绝不预选"相反——因为证据强度不同，不该套同一套保守度。

收款预选四级规则（用户确认过的语义）：

```
① 恰好 1 笔且金额吻合     → 预选该笔, confidence=exact
② 恰好 1 笔但金额不符     → 仍预选, confidence=amount_mismatch（提示核对）
③ 多笔收款               → 不猜, confidence=ambiguous
④ 无收款                 → confidence=no_payment（先开票后付款）
```

②「明知不符还选」的理由：开票金额与收款金额常不相等（含税/分期/合并开票），
让人从零开始选比"选好再改"更费事；`confidence` 负责把不确定说清楚。

#### 扫描器：接在 IMAP 同步后

判据宽松（任一命中即入池）：主题含「发票」/ 正文含「发票已开具、请查收」/
附件名以 `dzfp_` 或「发票」开头。宁可多建一条让人驳回，也不漏掉一张真票——
漏掉的票律师根本不知道它来过。

- **多附件各建一条**（财务会一次发多张，与到账"一封一条"不同）
- `dedupe_key = sha256(inbox_message_id | part_index | invoice_number)`，重扫幂等
- **跨表去重**：按 `invoice_number` 查 `Invoice` 表，已落账的直接跳过。
  `Invoice` 才是财务凭证，`intake` 只是过程态——判"处理没处理过"必须以 `Invoice` 为准
- 接在 `imap_fetcher` 同步后，与到账扫描**各自独立 try**，一方报错不拖垮邮件同步

#### API：8 个端点 `/api/v1/contracts/finance/invoice-intake`

`GET /pending`（只返回 pending）、`/pending/count`、`/{id}`、`/selectable-contracts`、
`POST /{id}/confirm`、`/reject`、`/reopen`、`/rescan`。

**挂载点必须与 `/finance/intake` 并列**：挂成 `/finance/intake/invoices` 会被
`intake` 的 `/{intake_id}` 通配路径吃掉。

#### 确认绑定：复用既有落盘链路

确认不自己写文件，直接调 `InvoiceFileService.save_invoice` —— 那条链路已做对
识别 → 命名（`发票（合同名）_YYYYMMDD开具.pdf`）→ 落 media → 镜像合同文件夹
→ 回填开票金额。邮件认领只是**换了个入口**，落地动作必须走同一份代码；
两套命名/落盘规则并存的那天，同一案子下就会出现两种文件名的票。

撤销连带删 `Invoice`、media 文件、合同文件夹副本（副本移入 `_已删除/` 而非物理删除，
可找回），并重算收款开票金额。

#### 统一同步端点 `POST /finance/intake/sync-pending`

一次编排两类（款项 + 发票）：先补扫已入库邮件（同步、秒级出结果），
再提交 IMAP 异步任务拉新邮件。**不阻塞等待**——IMAP 最坏要一分钟，
同步等会被网关/浏览器超时掐断。

### 修复

#### 「已收满」不再排除发票匹配

把到账侧的资格规则原样搬给发票，是错的——两个业务里「已收满」含义**相反**：

| | 已收满 = |
|---|---|
| 到账认领 | 这笔钱不能再记进这个合同 → **排除** |
| 发票认领 | 钱收齐了，**正该开票** → 不排除 |

实测：某非诉专项合同固定金额 40000、已收 40000、未开票，被自家 40000 的发票
排除在外（首页显示「费用已收齐」灰字，看起来像数据问题）。`eligible_contract_qs`
新增 `exclude_fully_paid` 参数（默认 True 保到账口径），发票匹配器与「换个项目」
下拉均传 False，两处同口径避免"下拉选不到、自动也不推"。

#### 排除线索先说原因，确定性匹配时干脆不显示

灰框的用途是解释"为什么排除了它"，但原顺序「合同名：原因」，长案名单行截断会把
原因整个裁掉。改为「原因：合同名」。进一步：**项目号已确定性命中（1.0）时不再收集
排除线索**——旁边挂着同客户三份已归档项目纯属噪音（实测卡片因此矮 58px）。

款项侧保留线索是对的（那边证据本就弱，线索帮人判断"为什么匹配不上"）；
发票侧证据强到 1.0 时，多余解释反成干扰。

#### `payment_options` 漏发导致详情弹窗崩溃

`InvoiceIntakeOut` 漏定义 `payment_pick_confidence` / `payment_pick_note` /
`payment_options` 三个字段（前端类型里有、schema 没发）。前端 `options.find()`
拿到 `undefined` 抛 TypeError，整棵详情子树被 ErrorBoundary 换掉，
表现成**「点详情没反应」**，且界面上看不到任何提示。

tsc 通过、2837 个单测通过、eslint 通过，全都抓不到——因为类型是手写的，
前后端契约没对上。**只有真跑起来才能发现**。前端同步加固 `?? []` / `?? {}`：
后端字段缺失不该让整张卡消失。

#### 日志 `extra` 键与 `LogRecord` 冲突

`extra={"filename": ...}` 与 logging 内建字段冲突会直接报错，改 `attachment_name`。

## 前端

### 新功能

#### `features/invoice-intake/` 独立 feature

```
types.ts / constants.ts / domain.ts / api.ts
hooks/use-pending-invoices.ts, use-selectable-contracts.ts
components/
  PendingInvoicesCard.tsx    首页分组（支持 bare 模式供合并卡使用）
  InvoiceIntakeRow.tsx       单行
  InvoiceDetailDialog.tsx    详情弹窗
  PaymentCompare.tsx         收款对照
  ContractPicker.tsx         换个项目
  ConfirmedInvoiceRow.tsx    刚确认完的行
```

严格遵守 feature 隔离：不 import `payment-intake`、不 import `workbench`
（`formatAmount` 与复制按钮各域一份——3 行纯函数重复优于破域耦合）。

#### 首页「待认领」合并卡

款项 + 发票合成**一张卡**（用户要求节约空间）：外层 `section` + `CardHead` 由首页提供，
两个 feature 各以 `bare` 模式只渲染内容区。两 feature 互不 import，视觉上却是一张卡。

不用「款项」「发票」两个文字标签（堆在一张卡里只是重复噪声），改为**左侧 2px 色条**
区分：款项 emerald、发票 indigo；发票组有内容时才画分隔线。合并卡里空态压成一行，
避免两组都空时首页出现两大块留白。

为了支持这个合并，两个**存量公共组件**做了向后兼容的扩展（影响面不只发票）：

- `CardHead`：`count` 改为可选（空字符串会渲染成一颗空胶囊，被误读成「0 条」，
  现在省略即不渲染）；新增 `action` 槽位放标题行右侧控件（即同步按钮）。
- `PendingIntakeCard`（款项侧）：新增 `bare` 模式，只渲染内容区不包外壳，
  供首页合并卡组合使用；默认行为与改造前完全一致。

#### 详情弹窗：回答三个疑问，不罗列字段

律师点开详情时只想问三件事，界面严格按这三问组织：

1. **这张票是真的吗** → 备注栏原文（列表被截断，这里给全文）+ 原始文件名 +
   「查看发票原件」跳原始邮件（复用 `material-prep?message=` 深链）
2. **凭什么说是这个案子** → 匹配依据**逐条**列出（项目号命中 / 购买方命中），
   不合成一句话——信息量正是详情的价值
3. **钱对得上吗** → 收款对照：金额相等给绿勾「金额吻合」，不等给**具体差额**
   （"发票比收款多 ¥400.00"）并说明开票金额按收款封顶

刻意**不重复列表已有信息**（金额/购买方/建议合同行内已看过）。
金额与发票号码**只读**：PDF 数字是税局权威数据，系统里改一个与原件不符的数字，
对账时会变成谁也说不清的坏账，识别错应重传原件。

#### 「换个项目」：搜索选项目

数据源 `/selectable-contracts`（发票口径，已收满的项目照样能选）。改判后**不带
`paymentId`**——原预选收款是相对原建议合同算的，换项目后不再成立，先挂项目名下、
收款到项目页再关联（弹窗里写明这点，免得困惑"怎么没挂到收款"）。

#### 待认领卡右上角同步按钮

空态下「待认领」原本是死角：用户知道该有东西进来，却只能等后台定时任务或绕去
收件箱页点同步。财务刚发来发票的那一分钟里，这个按钮是唯一即时出口。

点一下拉最近 **1 天**邮件。按返回数量立即报数，并在 2.5s / 6s / 12s 各刷一次，
把后台异步拉回来、刚入池的那批也接上——不这样做用户会以为"同步了但什么都没有"。

结果分三档文案，避免误导：收到 N 笔/N 张 / 已提交同步稍后可能再有 / 最近 1 天没有新的。

#### 手动同步窗口：7 天 → 3 天，选项收敛为 1/3 天

去掉 30/90 天档：发票与到账通知是时效件，放宽窗口只会灌入大量无关注销邮件。

### 优化

#### 确认后行留在原地供复制，刷新才消失

确认完最想做的下一件事是**复制那个重命名后的发票**（发给财务 / 存一份 / 微信传）。
若行立刻消失，就得绕到项目页去找，动作被打断。

留下的只是**前端内存态**（组件 state），不是数据库状态 ——
所以刷新页面即消失，绝不会在库里堆积。

> 中途走过一次弯路：先用"`confirmed_at` + 10 分钟窗口"在数据库层承载这个临时展示，
> 结果变成"处理过的还常驻待认领"，被用户直接指出。**用 DB 状态承载临时 UI 展示**
> 是病根——只要状态落库，就会堆积、就会被时间计算出岔子。

已确认行换绿底 + 「已绑定」徽标 + 文件名 + 复制按钮，与待办行的白底
「确认 / 换个项目」明显区分。复制失败兜底复制文件名（同项目页口径）。

#### 去掉结论行的双勾

`invoiceHeadline()` 返回的字符串自带 `✓`，行组件又渲染了 `Check` 图标，
界面上成了「✓ ✓」。去掉文案里的字符，图标与文案各管一件事。

## 实测验证

用 Playwright 真登录 + 真实数据跑通全链路（不止看单测）：

| 环节 | 结果 |
|---|---|
| 邮件扫描 | 真实邮件 → 号码/金额/项目号/备注案由四项全部正确抽取 |
| 匹配 | 项目号精确命中对应合同（score 1.0），预选唯一吻合收款（`exact`） |
| 确认 | 对应收款转为 `INVOICED_FULL`（2400/2400） |
| 落盘 | 文件落到合同已有的 `2-发票/` 目录，命名为「发票（合同名）_YYYYMMDD开具.pdf」 |
| 撤销 | 状态与开票金额正确回退，文件夹副本进 `_已删除/` |
| 详情弹窗 | 六区块正常渲染，控制台零错误 |
| 换个项目 | 搜索命中，可选 |
| 同步按钮 | 一次点击收进 3 张发票（含一张此前未发现的 ¥62,000 票，自动匹配到对应合同） |
| 确认后保留 | 行在 → 刷新后消失 |

## 已知限制

- **「换个项目」改判后不自动挂收款**：需到项目页关联（弹窗已说明）。
- **完整发票台账页未做**：首页只负责"还有什么要我做"，历史发票走项目页。
- **存量回填未做**：合同文件夹里已有的历史发票 PDF 未自动登记进系统
  （如某合同 `2-发票/` 下已有 3 张手工放的票，`contracts_invoice` 表里一条都没有）。
  属于独立议题，未擅自执行。
