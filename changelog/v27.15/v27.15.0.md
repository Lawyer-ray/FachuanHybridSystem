# v27.15.0 · 到账邮件转「待认领款项」+ 合同 AI 导入 + 同步窗口

本版本包含三块互不相干的工作，来自同一条开发分支上的并行会话：

1. **到账待认领**（财务）：银行到账邮件自动解析成待记账款项，人确认后才写入收款记录；
2. **合同 AI 导入**（合同）：新建合同页拖入合同文件，AI 解析回填表单；
3. **同步窗口**（收件箱）：手动同步默认只看最近 7 天，不再把邮箱历史翻个底朝天。

---

## 需求背景

### 一、到账通知能不能自动记账

律师的银行到账通知会发到邮箱。最初的设想是「收到到账通知 → 自动找到对应项目 → 自动绑定」，
做到一半在真实数据上撞了墙：

| 真实邮件 | 实际情况 | 原匹配器输出 |
|---|---|---|
| 某委托人存入 2400 元 | 合同应收 67044.53，这 2400 是尾款的一部分 | 判不出确定匹配（案号信号恒为 0） |
| 第三方代付 10000 元 | 对应项目已收清 50000 且已全额开票，客户额外多付 | **错配**到另一个无关项目（余额恰为 10000） |

两封都没匹配对。结论：**到账邮件几乎不含案号，最强信号只有付款人姓名 + 银行备注**，
天然不可靠（同名、代付、多付）。于是把方案改成——

> 系统负责「解析 + 排序 + 排除 + 解释」，**每一笔记账都必须人工确认**。

### 二、合同录入太慢

新建合同时要人工对照合同原文，逐个字段手填（甲乙方、金额、律师指派、签订日期…）。
一份合同几十个字段，抄错一位就是财务或诉讼主体错误。

### 三、同步按钮把邮箱历史全拉了

收件箱的「同步」按钮没有时间窗口概念，一律按来源的 `sync_since` 走。实测某邮箱
**半年 290 封全拉进来，其中只有 2 封是真正关心的到账通知**——既慢又淹没收件箱。

## 后端

### 新功能

#### 一、到账待认领（Payment Intake）

**新模型 `PaymentIntake`**（迁移 `0051`、`0052`）

一封到账邮件 = 一条待认领记录，状态机：

```
pending ──┬──► confirmed  → 创建 ContractPayment
          ├──► rejected   （不是记账事件：营销邮件误判等）
          ├──► ignored    （是钱但不记账：往来款/退款）
          └──► reopen ──► pending（撤销确认，同时删除已生成的收款）
```

- `dedupe_key = sha256(message_id|amount|received_at)` 保证重复扫描幂等；
- `match_snapshot` 存**不可变**的候选快照（含被排除线索），便于事后追责与调参；
- 数据库约束：`status=confirmed` 必须同时有 `payment`，且 `amount > 0`。

**`intake_eligibility`：项目资格判定（唯一真源）**

自动匹配与前端下拉**必须共用**这一份，否则会出现「下拉里能选、但系统永远不推荐」的矛盾：

| 排除条件 | 依据 |
|---|---|
| 已归档 / 未签约 | `status` |
| **已收满** | `fixed_amount` 非空且已收合计 ≥ `fixed_amount` |
| **案件已结案** | 关联案件全部 `closed` |

按用户要求：**项目收完款项、结案、归档后不再参与匹配**。
被排除但有关联线索的项目不丢弃，写进 `excluded_hints`（既守规则又不丢线索）。

**`transfer_notice`：到账通知解析器**

旧实现用 `re.sub(r"<[^>]+>", " ")` 剥标签，靠**插入的空格**把被 `<span>` 切碎的数字拼回来，
属于「碰巧能跑」。重写为 `html.parser` 结构化转换：

- 行内标签**不插字符** → `2,400.00` 不会再被拆开（旧实现在这种写法下会静默丢金额）；
- 跳过 `<style>/<head>` → Word 导出的上千字符 `@font-face` 不再污染待匹配文本；
- 结构化抽取金额 / 付款人 / 代付方 / 到账日；**抽不到金额显式失败**，不建 `amount=0` 的记录。

**`contract_match_v2`：匹配器第二版**

修掉 v1 的四个真实缺陷：

| # | v1 缺陷 | v2 修复 |
|---|---|---|
| 1 | 读 `case.case_number`（**该属性不存在**）→ 案号信号恒为 0，35 份有案号的合同从未被用上 | 改读 `case.case_numbers[].number` |
| 2 | 已收满的项目仍进候选 | 资格层硬排除 + `excluded_hints` |
| 3 | 「仅金额撞车」(0.55) 压过「实名命中」(0.45) → 代付那封错配 | 类别优先排序：`exact > partial > amount_only` |
| 4 | 「代 XXX 付」当普通子串 | 结构化解析 + 与委托人全称比对 |

判定类别：`exact`（案号或付款人/代付方命中委托人）、`partial`、`amount_only`（仅金额巧合，前端强提醒核对）。
**实名命中即判 `exact`，金额对不上不降级**——委托人本人存入的钱显然属于该项目，降级反而多一层无用判断。

**`intake_scanner`：扫描入库**

- 只扫 IMAP 来源，默认回看 **14 天**（用户前两周才开始让财务发到账邮件）；
- 必须命中款项关键词**且**能解析出金额才建单；
- 邮件同步完成后自动触发，整段 `try` 包住——扫描失败绝不影响邮件同步；
- `rematch_*`：匹配器改进后按当前逻辑重算存量快照（只重算 `pending`，
  已确认/已关闭的是审计凭证，改写等于篡改历史）。

**`intake_service`：确认权限与财务写入**

- 可见性：**收件人**（`source.credential.lawyer`）/ **主办律师**（`is_primary`）/ 管理员；
  建议项目主办律师 ≠ 收件人时**两人都能看到**（避免邮件归属人不懂业务、业务主办看不到到账）；
- 确认走独立事务 + 行锁，**不复用** `create_payment`（它在超付时直接抛错）；
  并发导致超付时不阻断（钱确实收了），升 `WARN` 写财务日志留痕；
- 撤销确认在同一事务内删除生成的收款记录，防留下无主的钱。

**9 个 API 端点**（`/api/v1/contracts/finance/intake`）

```
GET  /pending                    与我相关的待确认到账
GET  /pending/count              首页角标（轻量）
GET  /selectable-contracts       换项目下拉（与自动匹配共用资格规则）
POST /rescan                     手动补扫近 N 天
POST /rematch                    按当前匹配器重算存量
GET  /{id}                       详情（完整候选 + 被排除线索）
POST /{id}/confirm               确认并写入收款记录
POST /{id}/reject | /ignore      非记账 / 不需记账
POST /{id}/reopen                撤销裁定
```

> 静态路径必须注册在 `/{intake_id}` **之前**，否则会被通配吃掉（422 int_parsing）。

**Admin**：只读为主，把解析结果、候选快照、被排除线索全部摊开，便于排查"为什么没匹配上"；
禁止后台手工新增（绕过去重键）。

#### 二、合同 AI 导入

新建合同页（`/admin/contracts/contract/add/`）顶部新增「AI 智能导入合同」面板：
拖入 docx/pdf/txt，LLM 解析后回填表单草稿。

**链路（AI 只出草稿，绝不写库）**

- `document_snapshot`：确定性文本提取。docx **必须连表格一起抽**——签署页落款在 `w:tbl` 里，
  只取段落会丢「签约日期」；pdf 走 PyMuPDF；超长合同按「头部 + 关键词行」裁剪至 8 万字符。
- `extract_service`：Pydantic schema + 结构化受控重试（校验错误回喂，至多 3 次）。
- `normalize`（闸门层）：任何进 `Contract` 字段的值都过这里——
  - 金额：中文大写换算、「各付/共付」取合计、万位小数；**风险比例必须先排除**
    （否则「回款额 20%」的 20 会被写进固定律师费）；
  - 日期：「签订三日内」「至…为止」一律留空并标 `needs_review`；
  - 律所剔除：律所既非我方客户也非对方当事人，建 Client 会污染数据且 `ContractParty.client` 是 PROTECT；
  - `is_primary` 排他：并列指派收敛为一位，优先落在已匹配到系统账号的律师上。

临时文件只落 `MEDIA_ROOT/tmp/contract_intake/`，由既有 `cleanup_temp_files` 定时任务覆盖，无需新增调度。

#### 三、同步时间窗口

**`base.py`：`DEFAULT_SYNC_WINDOW_DAYS = 7` + `resolve_sync_since()`**

窗口与来源起点取**较晚者**（窗口只收窄，不越过配置起点去拉更早的邮件）。

**策略分界（关键）**

| 场景 | 行为 |
|---|---|
| 前端手动同步 | 传 7/30/90 → **只看最近 N 天** |
| 后台定时 / 首次建源 | 传 `None` → 按 `sync_since` **完整回填** |

「从历史时期完整同步」只在无人在场的初次回填时发生。

**IMAP 搜索条件改为 `UID n:* SINCE <起点>`**

`SINCE` 从"首次专用"变成**永久安全边界**：即使 `last_synced_uid` 因换库被清零，
也不会退化成拉全量历史（原实现存在这个隐患）。

**一张网收件箱**按窗口**提前停止翻页**（接口倒序返回，整页早于起点即 break）。
**一张网庭审日程忽略窗口**——庭期是未来时间，套用「最近 N 天」会把下周开庭全滤掉。

`sync` / `sync-all` 接口接受 `days`，省略即 `None`（全量回填），上限 365 天。

### 修复

- **撤销确认撞数据库约束**：先清 `payment` 再改 `status` 会瞬时违反
  `chk_paymentintake_confirmed_has_payment`。改为同一 UPDATE 内一并改掉。
- **`selectable_contracts` 内部切片**：`[:limit]` 后返回导致下游任何 `filter`/`count`/`get` 都抛
  `Cannot filter a query once a slice has been taken`。切片移到调用方。
- **`ineligible_reason` 对预加载 `payments` 崩溃**：`prefetch_related` 时 `payments` 不是 QuerySet，
  已兼容「注解 / Manager / 预加载列表」三种形态。
- **合同导入三处错误**（用户用乙律所账号导入两家律所共同承办的合同暴露）：
  1. **金额算成合同合计**：原文「乙方1、2 各支付壹万元整，共贰万元整」，本所应收 1 万却填了 2 万——
     把别家的收入算进自己账上。根因是整条链路没拿到「我方是哪家律所」。已从登录律师的
     `law_firm` 取我方身份写进 prompt，并加确定性兜底拆份额（要求原文存在 `总额÷家数` 的数字，
     否则交人工，不擅自造数）。
  2. **合同当事人填不进去**：内联是 `nested_admin`（`.djn-add-handler` / `.djn-inline-form`），
     代码按原生 Django 的 `.add-row a` / `tr.form-row` 写选择器，永不命中；且异步插行需轮询等待。
  3. **合同指派填不进去**：formset 前缀是 `related_name`（`assignments-group`），
     代码写成 `contract_assignments-group`，元素根本不存在。
- **律师姓名归一化键漂移**：建索引与查索引各写一份「去空白 + 去后缀」，且顺序不同，
  「张三律师」查不到键为「张三」的记录。收敛为单一 `normalize_lawyer_name_key`，
  后缀按「大律师」优先匹配避免只剥掉「律师」留下「大」。

## 前端

### 新功能

#### 一、首页「待认领款项」模块

首页右栏、收件箱之上新增独立常驻卡片。**有数据 / 空态 / 加载失败三态都渲染**——
用户要求「每次进首页都能看到」，无待办就隐藏会让人怀疑功能没在跑。

单行卡片信息密度按"窄栏一眼判完"设计：

```
¥10,000.00  2026-11-08        [仅金额吻合]
某人（代某供应链公司）
⚠ 仅有金额吻合，请核对后选择
  金额 10000 = 应收余额（固定收费 10000.00 - 已收 0）
ⓘ 某税务案：费用已收齐（50000.00/50000.00）
[确认(灰)] [换个项目]  [详情]
```

- **确认**：点了直接写入收款记录，**不弹二次确认**（卡片上金额、付款人、项目、理由都已在眼前，
  再弹一次只是让人把同一批信息读第二遍）；
- **换个项目**：搜选合格项目后再写入。此步保留弹窗——它不是"确认"而是"改判"，选项目本身是人的决策；
- **详情**：跳到产生这笔到账的那封原始邮件并**自动展开**；
- 只有金额证据的候选**不预选建议**，且「确认」置灰，避免暗示用户直接点。

新增 `features/payment-intake/`（独立业务域，不与 home/material-prep 混）。

#### 二、同步按钮带时间范围

主按钮点一下 = 同步最近 7 天；右侧下拉可选 30 / 90 天，并标注上次用的范围。

```
[⟳ 同步邮箱][▾]   ← 主按钮 = 7 天
                ├ 最近 7 天  (上次)
                ├ 最近 30 天
                └ 最近 90 天
```

#### 三、收件箱深链接 `?message=<id>`

`/material-prep?message=547` 直接展开那条消息的抽屉。

- 列表命中则直接展开；
- 被筛选挡住时先放开筛选再重找（**不是**提示"已切换"却实际没切）；
- 列表只取最近 200 条，目标更旧时按 id 单取（详情字段是列表行的超集）；
- 展开后把参数从 URL 抹掉，避免刷新又被强制弹开。

### 修复

- **接口前缀缺 `/api/v1` 导致首页卡片 404**：`createApiClient` 内部是
  `{ prefix: API_BASE_URL, ...options }`——传入的 `options` 在默认值**之后**展开，
  所以 `prefix` 会**整体覆盖** `/api/v1` 而不是相对拼接。只写 `/contracts/finance/intake`
  时请求落到 `http://host/contracts/finance/intake/...` → 404，卡片一直加载不出来。
  而 tsc / lint / 单测全绿（运行期语义，类型系统抓不到）。

### 优化

- **样式提权**：`CardHead` 从 `features/home/components` 移到 `components/shared`；
  新增 `shared/panel-styles.ts` 收敛 `PANEL` / `ROW_BTN` / `BTN_PRIMARY`。
  ≥2 个 feature 共用才提权，`payment-intake` 不再 import `features/home` 内部文件。
- **合同导入面板去掉 emoji 图标**（📄 与拖拽区箭头），同时清掉对应 CSS 规则。

## 升级说明

### 数据库迁移

```bash
cd backend/apiSystem && ../.venv/bin/python manage.py migrate contracts
```

- `0051_paymentintake`：新建待认领表；
- `0052_paymentintake_status_drop_awaiting`：状态枚举收敛（去掉未采用的「待建合同」）。

### 存量数据

- **收件箱历史邮件不删除**：新策略只是不再往里加历史噪声，已有的 290 封原样保留；
- **待认领记录**：升级后第一轮同步会自动把近 14 天的到账邮件转成待认领；
  若匹配器后续改进，用 `POST /intake/rematch` 按新逻辑重算存量快照。

### 已知限制

- 到账扫描**只覆盖 IMAP 来源**。一张网的法院邮件（诉讼费、保全费、案款）性质与律师费不同，
  暂未纳入，需单独解析规则；
- 一封邮件含多笔流水不在本期范围（银行日结邮件会遇到）；
- `plugins` 子模块中一张网 fetcher 的窗口改动尚未提交（需两段式 PR）。
