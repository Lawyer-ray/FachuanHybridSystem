## 后端

#### 安全

- **共享 MCP 无鉴权 + 静默降级超管（报告唯一实测可利用项，已复现并堵死）**
  - 复现方式与结果：`curl` 不带任何凭证 `POST http://127.0.0.1:8011/mcp` → `initialize` 返回 200 → `tools/call list_cases` **返回真实案件**（含公司名、案由、合同 ID）。回退账号（`backend/.env` 的 `FACHUAN_USERNAME`）实测 `is_superuser=True`。
  - 成因：`identity.py` 只把 `Authorization` 写进 ContextVar，不做校验；`client._headers()` 在无透传时**静默回退**到服务账号（超管）token。服务的 HTTP 端点本身无鉴权且绑 `127.0.0.1:8011` —— 本机任意进程（其他用户 shell、被 XSS 的前端、恶意 npm/pip 脚本、其他 agent 会话、CI runner）都能绕过 JWT/租户/审批读写全所数据。
  - 修复：`config.py` 新增 `http_transport_enabled()` / `require_request_auth()`；`identity.py` 的 ASGI 中间件在 HTTP 模式下对**非合法 Bearer 直接回 401**（不再回退）；`client._headers()` 在 HTTP 模式下无身份时**抛 `FachuanApiError`**，宁可报错也不悄悄升权。stdio 模式（每 pi 一进程、手工脚本）行为不变。
  - 复测：无 token → `401`；`make mcp` → `代码注册表 419 · 线上 419 · 工具面一致`。
  - 附带：`scripts/shared_mcp.sh` 的 `mcp-verify` 自己也被 401 拦了，改为先用 `.env` 服务账号走 `/token/pair` 铸 token 再握手（`streamable_http_client` 该版本只接受 `http_client=`，故传 `httpx2.AsyncClient(headers=...)`）。
- **OnlyOffice 插件桥不校验 origin（前端伪造注入链）**
  - 原实现只认消息体里的 `source: 'fachuan-plugin'`（攻击者可随意填），随后 `postMessage(msg, '*')` 把**选中的合同/案卷正文**投给被劫持的 `pluginWinRef`；反向可伪造 `selection` 把攻击者文本注入「划词直改」→ 进 AI 改写与文档落盘。
  - 改为：`e.origin` 白名单（取自 `docserver_url` 的 origin），回发用**具体 `targetOrigin`** 而非 `'*'`。白名单为空（DS 未就绪）时一律丢弃/不发送，不做「先到先信」。

#### 修复

- **合同建档编号并发必撞唯一约束（真实并发缺陷，已用线程实测证伪旧实现）**
  - 原实现：`_get_next_contract_sequence()` 内部的 `transaction.atomic()` 取号后**即提交并释放** `pg_advisory_xact_lock`；真正的 `contract.save()` 发生在 `filing_number_workflow.ensure_filing_number()` 的**另一个事务**里 —— 锁完全没覆盖写入。
  - 实测对比（同年份、同进程多线程同时冲）：
    - 旧实现 12 线程 → **7 个抛唯一约束异常**
    - 新实现 20 线程 → **全部成功、编号无重复**
  - 修复：新增 `FilingNumberService.assign_filing_number()`，把「锁 → 重读最新 filing_number（幂等短路）→ 取号 → 写回」全部放进同一个事务；`ensure_filing_number()` 改为调用它。`_get_next_contract_sequence` 增加 `_lock_held` 参数，避免嵌套 `atomic()` 把锁提前释放。
- **立案爬虫脚手架伪造「立案成功」**
  - `apps/automation/services/scraper/scrapers/court_filing.py` 的 `_login` / `_fill_case_info` / `_upload_files` 实现体只有 `logger.info`，从不登录/填表/提交，`_run()` 却返回 `"立案提交成功（需根据实际网站完善逻辑）"`；`BaseScraper` 据此把任务落库为 `SUCCESS` —— 律师会以为已立案（诉讼期限风险）。
  - 修复：全部假实现删除，改为 **fail-closed**：直接抛 `BusinessException(COURT_FILING_PLUGIN_MISSING)`，并在 `errors.hint` 里写明缺失的是哪个插件、怎么装。
  - **没有按报告建议直接删文件**：核验发现它是 `scrapers/__init__.py` 里插件 `ImportError` 时的 fallback，删掉会让"插件未装"的部署直接 import 失败。

#### 新增

- **`scripts/backup-db.sh` —— 数据库与 media 备份（此前全仓零备份）**
  - 依据：crontab 里此前只有 `.env`（9:30）和 `CLAUDE.md`（9:35）两个文本备份；`grep pg_dump|pg_restore|restic|borg|wal-g|pgbackrest` 全仓 **0 命中**。而库里是不可再生的案卷 / 身份证扫描件 / 财务流水，media 是原始文书 —— 磁盘故障或误操作即全所数据永久灭失（该项目已发生过 pytest flush 清表 98 条、`backend/` 两次整树删除）。

  - 防呆：**拒绝备份测试库**（`test_*` 前缀直接退出）；`pg_isready` 预检；产物 0 字节或 `pg_restore --list` 不可读即判失败（不产出误导人的"成功"）；media 自动探测 `backend/apiSystem/media`（settings 的 `BASE_DIR` 是 `apiSystem/apiSystem`，不是 `backend/media`）与 `backend/media` 两处。
