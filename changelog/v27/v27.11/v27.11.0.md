#### 修复 · 429 限流翻译丢失 Retry-After——模型不再盲撞限流墙(2026-10-25 审计七十二轮)

- **实锤**:REST 层限流处理器专门回传 `Retry-After` 头(`handlers.py` 的 handle_rate_limit_exception),但 mcp_server/client.py 的 `_handle` 把 429 与普通错误一视同仁——`HTTP 429: {detail}`,Retry-After 直接丢弃。模型不知道这是速率限制、该等多久,收到错误后的本能反应(立即原样重试)只会继续 429,白烧轮次。
- 修法:`_handle` 加 429 专用分支——读 Retry-After 头翻译成「建议等待 N 秒后再试」(无头时给 30-60 秒通用建议),文案明示「这是速率限制不是故障,立即原样重试只会继续 429」,并建议高频列表/检索操作降低频率或改用更大分页。
- 测试:TestHandleError 补 2 例(带头的秒数直译/无头的通用建议),文件 56 例全绿;`make mcp` 415/415。线上不打真限流(会锁账号污染限流计数),验证依赖单测真实路径 + REST 层头回传有据。

#### 优化 · 批量打包类下载工具补体积预期——docstring 不再让模型盲撞 15KB 闸门(2026-10-25 审计七十一轮)

- **扫描发现**:全仓 16 个文件 29 处 `client.download` 调用,只有 2 个文件(此前轮次改过的 inbox/documents)提过 20KB 截断线——其余工具的 docstring 只承诺「返回 data_base64」,模型满怀信心调用批量下载,然后撞 15KB 闸门失败重试,每次都浪费一轮。

#### 新增 · web_search 结果时间换算——相对时间转绝对日期(2026-10-25 审计六十九轮)

- **五十八轮刻意不取 cite-date 的理由不再成立**:当时嫌「3天前」这类相对时间对模型不友好就整个丢弃——但法律检索**完全没有时间线索**更糟,模型无法判断法条/司法解释新旧、政策是否被取代。正确做法不是丢,是**换算**。

#### 优化 · web_search 网络层对齐 fetch_url——trust_env 关闭+巨页防线(2026-10-25 审计六十八轮)

- **trust_env=False**:web_search 此前是 mcp_server 里唯一没关系统代理的 HTTP 客户端(fetch_url/client.py 都已关)——本机代理会把直连可达的搜狗也代理出去,表现为超时/502 极难排障;同一进程内两个工具一个直连一个走代理的行为分叉本身就是隐患。

#### 新增 · fetch_url 尊重目标站 robots.txt——对齐官方 fetch server(2026-10-25 审计六十七轮)

#### 修复 · fetch_url 响应体大小无上限——巨型直链不再打满内存(2026-10-25 审计六十六轮)

- **实锤**:旧实现 `http.get()` 非流式全量下载,唯一缓解是 20s 超时——高速服务器 20 秒能传几十 GB,模型让 fetch_url 抓一个巨型直链(比如 2GB 的 PDF)会把 worker 内存打满,大 PDF 还会整个塞给 pymupdf。官方 MCP 安全最佳实践同样要求限制响应大小。
- 修法:`http.stream` 流式下载 + **双保险**——Content-Length 预检(响应头一到即拒,一个字节不下载)+ 逐块累积(声明头可以骗,实读越线即刻中止);上限 10MB(`_MAX_BODY_BYTES`,覆盖正常网页与 500 页内文本型 PDF)。新 reason `payload_too_large`,message 指路「前端直接下载」。
- 连带重构:`_decode_body` 改收 `(data, charset_encoding)` 脱离 Response 对象(流式下 body 自己拼);`_request_capped` 统一出口把 `(status, headers, data, charset)` 带出 stream 上下文;重定向跳不读 body。
- **线上实测**:100MB 测速文件直链在 10MB 处流式中止返回 payload_too_large;正常抓取回归无恙(还命中六十四轮的缓存)。测试:TestBodySizeCap 3 例(声明超限/无声明 chunked 越线/上限内不受影响),单文件 71 例全绿;`make mcp` 415/415。技能 reason 表同步。

#### 修复 · 下载闸门对齐 pi 截断线——15KB-1MB 静默腐败区间关闭(2026-10-25 审计六十一轮)

#### 修复 · web_search「解析 0 条」如实归因——反爬/结构漂移不再伪装成「未找到」(2026-10-25 审计四十九轮)

- **真实数据定案**(抓真实搜狗页跑我们的解析函数):正常关键词、纯中文乱码、纯 ASCII 乱码查询**全都**能解析出模糊匹配结果(垃圾词也返回 5 条百度文库/微博类模糊结果)——搜狗几乎不返回真空结果页。推论:**解析 0 条几乎必然是反爬/验证码页或结果容器选择器漂移**,而不是「互联网上没有相关信息」。
- 旧文案「未找到相关搜索结果」在解析 0 条时是对用户的**错误事实性断言**源头:模型会告诉律师「网上查不到」,实际是我们没解析到。改为如实归因:命中反爬特征(复用 fetch_url 的 `_looks_like_antispider`,顶层导入消除重复)→「被反爬/验证码拦截,建议稍后再试」;其余 →「搜索页解析异常(结构可能变更或被反爬),这通常不代表没有相关信息,建议换关键词重试」。
- 解析 0 条记 **warning**(含页面字符数,供漂移诊断)——「用户会看到无法解释的结果」的失败不允许低于 warning。
- 归因提示是本系统文本,不套注入包裹标注(与限流提示同口径);docstring Notes 同步告诫模型勿据此断言「网上没有」。

#### 新功能 · fetch_url 分块续读——start_index 续取闭环(2026-10-25 审计四十八轮)

- 参考对标:官方 reference fetch server(modelcontextprotocol/servers)的核心模式 `max_length + start_index` 分块读取 + Anthropic《Writing effective tools for agents》的「截断必须给续读指引」。**我们的 fetch_url 截断曾是死路**:60KB 判决书默认只读前 6000 字符,`truncated=true` 之后模型无任何手段读到尾部——与二十二轮修掉的「列表 truncated 无续取」同一种语义病,文本内容版,一直没被发现。判决书全文动辄数万字符,这是法律检索工作流的真实痛点。
- 新增 `start_index` 参数(默认 0,负数按 0 处理):从正文的第几个字符开始返回;成功响应新增 `total_chars`(全文总长,模型可据此规划分块)与 `next_index`(下一次的 start_index;无更多内容为 null)。`truncated=true` 时模型把 `next_index` 传回即无遗漏续读——死路变闭环。
- **窗口越过末尾不是失败**(抓取本身成功):返回 ok=true + 明确提示「start_index 已超出正文末尾,没有更多内容」,不套外部内容包裹标注(本系统生成的文本);不违背「ok=true 时 text 非空」契约。
- **字节刀与续读指针的交互**(与四十七轮的 18KB 字节预算协同):字节刀落在窗口中段时,`next_index` 按「头标注之后实际送达的前缀长度」推进——续读既不跳过未读内容、也不谎称读完;边界退化(字节刀恰好切完整页)正确返回 null。
- 线上工具面核验:streamable-http 握手后 `tools/list`,fetch_url inputSchema 实测含 `max_chars/start_index/url`,仅 `url` 必填——完全向后兼容。
- 测试:`test_fetch_url.py` 补 TestStartIndexContinuation 6 例(首块 next_index/续块内容对齐/末块 null/越界提示不包裹/字节刀推进 next_index/负数归零),全文件 37 测试绿;ruff/mypy 干净,`make mcp` 415/415。
