## 后端

#### 新功能 · 补注册 10 个 workflow 工具（`672f1ffe`）

- `delete_workflow_run`、`get_step_registry`/`get_step_registry_flat`、模板管理 7 件（create/update/list/get/delete/duplicate + `start_workflow_from_steps`）——实现完整但从未注册（`KNOWN_UNREGISTERED` 名单挂了 8 个月,根源是当时权限链没想清楚）,注册完整性门禁抓出后全部补齐,工具面 400→410。
- 模板管理四件（create/update/delete/duplicate）加 `_require_admin` 门禁（与 REST `ensure_admin_request` 同口径,fail-closed）,防止 MCP 面成为 REST A-01 收紧后的降级绕过口;`delete_workflow_run` 接 run 案件访问校验。
- server.py `_workflow_tool` 包装:MCP inputSchema 剥离 `user/org_access/perm_open_access`（模型不应看到无法构造的 object 参数）。

#### 修复 · MCP 直连链路身份重建（`a02998d6`,安全审计）

- workflow 工具直接 ORM 不走 REST,签名的 `user` 参数模型永远传不进来,一律 None:归属校验全跳过、审批/创建不留痕;`get_workflow_detail`/`cancel_workflow` 连 user 参数都没有,REST 校验在 API 层,MCP 路径完全绕过（IDOR）。
- `_resolve_mcp_access`:MCP 调用从 ContextVar Bearer（ninja_jwt AccessToken）重建律师 + org_access + PERM_OPEN_ACCESS;`_mcp_guard_run_access`:仅带 Bearer（共享 MCP）时复用 REST 层同一 `WorkflowRunAccessService` 校验;stdio/解码失败回退匿名（既有行为）。
- 双律师并发 8 轮交错实测无身份串扰;`run_access_service` 的 `sync_to_async` 改 thread_sensitive 默认（True,与 Django async ORM 同口径,保事务可见性）。

#### 修复 · 传输层韧性（`fc0a4590`）

- `_guard_transport` 把 httpx 超时/断连翻译成 `FachuanTransportError`（含方法/路径/原因/重试指引）——此前直接冒泡被 SDK 包成 UnexpectedToolError 黑盒。
- GET 幂等重试一次（传输故障/502/503/504,0.5s 退避）;非幂等方法不自动重试（断连后重发=重复创建）。
- LLM 链路工具 12 处显式 `timeout=180`（诉讼文书生成/保全/授权材料/chat）,此前共用默认 60s 必然误杀。

#### 修复 · 错误直达模型（`e094cd5a`）

- `_workflow_tool` 异常翻译:`BusinessException`（NotFound/PermissionDenied）与 Django `DoesNotExist` → `ToolError`,中文 detail 原样直达模型;E2E 复测「NOT_FOUND: 工作流运行 #999999 不存在」完整可见（此前只有半句 "Error executing tool"）。

#### 修复 · client 抽象旁路（`f3ea3ef3`）

- `doc_convert.convert_document` 直连 `client._http`:绕过 1MB 闸门/传输翻译/文件名解析,还手工重写解析;改走 `client.download`（multipart POST）。
- `invoice_recognition` 两处直连 + 引用未 import 的 `FachuanApiError`（非 2xx 时 NameError 炸弹）;改走 `client.upload`。
- 固化门禁 `TestClientAbstractionBoundary`:tools/ 全部非注释行禁止 `client._http/_headers/_handle`。

#### 修复 · 审批链（`9abb9a42`）

- `approve_` 列入 `DANGER_PATTERNS`（双表:Python + approval-gate.ts,parity 单测守护）:approve_workflow_step 是工作流 gate 的人工确认动作本身,模型低危直调=替人批准自己发起的工作流,HUMAN-in-the-loop 被绕空。
