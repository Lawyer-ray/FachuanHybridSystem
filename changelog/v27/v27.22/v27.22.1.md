# v27.22.1 · claude-agent 只出工具卡片不出正文 + 窗口声明抬到 1M（候选不再截断）

> 承 `v27.22.0`（第五个 agent 接入）。那一版把 claude-agent 接进来了，真机五栏并答
> 立刻暴露出两件事：**它的正文被工具轮次吞掉**，**我们的上下文声明装不下五栏全文**。
> 两条都写在这份文件里，因为它们是同一个症状的两端——「回答被吃掉」。

## 一句话定位

| 之前 | 现在 |
|:-|:-|
| claude-agent 栏只有工具卡片，一个字正文都没有（`AgentRun` 记着 `out=1745` token） | 工具轮次之后的正文照发；并开 `include_partial_messages` 做逐 token 增量 |
| 上下文声明 128K（`pi/model_config`），而 `model_list_service` 里 kimi26 记的是 262144 | 两处同口径 **1M**，且 `FACHUAN_CONTEXT_WINDOW` 可覆盖 |

| 综合候选 >6000 字截断、>2.4 万字**整栏丢弃**（`too_long`） | 两档都删，长候选原样进 prompt，真上限交给网关 |
| prompt 里写死「不超过 1200 字」 | 删掉（模型自己不遵守：要求 1200、实跑 2042） |

## 一、claude-agent 正文被工具轮次吞掉

### 病（会话 335 / `63cc886b…`，五栏并答实测）

`AgentRun` 一行记录着 `status=ok`、`out=1745 tokens`、`tools=2`，库里**一条 assistant
都没有**；界面上只剩 `get_server_time` 与 `web_search` 两张工具卡片。

### 根因：判据写反了

`_translate` 把「本轮发过任何帧」当成「正文已经发过」：

```python
for block in msg.content:
    if TextBlock and not state.streamed_text:  -> delta
    elif ToolUseBlock:                         -> tool_call      # ← 也算 frames
if frames:
    state.streamed_text = True                 # ← 第一轮工具调用关死正文通道
```

工具循环的真实顺序是「第 1 轮 assistant 只有 `tool_use` → 第 2 轮才出正文」，所以第一轮
的工具调用把标志置真之后，后续每一轮的正文都被判定为「已发过」而丢弃。

### 改法

- 状态改名 `saw_stream_text`：**只由** `text_delta` 置真（判据是「流式通道通不通」，
  不是「发过没有」）；
- `AssistantMessage` 兜底分支改为「没见过流式正文才发」，且**不复位也不置真**——
  工具循环的每一轮都可能带正文，都要发；
- 打开 `include_partial_messages=True`：不开只有「整段 assistant 消息」一种粒度，
  前端表现为长时间空白后突然出现一大段。

## 二、窗口声明 128K → 1M（可覆盖）

`models.json` 的 `contextWindow` 决定 **harness 什么时候开始自动压缩**，两个方向都会坏：

| 声明 | 后果 |
|:-|:-|
| 比真实窗口小 | 模型装得下也会被提前摘要；综合结论「一次喂五栏全文」直接吃掉一半 |
| 比真实窗口大 | 在真实上限处被网关 400，而且是**跑到一半才炸**，整轮回答丢失 |

所以按业务方口径取 1M，但给环境变量覆盖口：`FACHUAN_CONTEXT_WINDOW`。
顺带把 `model_list_service` 里 kimi26 的 262144 改成 1M——那两处口径本来就不一致，
真值以模型卡/实测为准，改配置不该改代码。

`maxTokens` 8192 → 32768（`FACHUAN_MAX_TOKENS`）：思考与正文共用这份预算，
实测 kimi-2.6 在 6144 上限下吃到 **5958（96.9%）**，顶满即被视为「没写完」。

## 三、候选不再截断（删除两档静默降级）

`aggregate.py` 原有两档，前提都是「窗口装不下」：

| 档 | 旧行为 |
|:-|:-|
| 超 `MAX_CANDIDATE_CHARS`（6000 字） | 截断并在正文里标注 |
| 超 `HARD_CANDIDATE_CHARS`（2.4 万字） | 整栏丢弃（`too_long`） |

1M 生效后它们只剩一个后果：**聚合者读不到后文论证，却仍写出一段看似完整的结论**。
静默降级比报错危险，所以两档都删，长候选原样进 prompt，真上限交给网关（超了 400）。

`SYNTHESIS_MAX_TOKENS` 8192 → 32768：不改这一条，放开字数会立刻从「写短了」变成
「顶满 → 判定没写完 → 重试 → 整条失败」。

## 已知取舍与边界

- **`too_long` 留在 `DROPPED_REASONS` 关闭集里**，虽然现在不再产出：历史 `AgentSynthesis`
  快照按它落过库，`model_validate` 回放时不能因为「现在不产出」判定旧数据非法。
- **不把窗口再往上抬**（比如 2M）：声明超真实上限的失败是「跑到一半 400」，代价比
  「偶尔提前摘要」大一个量级；不确定的部署请用 `FACHUAN_CONTEXT_WINDOW` 显式声明。
- **不改网关侧超长报错文案**：那是网关的事，本仓库只保证「不会静默截断」。
- **不做候选按 token 计数的自适应截断**：1M 之下没有意义，而真超限时应当报错让人看到。
