# v27.22.5 · 威科凭证由服务端解析：`credential_id` 退出工具签名

> 承 `v27.22.4`。综合结论开始能核引用了，但核验第一步就要「传哪个威科账号」——
> 那一步对律师和模型都是**不可解的问题**。本版把它从签名里拿掉。

## 一句话定位

| 之前 | 现在 |
|:-|:-|
| MCP 工具 `capability_search(credential_id, …)` / `create_research_task(…)` / `check_law_references(text, credential_id)` **必填**凭证 | 三个 schema 的 `credential_id` 变 `int \| None = None`，服务端按当前用户自动挑本所威科账号 |
| 模型只能先调 `list_credentials`，再从 10 条里猜哪个是威科 | 模型不再需要知道凭证存在 |
| 库里 10 条账号混着法院送达 / OA / 工商 / 邮箱 / 东盟法 / 威科（威科只有 2 条），律师不知道 6 和 7 有什么区别 | 实现细节留在服务端 |
| 猜错 = 「登录工商去查法条」 | 解析不出 → **422 明说**「本所未配置威科先行账号凭证」 |
| `verify_citations` 没传凭证时本地短路 | 照发 `credential_id: null` 让服务端解析；解析不出时服务端 422，本地仍兜底降级为 `format_only` |

## `resolve_weike_credential_id` 的四条口径

```python
resolve_weike_credential_id(user=..., explicit=None)
```

| # | 规则 | 为什么 |
|:-|:-|:-|
| 1 | 显式指定 → **原样透传**，不二次猜测 | 调用方比我们更清楚它要哪个账号 |
| 2 | 否则在**当前用户可见范围**内挑威科凭证（非超管只看本所，A-07 归属口径，与 `LawVerificationService` 一致）；拿不到律所 → fail-closed 返回 `None` | 宁可降级为格式检查，也**不跨所借用**别人的威科账号 |
| 3 | 多条命中取 **id 最小**的一条 | 按 `last_login_success_at` 排序会让同一个问题在不同时间用不同账号，出问题难复现 |
| 4 | 一条都没有 → `None`，调用方降级并说明原因 | 综合稿本身有价值，核验不了不该把它一起丢掉 |

「只认威科」的判据：`url` 含 `wkinfo` / 站点名 `wkxx` / `wk` / `weike`。有专门用例保证
**不把工商账号当威科**。

## 改法：解析放后端端点，MCP 侧保持薄壳

- 解析放在**后端端点**（那里已经有 `request.user`），MCP 工具仍是薄壳——不在 MCP 进程里
  猜身份；
- 端点统一过 `_resolve_credential_for(request, explicit)`：显式给了就用，没给就按当前用户
  自动挑本所威科账号；解析不出 → 422 并说明「本所未配置威科先行账号凭证」（不猜、不跨所）；
- MCP 工具签名改成可选（参数移到末尾，Python 不允许默认参数后跟必填）；
- 解析口径与 `legal_research.services.credential_resolver` **单一同源**，前端不需要传。

## 已知取舍与边界

- **没做成通用「按 provider 挑凭证」**：`AccountCredential` 是通用表（法院送达 / OA / 工商 /
  邮箱 / 东盟法都在里面），通用解析需要每个 provider 一套识别规则与优先级策略。本版只解决
  **威科**这一条真实痛点，别的 provider 等有同样的使用者反馈再做。
- **不改 `list_credentials`**：它仍会把 10 条全列出来。删掉它没有收益（有合法用途：让律师
  自己检查账号配置），而「猜哪个是威科」的问题已经在解析层解决。
- **不做多把威科 key 的轮换**：库里 2 条威科凭证，`id` 最小那条固定使用。轮换要引入
  「同一问题用同一账号」与「限流换号」的矛盾，本版不做。
- **不把 `credential_id` 从 `SynthesisIn` 删掉**：留作显式覆盖口（调试、跨所排障），
  删了反而少一条逃生路径。
