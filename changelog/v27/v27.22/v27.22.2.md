# v27.22.2 · 插件能自带 MCP 工具：有 `mcp_tools.py` 就有工具，没有就没有

> 版本判定：承 `v27.21.9`（元典接入）里那条「插件能力只能被 app 层调用」的限制，
> 但落点是**工具面**而不是数据源，所以就地顺延第三位（`v27.22.1` → `.2`），不另开次版本。

## 一句话定位

| 之前 | 现在 |
|:-|:-|
| `mcp_server/server.py` 的 409 个工具是**硬编码 import 清单**，多一个工具必须改主仓 | 插件目录里放 `mcp_tools.py`，工具自动出现在 `tools/list`；不放则什么都不发生 |
| 插件自带的能力（威科私有 API、法院自动化、OCR…）只能被 app 层调用，模型调不到 | 插件能力可以变成模型能直接调的工具 |
| 想加工具 ⇒ 必须往主仓写插件名（被 git hook 禁止） | 靠**目录扫描**发现，主仓里一个插件名都不出现 |

## 为什么靠目录扫描而不是注册表

主仓有一条 git hook：**「Forbid committing weike private implementation paths」**。
所以 `PLUGINS = ["weike_api_private", ...]` 这种写法是被禁止的——私有实现名不能进主仓。
唯一可行形态是约定式：扫 `plugins/*/mcp_tools.py`，谁的目录里有就把谁的 `MCP_TOOLS` 收进来。

`plugins_root()` 用 `importlib.util.find_spec("plugins")` 解析而不是 `Path(__file__).parents[1]`：
MCP 既可能以 `python -m mcp_server`（cwd=`backend/`）启动，也可能被 pytest / 验收脚本
以别的 cwd 导入，包解析对两者都成立，路径拼接只对前者成立。

## 插件侧契约

```python
# backend/plugins/<插件名>/mcp_tools.py
def search_xxx(keyword: Annotated[str, Field(description="检索关键词")]) -> dict:
    '''一句话说明（原样进 tools/list 的 description）。'''

MCP_TOOLS = [search_xxx]          # 必填：要暴露的函数

def check_available() -> bool:    # 可选：缺凭据时返回 False，整块不出现
    return True
```

## 四条约束（都有单测钉住）

| 约束 | 为什么 |
|:-|:-|
| 没插件 = **连名字都不出现** | 不是「有工具但一调就报错」——后者会让模型反复重试一条永远失败的路径 |
| 撞名以**内置**为准 | 内置工具是审批与审计口径的基准，不能被插件覆盖 |
| 一个坏插件不拖垮 MCP | import 失败 / 契约不合法 / `check_available()` 抛异常 → 跳过 + warning。MCP 起不来等于全所 AI 功能停摆 |
| `FACHUAN_PLUGIN_TOOLS=off` 一键回滚 | 与 `FACHUAN_MCP_TOOL_TIERS=off` / `FACHUAN_MCP_SHARED=0` 同风格 |

容错只覆盖「插件坏了」：`_NOT_OURS` 里显式放行 `KeyboardInterrupt` / `SystemExit` /
`GeneratorExit`，控制流异常照常向上抛（不是宽 `except Exception`，也符合仓库的
`test_exception_ratchet`）。

## 零改动项（这次没碰的地方，别以为是漏了）

- **分层与审批不用改**：`_tool_annotations` 按名字 + `classify_risk` 自动推
  `readOnly` / `destructive`；未登记进 `DIRECT_TOOLS` 的插件工具默认走 `deferred`
  （`tool_search` 按需加载），不白占每轮的固定前缀。
- **工具面核对自动包含插件工具**：`make mcp` 的 registry 侧 import 同一个
  `server` 模块，所以插件工具进不进去一目了然。
- **名字带 `delete_` / `submit_` 前缀会被判高危并弹审批卡**——刻意的，插件作者要按
  前缀纪律起名。

## 已知取舍与边界

- **不做插件热重载**：插件装了/删了要重启 MCP 进程才生效。理由是运行期重扫会带来
  「工具面在会话中途变化」的审计歧义（模型上一轮看到的名字下一轮没了），代价不划算。
- **不递归子目录**：只认 `plugins/<name>/mcp_tools.py`，`_` 开头的目录跳过。插件自己的
  子目录不该被当成独立插件。
- **不做 per-plugin 权限模型**：插件工具与内置工具走同一套审批与风险分级。多一套
  「谁可以调哪个插件的工具」会在四层架构里再开一层，本版不做。
- **不做插件工具的 key 轮换 / 凭证注入**：凭证解析归 `v27.22.5` 的 resolver 与
  `v27.21.10` 的元典 env 注入，插件自己只需声明 `check_available()`。
- **不保证插件工具名稳定**：它是函数名，改插件即改工具面——这是插件作者的接口契约，
  写进 README 而不是主仓代码里。
