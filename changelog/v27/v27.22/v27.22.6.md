## 一、任务式检索 100% 失败（最严重的一条）

`ExecutorSourceGatewayMixin._fetch_candidate_batch` 曾是

```python
def _fetch_candidate_batch(self, **kwargs):   # 实例方法
    raise NotImplementedError                  # 「由组合本 mixin 的宿主类提供」
```

而唯一调用方 `_fetch_candidate_batch_with_retry` 是 `classmethod`，写的是
`cls._fetch_candidate_batch(...)` → 运行时 `missing 1 required positional argument: 'self'`。
`v27.21.9` 的「残余风险」里已记过这个洞，本版收掉。

新实现的关键点：

- **`classmethod`**，与调用方同形；
- 三个来源客户端的 `search_cases` 签名并不一致（`base.CaseSourceClient` 只有
  offset/raw_payload，威科多出 `advanced_query` / 法院 / 案由 / 日期筛选），所以先
  `inspect.signature` 取参数名，**只透传对端认识的字段**；
- 对端没有 `offset` 时退回「取整窗 + 切片」（元典翻页依赖这条退化路径）。

## 二、威科详情静默回退网页壳

`v27.4.4` 的「Service 层静态方法棘轮」把 `_response_status` / `_response_headers` /
`_response_body` 从 mixin 下沉成 `weike/transport` 的模块级函数，但 `document.py` 里还留着
`self._response_status(...)`。`AttributeError` 被外层 `except` 吞掉 → 详情"拿到"的是
Playwright 抓来的网页壳，PDF 下载报错。现场证据：task `127 / 128 / 129`。

**测试为什么一直是绿的**：用例改成给**实例**塞 `MagicMock`，于是生产代码里那条不存在的
`self._response_*` 在 CI 里永远命中桩。现在 `autouse` fixture 按生产形态 patch **模块级**
函数，并新增「真实组合（`WeikeDocumentMixin + WeikeTransportMixin`）」回归类——
谁再把调用改回 `self.*`，这里直接 `AttributeError`。

## 三、标题粗筛把候选全量误杀

```python
query_tokens = _split_tokens(f"{keyword} {case_summary}")   # ← 分母把整段案情算进去了
overlap = matched / len(query_tokens)
return overlap >= min_overlap
```

`_split_tokens` 只按空白/标点切分（**不做中文分词**），长案情会切出
「合同约定逾期付款违约金按日万分之五计算」这种整句 token——分母被撞大，overlap 恒在
`0.1` 左右，于是所有候选被跳过。

改法：分母**只算 keyword 的 token**；`case_summary` 的 token 只在「keyword 一个都不中、
但摘要 token 命中标题」时按 **1 个命中**记账（宁可放过，不可错杀）。

## 四、引用抽取的静默假绿（已落库 `51bccaf51`）

两层，都是「空格」：

1. 抽取正则 `第(?P<article>[数字…]+)条` 不允许「第」与数字之间有空白 → 模型爱写
   「第 874 条」，`extract_statute_refs` 一条都抽不到（实测 0 条，去空格后 2 条）；
2. 插件侧 `verify_references` 用同一套写法 → 服务端也返回 0 条。

改法三层：两处正则允许空白 → `LawVerificationService.check_references` 入口归一化
（`第 874 条` → `第874条`，不改任何落库内容）→ **防假绿兜底**：核验返回 0 条时用本地
抽取器交叉验证，本地抽到而核验没返回，就逐条报「未核验」并写明
「抽出 N 条引用，但核验未返回结果」，绝不允许 `unverified=[]`。

## 五、那条偶发外键失败（已知 flake）：根因与修法

现象：2026-11-22 五文件联跑时，`test_synthesis_verify.py::
test_verify_never_reports_green_when_extraction_failed` 报
`organization_accountcredential.lawyer_id` 外键违规；之后用**完全相同**的命令连跑 6 次全绿。

### 根因两层，各自都有实测证据

| # | 机制 | 证据 | 对策 |
|:-|:-|:-|:-|
| 1 | 异步用例在 `sync_to_async` 里**写库**，走的是另一条连接；非事务模式下 fixture 的行还在未提交事务里 → 另一条连接既读不到、也过不了外键校验 | 临时探针：同一份数据 `db` 下必报 `ForeignKeyViolation`、`transactional_db` 下正常（`2 passed`） | ① fixture 改要 `transactional_db`；② 这个用例的凭证解析改成打桩，**彻底去掉跨连接写** |
| 2 | 两个 pytest 进程共用一个测试库：`TransactionTestCase` 的 teardown 会 `flush`（Postgres 是 `TRUNCATE ... CASCADE`），把另一个进程正在用的 fixture 行删掉 | 失败只出现在并行会话同时跑 pytest 那一次；之后同命令连跑 6 次全绿 | `conftest` 加 flock 撞库探测：撞了就只给自己换库名 `..._s<pid>` |

### 三个实现坑（都踩过）

1. **`pytest_configure` 里改库名来不及**：pytest-django 在它之前就加载了 settings。实测改完
   环境变量，它仍去建 `test_fachuan_test`，直接撞上别人的库
   （`database ... is being accessed by other users`）。
2. **`django_db_modify_db_settings` 在 pytest-django 4.14 是 fixture、不是 hook**：写成同名
   函数永远不会被调用（本版一开始就这么写，跑了三轮才发现）。正确做法是**覆盖同名
   fixture**，并依赖 `django_db_modify_db_settings_parallel_suffix` 让 xdist / tox 后缀照旧生效。
3. **只改 `settings.DATABASES` 不够**：`_install_runtime_db_guard()` 在 `pytest_configure` 里
   就碰过 `connections['default']`，连接对象已建立并**拷贝**了一份 `settings_dict`，必须同步改它。

### 为什么不给库名永远加 pid 后缀

每次运行都会新建一个库（447 个迁移 ≈45s），而默认路径本来就是「一次一个库」；更麻烦的是
被 `SIGKILL` 打断时会留下 `test_xxx_s<pid>` 孤儿库。flock 方案只在**真的撞库时**才换名：
正常单跑库名不变、`--reuse-db` 语义不变，进程崩溃锁由内核释放、不留假占用。

### 为什么不用「失败重试一次」盖住它

重试会把「另一个进程正在 truncate 你的库」这类真实环境问题伪装成通过，下一次以更贵的
方式出现（数据泄漏到别的用例、断言随机漂移）。

## 已知取舍与边界

- **不引入中文分词器**：`_split_tokens` 的粗粒度是既有设计（粗筛只挡明显无关，命中概率
  交给相似度打分）。换分词器是另一件事，会同时改变打分与粗筛两处口径。
- **不改 `min_similarity_score` 的默认值**：`0.9` 是既有任务的落库口径，改默认会让历史
  任务与新任务的命中率不可比。要下调请调用方显式传（`0.5` 时的实测命中区间是 `0.55–0.96`）。
- **不用统一接口替换 `inspect.signature`**：抽一个 `search_cases_v2` 要同时改三个客户端
  与一批既有断言，风险大于收益；签名反射只有一处，且有两条用例钉住（有 `offset` / 无 `offset`）。
- **不把 `too_long` 式的"静默降级"一律改成抛错**：详情链路仍保留 Playwright 兜底
  （网页壳总比 500 好），本版只是让「本该走 API 却走了兜底」这件事不再被测试掩盖。
- **不用「失败重试」盖住那条 flake**：理由见第五节——重试会把环境问题伪装成通过。
- **SQLite 测试库不做撞库隔离**：它按文件路径走，换库名没有意义。并发跑 SQLite 测试库仍会
  互相干扰，需要并行时用 `DATABASE_PATH` 指到不同文件。
- **不清理历史残留的 `test_*` 库**：撞库隔离只影响**新**会话；库里已有的孤儿测试库要手工
  `DROP`（本仓库另有「僵尸表告警」管表级残留，管不到库级）。
