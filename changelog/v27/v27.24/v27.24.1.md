## 后端

#### 新功能：列表带附件元信息

- `InboxMessageOut`（列表 schema）新增 `attachments: AttachmentMeta[]`，与详情**共用同一个解析器**（`get_public_attachments_meta`，已剔除 `local_path` 等内部字段）
  - 数据来自已读入内存的 `attachments_meta` JSON，**不额外查库**；`attachment_count` 语义不变
  - 详情原先自己声明同名字段 → 上提到父类，避免「父/子两份解析器二选一」的漂移隐患

#### 新功能：附件首页缩略图端点

- `GET /api/v1/inbox/messages/{message_id}/attachments/{part_index}/thumbnail?page=1&width=320`
- `apps/message_hub/services/attachment_thumbnail_service.py`（新）
  - PDF 走 PyMuPDF 渲染（zoom 由目标宽度反算，夹在 `[0.12, 4.0]`）→ PIL 收敛 → JPEG(q82)；位图直接缩放
  - **落盘缓存** `MEDIA_ROOT/inbox_thumbnails/<message_pk>/<key>.jpg`，键 = sha256(message, part, page, width, size, filename, content_type)：同名替换会换键，不会给出上一版文件的图
  - **不支持的类型在取字节之前就拒**（400 `INBOX_NO_THUMBNAIL`）：不为一枚缩略图去 IMAP 拉 20MB 的 docx
  - 取字节失败 / 渲染失败分别给 `INBOX_THUMBNAIL_FETCH_FAILED` / `INBOX_THUMBNAIL_RENDER_FAILED`（4xx + 原因），不冒 500
  - 异常族按来源收窄（`ValueError/OSError/RuntimeError` + `imaplib.IMAP4.error` + `httpx.HTTPError`），**不新增宽 `except Exception`**
- 响应带 `ETag`（= 缓存键）+ `Cache-Control: private, max-age=86400` + `nosniff`；命中 `If-None-Match` 回 **304** 且不带 body
- 删除材料包时连带回收 `inbox_thumbnails/<pk>/`（`_purge_message_thumbnails`，尽力而为不阻断删除）

#### 优化：MCP `list_inbox_messages` 的行投影

- 列表多了附件元信息 → 每条从约 0.57KB 涨到最多 1.8KB（一封法院送达带 6 份文书），**会撞上 pi 对工具输出 20KB 的腰斩线**，模型拿到半截 JSON
- 因此工具侧做投影：附件只留**前 3 份的「文件名 + 页数」**，超出部分记在 `attachments_truncated`（不让模型以为材料只有 3 份）；全字段/正文走 `get_inbox_message`
- 默认 `limit` 30 → **20**（20 × 约 0.7KB ≈ 14KB，留在截断线内）；无附件行的空 `attachments` 直接去掉

#### 说明：为什么没复用 `apps/agent/services/attachment_render`

那个包是**给模型看**的页图渲染：有文字层的页直接返回文本不出图（`RenderStrategy.TEXT`）、缓存是 7 天 TTL + LRU、长在 `apps/agent` 下。三条硬分歧导致复用会两败俱伤——理由写进了新模块的 docstring，避免下一个人再问一遍。

## 前端

#### 新功能：行内附件小样

- 收件箱行从 `<button>` 改为 `<li>` + 铺满整行的「拉伸按钮」（`打开：<主题>`）：
  **行内要放真按钮**，`<button>` 嵌 `<button>` 是非法的
- 右侧份数胶囊变成按钮（`📎 3 附件`）→ 一点预览第一份；**多份**时才给展开箭头，展开一条横向附件条：每份一张缩略图 + 文件名 + 页数，点谁预览谁
- 老数据（有 `has_attachments` 无 `attachments`）退回纯文本胶囊，不给点了没反应的假入口

#### 新功能：应用内预览弹窗（`AttachmentPreview`）

- PDF：pdf.js 逐页渲染（canvas 由 ref 直接挂，1 页位图不进 React state），支持翻页（`←/→`、页脚控件）与缩放（100/150/200%）
- 位图：直接显示；Office/压缩包：明确说明「不支持在线预览」+ 下载入口
- 多附件：左侧栏缩略图切换（`←/→` 在单页/图片上改为切附件），切换时页码归零
- 三条硬约束写进注释：**不标已读**（只看附件不该刷掉 185 条未读）、**不触发拆解/OCR**、**不预取**
- 抽屉附件清单同步升级：小样 + 应用内预览（眼睛）+ 新窗口打开 + 下载

#### 新功能：缩略图取数

- `fetchAttachmentThumbnail(messageId, partIndex, {page,width})` → **带鉴权的 ky 请求拿 blob**，不走票据：票据单次使用、URL 每次都变，浏览器 HTTP 缓存永远命不中
- `useAttachmentThumbnail` 做 object URL 生命周期管理（卸载 revoke + 丢弃迟到响应），避免一屏几十张小图反复展开时稳定泄漏
- `domain.ts` 新增纯函数 `attachmentDisplayName` / `attachmentKind` / `attachmentPagesLabel`，与后端 `thumbnail_kind` 同口径

## 说明与遗留

- 缩略图**只作用于「用户要看」的时刻**（展开附件条 / 点胶囊 / 开弹窗）。列表 200 行绝不预取——那等于把服务端当渲图农场
- 附件「同名替换」在真实数据里极少（重新同步 / 客户重传），所以缓存键保守地带上了 size + 文件名；代价是**改名会留下约 10KB 的孤儿图**，删消息时整目录回收。不做「改名即清空」，因为那会让改名后所有缩略图重渲一遍
- 老消息的 `page_count` 仍由详情接口回填（`ensure_page_counts`），列表里可能暂时只有体积没有页数——这是既有的「一次写、后续直读」策略，本次没有改动
- 未做：**按「像不像法律材料」给列表排序/打标**（用已有 OCR/规则引擎做可信度信号）。那才是分诊的终局，但属于另一条能力轴，不在本条范围内
- **已跑 `make mcp`**：`list_inbox_messages` 的投影是代码改动，常驻进程不重启就还是旧行为（工具面 431/431 一致，见重启输出）
