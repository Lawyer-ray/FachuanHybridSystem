# v27.24.0 · 恢复注册功能：首位用户即律所管理员，后续用户走「注册 → 管理员审批」闭环

> 能力轴：**账号生命周期**（注册 → 激活 → 首次登录）。此前 `is_active` 与
> `ALLOW_FIRST_USER_SUPERUSER` 绑死，注册接口能调通但产不出任何可登录账号，
> 且「请等待管理员审批」这句承诺在代码里没有对应实现。

## 一句话

| 之前 | 现在 |
|:--|:-|
| 任何注册都得到 `is_active=False`（`is_active = is_first_user and ALLOW_FIRST_USER_SUPERUSER`，而后者默认 `False`），**账号永远登不上** | 系统尚无已激活账号时，首位注册者无条件成为律所管理员并触发系统初始化；其余账号待审批 |
| 响应写「注册成功，请等待管理员审批」，但全仓**没有**待审列表、没有激活接口、没有 admin action | 新增 `LawyerApprovalService` + 3 个 API + Django admin 批量「通过注册审批」 |
| `requires_approval` 取的是 `not user.is_active`，变量却叫 `is_first`；`setup_in_progress` 跟着说谎 | 两个字段各自回归真实语义 |
| 注册不填「真实姓名」→ `IntegrityError`（列 `NOT NULL default=''`，代码显式传 `None`），被 `except` 吞成 `HTTP 200 "注册失败，请稍后重试"` | `real_name or ""`，正常注册 |
| `/admin/register/` 被 `ALLOW_ADMIN_REGISTER=False` 挡住，而登录页那个「立即注册」链接**恒显** → 点进去必报「注册入口未开放」 | 默认改 `True`；表单注册与 API 注册共用同一套语义 |
| 表单注册后按 `user.is_admin` 决定是否 `login()`——Django `login()` 不校验 `is_active`，未激活账号会被直接建会话 | 判据改为 `user.is_active` |
| 登录页印着 `法穿 / 1234qwer`（口令早在 `v27.3.6` 就从源码删除）和「一键创建默认管理员」按钮（非 DEBUG 必然失败） | 整块删除 |
| 待审批账号连审批都保存不了：`LawyerAdminForm.clean()` 强制 `lawyer_team`，而系统初始化在非 admin 首位用户时被跳过 → 全新库没有任何团队 | 团队必填收窄为「仅对已激活律师生效」 |

## 设计决策：把两件事拆开

原先 `is_active` / `is_admin` / `is_staff` / `is_superuser` 全绑在 `should_grant_admin` 一个布尔上：

| 权限 | 首位用户（系统无已激活账号） | 后续用户 | 控制开关 |
|:--|:--|:--|:--|
| `is_active` | ✅ 无条件 | ❌ 待审批 | — |
| `is_admin` / `is_staff`（律所管理员） | ✅ 无条件 | ❌ | — |
| `is_superuser`（平台超管） | 仅当 `ALLOW_FIRST_USER_SUPERUSER=true` **且**提供 `BOOTSTRAP_ADMIN_TOKEN` | ❌ | 安全审计 C-02 |

理由：C-02 的真实威胁是「公开实例上零凭证抢占**超管**」，不是「抢律所管理员」。
首位注册者本来就该是这套自托管系统的主人；让超管继续受令牌约束，审计结论因此保住。

`is_first_user()` 的判据从「表里有没有 `Lawyer` 行」改为「有没有**已激活**账号」——
后者才是「还没有任何人能登录」的真实语义，顺带让历史孤儿行不再永久占死首位名额
（dev 库里 `smallXia` / `猪猪侠天下无敌` 两条正是这么卡住的）。

## 已知取舍与边界

| 不做的事 | 为什么不做 |
|:--|:--|
| React SPA 加 `/register` 页面 + 待审批页 | 用户明确裁决「前台不做注册和审批」。注册与审批只走 API + Django admin 两个后端面 |
| 首位用户默认授予 `is_superuser` | 会推翻安全审计 C-02。超管仍需 `ALLOW_FIRST_USER_SUPERUSER` + `BOOTSTRAP_ADMIN_TOKEN`；律所管理员不需要 |
| 给 `approve` 加「审批人无律所时自动回填唯一律所」 | 本机 4 个真实超管都带律所，不构成现实问题；无律所审批人是 `createsuperuser` 建的纯 CLI 超管这一少见情形。真出现再加 |
| 用 PG advisory lock 消除首注册并发竞态 | `is_first_user()` 是「先查后写」，两个请求同时命中可能都成为管理员。自托管单实例风险低；多实例部署时需要另做 |
| 把 `is_active` 判断塞进 `AuthService.login` 以区分「未激活」与「密码错」 | 会让登录响应成为账号存在性/状态的预言机。改用运维侧通道（管理员审批列表）暴露状态，登录侧维持统一话术 |
