# v27.17.0 · 法院短信接进「记一笔」：文书自动识别关键日期，律师只做确认

> 分支 `feat/court-sms-auto-date-capture`。
>
> 前置：`v27.1.6` 已把「记一笔」升级为「识别 → 逐条人工确认 → 写入日历」，并在
> recognize 端点预留了 `source_court_sms_id` 管线模式（案件/日志由短信侧预绑定）。
> 但那条缝**一直没人接**——`recognizeFile()` 从不传这个字段，全仓只有测试引用它。
> 本版把这条缝接通，并补上它缺的三样东西：自动触发、幂等、状态回显。
>
> **后端含一次加列迁移**（`document_recognition.0009`：`source_document_path` +
> `classification_hint` + 一条复合索引），本地开发库已应用，其他环境部署需 `migrate`。

## 一句话定位

法院短信是**来源**，记一笔是**第二段落**。短信状态机一行没改：日期识别完全跑在
旁线上，它失败、超时、卡住都不会让 `CourtSMS` 的任何一个字段发生变化。

## 为什么不是「塞进 process_sms」

最直觉的做法是在 `process_sms` 的 `completed` 之前加一个 `extracting` 阶段。否决理由：

| 理由 | 说明 |
|:--|:--|
| 权限错位 | 短信写操作（assign/retry/delete）已全部收敛为管理员专用；而「确认日期写日历」必须由有权限的律师本人做 |
| 语义污染 | `completed` 的含义会变成「文书归档 + LLM 也跑完了」，一次 LLM 抖动就让整条短信看起来失败 |
| 无法独立重跑 | 识别想重试就得重跑整条短信流程（含爬虫下载） |
| 耦合方向错 | 短信侧会被迫 import 识别域，任何识别域改动都能波及短信主线 |

旁线的方向是单向的：**短信侧只递一个纯数据 DTO 出去，识别域从不反向依赖短信模型**。

## 后端

#### 新增：日期捕获旁线服务（`apps/document_recognition/services/date_capture_service.py`）

| 能力 | 实现 |
|:--|:--|
| 送入识别 | `capture_dates_for_source(DateCaptureSource)` — 短信的**每份**文书各建一个识别任务，逐份返回 `created/retried/reused/skipped` |
| 幂等键 | `(source_court_sms_id, source_document_path)` — 单靠 `file_path` 不行：重跑复用同一行，「重新送」要新建行 |
| 失败处理 | 已有 `failed` 任务**原地重跑**（复用已落库文件，不新建行）；`force=True` 才无条件新建 |
| 逐份隔离 | 单份文书建任务抛错只写该行 `reason`，其余照送（一条短信混着坏文件是常态） |
| 前置校验 | 无文书 / 无 `case_log_id` / 文件已不在磁盘 → 明确 `skipped` + 人话原因，不建空任务 |
| 状态汇总 | `list_source_tasks()` 给出每任务的状态、候选数（pending/confirmed/skipped）、确认进度 |

#### 新增：两个 API（普通律师可用）

| 端点 | 作用 |
|:--|:--|
| `POST /court-document/sms/{id}/capture-dates` | 送识别（幂等）；`?force=true` 无条件新建 |
| `GET /court-document/sms/{id}/capture-status` | 派生任务列表（轮询 + 「继续确认」入口） |

**权限口径**：读短信按 `CaseAccessPolicy`（与法院短信详情接口同口径，未绑案件的
公共短信全员可读），**不做** `_require_admin`——语义是「读这份文书 + 给**自己**写日历」，
与 QuickAdd 上传同权限级；写入日历的权限由既有 `dates/confirm` 按案件 ACL 兜底。
任务列表另叠加任务归属过滤（普通律师只看自己建的，管理员看全量）。

#### 复用：法院短信已算出的结果直接带给记一笔

按你的要求「短信识别结果也可以套用给记一笔」，管线模式下识别不再从零算：

| 字段 | 策略 |
|:--|:--|
| 案号 | **短信正文解析结果优先**，直接覆盖单份文书自己的提取结果（短信侧是在正文上解析的，比单份文书更可信） |
| 当事人 | 识别没提取到时回填短信解析出的当事人 |
| 文书类型 | 只在分类器认不出（`other`）时用短信类型兜底；认得出的一律信分类器（短信链接里混着应诉/举证通知，短信类型粒度太粗） |
| 案件 / 案件日志 | 直接用短信第一轮绑定结果预绑定 → 识别期不匹配、不重命名、不建日志、不重复通知 |

#### 修复两处「一碰就炸」的既有缺陷（都是本次真实跑出来的）

| 缺陷 | 后果 | 修法 |
|:--|:--|:--|
| `tasks.py` 裸写 `binding_error_code = result.binding.error_code` | 管线模式绑定成功时 `error_code` 是 `None`，而列是 `NOT NULL` → **识别成功却因 NotNullViolation 整条记为失败** | `or ""` |
| `DocumentType` 当 TextChoices 用（`in DocumentType.values`） | 首次跑就 `AttributeError` | 改 `DocumentType(hint)` + `try/except ValueError` |
| async 视图里直接调 `resolve_request_org_access` | 它查团队关系（ORM）→ `SynchronousOnlyOperation` 500 | 移进 `sync_to_async` 的 `_do()` 里 |

## 前端

#### 交互：打开已完成的短信 → 自动识别 → 只做确认

```
收法院短信（completed）
  └─ 弹窗打开
       └─ 旁线自动送识别（幂等，反复打开不重复烧 LLM）
            └─ 文书列表下方出现「记一笔 · 关键日期」
                 ├─ 识别中  → 「正在识别文书里的开庭/举证/上诉等日期…」
                 ├─ 有待确认 → 每份文书一行 +「确认日期」按钮
                 ├─ 已写入   → 「已写入日历 N 条」
                 ├─ 识别为空 → 「没识别到关键日期（通知书/回证类常见）」+「再识别一次」
                 └─ 识别失败 → 失败原因 +「重新识别失败的文书」
```

「确认日期」直接接管后端已建好的识别任务（`RecognizeDialog` 新增 `taskId` 模式）：
**不重传文件**，弹窗内也**不出现案件选择器**——案件由短信侧定死，日期写到哪份日历
不能在同一张弹窗里被换掉（换成只读 chip 明确显示「已由法院短信绑定：XXX」）。
写入成功即刷新日历 query。

#### 为什么必须保留「人工确认」这一步

后端只有 `confirm_candidates` 一条写提醒的路径，它同时承担着与既有提醒
（`case_log_id + due_at`）去重的职责。自动写 = 跳过唯一的复核关口。
法律日期错一天的代价远大于点几下——这条底线没变。

## 已知边界

- **自动触发在前端**（弹窗打开时调 capture-dates），不是后端 `completed` 时自动推。
  这样「反复打开不重复烧 LLM」由幂等键天然保证，也不需要为新短信加一个后台钩子。
  若将来要「完全不打开弹窗也识别」，只需在 `process_sms` 的 completed 之后
  **异步投递**一次 capture（不阻塞、不改状态），服务层已可直接复用
- **识别为空不算失败**：判决书/回证类文书确实常常没有未来日期，界面明说
  「没识别到关键日期」，给「再识别一次」但不会自动重试（避免对无日期文书反复烧 LLM）
- **一条短信多份文书时按任务逐个确认**：日期写在哪份文书的候选上由律师自己看，
  不做跨任务合并——合并会丢失「这个日期来自哪份文书」的溯源
- **`classification_hint` 目前只会是空串**：短信三档类型都映射到 `other`，
  等于「有提示但粒度不够」。字段先落库，等短信侧分出更细的类型（如传票/判决书）即可生效

## 补丁：文书识别只能读到前 3 页，末页上诉期整段丢失

> 同分支追加。上版上线后拿一条**真实 7 页民事判决书**复核，发现识别「未识别到关键日期」，
> 而律师指出「如不服本判决…十五日内…」那句明明有日期。查证后确认：**那句话在 PDF 第 7 页，
> 我们根本没读到它。**

### 事故链（三个缺陷叠在一起）

| # | 缺陷 | 实测 |
|:--|:--|:--|
| 1 | `TextExtractionService()` 无参实例化 → `text_limit=None` → 下层 `extract_pdf_text(limit=None)` 回落到 `DEFAULT_TEXT_LIMIT=1500`（**预览/摘要**用的默认值） | 7 页 3900+ 字只读到前 3 页 **1381 字**，第 7 页上诉期条款丢失 |
| 2 | 只降置信不排位：`STALE_DAYS=180` 只把过期日期压到 0.3 置信度，仍与真期限争夺 `MAX_CANDIDATES=8` 名额 | 放开截断后，正文 6 条历史日期（立案/签约/对账/落款）把 2 条真期限挤到名额边缘 |
| 3 | 前端 `DEFAULT_CHECK_CONFIDENCE=0.5` 默认不勾低置信行 | 历史日期虽默认不勾，但仍占名额、仍污染列表 |

**页数限制其实没问题**（`max_pages=None` 全程不限），病因纯粹是字符数硬上限。
同仓库 `apps/documents/judgment_pdf_extractor` 早就踩过同一个坑（49 页判决书只读到 13 页，
末尾判决主文丢失）并写了全文提取绕过它——识别域没跟上。

### 修复

1. `TextExtractionService.DEFAULT_TEXT_LIMIT = 200_000`，`text_limit=None` 时用它而不是
   传给下层 None（**不靠 None 的隐式语义**：下层会把 None 当「用预览默认值」）。
   与 `judgment_pdf_extractor._MAX_EXTRACTION_CHARS = 200_000` 同口径。
2. 候选名额分配第一维改为「是否已过期」：未过期优先进 `MAX_CANDIDATES`。
   过期候选**仍然返回**（折叠到后排，律师仍可手动勾选），只是不占前排。

### 实测（同一条短信 #290，同一份 7 页判决书）

| 指标 | 修复前 | 修复后 |
|:--|:--|:--|
| 提取字数 | 1381（前 3 页） | **3619**（全 7 页） |
| 含「如不服」 | False | **True** |
| 日期候选 | 空 | **2 条真期限**（见下） |

```
2026-11-20  appeal_deadline  llm  0.9  「如不服本判决，可以在判决书送达之日起十五日内…上诉」
2026-11-15  payment_deadline llm  0.9  「本判决发生法律效力之日起十日内…缴纳受理费」
```

历史事实日期（立案/签约/对账/落款）全部被排到名额之外。
对照传票（#286）仍正确输出 `2026-11-09 14:30 hearing conf=0.99`，未受影响。

### 已知边界：上诉期的锚点是落款日，不是真实送达日

`2026-11-20` = 落款日 `2026-11-05` + 15 天。真实送达日系统并不知道，落款日是最早可能起算日，
因此**只会提前提醒、不会滞后**（宁可早一点提醒律师复核）。若将来接入实际送达回证时间，
把锚点换成它即可，规则层（`_find_issue_date`）已集中在一处。

## 补丁 2：上诉期必须以「送达之日」起算，不能用文书落款日

> 同分支追加。业务口径确认：**`CourtSMS.received_at`（法院短信转发到手机的时刻）就是送达日**，
> 法院与你方两侧均按此运营，不存在别的口径。

### 问题

旧规则把「如不服本判决，可以在判决书**送达之日**起十五日内上诉」的锚点一律取**落款日**
（`_find_issue_date`：全文最后一个日期）。但法院文书落款普遍早于实际送达
（用印/打印/邮寄需要时间），用落款日当锚会**把届满日算早**——律师按这个日期排期，
以为还剩几天，实际可能已逾期。

同一份 7 页判决书实测：

| 锚点 | 上诉期届满日 |
|:--|:--|
| 落款日 2026-11-05（旧） | 2026-11-20 |
| **收到日 2026-11-06（新）** | **2026-11-21** |

### 修复

`date_candidate_service._apply_relative_deadline_rules` 新增 `delivery_date` 参数：
传入时以它为锚（`收到日 + N 天`），否则回落落款日。

链路：`CourtSMS.received_at` → `tasks._load_pipeline_hints` → `recognize_document(received_at=...)`
→ `build_date_candidates(received_at=...)` → 相对期限锚点。记一笔独立上传拿不到收到日，
仍回落落款日（宁可保守早提醒，不凭空编日期）。

adapter 转发签名同步补齐（改内部签名必须同步 adapter，否则异步执行期 TypeError）。

### 测试

新增 `TestAppealDeadlineAnchoredOnDeliveryDate`（3 条）：传收到日 → 11-21；
不传 → 回落 11-20；送达晚于落款（11-20 收到）→ 顺延到 12-05。
`document_recognition` 全量约 800 条全绿。

### 待定（未改，需法律口径确认）

判决主文的「**本判决发生法律效力之日起**十日内支付…」是**两级推演**：
送达 → 上诉期届满（15 日，无上诉才生效）→ 再起算 10 日。
当前实现只按「送达日 + 10 日」算，比正确值**早约 15 天**。

这涉及「假设对方不上诉」的法律判断，不是工程能单方面决定的，因此**本补丁不改**，
留待确认后再动。

## 补丁 3：只记「由送达日直接决定」的硬期限，不记生效日推演出的履行期

> 同分支追加。口径（业务确认）：**生效日期必须和书记员确认，系统不记录、不推算**；
> 只记上诉期、保全到期、举证期限这类关键日期。

### 问题

判决主文写的是「被告于**本判决发生法律效力之日起**十日内支付…」（本条判决书三处皆是）。
旧实现把它当「送达日 + 10 日」算，给出 2026-11-16。这是**错的**：

```
送达 11-06 → 上诉期届满 11-21（无人上诉才生效）→ 再起算 10 日 → 12-01
```

生效日取决于对方是否上诉，只有书记员能确认。按「送达+N」硬算是假日期；
按「送达+上诉期+N」推演又是替律师做「假设对方不上诉」的法律判断。两条都不该走。

### 修复

| 规则 | 行为 |
|:--|:--|
| 起算点为「发生法律效力/生效」的句子 | **整句跳过**，不产生候选（`_EFFECTIVE_FIRST_RE`） |
| LLM 仍返回此类履行期候选 | 兜底剔除（`_is_effective_first_derived`，按 context + 日期附近窗口判断） |
| **过去 且 类型=other** 的候选（立案日/签约日/对账日/落款日） | 丢弃——是叙事时间线，不是关键日期 |
