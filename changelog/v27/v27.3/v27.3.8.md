## 后端

### 安全加固：批量打印写权限收敛到管理员（L-4）

打印规则/预置是**全局**资源——一条规则决定全所所有文档落到哪台打印机、用哪套预置，写操作没有归属概念。此前 `create_rule` / `update_rule` / `delete_rule` / `sync_presets` 四个端点只挂了 `JWTOrSessionAuth()`，**任何登录用户都能改全局规则**（横向越权 + 完整性破坏）。

- 统一接入既有 `ensure_admin_request`：`is_admin` / `is_superuser` 才算管理员，`is_staff` 不算（与 reminders / message_hub / archive 收敛口径一致）
- 读端点保持开放（前端规则列表页需要），只收敛写
- `lp` 参数注入面：`subprocess.run` 用 list 且无 `shell=True`，**不存在 shell 注入**；但以 `-` 开头的打印机名/选项名会被 `lp` 解析成选项，含换行的值会拆出额外参数。加白名单式校验，命中即拒

### 顺带修复存量路由缺陷：`/presets/sync` 被动态段吞掉

`/presets/{preset_id}` 注册在 `/presets/sync` 之前，ninja 按注册顺序匹配 path，导致 **`sync` 被 `{preset_id}` 吞掉——任何方法请求 `/presets/sync` 都返回 405**，前端「同步预置」按钮一直是坏的。调整为静态段优先，并补正向测试固化。

### 安全加固：JWT 退出 `?token=` 查询参数（M-2）

`JWTOrSessionAuth` 为兼容 `<img src>` / `<iframe src>` / `<a download>` 场景支持从 `?token=` 取 JWT，导致**完整 JWT 落入 nginx access log、浏览器历史、Referer 头及任何中间代理日志**——拿到 JWT 即等于拿到身份（2 小时有效期 + 可换 refresh）。

- **新增 `apps/core/security/download_tickets.py`**：票据只含 `user_id` + 随机 `jti`，经 `django.core.signing` 加 `SECRET_KEY` 签名并带时间戳，**60 秒有效、单次使用**（兑现后 jti 入缓存，重放被拒）。缓存故障时退化为「仅签名 + 过期」，不因缓存挂了拒绝合法下载
- `JWTOrSessionAuth`：query 只认 `?ticket=`，**不再读取 `?token=`**。票据路径与 JWT 路径同口径校验 `is_active`（`ninja_jwt` 的 `get_user` 拒 inactive），否则停用账号会经票据重新获得访问权
- **新增 `POST /api/v1/download-ticket`** 签发票点（复用普通 API 限流，已认证）
- settings 新增 `DOWNLOAD_TICKET_TTL_SECONDS` / `DOWNLOAD_TICKET_SINGLE_USE`
- `media_protected` 的 docstring 原先宣传 `?token=`，已同步更正（否则下一个人照文档又把 JWT 塞回 URL）

### 安全加固：验证码识别端点改为服务间共享密钥（M-5）

`/api/v1/automation/captcha/recognize` 原为 `auth=None` 的匿名端点，可被公网当免费 OCR 刷。上一轮只叠了 IP 限流——**限流是限流，不是认证**。

关键事实：仓库内（含 plugins）**没有任何调用方走 HTTP 打这个端点**——浏览器自动化与 `court_automation` 插件全部进程内直连 `CaptchaServiceAdapter` / `build_captcha_service()`。这个 HTTP 端点没有内部消费者，匿名开放纯粹是白送算力。

- 要求 `X-Captcha-Secret` 头匹配 `CAPTCHA_RECOGNIZE_SECRET`（settings 新增，环境变量配置）。选自定义头而非 `Authorization`：本端点对浏览器侧无凭证，自定义头不触发 CORS 预检，也不与用户 JWT 语义混淆
- **未配置密钥时端点整体不可用**（403 `CAPTCHA_SERVICE_DISABLED`）——fail-closed：生产忘配的表现是「功能不可用」而不是「匿名可刷」
- 密钥比对用 `hmac.compare_digest` 避免时序侧信道；密钥不记入日志
- 授权校验放在最前，未通过不构造/调用 OCR 服务（不白费算力）

### 安全加固：ICS 订阅令牌闲置轮换（M-4 后半）

`CalendarFeedToken` 原先只有 `token` / `created_at` / `updated_at`：**一次生成永久有效**，泄露后无感知、无手段止损。

- 新增 `last_used_at` 字段（迁移 `0013`，纯 AddField 可空，无需回填）
- 每次拉取 Feed 刷新时间戳；**闲置超 180 天自动换发新令牌**，旧令牌即时失效。判定口径取「最后拉取时间」，无记录时退回「创建时间」——否则从没用过的令牌永远判为闲置，每次拉取都白换一次
- **轮换而非拒绝**：日历 App 手里是旧 URL，直接 403 会让订阅静默失效且难以排查。轮换后本次请求仍用新令牌放行，用户下次在后台重新获取链接即可
- 用户主动 `regenerate` 时清空 `last_used_at`，避免继承旧时间戳立刻又被判闲置
- API / admin 的 token 端点返回 `last_used_at`，前端可展示「最后拉取时间」

## 运维注意

- **`CAPTCHA_RECOGNIZE_SECRET` 需在生产环境配置**，否则 `/api/v1/automation/captcha/recognize` 不可用。由于仓库内无 HTTP 调用方，正常业务流程不受影响；确需外部脚本接入时配一个强随机值并同步给调用方
- 前端下载/预览路径从「拼 JWT」改为「换 60 秒票据」，多一次 API 往返。票据单次使用，重试/刷新需重新获取（前端已按点击时机取票）
