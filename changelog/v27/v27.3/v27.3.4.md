# v27.3.4

v27.3.3 上线的案号查 GUID 在真实环境（admin 进程触发）报「OA 案件列表页缺少 __VIEWSTATE」，跟进两轮诊断后的完整修复：**JTN 纯 HTTP 链路的网关自愈机制**。本版本全部为后端修复，2 commits。

## 后端

#### 修复：案号查 GUID 会话自愈——网关回调 Set-Cookie + 单 client 表单登录

- **根因（诊断实锤，两层叠加）**：
  1. `ims.jtn.com` 前置飞连/SSO 网关——缓存会话失效后，纯账密 httpx 登录拿到的 cookie 是 `access.jtn.com` SSO 门户的（非 OA 会话），旧失败判定认不出该形态而误判登录成功，最终误报「缺少 __VIEWSTATE」；
  2. 网关回调页（`corplink/agw/callback`）响应会 **Set-Cookie 下发全新网关会话（corplink_at/it）**，但旧实现每次新建 httpx client，把这笔自愈丢弃了。
- **修复**：`case_guid` 会话建立重写为**单 client 顺序自愈状态机**（`_ensure_list_session`）——首个 GET 吃下回调 Set-Cookie（网关层恢复）→ 被放行到 OA 应用层登录页 → 提取 CSRFToken 表单 POST 账密（`rurl` 302 回列表页）→ VIEWSTATE 就绪即搜索。轮间 0.3s 间隙，最终失败并入外层整体重试一次
- **`http_session` 新增 `is_sso_gateway_url`**（`access.jtn.com/login`、`corplink/agw`）并入 `is_oa_login_page` 失效判定
- **`auth.http_login` 修误判**：POST 后落在 SSO 门户/网关即明确报「登录被 SSO 网关拦截」，不再假成功；失败判定升级为强口径（登录页+账密表单，或错误文案），会话 cookie 改读客户端累积 jar（会话常由 GET 登录页 Set-Cookie 下发）

#### 修复：自愈前清残留网关 token——旧 corplink 同名共存压过新值致回调死循环

- admin 进程实测仍失败：cookie 缓存里残留已失效的 `corplink_at/it`（domain `.ims.jtn.com`），网关回调新下发的 token 是 host-only 串——域名串不同，httpx cookie jar 同名**共存**，请求时旧值在前被网关永远拒绝，每轮新 code 弹回调死循环
- 修复：`_ensure_list_session` 前置清掉 jar 里的 `corplink_at/it`（按 cookie 的 domain/path/name 精确 clear），让网关授权链以干净状态重发；授权服务 session cookie 不动（保住免登授权链）
- 顺修 `cookielib jar.clear()` 误用：首参是 domain 字符串而非 Cookie 对象，KeyError 被吞导致清理空转

#### 新增测试（10 例）

- 自愈链模拟器（httpx MockTransport 真 302 重定向 + Set-Cookie）：缓存新鲜直达 / 缓存失效自愈 / 无缓存冷启动自愈 / 多命中去重 / 0 命中 / 登录失败报账密错误 / 网关死拦报会话无法建立 / 搜索中途失效整体重试一次 / 无 VIEWSTATE 异常页 / 残留旧网关 token 不阻塞自愈
