# v27.3.3

本分支四块主线：**① 案号查 GUID（律所ID）**——合同编辑页按律所OA案件编号一键查 OA 案件 GUID 并自动填充，纯 HTTP 只读、无浏览器（服务器部署可用）；**② JTN 纯 HTTP 会话基建收敛**——四处各写一份的登录/失效判定/客户端构造统一到 `jtn/http_session.py`，顺修两处隐患；**③ Django-Q 队列按 SECRET_KEY 指纹隔离**——根除跨密钥纪元偷任务丢任务；**④ 凭证归属钉死**——案号查 GUID 用请求者本人的 JTN 凭证发起。全部为后端改动，5 commits / 16 文件。

## 后端

#### 新功能：合同「律所ID」与案号查 GUID（contracts + oa_filing）

- **`Contract.law_firm_oa_guid` 新字段**（律所ID，存 OA 案件 GUID/keyid；迁移 `contracts.0046` 已应用），进「律所OA信息」区块
- **JTN `case_guid/` 模块**（方法一：案件管理页搜索，纯 HTTP 三步）——GET 列表页取 `__VIEWSTATE`（每次现取）→ POST `project_no` + `currentPage=1` → 行内 `projectView?keyid=` 提取 GUID；无浏览器、无 Playwright 兜底；lxml 行解析为主（行文本含案号才收，0 命中不整页正则捞回，防误提页面其他区域 keyid），仅 lxml 异常才回退整页正则
- **链路**：合同编辑页「查询ID」按钮 → admin 端点 `POST /admin/contracts/contract/{id}/lookup-oa-guid/`（JSON，方法/权限/参数校验）→ `ScriptExecutorService.lookup_oa_case_guid`（`run_coro_sync` 桥接 + VPN 类错误友好化）→ 新增 `CaseGuidLookupAdapter` 协议 + JTNAdapter 实现
- **交互**：读取表单内未保存的案号发起查询；唯一命中自动填入并高亮，多命中点选填入，0 命中提示「仅能查询当前 OA 账号可见的案件」（OA 权限过滤）；真实冒烟与接口文档取证值逐字一致（完整案号唯一命中 / 部分案号 4 命中 / 不存在 0 命中）
- 凭证归属：`_find_credential` 按登录用户过滤 + cookie 缓存按账号隔离，谁登录就用谁的 JTN 账号发起查询（防回归测试钉死）

#### 重构：JTN 纯 HTTP 会话基建收敛至 `jtn/http_session.py`（oa_filing）

- **统一常量出口**：headers / timeout / 登录 URL 收敛到 `auth/constants.py`，case_import / client_import / case_guid 删除各自的 4 份拷贝
- **失效判定小件**：登录 URL、短占位页（location.replace）、账密表单（头 2500 字符）、错误文案——四种历史口径全部收敛为可组合小件
- **`auth.service.http_login` 升级**：失败判定由「URL 含 login」升级为强口径（停在登录页且带账密表单，或正文错误文案）；会话 cookie 改读客户端累积 jar（会话常由 GET 登录页 Set-Cookie 下发，POST 响应常不带，与生产验证过的旧 case_import 实现对齐）
- **会话策略**：`resolve_session_cookies` 缓存 cookies 优先（SSO 扫码登录产物，兼容仅扫码账号）+ `http_login_cookies` 友好错误包装；case_guid / client_import 已接入；**case_import 刻意保持每批全新登录**——磁盘缓存失效会拖垮整批 HTTP 链路回退 Playwright，比省 2 个请求更伤（批内复用靠内存缓存）
- **`build_client` 客户端工厂**：统一 headers / follow_redirects / trust_env=False（防代理环境变量劫持），`connection_close` 变体保留给串行分片场景
- 顺修：**client_import Playwright 链登录 `timeout=1` 笔误**（1 秒超时在 VPN 抖动时假报「账号或密码错误」，改走共享登录后统一 15s）；仅扫码账号在 client_import 的 HTTP/Playwright 链路从必挂改为可用缓存会话
- 未动（行为差异大，另行处理）：filing 的 SSO 扫码探测、四个 Playwright `_login` mixin、case_import 的飞连网关拦截检测

#### 修复：Django-Q 队列按 SECRET_KEY 指纹隔离（core）

- 问题：Redis broker 队列键只含集群名（`django_q:default:q`），与签名密钥无关；SECRET_KEY 轮换后新旧进程混跑（`--reload`/watchfiles 重启孤儿化的 qcluster 僵尸树仍持旧 key），异 key 方 BLPOP 偷走对方任务即 BadSignature 静默丢弃（出队即删无法重投），定时任务周期性无痕丢失（10-05/10-06 两起）
- 修复：`resolve_q_cluster` 按 SECRET_KEY 派生集群名（`default-<sha256[:8]>`），队列键变为 `django_q:default-<指纹>:q`，不同密钥纪元进程天然读写不同队列，跨纪元互偷在结构上不再可能；`DJANGO_Q_CLUSTER_NAME` 环境变量可显式覆盖（多栈手动分队列）；Schedule 注册不绑 cluster、tasking 工具动态跟随，改名无副作用
- 配套：backend/CLAUDE.md 新增「Django-Q 队列与僵尸集群防范」章节（诊断三步：数心跳键 / 枚举进程树 / 反序列化心跳包；清剿与规避纪律）
