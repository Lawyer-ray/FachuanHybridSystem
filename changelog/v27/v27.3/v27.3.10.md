# v27.3.10

分支 `fix/case-number-parse-completeness`：案号变更页两个使用阻塞修复 + 要素式转换服务鲁棒性与报错优化。2 个 commit，含 plugins 子模块更新（`33a3496`）。

## 后端

### 修复：案号解析「解析裁判文书」提取主文不完整（commit `167d1f23d`）

`JudgmentPdfExtractor.END_KEYWORDS` 把「案件受理费」当硬截止词。判决书中它通常是主文后的独立段落，但**调解书**常把它写成编号条款（如「二、案件受理费…」），其后还有关键的强制执行触发条款（如「三、若…未按时足额支付，则…有权申请强制执行」）——在此截断会丢掉执行依据。

- 改为：仅当前置不是条款编号前缀（一、/（一）/1. 等）时，「案件受理费」才作为主文截止点
- 补回归测试：调解书编号条款中的诉讼费不截断

### 修复：案号解析兜底 LLM 选择器永久停在「加载中...」（commit `167d1f23d`）

案号变更页（`/admin/cases/case/<id>/change/`）兜底下拉框两个叠加缺陷，前后端各一处：

- **前端**（`case_number_parse.js`）：`for` 循环里用 `var llmSelect` 声明，而 `fetchLLMModels` 回调是异步的 → 所有闭包共享最后一个迭代的 select 引用，第一行永远不更新。改用 IIFE 逐行绑定当前 select
- **后端**（`llm_models_view`）：原逻辑 `[] if result.is_fallback else result.models` 丢弃了 `ModelListService` 合并 SystemConfig/LLMProvider 后的模型，而该方法恒返回 `is_fallback=True` → 接口恒为空列表。改为直接返回 `result.models`（与其它调用方一致）
- 补 `is_fallback` 时仍返回合并模型的回归测试

### 修复：要素式转换服务瞬时断连自动重试 + 报错带环节定位（commit `23b5f59ea`，含 plugins `33a3496`）

转换偶发失败（`RemoteProtocolError: Server disconnected without sending a response`），排查确认远端 znszj 调用方式**未变更**（对比线上前端 JS 逐项核实：验签链、转换链、请求头、参数均一致），属瞬时网络故障；且原实现一次失败即整单报错、报错文案无定位信息。

**可靠性（plugins/doc_convert/znszj_client.py）**：

- 全部请求环节对 `httpx.TransportError`（断连/超时/DNS 等）自动重试，共 3 次尝试、间隔 1s/2s 递增，每次重试打 warning 日志；同步/异步链路均覆盖
- HTTP 状态码异常与业务 `success=false` 应答统一转为带上下文的业务异常，不再裸抛 traceback
- `signatureCode` 解析加格式防护，token/mac/sbbs 缺失时报 `ZNSZJ_INVALID_RESPONSE` 而非 KeyError（远端改格式时快速定位）

**报错提示（apps/doc_convert）**：

- `ZnszjUnavailableError` / `ZnszjInvalidResponseError` 新增 `step`（失败环节：认证·获取签名地址 / 认证·换取令牌 / 认证·换取设备码 / 上传传统文书 / 智能转写 / 保存并获取下载链接 / 下载文书）
- 页面错误框文案改为可行动提示：「要素式转换服务暂时不可用，请稍后重试」
- 历史记录 `error_message` 附带技术细节（环节 + 原因），回看失败记录可直接定位
