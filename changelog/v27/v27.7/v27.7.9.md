# v27.7.9

记一笔「识别并确认」弹窗永停「正在上传文书…」修复：粘贴/上传文书后弹窗卡在第 1 步不动，而后端识别任务其实早已完成。根因是通用轮询守卫 `usePollSession` 的「卸载即失效」在开发态 StrictMode 下不可逆，唯一一次上传的返回被当作过期会话静默吞掉。

## 前端

#### 修复

- **记一笔文书识别永停「正在上传文书…」**：v27.2.18（#527）把 `useRecognize` 的 `cancelled` ref 换成 `usePollSession`，旧实现的 effect setup 会把 `cancelled` 复位、cleanup 置位（可逆），新实现的 cleanup 直接 `session++`（不可逆）。开发态 StrictMode 对新挂载组件把 effect 跑成 setup→cleanup→setup；识别弹窗按需挂载（每次打开都是全新 mount），其提交 effect 用 `submittedFile` ref 防重，第二次 setup 不会再提交，于是唯一那次上传返回时 lease 已 stale，命中 `if (lease.isStale()) return` 后 phase 永停 `submitting`。现改为 `unmounted` 标志：setup 复位、cleanup 置位，`isStale = 会话号不符 || unmounted`——StrictMode 的假卸载可逆，真卸载仍让全部 lease 失效并唤醒挂着的 sleep。生产构建无双调用不受影响，但本机 5090 开发态自 10-04 起该路径一直不可用
- **`usePollSession` 返回对象引用稳定**：原来每次渲染都返回新对象，消费方 `useCallback(..., [pollSession])` 的 `submit` 跟着漂移，弹窗以 `submit` 为依赖的提交 effect 每次渲染都重跑（此前仅靠 ref 防重兜住）。现 `useMemo` 钉死，三个消费方（recognize / doc-parse / converter）同时受益

#### 测试

- 新增 `hooks/use-poll-session.dom.test.tsx`（7 例）：挂载 effect 签发的 lease 经 StrictMode 双调用后仍有效且 sleep 按时醒来、真卸载后失效并立即放行 sleep、`begin()`/`invalidate()` 语义、已失效 lease 的 sleep 不占计时器、返回引用稳定
- 新增 `RecognizeDialog.strict-mode.dom.test.tsx`（2 例）：真实 `useRecognize` + 真实 `usePollSession`、只 mock api 层，顶层 `<StrictMode>` 下渲染弹窗——成功路径推进到识别终态且上传恰好一次（防重不能退化成重复上传）、上传失败落 error 态而非永停。既有 `RecognizeDialog.dom.test` 把 `useRecognize` 整个 mock 掉、`use-recognize.dom.test` 不带 StrictMode 且从测试体直调 submit，两者都碰不到这条路径
- **测试坑**：RTL `renderHook` 用函数组件 wrapper 包一层 `<StrictMode>` **不会**触发 effect 双调用（React 只对带 PlacementDEV 的最顶层新挂载 fiber 双调用、且要求它已处于 StrictMode 内，wrapper 本身是顶层新挂载却不在 StrictMode 内，整棵子树被跳过），必须用 `reactStrictMode: true` 选项或把 `<StrictMode>` 放最顶层，否则回归测试假绿
