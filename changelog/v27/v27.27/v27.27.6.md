# v27.27.6 · 「这一页没取到字」不再被说成「空白页」：页级取字失败全链路可见

> 同一条主题线（材料预处理阅读器 + 页质量提示）的第六次迭代，只加第三位。

## 一句话

| 之前 | 现在 |
|:--|:-|
| 某一页 OCR **彻底失败**（`ocr_failed=True` + 空正文）时，`page_quality` 把它归进 `blank`（理由「空白页」）且 `needs_visual_review=False` → 不进 `details`、不贴段级 `quality_flags`、而 `blank_pages` 前端本就刻意不渲染。**律师侧唯一表现是「正文里少了一页」，收尾还是绿色成功提示** | 取字失败的页单独成桶 `ocr_failed_pages`，判据理由写明「不是空白页」；段级 `quality_flags` 带页号、左栏段行出现琥珀三角、收尾提示降级为 **warning** 并点名「N 页未取到任何文字」 |

原因是一份真实事故：一份 37 页扫描卷宗里，**某一页**整页正文丢了——那一页承载的是整案的
核心事实（诉讼标的金额、生效刑事判决的编号都在上面）。它的词条是 `ocr_failed`，
界面上却显示「空白页」，任务状态成功，日志里一条都没有。
「我们没读出来」被静默归成了「原件本来就没字」——这两件事的处置完全相反。

同批次还顺手清掉了 MinerU 凭证池里两个已过期的 Key（`A0211 user token expired`）：
它们让一批 26 页的云解析整批 `401` 失败，退化成逐页本地 OCR，一条 37 页材料跑了 20.7 分钟。

## 后端

#### `page_quality.py`：新 kind `ocr_failed`

- `PageKind` 增 `"ocr_failed"`；`assess_page_quality()` 增 `ocr_failed: bool = False` 入参
- 分支**优先于 `blank`**：`ocr_failed` 是取字链路自己报的可复核事实，不是启发式，
  不能落到「原文就是空白」那一支
- 两条文案分开：无正文 → 「取字失败：这一页没有识别到任何文字（**不是空白页**），请核对原图并手工补录」；
  有部分正文 → 「取字部分失败：这一页的识别过程报错，正文可能不完整，请核对原图」
- 两类都 `needs_visual_review=True`（这就是段级 `quality_flags` 的开关）
- `rescue_image_region()` 显式跳过 `ocr_failed`：这页缺的是整页正文，不是某个 image 块；
  图片块补救只重识别一个矩形区域，对这种页既救不回内容又要多付一次云端调用

#### `page_quality_summary.py`：新桶 `ocr_failed_pages`

- `_KIND_BUCKETS` 加一档（该元组是显式清单，故意不加就会 KeyError 而不是静默丢页）
- `build_page_quality_summary` / `qualities_by_page` 两处都透传 `page.ocr_failed`
- 输出新增 `page_quality.ocr_failed_pages`；**不并进 `blank_pages`**——并桶等于把律师最需要
  知道的事静默成最不需要管的事
- 已确认 `page_quality` 是两阶段链路里**唯一**会真正落库到 `summary_payload` 的取字侧区块
  （`service.py` 的分段阶段只重读它，`ocr_miss_count` 那些顶层键只进磁盘 `extract_summary.json`），
  所以告警必须挂在这个区块里才到得了前端

#### `pipeline.py`：`pdf_split_pages_without_text`

- `extract_pages()` 里检测到 `ocr_failed_pages` 非空时打一条 **WARNING**，带
  `page_numbers` / `failed_count` / `total_pages` / `ocr_provider` / `ocr_fallback_reason`
- 为什么必须留日志：这类页既不进 Markdown、也不让任务失败，日志里没有就完全无迹可寻

## 前端

- `quality-types.ts`：`PageQuality` 增 `ocr_failed_pages?: number[]`（旧任务没有该键，按可选读）
- `draft/page-quality.ts`：`readPageQuality` 收窄新键，并把它计入「有质量数据」判定
  （它可能**单独**出现在一份其余完全干净的任务里）；新增 `ocrFailedPagesOf(seg, quality)`，
  与 `graphicPagesOf` 同口径按 `seg.refs` 位置求交（跨源重复页号保留两次）
- `RailSegRow.tsx`：`SegmentMarks` 新增 `data-ocr-failed-mark`（琥珀三角，**优先于**证件/图纸徽标），
  tooltip 会列出具体页号。这一类的正文里根本没有那几页，所以只能挂在段行上，挂不进正文
- `auto-split-apply.ts`：`summarizeAutoSplitResults` 增一层判断——`warned` 原来只由
  「整份任务失败数」决定，页级失败时仍弹绿色成功；现在 `ocr_failed_pages` 非空也置 `warned=true`，
  并在文案尾部追加「N 页未取到任何文字，正文里没有这几页，请核对原图补录」

## 说明与遗留

- **`ocr_miss_count` 语义没有动**：它是「这一轮需要走 OCR 的页数」（cache miss），不是失败数。
  改名会撞既有契约与测试，另开一件
- **`PdfSplitReviewFlag.OCR_FAILED` 仍然是死代码**：`models.py` 有枚举、`segment_merge.py` 参与严重度排序、
  前端 `review-hint.ts` 也有文案「这一段的文字没有取出来，正文可能是空的」，但**后端从来没人给它赋值**。
  本次没有走这条通道（`review_flag` 每段只有一个值，硬塞会顶掉「建议复核」）；
  要接的话得先定「复核 flag 的优先级」，属于另一件事
- MinerU 凭证清理是**数据修正**，不在代码里：失效 Key 由 `POST /api/v4/file-urls/batch` 探活确认
  （两个都返回 `A0211 user token expired`），当前池里只剩 1 个可用 Key
- 遗留观察（未修）：`MineruBackend._request_upload_url` 的 3 次重试**复用同一个 `self._active_key`**，
  所以 Key 一旦失效，重试再多次也不会换 Key —— 本次 20 分钟事故的直接放大器。修复点在
  「鉴权类失败要回到凭证池换下一个 Key」，需要连同 `_release_key` 的成功/失败记账一起改
