# v27.27.5 · 「后端清单暂不可用」不是选项，是空清单误报 —— 修掉那句谎话和永不重试

> **版本判定**：§1.2 同一条线（`v27.27.x` 的 AI 选择器）→ 第三位 +1。
> 判号按 PIT-026 规则 1：`origin/main` 最新 = `v27.27.1`，本分支第 4 条 → `v27.27.5`。

## 用户看到的是什么

菜单里只有两行：`后端清单暂不可用，本轮使用默认 AI。` / `已选 0/5`，一个后端都没有。

**它不是"不可用的选项"，是清单为空时的兜底文案。** 空的原因有三个，旧代码把它们说成同一句：

| 真实原因 | 旧表现 | 现在 |
|:--|:--|:--|
| 请求还在飞（端点冷启动 5–15 秒） | 「暂不可用」——看着像功能坏了 | `正在拉取 AI 清单…`，拉到就自动填上 |
| 请求失败（网络 / token 刷新中 / 后端正好在 reload） | 「暂不可用」且**永不重试**，只能刷页面 | `AI 清单没拉到` + 「重试」按钮；打开菜单也会自动重拉一次 |
| 服务端确实一个后端都没有 | 「暂不可用」 | `后端清单为空，本轮使用默认 AI。` |

## 为什么慢（实测，不是猜）

`GET /api/v1/agent/backends` 经 vite 代理实测 **15.05 秒**。逐段计时定位到
`qoder_models.for_display()` —— 它要起 `qodercli --list-models` 子进程：

| 位置 | 实测 |
|:--|:--|
| `_qoder_probe` / `_dsh_probe` / `_opencode` / `_codex` / `_cline` | 各 0–11 ms |
| `_available_models()`（平台模型） | 7 ms |
| `qoder_models.for_display()` | **15.06 s**（该次子进程跑满 15s 超时，返回空） |
| 同一 CLI 单独再跑 | **5.13 s**，返回 20 个模型 |

也就是说：**冷路径 5–15 秒**，而菜单在首屏就会打开。前端首帧 `backends=[]`，于是显示那句误报。

后端真正的问题不在慢，在**只缓存成功**：`list_models()` 的缓存在失败时为空 →
每次 `/agent/backends` 都重新起子进程、每次都等满超时。

## 改了哪些文件

- `backend/apps/agent/backends/qoder_models.py`：加**失败缓存**（`FAILURE_TTL_SECONDS=60s`，
  窗口内直接返回上次结果、不再起子进程）；`invalidate()`（登录成功时调）同时清掉失败窗口，
  刚登录要能立刻重试
- `frontend/.../backend-types.ts` + `store/backends.ts`：新增 `backendsState: idle|loading|ready|error`；
  失败不再静默（旧实现 catch 里什么都不做）；在飞时不重复发
- `frontend/.../Composer.tsx` + `ComposerToolbar.tsx` + `AnswerAgentMenu.tsx`：三态文案 + 「重试」，
  并在 `idle`/`error` 时打开菜单自动重拉一次
- 测试：`tests/ci/unit/agent/test_qoder_models.py`（5 条，全离线）+ store 2 条 + 菜单 5 条

## 已知取舍

- **没做磁盘缓存**：进程重启/多 worker 时仍会各付一次 5 秒冷启动。要不要落盘（`~/.fachuan-agent`
  下一个小 JSON）等真觉得碍事再说——现在前端已把它显示成"正在拉取"，不再谎报坏了。
- **没降超时**：`--list-models` 冷启动实测 5.13 s，把 15 s 砍到 5 s 会把正常的一次判成失败。
