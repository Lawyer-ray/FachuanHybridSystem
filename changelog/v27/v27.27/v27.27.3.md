# v27.27.3 · 刷新后勾的 AI 与模型又丢了 —— 这次是真根因（写键 ≠ 读键）

> **版本判定**：§1.2 同一条线（`v27.27.0` / `v27.27.1` 都是「按会话记住本轮选择」这条）→ 第三位 +1。
> 判号按 PIT-026 规则 1：`origin/main` 最新 = `v27.27.1`，本分支第 2 条 → `v27.27.3`。

## 一句话

| 之前（v27.27.1 之后仍然坏） | 现在 |
|:--|:--|
| 律师在**新对话**里勾 AI、选模型 → 发第一条消息 → 「已选 0 个」，刷新也回不来 | 建会话那一刻把这次选择搬到新会话名下，刷新照旧在 |
| 前两次修的是「按会话存 + 两件事一起装回」，方向对，但**写键与读键不是同一个** → 存了也读不到 | 补上缺的那一步：`copilot:agents:new` / `copilot:models:new` → `copilot:agents:<新 id>` |
| 顺手发现：登出/401 的 `reset()` 不清 `new` 键 → **上一个账号勾的 AI 出现在下一个账号输入区** | `reset()` 一并清掉 |

## 根因（三条只读取证 lane 交叉确认）

写盘用的是 `get().sessionId`，读盘用的是「当前会话 id」——两者在**建会话前后**不是同一个值：

1. 新对话里勾选：`sessionId === null` → 落 `copilot:agents:new`（`store/answers.ts:57,64,77,104`）
2. 发第一条消息：`ensureSession` 建会话 → `set({ sessionId })` + `storeSession(id)`（`store/turn-send.ts:97-99`）
3. `sessionId` 一变，`use-active-session.ts:112-114` 的 effect 立刻 `hydrateAnswerSelection(<新 id>)`
4. 该键不存在 → 读回 `[]` / `{}` → **当场把刚勾的选择清成 0**；刷新读的还是 `<新 id>` → 永远 0

全仓没有任何 `new → <id>` 的迁移（写键只有 4 处，全是当前 sessionId；copilot 域没有 `persist`/`subscribe` 中间件）。

**被证伪的两条候选**（都查过了，不是它们）：`switchSession` 的两处 `set` 都不含 `answerAgents`，不存在「异步覆盖」；刷新首帧也不是 `null`——`sessionId: readStoredSession()` 是同步读的（`store/index.ts:40`）。

## 前两次为什么没拦住

`answers.test.ts` 原有 8 条用例**写盘与 hydrate 用的都是同一个 sessionId**，所以「写键 ≠ 读键」这件事结构上测不到。这次补的 5 条里，端到端那条走真实 `ensureSession`，**把迁移那行删掉就当场变红**（已实测：1 failed / 12 passed）。

## 改了哪些文件

- `persistence.ts`：新增 `seedAnswerSelectionFromNew(sessionId)`（只补空位、只搬不删）与 `clearNewAnswerSelection()`
- `store/turn-send.ts`：`ensureSession` 在 `set({ sessionId })` **之前**搬家
- `store/index.ts`：`reset()` 里清 `new` 键（修跨账号串味）
- `store/answers.test.ts`：+5 条（跨挂载回归、只补空位、new 键保留、reset 清键、端到端 ensureSession）

## 已知取舍

- **`new` 键留着不删**：它的语义是「下一条新对话的初值」，连续开新对话不必每次重勾。代价是它可能比最近一次会话里的选择旧一点——这是刻意的，比「每开一个新对话都空白」好。
- **只补空位**：目标会话已有自己的选择就绝不覆盖，避免把 A 会话的偏好带进一个调过的会话。
- **没处理**「发送请求在途的那 200ms 里又去改勾选」这种race：那时写盘仍落 `new`，进会话后会被读回迁移时的那一刻。期间输入区处于 sending 态，实际按不到，不值得为它加第三条写路径。
