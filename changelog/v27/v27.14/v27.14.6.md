### 修复

#### 执行担保 500（第一次）：`parse_case_number` 调用断链

**现象**：`POST /api/v1/court-guarantee/execute` 必 500

```
AttributeError: type object 'CourtZxfwGuaranteeService' has no attribute 'parse_case_number'
```

**根因**：v27.4.4（`2cc9b3cf`）把 Service 层静态方法下沉为模块级纯函数
（棘轮 264→12），`CourtZxfwGuaranteeService.parse_case_number` 被移到
`apps.automation...guarantee.data_mixin.parse_case_number`。重构方同步改了
`data_mixin` 的单测，但**漏改插件侧调用方** `plugins/court_automation/guarantee/api_endpoint.py`。

**修复**：`guarantee/helpers.py` 新增 `_parse_case_number`，API 层直接调用。
有意**不**跨模块 import `apps.*` 爬虫实现——`four-layer.md` 明令禁止跨模块导入，
且会平白让插件 API 层依赖 apps 的 scraper。解析口径与原实现一致。

主仓库侧补 6 例回归测试，其中一例与 apps 侧实现做同口径比对，防两侧漂移。

> plugins 子模块改动：FachuanPlugins `c4b29a6`（两段式 PR，先 plugins 后主仓库）。

#### 执行担保 500（第二次）：`_random_wait` 被当实例方法调用

**现象**：修好上一处后继续 500

```
AttributeError: 'CourtZxfwGuaranteeService' object has no attribute '_random_wait'
```

**根因**：同一个 commit（v27.4.4）把 `_random_wait` 从 `GuaranteeBaseMixin` 静态方法
下沉为 `base_mixin.py` 模块级函数。`guarantee_service.py` 改了，但 **7 个 mixin 内的
61 处调用点仍是 `self._random_wait(...)`**，运行到即炸。

用户只看到第一处报错（程序死在第一个调用点），实际全包 AST 扫描发现 61 处。

**修复**：
- 61 处 `self._random_wait(` → `_random_wait(`，7 个文件补 `from .base_mixin import _random_wait`
  （base_mixin 不反向依赖，无循环导入）。
- 只删 `_random_wait` 行上已失效的 `# type: ignore[attr-defined]`；**其余跨 mixin 调用
  （`_close_popovers` / `_wait_court_options_ready` 等）的 ignore 全部保留**——它们
  是合法的 MRO 动态解析，删掉会让 mypy 从 0 error 冒到 68 error。
- 新增结构守卫 `test_no_sunk_function_called_as_instance_method`：AST 检出
  「`self.X` 调用、包内无类定义该方法、但有同名模块级函数」。
  已用变异测试验证可捕获本 bug；对两类合法写法做了排除：
  单独注解的 `Callable` 属性（`weike/document.py`）、
  显式 `X = staticmethod(X)` 重绑定（`contracts/admin` `action_mixin.py`）。

### 新功能

#### 消息轮询周期按来源各自生效

**问题**：`MessageSource.poll_interval_minutes` 只在 admin/API 出现，调度逻辑
**一次都没读过**——改这个字段完全不影响实际行为。真实周期由 django-q 里
`message_hub:sync_all_sources` 的硬编码 30 分钟决定，所有来源无差别全量扫：
邮箱设 60 分、一张网设 720 分都形同虚设（后者实际被过度同步 24 倍）。

**改动**：
- `sync_all_sources` 改为按来源自己的 `poll_interval_minutes` 判断是否到点，
  只派发到点的来源；新增 `_is_source_due` 纯函数承载判定。
  - `<= 0` 视为不自动轮询（手动上传 / 客户链接类来源沿用该约定）
  - 从未同步过（`last_sync_at` 为空）立即同步，避免新来源要等满一个周期
- 调度心跳 30 分钟 → 1 分钟：调度器只负责「每分钟看一眼谁到点」，
  拉取频率交给各来源字段，周期误差不再受心跳粒度放大。
- 锁 TTL 25 分钟 → 60 秒，随心跳一起收窄，否则 1 分钟心跳会被旧锁整条废掉。
- `_register_schedule` 修正「只在记录不存在时创建」的缺陷：比对 `func` 与
  `minutes`，任一不符即就地校正。此前把间隔调小后存量记录不跟随更新，
  **改代码不生效**。

> 部署提醒：心跳由 `AppConfig.ready()` 注册，**必须重启 qcluster 才生效**。

#### 邮件 → 在办项目 自动关联候选（一期：只读）

新增 `apps/message_hub/services/contract_match.py`：多信号加权打分 + 阈值，
**不写任何财务数据**。接口 `GET /api/v1/inbox/messages/{id}/contract-match`。

**为什么是打分而不是「匹配/不匹配」**：108 个在办合同里 `fixed_amount` 大量为空
或重复（30000 出现多次），只靠金额必然错。写错财务数据比不写更糟，所以一期只出
候选 + 理由，律师确认后自己去关联。

**核心设计：比「应收余额」而不是「合同总额」**

合同总额 30000 已收 28000，这时来 2000 才是对的；只比总额会把所有 30000 的合同
都命中。三种风险收费分别算：

| 收费模式 | 应收余额 |
|---|---|
| `FIXED` | `fixed_amount` − 已收款 |
| `SEMI_RISK` | `fixed_amount` + 标的额×`risk_rate`% − 已收款（前期与尾款分段可比）|
| `FULL_RISK` | 标的额×`risk_rate`% − 已收款（缺标的额则明确落人工，不瞎猜）|
| `CUSTOM` | 不自动判，标记需人工 |

标的额取 `Case.target_amount`（合同上没有该字段），多案件取最大值。
脏数据 `fee_mode='risk'` 按风险类处理并给明确说明，不会崩。

**阈值**：只有案号精确命中能达到「确定匹配」（0.99）；金额即使精确命中也只是候选
——同名同额合同太多，金额单独不足以定案。

**真实回归**：银行到账通知「张某…汇入人民币 2400 元」→ 金额与任何合同应收余额
都对不上，但付款人姓名命中在办合同，当事人信号把它顶出来。该场景已写成单测锁住。

**一期不做**：自动写入收款/发票（等匹配准确率有真实数据后再定）；发票分流
（`Invoice` 模型已支持先开票后付款，二期只加一个分支）。

### 优化

## 前端

### 新功能

#### 收件箱来源筛选条增加按档位同步按钮

同步按钮贴在**来源筛选条最右端**，作用于当前选中的档位。不放顶栏是因为顶栏与
筛选状态脱节——用户选着「邮箱」却不知道点顶栏的同步是同步全部还是邮箱，
这个歧义会直接变成投诉。

- 档位→目标映射写在 `constants.ts:INBOX_SYNC_SPEC`（唯一真值）：
  全部→`sync-all`；一张网→`court_inbox`；邮箱→`imap`；
  法院短信→置灰（**没有 MessageSource，不存在「拉取」动作**）；
  材料包→置灰（无「拉新」语义）。
- 按钮文案随档位变（「同步一张网」/「同步邮箱」），固定 `min-width` 防抖动。
- 开庭排期（`court_schedule`）不出现在任何具体档位的同步目标里，继续由后台定时跑；
  只有「全部」会连带带上。
- 状态机 `use-sync-sources`：idle → syncing → 刷新列表 → idle。
  完成后 toast「新增 N 条」；轮询 60s 未完成则转 `background` 态并提示
  「仍在后台进行，稍后刷新查看」，避免无限转圈被当成卡死。

> 完成判据用 `last_sync_at` 变化而非 `last_sync_status`：后端 `SyncStatus` 只有
> `pending/success/failed`，**没有 running**，任务提交前后都是 `success`，
> 无法区分「未开始」与「已完成」。

#### 可能关联的在办项目面板

`ContractMatchPanel` 在消息抽屉里展示候选项目与**匹配理由**——律师需要判断
「为什么系统觉得是这个项目」。只给名字，他要么无脑信、要么完全不看；
给出「当事人命中 张某」他才能一眼判断对错。

只在 `imap` 来源显示（一张网/短信是法院送达，与我方项目无对应关系；
材料包本身是项目产物，反向匹配没有意义）。无候选时回显系统识别到的案号/金额，
让律师知道系统到底抽到了什么。

### 修复

#### 阶段切换不流畅

主区域原本是裸的条件渲染，无 key、无过渡，切换时整块 DOM 销毁重建 → 硬切。
另外切档位会把 `source` 放进 `queryKey`，新 key 首请求期间 `data` 为空，
列表整块闪成 loading，加重了「卡一下」的观感。

- `useInboxList` 加 `placeholderData: keepPreviousData`：切档期间保留上一档
  数据直到新数据到达，不再闪 loading。
- `DeskPage` 主区域包一层 `key={stage}` + `app-stage-enter`：换阶段时这层
  重挂，过渡才会播。只给主区域不给整页——页签应保持常驻，不该跟着淡。
- 新增 `app-stage-enter`：纯淡入不位移，0.16s（比换页的 0.22s 更短）。
  阶段切换是同一页内换内容，加位移会像换页反而更跳。
  `prefers-reduced-motion` 下不播。

#### 法院短信档位内容为空

**不是 bug，是两张表没打通**：
- 短信数据在 `automation_courtsms`（由短信转发 / admin 录入产生）；
- 收件箱列表读 `message_hub_inboxmessage`，其中 `source_type='court_sms'` 为 0 条；
- 两者之间只有一个**单向** admin 按钮（`InboxMessage` → `CourtSMS`），反向不存在。

按「先给指引、打通另立项」处理：新增 `INBOX_EMPTY_GUIDE`，法院短信档位空态显示
「暂未接入收件箱」+ 跳转到 admin 法院短信管理的入口，而不是笼统的「这一分类下暂无消息」。
admin 根地址由 `getApiBaseUrl()` 推导（同源），不引入新的 env 变量。

> 空态判据用 `narrowed`（搜索/未读）而非 `isFiltering`（含档位）：选档位本身就是
> 选通路，不该被当成「筛选后为空」，否则通路说明会被降级成「暂无消息」。

#### 邮件正文显示不出来

**现象**：`【到账通知】请申请开票` 打开只有「这条消息没有附件」，正文空白。

**根因**（消息 id=533 实证）：`body_text` 长度 0、`body_html` 长度 2007。
该邮件本身只有 HTML 部分、没有 `text/plain`，后端提取是对的。但渲染逻辑是：

```tsx
hasText ? <pre>{body_text}</pre> : (!body_html && "没有正文内容")
```

有 HTML、无纯文本时**两不沾**，什么都不渲染。

**修复**：新增 `MailHtmlBody`，有 HTML 就渲染它。
**用 sandboxed iframe 而非 `dangerouslySetInnerHTML`**：邮件 HTML 是完全不可信的
外部输入，项目里没有 DOMPurify，手写净化器一定会漏。iframe 不给
`allow-scripts` / `allow-same-origin`，用浏览器机制做隔离而不是靠代码「记得净化」。
同时剥掉邮件自带 `html`/`head`（Outlook 导出的 vml/条件注释会把布局搅乱）。
