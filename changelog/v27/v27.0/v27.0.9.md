## 后端

### 背景：为什么这批 bug 能长期存活

这些坏 import 全部是**函数体内懒导入**，且调用方带 `# pragma: no cover`，因此三道防线全部失效：

1. **ruff 拦不住**：`F821` 只检查「未定义的名称」，不解析「模块是否存在」；导入的符号被使用时 `F401` 也不适用（已实测：`from apps.core.nonexistent import Foo` 过 ruff 全绿）
2. **mypy 拦不住**：CI 使用 `--follow-imports=silent`，抑制 import 解析失败
3. **测试反而掩护**：个别测试用 `sys.modules[<坏路径>] = Mock` 注入假模块让坏 import「成功」；另有测试只构造响应 Schema、从不真正调用 endpoint（伪覆盖）

### 修复（8 处 import 不存在的模块/符号）

- **contracts**：`api/archive_api.py` 的合同归档上传 endpoint 引用 `apps.core.services.file_upload_service`（整个模块不存在），而该 endpoint 已上线服务——用户每次上传归档文件都会 `ImportError`。改用 `storage_service.validate_file`（该函数正是从已废弃的 `FileUploadService.validate_file()` 合并而来）
- **workflow**：`temporal/activities.py` 的 `analyze_single_evidence` 引用 `apps.documents.services.text_extractor`（不存在，且全仓无 async 版 `extract_text`）。改用同步的 `apps.core.services.pdf_utils.extract_text` + `asyncio.to_thread()`，与同文件 `download_litigation_document` 的写法一致（原代码 `await` 一个同步函数，即使 import 正确也是错的）
- **cases**：`admin/caselog_admin.py` 引用 `apps.core.service_locator`（模块不存在），管理员打开有案件日志的列表页必然 500。改用 `apps.core.interfaces`
- **evidence**：`admin/evidence/mixins/views.py` 复制粘贴 bug——同文件 `formfield_for_foreignkey` 用正确的 `apps.documents.models`，`get_form` 却误写 `apps.evidence.models`（后者无 `DocumentTemplate`）
- **core**：删除 `service_locator_mixins/core_mixin.py` 的 `get_prompt_template_service`——零调用方，且依赖的 `build_prompt_template_service` 全仓无定义，原先靠 `# type: ignore[attr-defined]` 主动掩盖；core 亦不应反向依赖 `apps.litigation_ai` 的 PromptTemplateService
- **litigation_ai**：删除管理命令 `init_litigation_ai_flow_prompts.py`——依赖已删除的 `PromptVersion` 模型、零调用方、无外部引用，与 #484 清理零引用命令的做法一致
- **workflow**：删除 `temporal/activities.py` 的 `execute_court_filing` activity——其调用的 `CourtFilingService` 全仓不存在（非改名，整个类缺失）。经确认该 activity 是冗余死路径：`workflows.py` 注释明确「有 mcp_tool 的步骤走 `execute_mcp_tool`」，`step_registry` 给该步标记的正是 `mcp_tool`，真实流程为 MCP → HTTP → 插件 `/court-filing/execute`，由插件内部按 `request.user` 查该律师的一张网凭证并启动后台立案线程；全仓无任何 workflow 真的通过 `INTERNAL_ACTIVITY_MAP` 调用它。同时移除 `INTERNAL_ACTIVITY_MAP` 中的注册（保留 `MCP_TOOL_MAP` 注册，走实际可用路径）

### 修复（MCP 立案 URL 404）

- mcp_server：`tools/automation/court_filing.py` 三个函数请求 `/automation/court-filing/...`，但插件实际挂载于 `api_v1.add_router("/court-filing", ...)`，即正确路径为 `/api/v1/court-filing/...`（`mcp_server` 的 `BASE_URL` 已含 `/api/v1`）。原 URL 必然 404，改为 `/court-filing/...`

### 修复（日志 filter 进程级污染）

- workflow：`management/commands/start_temporal_worker.py` 的 `_setup_logging()` 为绕开 Temporal sandbox 受限导入，直接改写**类方法** `RequestContextFilter.filter = lambda self, record: True`——这是进程级且永不恢复的 monkeypatch。一旦在同进程执行过，该 filter 即退化为 no-op，不再向 LogRecord 注入 `request_id` / `trace_id` / `span_id`，导致同进程内后续对它的断言全部失败（`tests/ci/unit/core` 的 `TestRequestContextFilter` 在大批次混跑时必现，main 上同样复现）；生产环境下同进程若还有别处依赖该 filter，日志 trace 字段同样会丢
- 改为 `_temporal_sandbox_logging()` 上下文管理器：只从 root logger **实例**上摘除 `RequestContextFilter` 实例，退出时恢复原 filters，**绝不改动类本身**；以 `_get_request_context_filter_types()` 安全获取类型，模块未加载时返回空元组
- 新增回归测试 `test_does_not_mutate_filter_class`，断言 `RequestContextFilter.filter is original`，防止未来退化成类级 patch

### 修复（测试掩盖 bug 的问题）

- 测试不再是坏 import 的掩护：`test_activities_round4.py` 原先用 `sys.modules[...] = Mock` 为不存在的模块注入假模块，使坏 import「成功」；现改为 patch 真实模块路径，并断言 `asyncio.to_thread` 的实际调用参数
- 同步更新 4 个 workflow 测试文件中断言「已删除的 activity 注册在 `INTERNAL_ACTIVITY_MAP`」的用例，并清理因此不再使用的 import

### 新增（结构守卫，永久拦住本批问题）

- 测试：新增 `tests/ci/structure/test_absolute_imports_resolve.py`——用 `importlib.util.find_spec` 扫描全仓 `apps/` + `plugins/` 的**绝对导入**，断言目标模块真实存在。本批 8 处坏 import 之所以能长期存活，正是因为三道防线全部失效（ruff 的 `F821` 只检查未定义的*名字*、不解析*模块*是否存在，实测 `from apps.core.nonexistent import Foo` 过 ruff 全绿；mypy 被 CI 的 `--follow-imports=silent` 抑制；测试反而用 `sys.modules` 注入假模块掩护）。本守卫直接问解释器「这模块到底存不存在」，从机制上堵住这类运行时炸弹
- 范围取舍（均按真实代码树校准）：只查绝对导入（相对导入 `from .models import X` 的 `module` 只是 `"models"`，不可解析，不排除会产生上千个假阳性）；排除 `if TYPE_CHECKING:` 块（仓内有 7 处历史遗留路径只出现在类型注解中，如 `apps.users.models`）；只断言模块存在、不断言符号（符号受 `X as Y` 别名与 `__all__` re-export 影响）；不扫 `migrations/`（历史迁移按设计引用当时的模型快照）
- 含自检用例 `test_guard_actually_detects_broken_import`，内置含坏 import 的样例并断言守卫只抓到应抓的那一个——防止未来检测逻辑被改坏导致守卫退化成永远通过的摆设
