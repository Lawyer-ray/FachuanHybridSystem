# v27.0.10

修复一张网（zxfw.court.gov.cn）message_hub 同步在获取 Token 时的「Token 获取超时（120 秒）」问题：即便已安装 `captcha_ocr`（ddddocr）插件，后台任务仍会静默降级到需要人工输入验证码的识别器，而后台任务无人工应答，必然等到超时。本次改动横跨 plugins 子模块与主仓库，仅后端，无前端改动。

## 前端

本次无前端改动。

## 后端

### 修复（后台任务不再静默降级手动验证码登录）

- 影响面：`apps/message_hub` 的一张网同步由 django-q 定时任务（每 30 分钟）驱动，是无人值守的后台任务。当其缓存/DB 均无有效 Token、需要重新登录时若遇到验证码：修复前会落到 `FileBasedCaptchaRecognizer`，把验证码图片存盘并轮询最长 300 秒等待人工写入 `.answer` 文件；后台没有前端界面也没有人工应答，因此每次必定等满超时，最终只暴露一句难懂的 `TimeoutError: Token 获取超时（120 秒）`。这不是偶发，而是结构上注定失败。

### 根因（两层叠加）

- **运维时序**：`captcha_ocr` 是构建后部署的插件目录，若 qcluster worker 的启动时间早于插件落地时间，Python 的 importlib 会缓存 `plugins/` 父目录列表，导致已运行的长生命周期 worker 一直判定「无插件」。叠加本仓库已知的多棵 qcluster 树并存（孤儿 worker）问题，表现为「插件已装却不生效」。
- **代码缺陷（真正要根治的）**：
  - `get_captcha_recognizer()` 只看插件是否可 import，**从不读取 `CAPTCHA_AUTO_RECOGNIZE`**（其日志却谎称由该配置决定）;
  - 插件被检测到但加载失败（ddddocr 缺失、onnx 模型损坏等）时，异常被 `logger.debug` 吞掉，真实原因不暴露;
  - 后台上下文没有 human，却被允许进入最长 300 秒的文件轮询。

### 具体改动（plugins 子模块 commit `7aa5563`）

- `court_automation/login/captcha_recognizer.py`：`get_captcha_recognizer()` 新增 `allow_manual` 关键字参数。后台上下文传 `allow_manual=False` 时，插件不可用立即抛出**可操作的** `RuntimeError`（提示安装/修复 `captcha_ocr` 插件并重启 qcluster），绝不再静默进入手动轮询；默认 `allow_manual=True` 保持既有交互式行为不变（无插件无 task 仍走 `FileBasedCaptchaRecognizer`）。
- `court_automation/login/captcha_recognizer.py`：插件被 `has_captcha_ocr_plugin()` 检测到但 `DdddocrRecognizer` 导入/初始化失败时，日志从 `logger.debug` 提升为 `logger.warning` 并附带真实失败原因;每次构造识别器前调用 `importlib.invalidate_caches()`，强制重扫文件系统，使已运行的 worker 在插件后装后也能自愈（下一轮同步即可识别到）。
- `message_hub/services/court/court_fetcher.py`：`_acquire_token()` / `_aacquire_token()` 显式以 `get_captcha_recognizer(allow_manual=False)` 构造「仅自动」识别器并注入 `CourtZxfwService`，**同时覆盖 HTTP 快登与 Playwright 兜底两条登录链路**（修复前仅 Playwright 链路可用）。
- `court_automation/login/court_zxfw_service.py`：修正误导性日志，原为「使用默认验证码识别器（由 CAPTCHA_AUTO_RECOGNIZE 配置决定）」，改为打印实际识别器类型并说明由「captcha_ocr 插件是否可用」决定。

### 具体改动（主仓库 commit `1226eeea`）

- 新增回归测试 `tests/ci/unit/automation/test_captcha_recognizer_background.py`（9 用例），锁定修复契约：后台上下文（`allow_manual=False`）下插件不可用必须立即失败、绝不静默返回 `FileBasedCaptchaRecognizer`；插件加载失败必须记录真实原因（warning）而非 debug 静默吞掉；默认 `allow_manual=True` 的交互式行为保持不变；每次构造前调用 `importlib.invalidate_caches()`。
- 同步更新 plugins 子模块指针至 `7aa5563`。

### 具体改动（主仓库 commit `40cc36bf`，开发体验）

- `Makefile`：`QCLUSTER_WATCH_PATHS` 由 `apps apiSystem` 追加 `plugins`。`qcluster-dev` 的 watchfiles 原先不监听 `plugins`，而一张网登录链路的修复代码均在 `plugins` 下，导致改完插件 qcluster 不自动重启、旧代码继续跑，必须以手动重启才能生效。`watchfiles` 的 `--ignore-paths` 已含 `.git`，故切分支/拉取子模块不会误触发热更，只有业务 `.py` 变动才会重启。

### 说明（部署）

- 修复生效需重启 qcluster。本次已提供两种途径：`importlib.invalidate_caches()` 让仍在运行的 worker 自愈插件后装；`Makefile` 追加 `plugins` 监听目录让后续插件改动能自动热更。但**当前改动之后**仍需重启一次 qcluster 让新代码首次加载。
- 建议排查同类「配置看着对却不生效」问题时，先比对 worker 启动时间与目标插件目录的 mtime——插件在长生命周期 worker 之后部署是高频诱因。
