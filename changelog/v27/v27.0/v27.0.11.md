# v27.0.11

本期三条线：**材料预处理的 PDF 内容识别与自动拆分**、**AI 平台的「Key ↔ 模型」配置与并发能力**、以及 **Agent 工具进程（MCP）的启动修复**。其中 Agent 路径此前因 MCP 子进程无法启动而在生产上完全跑不通，本期修复后已端到端实测贯通。

## 前端

#### 新增

- material-prep：接入 PDF 自动拆分。新增 `use-auto-split` 触发异步识别，`applyAutoSplit` 把云端建议写回草稿——只替换该源上「未被人工编辑、且页覆盖完整」的分段，存在人工拆分或跨源合并时直接放弃，避免覆盖人工成果；低置信度分段带复核标记
- material-prep：材料段类型候选集由 10 种扩至 23 种（新增证据清单及明细、财产保全资料、双方当事人主体信息、授权委托材料、送达地址确认书、诉讼费用退费账户确认书、借款合同、放款凭证、利息计算表、送货单、收货单、发票、未识别材料）
- material-prep：`api.ts` 新增 PDF 识别接口封装；`types.ts` 补充 `PdfSplitSegmentSuggestion` 等类型

#### 优化

- material-prep：`Reader` / `ReaderToolbar` / `SegmentHeader` 适配自动拆分结果的展示与手动复核入口

## 后端

#### 新增

- pdf_splitting：接入云端逐页文档识别（MinerU / Textin），保留逐页文本、区块与表格结构。内容拆分任务优先使用已配置的云端解析平台，云端解析失败时回退本地 OCR，并记录实际使用的引擎与降级原因
- pdf_splitting：材料预处理自动拆分。扩展银行与物流材料关键词规则（模板规则 7 → 14 条），依据云端版面标题生成开放集分段名称；新增迁移 `0006_alter_pdfsplitsegment_segment_type` 扩展段类型
- core：AI 平台的 `api_keys` 支持 `key|model1,model2` 声明该 Key 的模型白名单，不含 `|` 的 Key 视为不限模型；旧格式（逗号 / 分号分隔多 Key）语义不变，**无需数据库迁移**
- core：新增 `LLMProviderService.fetch_remote_models`——逐个 Key 请求网关 `/models`，聚合出模型并集与交集（交集即任意 Key 均可运行的模型）
- core：LLMProvider Admin 改为「一 Key 一行」行编辑器（新增 `change_form.html`）：每行独立「获取模型」、模型 chip 多选、显式「不限模型」开关、增删 / 复制行、粘贴多行 Key 自动拆分；保留 textarea 作为存储真源，并提供「原始文本模式」切换
- core：`_KeyPool` 提取为公共模块 `apps/core/llm/key_pool.py`，新增进程级内容寻址注册表 `shared_pool`
- workbench：新增 `MultiKeyOpenAIModel`，在 pydantic-ai 的 Model 层按请求从 Key 池取槽位，实现 Agent 路径的多 Key 轮询
- workbench：新增 `LoopScopedTransport` 与进程级共享 HTTP 客户端

#### 修复

- mcp_server：**修复 Agent 路径在生产上完全不可用**。`python -m mcp_server` 入口缺 Django 初始化（工具模块在导入期访问 Django 模型，抛 `AppRegistryNotReady`），且 Django 启动的 59 行日志默认写入 **stdout**，会插进 MCP stdio 的 JSON-RPC 通道导致握手失败。入口现自行补齐 `sys.path` 与 `DJANGO_SETTINGS_MODULE` 并调用 `django.setup()`，同时在 setup 期间把 stdout 改道到 stderr
- core：Agent 路径原先只取 `api_keys[0]` 单 Key，网关的「每 Key 并发上限」完全用不上——10 个并发请求全压在同一个 Key 上，超出上限的部分直接吃 429，只能靠重试拉长尾延迟
- core：`build_model` 原先每请求新建一个 `httpx2.AsyncClient` 并追加进只增不减的全局列表，长跑必然耗尽文件描述符
- core：服务路径与 Agent 路径各持一套 Key 池，两条路径并发时单 Key 峰值可达上限的两倍
- core：拉取远端模型列表会把向量、重排、OCR 等**非对话模型**一并写入「模型列表」，调用时直接返回 `400 Invalid model name`
- core：LLMProvider Admin 的「获取远端模型列表」按钮**从未生效**——脚本置于 admin 的 `extrahead`（位于 `<head>` 内），执行时 DOM 尚未解析即 return
- core：Key 池的失败冷却由「按 Key」改为「按 (Key, 模型)」记账，避免某模型的无权限 403 误伤同一 Key 对其他模型的正常请求
- pdf_splitting：修复 MinerU 结果下载重用连接导致的失败
- ci：补齐 LLMProviderAdmin 旧测试对 `probe_chat` 的 mock 签名（该漏改使 HEAD 上 3 个用例报 `TypeError: unexpected keyword argument 'probe_chat'`）

#### 优化

- core：移除从未生效的 tenacity 重试层。`AsyncHTTPX2TenacityTransport` 未传 `validate_response`，`retry_if_exception_type(httpx2.HTTPStatusError)` 在 transport 层永远拿不到该异常；而补上它会把异常提前抛出、被 openai SDK 归类成 `APIConnectionError` 从而丢掉状态码语义。改为显式委托 SDK（默认重试 2 次，覆盖 408 / 409 / 429 / 5xx 并尊重 `Retry-After`）
- core：模型探测辅助方法由 `@staticmethod` 改为 `@classmethod`，与文件内其余方法保持一致，并校准结构棘轮基线
- core：Key 池的「每 Key 并发上限」现由服务路径与 Agent 路径**共用同一实例**记账；Agent 全局并发容量改为「Key 数 × 每 Key 上限」，不再硬编码
- ci：修复陈旧断言、补齐下载 mock、消除 Redis 缓存导致的顺序相关不稳定用例；合并重复的 LLMProviderAdmin 测试文件（旧文件独有用例已移植，确认无覆盖丢失后删除）

- MCP 入口在清空 `PYTHONPATH` / `DJANGO_SETTINGS_MODULE` 的环境下仍可启动，stdout 仅剩探针输出一行；复刻生产 `StdioTransport` + `fastmcp.Client` 握手成功，注册 378 个工具
- `make -C backend ci-check` 13 步全绿

#### 说明（部署）

- 本期含 1 个数据库迁移：`pdf_splitting/migrations/0006_alter_pdfsplitsegment_segment_type.py`，部署时需执行
