# v27.2.3

后端性能专项二期：psycopg3 进程级连接池、收件箱搜索 trigram 索引、Django Admin N+1 清理（95 个列表页全量实测）。另合入 dependabot uvicorn 0.53.0 → 0.54.0（PR #506）。

## 后端

#### 新功能

- **psycopg3 连接池**（`OPTIONS["pool"]`，新增依赖 `psycopg[pool]`）：
  - 开关 `DB_POOL`：默认 dev（DEBUG）开启、生产关闭（生产的并发模型需按部署评估后开启），显式 `true/false` 永远优先；**pytest 下强制关闭**（测试库每次重建，池会持有失效连接）
  - 池参数 `DB_POOL_MIN`（默认 2）/ `DB_POOL_MAX`（默认 16），池满等待 `timeout=10s`
  - 与 `CONN_MAX_AGE` 互斥：启用池时强制 `CONN_MAX_AGE=0`（连接生命周期由池接管）
  - 实测：并发 8 线程×5 请求从「池满阻塞 25 秒（psycopg_pool 默认 get 超时 30s）」修到 **203ms 全部完成**；串行 8.4ms/req、连接数稳定不增长

#### 优化

- **收件箱搜索 trigram 索引**（迁移 `message_hub/0014`）：`subject` / `sender` / `body_text` 三列各建 `pg_trgm` GIN 索引（迁移内含 `TrigramExtension`，幂等），`icontains`（`LIKE '%kw%'`）从全表扫走向量索引——消息量持续增长后搜索延迟保持稳定；三列独立索引支持 OR 组合查询各取 bitmap
- **Django Admin N+1 清理**（95 个列表页全量实测，中位 30ms；两个「千毫秒级」页面实测为冷启动假象、预热后 18ms/8ms 无需处理）：
  - `labor_arbitration/arbitrationdocument`：**106 查询 → 6**（193ms → 91ms）——`image_count` 列改 `annotate(Count)`，替代每行一次的 `images.count()`
  - `cases/caselog`：**55 查询 → 6**（99ms → 30ms）——根因是既有的「changelist_view 批量预填缓存」跑在 `super()` 之后，而列表渲染发生在 `super()` 内部，**缓存从未被消费**（50 行逐行查询照旧 + 白跑一次批量导出）。改为 `get_queryset().prefetch_related("reminders")`（`due_at, id` 升序与 service 导出序一致），`CaseLog._exported_reminders` 增加 ORM prefetch 分支（命中零查询），删除无效的时序错误代码
  - `invoice_recognition/invoicerecognitiontask`：**13 查询 → 5**——`record_count` / `total_amount_display` 两列的行级 count 与 service 聚合，合并为一次 `annotate`（`Coalesce(Sum(filter=Q(is_duplicate=False)))` 与 service 逻辑一致）
  - `labor_arbitration/arbitrationdocumentsource`：**11 查询 → 5**——`document_count` 列改 `annotate`
- `core/court`（10q）、`automation/tokenacquisitionhistory`（14q）：确认为分散的 filter/autocomplete 固定查询、非行级放大，收益低不处理
