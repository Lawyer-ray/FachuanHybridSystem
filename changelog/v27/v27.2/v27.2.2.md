# v27.2.2

前后端性能专项优化：首页首屏请求耗时实测 -81%，首屏 vendor 体积 -42%，分包与缓存粒度全面修正，API 响应压缩（全量收件箱 174.6KB → 14.2KB）。

## 前端

#### 优化

- **收件箱列表服务端截取**：`listInbox` 改传 `?limit=`（默认 6），不再全量拉取收件箱后在前端 slice——此前后端每请求序列化全部 345 条（约 200KB JSON），前端只用前 6 条，收件箱持续增长时线性恶化
- **manualChunks 宽匹配修复**：原 `id.includes(pkg)` 匹配把 `lucide-react`、`@radix-ui/*`、`@tanstack/react-query`、`zustand`（路径均含 "react"）全部吸进 vendor-react（424.9KB），vendor-query/vendor-state 实际产出空 chunk。改为 `node_modules` 包边界精确匹配后：
  - vendor-react 424.9KB → **245.2KB（-42%）**，仅含 react/react-dom/react-router/scheduler
  - lucide 图标（22.1KB）、radix 全家（95.1KB）、react-query（35.3KB）各自独立成 chunk，缓存失效不再互相放大（业务发版只失效业务 chunk）
  - 首屏关键路径 JS 总量 700.2KB → 670.6KB
- **识别弹窗懒加载**：`RecognizeDialog`（26.8KB）改为 feature 出口 lazy 组件 + 仅 `dialogOpen` 时挂载，并在选文件/文字解析期间预载 chunk；domain 纯函数保留静态导出
- **账号绑定设置页懒加载**：`BindingsPage`（5.3KB）改 lazy 出口，仅 `/settings/bindings` 路由按需加载；登录/首页首屏不再常驻该页代码
- feature 出口新增 `RecognizeDialogLazy` / `preloadRecognizeDialog` / `BindingsPageLazy`，消费方不再穿透内部目录

#### 自测

- `pnpm build` 无 INEFFECTIVE_DYNAMIC_IMPORT 警告，新增 RecognizeDialog / BindingsPage 独立 chunk
- eslint 通过、vitest 92 用例全过
- 浏览器实测（真实登录）：首页日历/收件箱（6 条）/快捷工具渲染正常，「快速记一笔」懒加载弹窗完整弹出、候选解析正确

## 后端

#### 新功能

- **收件箱列表 `limit` 参数**：`GET /inbox/messages?limit=N` 服务端截取前 N 条（按收到时间倒序），不传保持全量兼容旧调用方

#### 优化

- **API 响应 GZip 压缩**：新增 `GZipMiddleware`（中间件链最外层）。此前客户端声明 `Accept-Encoding: gzip` 服务器仍返回未压缩 JSON（全量收件箱 174.6KB 裸传）。实测压缩率：全量收件箱 **12.3 倍**（174.6KB → 14.2KB）、日历 / limit 列表约 5 倍。SSE 流式接口（workbench stream_chat）兼容——Django 的 `compress_sequence` 每事件块 flush 不缓冲整流
- **ninja Schema 序列化性能补丁**（`apps/core/infrastructure/ninja_perf.py`，CoreConfig.ready() 自动应用）：`DjangoGetter.__getattr__` 增加字段级缓存 + 原生 getattr 快路径（上游源码注释自认该缓存而未实现）。序列化路径每请求曾高达 6.5 万次 `__getattr__` 调用；补丁对实例短生命周期做 memo，无跨请求泄漏，ninja 结构变化时自动跳过回退上游实现
- **开发环境 DB 连接复用**：`CONN_MAX_AGE` 从「dev 固定 0（每请求建连即释放）」改为 dev 默认 60s / 生产默认 600s，可用环境变量 `DB_CONN_MAX_AGE` 覆盖（设 0 恢复旧行为）；`CONN_HEALTH_CHECKS` 探活保证复用安全

#### 性能实测（本地，收件箱 345 条数据量）

| 场景 | 改动前 | 改动后 |
|---|---|---|
| `GET /inbox/messages`（全量，Django 测试客户端） | 48.5ms | 44–51ms（序列化补丁，收益小幅） |
| `GET /inbox/messages?limit=6`（前端实际用法） | 48.5ms | **9.1ms（-81%）** |
| HTTP 层 `limit=6` vs 全量（真实 uvicorn + JWT） | ~50–60ms | 30ms vs 60–74ms |

- calendar 接口复查：预热后 15–21ms，其中 11ms 为 PostgreSQL 执行等待（SQL 下限），无进一步优化空间

#### 自测

- 集成测试新增 `test_list_messages_limit`（含倒序头部一致性与 limit=0 边界），message_hub 13 用例全过
- core / cases 单测目录 140+ 用例通过（验证序列化补丁对全部 ninja 接口无副作用；GZip 中间件加入后复跑 message_hub + core 全过）
- ruff / mypy（含改动文件）全绿
- HTTP 实测：`Content-Encoding: gzip` + `Vary: Accept-Encoding` 响应头正确，压缩数据可正常解压
