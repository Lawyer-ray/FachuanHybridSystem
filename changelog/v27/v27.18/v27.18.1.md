# 一、双引擎交叉校验（分支原定目标）

## 解决什么

纸质/扫描卷宗靠云端 OCR 取字，**单引擎读错一个字，律师无从发现**。真实案例：
同一份卷宗里的借款人姓名，两个引擎读出三个不同结果——

| | 第 1 页 | 第 3 页 |
|:--|:--|:--|
| MinerU | 曾妙**焮** | 曾妙**欣** |
| PaddleOCR-VL | 曾妙**焱** | 曾妙**焱** |

姓名错一个字，起诉状主体就写错。这类错误单引擎永远自己发现不了。

## 怎么做

按**任务粒度**可选：勾 1 个引擎 = 只取字；勾 2 个 = 取字 + 交叉比对。

```
两个引擎并行跑同一份 PDF → 各自产出「页 → 行 → 坐标」
  → 逐页按坐标把行对齐
  → 同一位置两种写法不同 → 产出分歧（带两个版本 + 各自 block 坐标）
```

**刻意只报分歧，不投票、不产出「最终文本」**。理由：机器投票选出来的"正确"
没有任何人能担保，而律师需要的是"这里两个引擎读得不一样，你来看一眼"。

### 判据（`services/split/dual_engine.py`）

归一化后**完全相同**（只差全半角标点、Markdown 标记）→ 不报，那是排版差异不是识别差异。

| 情形 | kind | severity |
|:--|:--|:--|
| 只差 **1 个字符** | `char` | 命中锚点 → `high`，否则 `medium` |
| 差 2 字符以上且相似度 ≥ 阈值 | `line` | `high` |
| 相似度过低 | — | 不报（交给 missing/整行差异） |

**锚点邻域**（`_anchors_nearby`，window=2）：行内含身份证号等唯一标识，或**相邻两行**内出现，
单字分歧升级为 `high`。理由：卷宗表单里「姓名」与「身份证号码」经常是相邻两行（表格里
甚至分成两格），只看本行会把「张三丰/张四丰」这种绑定到具体自然人的姓氏分歧降级成
`medium` —— 它和普通正文的分歧不是一个量级。

偏差阈值刻意宁可多报：`line` 级别一律 `high`，因为差两个字以上已经超出"一眼能判断"
的范围，必须人看。

### 接入（`services/split/dual_engine_runner.py`）

| 引擎码 | 实现 |
|:--|:--|
| `mineru` | `MineruBackend` |
| `paddleocr_vl` | `PaddleOCRApiEngine(model="paddleocr_vl_1_6")` |

- `SUPPORTED_ENGINES` 目前只这两个；`textin` 前端可勾但本模块不支持，会如实记进
  `summary.dual_engine.unavailable`（**不静默吞掉**，用户能看出"我勾了三个只跑了两个"）
- 工厂**延迟到线程里构造**：构造函数会读配置/校验 Key，没配 PaddleOCR 的部署
  即使误开双引擎也不该在 import 阶段就炸
- `page_numbers` 支持只跑指定页 —— 关键页试点不该为整本付两次云端费用

### 前端呈现

- `EngineDisagreementDrawer.tsx` —— 全局分歧清单
- `PageCell.tsx` 双框 —— 同一页上两个引擎的定位框叠着画，一眼看出差在哪
- `draft/engine.ts` 引擎码 ↔ 中文名映射；`draft/review.ts` 分歧的复核状态

## PaddleOCR 侧收口

`paddleocr_api_service.py`（+942/−88）把 PaddleOCR 收到 **v2 Job API**，启用
**PaddleOCR-VL-1.6**：提交 job → 轮询状态 → 解析 layout。大文件用长超时 + 多轮询
（`job_timeout` / `max_polls` 跟体积走）。

## 评测工具

`services/split/eval_metrics.py` + `scripts/eval_baseline.py` / `eval_table_split.py`：
拿固定样本跑两个引擎，量化"分歧率 / 命中率"，供调参时对比，避免凭感觉改阈值。

# 二、自动分段进度可见（联调暴露）

## 问题：跑了 20 分钟，界面上什么也没有

真实 164 页卷宗点「自动分段」后，进度反馈**只是工具条按钮里的一行字**
（`ReaderToolbar.tsx`：`{autoSplitRunning ? autoSplitProgress || '识别中…' : '自动分段'}`）。
没有进度条、没有耗时、没有"现在在干什么"。更糟的是任务不是当前页面发起的时
（刷新 / 换设备 / 别人发起），前端**完全拿不到进度**——`running` 只是局部
`useState`，组件重挂载即丢失，成为"幽灵任务"。

## 后端

### 双引擎拆成独立阶段（`cross_check`）

这是最硬的一个坑。原来双引擎内联在取字阶段里，而 `Q_CLUSTER.timeout` 默认 **600s**
是**单个任务**的硬阈值——超时直接杀 worker 进程，**连 `finally` 都不执行**。

实测后果：

```
任务 3365293d：extract 跑完 368s → 进入双引擎
  → 600s 到点，worker 被杀
  → django_q_task 表里一行记录都没有（既非成功也非失败）
  → DB 只剩一个 stage=cross_check 的僵尸，心跳冻结
```

心跳线程救不了它——进程整个没了，线程也没了。

修法：跟既有的 `extract → segment` 一样，把交叉比对拆成独立任务，
让每段拥有自己完整的 600s。

```
extract (368s) → cross_check (30s) → segment (47s)   全部 success=t
```

验证证据是 `django_q_task` 里三条独立记录。

改动：
- `models.py` `PdfSplitStage` 新增 `CROSS_CHECK`（迁移 0013）
- `two_stage.py` 新增 `TASK_CROSS_CHECK` / `submit_cross_check_stage` /
  `advance_after_extract`（有双引擎才排 cross_check，否则直接分段——多排一个空阶段
  只是白跑一趟 worker）
- `tasks.py` 新增 `run_cross_check_stage`；比对失败**仍然推进到分段**（分歧是附加
  信息，不该让可选功能把整份卷宗判失败）
- `service.py` 双引擎从 `extract_stage` 内联调用移出，独立成 `cross_check_stage`

### 心跳与看门狗

- 新增 `services/heartbeat.py`：`periodic_heartbeat(job_id, interval=15)` 上下文管理器，
  守护线程 + `Event.wait` 停止，`try/finally` 保证退出即停
- `job_recovery.STALE_SECONDS` 600 → 1800

原来的 600s 会让看门狗把**仍在正常工作**的任务判死并重排——重排意味着整份卷宗
再花一次云端费用。

### 进度语义

`PdfSplitJobOut` 新增 `stage` / `started_at` / `finished_at` / `elapsed_seconds`。

`progress` 的区段划分：取字 `0→100`，进双引擎时**回退到 90**（取字确实做完了，
但整条流水线没完；停在 100 就是谎报"快完了"），收工推到 99，分段完成才 100。
`processed_pages` 全程不回退（那是取字的真实完成量）。

### 新增"查进行中任务"接口

```
GET /api/v1/pdf-splitting/inflight-job?source_name=&total_pages=
```

这是修"幽灵任务"的关键。原来只有 `GET /jobs/{job_id}`，前端手里没有 jobId 就彻底失联。

## 前端

- **`AutoSplitProgress.tsx`** —— 底部浮条（与 `SelectionBar` 同一范式，不参与 flex
  高度分配，不影响 `Flow` 的滚动）。内容：进度条（按阶段映射，`cross_check` 停在 90
  不显示 100%）、当前处理内容（`正在识别文字（84/164 页）` / `双引擎交叉比对中
  MinerU × PaddleOCR-VL` / `正在智能分段`）、**已用 3 分 12 秒**、停滞警示
- **`use-auto-split-task.ts`** —— 打开阅读器自动查 `/inflight-job`，命中就接管轮询，
  **不用再点按钮**
- `auto-split-helpers.ts` `pollJob` 回调从 `(text: string)` 扩成 `(text, snapshot)`，
  结构化快照不再在内部丢掉
- 工具条按钮收敛为固定「识别中…」，长文案交给面板（原来会撑爆 `max-[760px]` 的横滚条）

**停滞提示不再直接抛错中断轮询**：改成显示"已 N 分钟无响应，可能已中断"，让用户决定。

# 三、材料包删除彻底化

## 问题：删了等于没删

删材料包只删了收件箱那条 `InboxMessage`，而一次自动分段在 `pdf_splitting` 侧留下
三类数据，**都不属于收件箱**：

| 残留 | 实测（一份 164 页卷宗） |
|:--|:--|
| `PdfSplitJob` + `PdfSplitSegment` 行 | 1 条任务、46 段 |
| 任务目录 `jobs/<uuid>/` | **70MB**（含源 PDF 完整副本 + 预览图 + 导出 zip） |
| OCR 页缓存 `ocr_cache/<sha256>/` | 372KB |

而 `find_reusable_job` 只按「文件名 + 页数 + 已出结果」匹配——**删掉材料包后那条任务
仍然命中**，下次上传同名文件点自动分段，直接拿回已删除材料的分段结果。

全仓**没有任何清理路径**。实测 49 个任务里 47 个是孤儿，`jobs/` 目录 87MB 无人回收。

## 修法

### 删除顺序反过来

原实现先删附件物理文件、再 `message.delete()`。只要 DB 删除失败，就留下
「文件已经没了、记录还在」的**破包**——重开材料包指向不存在的文件。

改为**先删 DB 行，再删物理文件**：最坏情况只剩孤儿文件（可清理、不影响界面）。

### 被财务凭证引用时明确拒绝（409）

`PaymentIntake` / `InvoiceIntake` 对 `InboxMessage` 是 `on_delete=PROTECT`（删消息
不得静默抹掉财务凭证来源）。原来命中时抛 `ProtectedError` → 500「系统错误」，
**而附件已经被删了**。

现在：动任何文件**之前**先查反向关系，命中抛 `ConflictError` → 409，
文案直说哪类凭证几条：

> 该材料包已被待认领的发票记录 2 条引用，不能再删除；请先处理这些凭证

### 新增 `services/cleanup_service.py`

`purge_split_jobs_for_attachment(...)` 回收任务行 + 任务目录 + OCR 缓存。

**关键：不能只按"同名同页数"就删任务。** 复用逻辑刻意跨用户，一个任务可能被多个
材料包共用，无脑删会让别的包下次被迫重跑几分钟。所以先判断"还有几个活着的材料包
能命中这个任务"，有就别动。附件缺 `page_count` 时按"可能复用"处理（宁可多留）。

### 新增管理命令

```
python apiSystem/manage.py purge_orphan_split_jobs --dry-run
```

兜底清理历史孤儿，双向都查：
- **DB → 磁盘**：任务行没有活包引用 → 删行 + 目录
- **磁盘 → DB**：有目录无任务行（历史删除记录但没清目录）→ 删目录
- **OCR 缓存孤儿**：用全库现存附件的 sha256 集合做差（源文件副本丢了就反查不到桶名）

实测在开发库上清掉 47 个孤儿任务、56 个目录、87MB。

# 四、MinerU 上传超时（大文件必失败）

## 问题：三个缺陷叠加

| 缺陷 | 后果 |
|:--|:--|
| `timeout=30` 单一标量同时用于元数据请求和 65MB 文件上传 | 元数据几百字节 30s 够用，65MB PUT 远超 |
| `content=f.read()` 整包读进内存 | 65MB 常驻，双引擎并发时内存峰值翻倍 |
| 上传零重试 | 一次网络抖动就彻底放弃 |

5 页试点能成功（切出来只有几 MB），**全本 65.7MB 必然触发**
`write operation timed out`——双引擎里 MinerU 这一侧永远没有结果，只剩
PaddleOCR-VL 单边，比对失去意义。

## 修法

**超时按体积换算，且分阶段**（`_upload_timeout_for`）：

```python
estimated = size / (512KB/s) * 4.0倍余量
total = clamp(estimated, 120s, 3600s)
httpx.Timeout(total, connect=120, write=total, read=total)
```

不用写死大值：小文件不必白等，大文件有足够余量，上限 3600s 防无限挂起。
`connect`/`write` 走小底（对方几乎不花时间），`read` 跟体积走（等对象存储回 200）。

65.7MB 算出 `read=526s`，而实测真实上传只需 **12.5 秒**——旧代码 30s 毫无余量。

**流式上传**：改传文件句柄而非 `f.read()`，httpx 分块读盘且能算出 `Content-Length`
（预签名校验需要）。

**重试 3 次 + 每次重开文件**：失败的 PUT 可能已把句柄读空，复用会传出**残缺字节**，
而对象存储不校验内容会当成成功。`trust_env` 逐轮轮换（与既有结果下载同口径，
绕代理隧道断流）。

**拆成两步不同超时**：`_request_upload_url`（几百字节 JSON，用元数据超时）与
`_put_file_streaming`（跟体积走）分离。

# 五、顺手修掉的

- **`test_sonner` mock 与真实库不符**：`vi.mock('sonner')` 把 `toast` 当成普通对象，
  而 sonner v2 的 `toast` 是**可调用对象**（`toast('文案')` 和 `toast.error(...)` 都成立），
  所以 `toast(\`${subject} 已删除\`)` 这条路径从来没被测到。改成 `Object.assign` 形状。
- **`line_boxes` 测试预期自相矛盾**：同一个夹具里两个结构完全相同的块
  （content 1 行 + ocr_text 2 框）给了相反预期（一个要求挂 2 个框、一个要求放弃）。
  查坐标发现那两个框 y 区间**重叠 8 个单位**——是同一行的重复检测，不是两行。
  挂上去等于宣称一行文字占两个高度，坐标是假的。按实现的红线（框数 ≠ 行数一律放弃）
  统一预期，并补一条测试单独锁住这个语义。
- **`platform-selection` 的 VL 正主断言写错了**：原断言要求只勾 `paddleocr_vl`
  时它当正主，但后端根本没这个值——`ProviderType` 只有 `mineru`/`textin`，
  `_normalize_cloud_backend('paddleocr_vl')` 实测返回 `'auto'`（与 `'bogus'` 同一档）。
  发一个认不出的值会让「锁定」语义静默失效（用户以为锁了 VL，实际是 auto 挑的
  别的平台），比直接退回 auto 更糟。改断言为 `'auto'`，并把原因写进用例注释。
- **勾两个引擎时菜单底部一句话都没有**：`ReaderToolbar` 里 `crossChecks(...)`
  为真时直接 `? null :`，于是最该提示的那一态反而空白——用户看不到「将要交叉比对」，
  更看不到它会**再付一次云端费用**。补上该分支的提示文案。

# 七、已知边界

- **双引擎只适合中小文件**：164 页全本要再付一次完整云端费用，且 cross_check 虽已有
  独立 600s 预算，若单份比对比 600s 更长仍需进一步拆分。建议先用关键页试点
- **`textin` 不可当双引擎成员**：前端可勾但本模块不支持，会进 `unavailable`。
  若只勾 `mineru,textin`，门禁（≥2）会通过但实际只跑一个引擎 → `compare_pages`
  返回空 → 用户看到"0 分歧"会误以为是好消息
- **OCR 缓存跨材料包存活**：删材料包时若源文件副本已丢就反查不到缓存桶名，
  需靠 `purge_orphan_split_jobs` 兜底
- **前端已全绿**：`platform-selection.test.ts` 与 `ReaderToolbar.dom.test.tsx` 两条
  遗留失败已在本版一并收掉（见下）
- **`frontend/src/types/api-schema.d.ts` 已重新生成**（后端新增 `stage` /
  `elapsed_seconds` / `/inflight-job`），`backend/openapi.json` 同步 +137 行
