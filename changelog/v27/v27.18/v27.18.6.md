# v27.18.6 · 法院短信链路三连修：移除 CloakBrowser、直连绕开死代理、终止重复签收死循环

> 分支 `fix/startup-db-async-context`（6 个提交，23 文件 +593/−159）。
>
> 本版不是一次计划内的改动，而是**一条真实故障链的连续排障记录**：从一次
> uvicorn 启动时的 `SynchronousOnlyOperation` warning 开始，逐层挖出四个
> 互不相干、但刚好串在同一条业务链上的缺陷。
>
> 四个缺陷的因果顺序是**倒着暴露**的——最表面的那个（浏览器要 license）先报错，
> 修掉它才露出代理问题，修掉代理才让下载第一次真正跑通，进而引爆了埋了两个月的
> 状态机死循环。
>
> **无迁移、无 API 变更**。本版只有一处行为变更是用户可感知的：短信不会再重复签收。

---

## 故障链全貌

```
uvicorn 启动 warning（SynchronousOnlyOperation）
  └─ ① 六条定时任务在 ASGI 下从未注册成功
       ↓ 无关，但同一轮排查中被发现
  法院短信任务失败：No CloakBrowser license key
  └─ ② 浏览器降级链被 Pro 二进制的授权校验挡死
       ↓ 移除 CloakBrowser 后，降级链能跑了
  法院短信任务失败：API 全部 Connection refused
  └─ ③ .env 里的死代理（127.0.0.1:7897 无监听）劫持了所有 httpx 请求
       ↓ 修好代理后，下载第一次真正成功
  法院短信无限重复签收 / 重复下载
  └─ ④ 状态机死循环：MATCHING 回流到下载分支
```

**关键洞察**：③ 长期掩盖了 ④。代理故障让下载**从来没成功过**，所以 ④ 永远
走不到触发条件。修好 ③ 的当天 ④ 立刻现形——两个 bug 是一体两面。

# 一、后端修复

#### 修复：`AppConfig.ready()` 的 sync ORM 摆渡出事件循环线程

**症状**：uvicorn 每次启动都打一条 `记忆定时任务注册失败`，
`django.core.exceptions.SynchronousOnlyOperation: You cannot call this from an
async context`。

**影响面比日志显示的更大**。ASGI 进程里 `get_asgi_application()` 在事件循环线程
构造，`ready()` 随之在该线程执行，凡是「ready 里查调度表」的 app 全部中招：

| 调用点 | 表现 |
|:--|:--|
| `apps/agent` | 冒成 `warning`，日志可见 |
| `apps/core` | 被 `except` 吞成 **debug**，静默 |
| `apps/pdf_splitting` | 同上，静默 |

也就是说**文件清理、磁盘监控、PDF 看门狗、行为偏好推断四条定时任务在 ASGI 部署下
从未注册成功过**——静默不注册比报错更糟。

**修法**：新增 `run_startup_db_sync()`。无事件循环时就地执行（`manage.py` / wsgi /
django-q worker / pytest 零开销），有事件循环时起一次性线程跑完 `join()`。

**为什么不用现成的**（四条路全部实测否决）：

| 方案 | 结果 |
|:--|:--|
| `async_to_sync(sync_to_async(fn))()` | 同线程嵌套直接 `RuntimeError: You cannot use AsyncToSync in the same thread as an async event loop` |
| 加 `thread_sensitive=True` | 更糟——复用当前循环线程的 executor，等于在事件循环里跑 sync ORM |
| `asyncio.to_thread` / `sync_to_async` | 都是 await 语义，同步函数拿不到返回值 |
| `allow_async_unsafe()` | 会**阻塞整个 ASGI 进程**，且其模块 docstring 明确「新代码禁用」 |

独立线程是唯一既正确又不会死锁的选择：不在事件循环里，也不占用 asgiref 的
thread-sensitive executor（因此可从 thread-sensitive 线程再调用而不自锁）。

#### 修复：移除 CloakBrowser，回归原生 Playwright

**症状**：`CloakBrowserLicenseError: No CloakBrowser license key`。

**根因**：CloakBrowser 的 Pro 二进制在**首次使用时**才调 `ensure_binary()`，会联网
拉包并要求 license key。无终端环境（django-q worker / CI / Docker）无法弹菜单，
直接抛错——把「装浏览器」这个一次性动作变成了任务执行期的授权故障。

更糟的是 `service.py` 直接裸调 `ensure_binary()`，**绕过了同目录下已经写好错误翻译的
`launcher.py`**，所以抛出来的是授权错误，把真正的失败原因盖掉了。

**改动**：
- `ensure_browser_binary()` 改为校验 Playwright Chromium 路径，缺浏览器时只给
  `playwright install chromium` 一条可执行指引，不再引入授权概念；
- 新增 `ensure_browser_binary_async()`——`sync_playwright()` 在事件循环内会抛
  `using Playwright Sync API inside the asyncio loop`，异步路径必须走异步版
  （**此 bug 是实跑才发现的，单测全 mock 掉 `ensure_binary` 测不出来**）；
- 五个启动路径全部改用原生 `launch` / `launch_persistent_context`，并补 `pw.stop()`
  回收（原先依赖 CloakBrowser 内嵌停止 driver，换成原生后会泄漏 driver 进程）；
- 去掉 Playwright 不认识的 `humanize` 参数（反检测本就由 `anti_detection` 注入）。

#### 修复：法院直连绕开进程代理

**症状**：`ConnectError: [Errno 61] Connection refused`，连续 3 次。

**根因**：`backend/.env` 有 `HTTPS_PROXY=http://127.0.0.1:7897`（本地代理软件），
`load_dotenv()` 注入 `os.environ`，`httpx.Client()` 默认 `trust_env=True` 会读它。
当天代理软件未运行、端口无监听 → 法院 API 全部被拒。

日志只说「直接 API 连续 3 次调用失败」，**完全看不出是代理导致**——这是本次排障
耗时最久的一环。

**定性**：法院/政务站点全在国内，本就不该走出口代理；走代理反而更慢更不稳。

**修法**：新增 `court_client()` 工厂固定 `trust_env=False`（调用方误传也会被覆盖），
替换 5 处裸 `httpx.Client`：zxfw 直连列表 / 下载 / 签收确认、hbfy 会话、
daolv-sifa 会话。

**实测**：进程内代理变量仍在、代理软件未启动的情况下，API 返回 200 拿到文书列表，
PDF 下载 139KB 真文件。

#### 修复：终止短信下载成功后的无限重复签收 / 重复下载

**症状**：SMS 296/297 在无人工干预下循环十余次，每轮都重新签收法院接口
（`updateSdxxBySdzt`）并重复下载同一份文书。

**三个环节互相咬合**：

| # | 位置 | 行为 |
|:--|:--|:--|
| 1 | `_process_downloading_or_matching` | SMS 是 `MATCHING` 且有 `download_links` → 新建下载任务 |
| 2 | 同一函数 | 建完任务把状态改回 `DOWNLOADING` |
| 3 | `_handle_sms_download_success` | 下载成功 → 置回 `MATCHING` + **无条件** `submit_task(process_sms)` |

```
MATCHING → 建任务 → DOWNLOADING → 下载成功 → MATCHING → 再建任务 → …
```

**根因**：`MATCHING` 有两种来源，代码没区分——

| 来源 | 需要建任务？ |
|:--|:--|
| 客户转交通道建记录即置 `MATCHING`（`v27.18.x` 材料预处理引入） | 需要 |
| **下载成功后被置回 `MATCHING`** | 不需要，产物已就绪 |

**修法**：
- 用 `scraper_task_id` 作为「已走过下载」的可靠标记：`MATCHING` + 已有任务时直接进
  匹配，不再建任务。转交通道该字段为空，**原逻辑零改动**；
- 下载成功的后续任务改投 `process_sms_from_matching`，该入口只跑
  「匹配 → 重命名 → 通知」，**结构上不可能回头下载**。原 `process_sms` 是从
  `PENDING` 起的全流程入口，正是它把流程绕回了下载分支。

**为什么埋了两个月没爆**：`f644aa44`（材料预处理整条链路）为了让客户转交通道复用
`process_sms`，把分发条件从 `PARSING` 扩成了 `in (PARSING, MATCHING)`：

```diff
- if sms.status == CourtSMSStatus.PARSING:
+ if sms.status in (CourtSMSStatus.PARSING, CourtSMSStatus.MATCHING):
```

改动本意没错，但没意识到 `MATCHING` 有两个来源。当时「sms 套件 269 例全通过」——
测试覆盖的是客户转交（`MATCHING` 无 `scraper_task`），**没覆盖「下载成功后
`MATCHING` 有 `scraper_task`」这条路**，后者必须真实跑完一次下载才能触发。

而那条路被 ③ 的死代理封死了，于是缺陷一直潜伏。
