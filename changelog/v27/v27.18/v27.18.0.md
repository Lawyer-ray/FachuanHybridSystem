## 一句话定位

法院短信是**来源**，记一笔是**第二段落**。短信状态机一行没改：日期识别完全跑在
旁线上，它失败、超时、卡住都不会让 `CourtSMS` 的任何一个字段发生变化。

# 一、功能：短信文书自动送识别，律师只做确认

## 为什么不是「塞进 process_sms」

最直觉的做法是在 `process_sms` 的 `completed` 之前加一个 `extracting` 阶段。否决理由：

| 理由 | 说明 |
|:--|:--|
| 权限错位 | 短信写操作（assign/retry/delete）已全部收敛为管理员专用；而「确认日期写日历」必须由有权限的律师本人做 |
| 语义污染 | `completed` 的含义会变成「文书归档 + LLM 也跑完了」，一次 LLM 抖动就让整条短信看起来失败 |
| 无法独立重跑 | 识别想重试就得重跑整条短信流程（含爬虫下载） |
| 耦合方向错 | 短信侧会被迫 import 识别域，任何识别域改动都能波及短信主线 |

旁线的方向是单向的：**短信侧只递一个纯数据 DTO 出去，识别域从不反向依赖短信模型**。

## 后端

### 新增：日期捕获旁线服务（`services/date_capture_service.py`）

| 能力 | 实现 |
|:--|:--|
| 送入识别 | `capture_dates_for_source(DateCaptureSource)` — 短信的**每份**文书各建一个识别任务，逐份返回 `created/retried/reused/skipped` |
| 幂等键 | `(source_court_sms_id, source_document_path)` — 单靠 `file_path` 不行：重跑复用同一行，「重新送」要新建行 |
| 失败处理 | 已有 `failed` 任务**原地重跑**（复用已落库文件，不新建行）；`force=True` 才无条件新建 |
| 逐份隔离 | 单份文书建任务抛错只写该行 `reason`，其余照送（一条短信混着坏文件是常态） |
| 前置校验 | 无文书 / 无 `case_log_id` / 文件已不在磁盘 → 明确 `skipped` + 人话原因，不建空任务 |
| 状态汇总 | `list_source_tasks()` 给出每任务的状态、候选数（pending/confirmed/skipped）、确认进度 |

### 新增：两个 API（普通律师可用）

| 端点 | 作用 |
|:--|:--|
| `POST /court-document/sms/{id}/capture-dates` | 送识别（幂等）；`?force=true` 无条件新建 |
| `GET /court-document/sms/{id}/capture-status` | 派生任务列表（轮询 + 「继续确认」入口） |

**权限口径**：读短信按 `CaseAccessPolicy`（与法院短信详情接口同口径，未绑案件的
公共短信全员可读），**不做** `_require_admin`——语义是「读这份文书 + 给**自己**写日历」，
与 QuickAdd 上传同权限级；写入日历的权限由既有 `dates/confirm` 按案件 ACL 兜底。
任务列表另叠加任务归属过滤（普通律师只看自己建的，管理员看全量）。

### 复用：法院短信已算出的结果直接带给记一笔

管线模式下识别不再从零算：

| 字段 | 策略 |
|:--|:--|
| 案号 | **短信正文解析结果优先**，直接覆盖单份文书自己的提取结果（短信侧是在正文上解析的，比单份文书更可信） |
| 当事人 | 识别没提取到时回填短信解析出的当事人 |
| 文书类型 | 只在分类器认不出（`other`）时用短信类型兜底；认得出的一律信分类器（短信链接里混着应诉/举证通知，短信类型粒度太粗） |
| 案件 / 案件日志 | 直接用短信第一轮绑定结果预绑定 → 识别期不匹配、不重命名、不建日志、不重复通知 |

### 新增：文书模板过滤（`services/document_template_filter.py`）

法院一次送达常带 9~12 份文书，其中模板类结构固定、**从不含期限**，送识别只是白烧 LLM。

| 排除 | 保留（反向守住） |
|:--|:--|
| 廉政监督卡、送达地址确认书、退费申请书<br>诉讼权利义务告知书、民事诉讼风险提示书、司法作风监督卡、满意度评价表… | 传票、判决书、裁定书、**告知书**（含保全到期日！）<br>举证通知书、交费通知书、受理案件通知书、诉讼材料提交告知书 |

刻意用**精确类型名**而非模糊词包含：「告知书」既可能是模板也可能是含保全到期日的实体
文书，通配词一刀切会漏掉真期限。宁可多烧一次 LLM，也不漏期限。

## 前端

### 交互：打开已完成的短信 → 自动识别 → 只做确认

```
收法院短信（completed）
  └─ 弹窗打开
       └─ 旁线自动送识别（幂等，反复打开不重复烧 LLM）
            └─ 文书列表下方出现「记一笔 · 关键日期」
                 ├─ 识别中  → 「正在识别文书里的开庭/举证/上诉等日期…」
                 ├─ 有待确认 → 每份文书一行 +「确认日期」按钮
                 ├─ 已写入   → 「已写入日历 N 条」
                 ├─ 识别为空 → 「没识别到关键日期（通知书/回证类常见）」+「再识别一次」
                 └─ 识别失败 → 失败原因 +「重新识别失败的文书」
```

「确认日期」直接接管后端已建好的识别任务（`RecognizeDialog` 新增 `taskId` 模式）：
**不重传文件**，弹窗内也**不出现案件选择器**——案件由短信侧定死，日期写到哪份日历
不能在同一张弹窗里被换掉（换成只读 chip 明确显示「已由法院短信绑定：XXX」）。
写入成功即刷新日历 query。

### 为什么必须保留「人工确认」这一步

后端只有 `confirm_candidates` 一条写提醒的路径，它同时承担着与既有提醒
（`case_log_id + due_at`）去重的职责。自动写 = 跳过唯一的复核关口。
法律日期错一天的代价远大于点几下——这条底线没变。

- `court-sms/use-date-capture.ts` — 旁线编排（自动送 + 轮询 + 汇总；`usePollSession` 保证重入安全）

# 二、日期识别口径（业务确认）

拿真实文书逐条核对后定下的口径，代码与测试都按此实现：

| 文书 | 记什么 | 不记什么 |
|:--|:--|:--|
| **判决书 / 调解书** | 上诉期、复议期、保全到期日 | 判项给付义务（生效 10 日内支付）、调解书分期付款、正文引述的合同条款付款期、**开庭日**（已开过的庭是历史陈述） |
| **裁定书** | 上诉期、复议期、保全到期日 | — |
| **保全告知书** | 保全/冻结/查封到期日、续封申请截止日 | — |
| **传票 / 开庭通知** | 开庭时间 | — |
| **交费通知书** | 缴费期限（依据收到的通知书起算） | — |
| 判决书里的「向本院缴纳诉讼费」 | **保留**（法院收的钱要跟进） | — |

**起算点**：所有「送达之日起 N 日」「收到之日起 N 日」一律以 **`CourtSMS.received_at`
（= 收到日 = 送达日）** 为锚，不用文书落款日——落款普遍早于实际送达，按落款算会把
届满日算早，律师排期会误判剩余时间。记一笔独立上传拿不到收到日才回落落款日。

**其他**：已过期的期限保留（律师需要知道「这个已经过了」，置信度降 0.3、默认不勾）；
超过 10 年的未来日期降置信（房贷 30 年到期日之类）。

# 三、缺陷清单（全量扫描 119 份 PDF 后发现并修复）

## 1. 文书识别只能读到前 3 页，末页上诉期整段丢失

`TextExtractionService()` 无参实例化 → `text_limit=None` → 下层 `extract_pdf_text`
回落到 `DEFAULT_TEXT_LIMIT=1500`（**预览/摘要**用的默认值）。7 页 3900+ 字的判决书
只读到前 3 页 **1381 字**，第 7 页「如不服本判决…十五日内…上诉」整段丢失 → 日期候选为空。

同仓库 `apps/documents/judgment_pdf_extractor` 早踩过同一个坑（49 页判决书只读到 13 页），
并为此写了绕过 `MAX_TEXT_LIMIT` 的全文提取——识别域没跟上。

修法：`DEFAULT_TEXT_LIMIT = 200_000`，`text_limit=None` 时显式传它而非 None
（下层把 None 当「用预览默认值」，不能靠隐式语义）。

| 指标 | 修复前 | 修复后 |
|:--|:--|:--|
| 提取字数 | 1381（前 3 页） | **3619**（全 7 页） |
| 含「如不服」 | False | True |
| 日期候选 | 空 | 上诉期 + 缴费期限 |

## 2. 文书错配：57/63 条短信指向别人的判决书

`collect()` 无条件把**案件日志下的全部附件**当成本短信的文书。案件日志会长期累积
同一案件多次送达的全部文书，于是：

```
某条「廉政监督卡」短信（案号 A）
  → 实际取到的文书：另一案件的民事判决书.pdf
```

后果：一条廉政监督卡短信会去识别**别人的判决书**，把上诉期、缴费期限写进自己案件的日历。

修法：`collect(include_case_log_attachments=False)` 用于送识别，只认这条短信自己下载的
文书（`court_document` / `document_file_paths` / `task_result`）；详情展示仍用默认 True。
修复后 63 条里 **6 条**真正送识别（全是自己的文书），57 条错配归零。

> 其余看似「不送了」的短信，实为其 `document_file_paths` 指向的文件已不在磁盘
> （历史清理），本来就没有可识别的东西。

## 3. 无年份的日期被 LLM 猜年份

原文「依据…裁定书于**3月26日**冻结了被执行人账户，上述账户冻结期限为一年」——
全篇没有 3月26日 的年份，LLM 补成 2026-03-26，到期日算成 2027-03-26，**差整整一年**。

修法两层：LLM 提示词明确「日期必须带年份，原文无年份时省略」+ 确定性后置校验
`_has_explicit_year` 兜底。

**这一条第一次修得过头**：用「全文有没有年份」做兜底，把同一份文书里那条**合法**的
`2026年9月20日 + 一年 = 2027-09-20` 也一起删掉了（业务方指出「285 有日期啊」）。
改成**逐候选看证据链**：候选日期带年份明文出现 / 是文书落款日 / 能由带年份的原文日期
按 +整年、+整月、+N日(≤90) 精确推算，任一成立即放行。年份锚点同时认阿拉伯与中文数字落款。

## 4. 他案引用的期限被当成本案期限（最危险）

某份判决书实际是「**驳回原告诉讼请求**」，没有任何缴费义务。但旧逻辑给出
「11-07 前交检测费」——来自正文引述的**另一个仲裁裁决**：

> 某仲裁委员会…作出…仲裁裁决书，裁决：一、某公司于**本裁决书送达之日起十日内**支付检测费…

律师会按这个日期去催款，但判决根本没判被告付钱。

修法：`_anchor_points_to_other_matter` — 锚点前后出现「仲裁/裁决书/另案/他案/本函/
书面通知/告知函/律师函/合同约定/协议约定」→ 跳过。同时覆盖证据材料里引述的**商业函件**
（「现本人要求公司在收到**本函**之日起十五日内作出书面答复」）。

## 5. 复议期完全识别不出来

裁定书写「如不服本裁定，可以自**收到裁定书之日起五日内**向本院**申请复议**一次」——
这是律师必须跟进的救济期限，但动词表里没有「复议」，落到 `other`，过期后被
「纯历史事实」过滤删掉，**律师完全看不到复议期已过**。

修法：动词表补「复议/申请/提出异议」→ `submission_deadline`，并把「上诉」排到
「申请」之前（先匹配到的赢）。

## 6. 判决书里记了当事人义务与历史开庭日

按业务口径改为**按类型白名单**（比逐条解析话术可靠——调解书分期付款有
「向原告支付」「被告定于 X 日前支付」等多套写法，漏一个就漏全部）：

| 类型 | 判决书/调解书里 | 理由 |
|:--|:--|:--|
| 上诉期 / 复议期 | 保留 | 律师最关心的救济期限 |
| 保全到期日 | 保留 | 判决正文可能载明保全期限，需跟进续封 |
| 缴费期限 | 剔除，**除**「向本院缴纳」 | 判项给付/调解分期是当事人义务；诉讼费由法院收，要跟进 |
| 开庭时间 | 剔除 | 判决书里的开庭日都是已开过的庭（历史陈述） |

## 7. 离谱的未来日期

一份银行贷款合同给出 `2051-04-25`（30 年期房贷到期日）。加规则：超过 10 年的
未来日期降置信到 0.3（默认不勾，仍可见）。

# 四、实测（真实数据，只读干跑）

全部验证均为**只读**：直接读已归档 PDF + 在内存中跑规则/识别，未新建任何短信、
识别任务或提醒，也未修改任何既有记录。

## 单条短信端到端（短信 #290，7 页判决书）

```
capture-dates  → [('created', 26, 'pending')]
再调一次      → [('reused', 26, 'success')]     ← 幂等，不重复烧 LLM
capture-status → 案号复用自短信、当事人回填自短信
                 候选=[2026-11-21 上诉期]
dates/confirm → reminder 写入案件日志
caption-status → pending=0 confirmed=1 complete
无文书短信     → skipped「该短信没有可识别的文书」
不存在短信     → 404
```

## 全量扫描（36 份有文本层的法院文书）

| 文书 | 识别结果 |
|:--|:--|
| 3 份判决书 | **各 1 条：只剩上诉期** |
| 2 份民事调解书 | **0 条**（无上诉期，分期付款是当事人义务） |
| 3 份保全告知/裁定 | 保全到期日 `2027/2028` + 续封申请截止日 |
| 2 份传票 | 开庭时间 |
| 交费通知书 | 缴费 `11-05` / `11-10`（靠收到日起算） |
| 民事裁定书 | 复议期 `11-01` |
| 补充证据材料（内含判决书） | 上诉期 + 向本院缴纳诉讼费 |
| 银行材料包 | 2051 已降置信，不默认勾选 |

## 关于「不回溯」（业务要求）

`capture_dates_for_source` 只有**单条短信**入口，**不存在批量重跑机制**。
代码上线后，只有新提交的短信会走新规则；已有识别任务与候选不受影响，无需数据迁移。

# 六、已知边界

- **自动触发在前端**（弹窗打开时调 capture-dates），不是后端 `completed` 时自动推。
  好处是「反复打开不重复烧 LLM」由幂等键天然保证，也不必给新短信加后台钩子。
  若要「完全不打开弹窗也识别」，只需在 `process_sms` 的 completed 之后**异步投递**
  一次 capture（不阻塞、不改状态），服务层已可直接复用
- **识别为空不算失败**：判决书/回证类文书确实常常没有未来日期，界面明说
  「没识别到关键日期」并给「再识别一次」，但不会自动重试（避免对无日期文书反复烧 LLM）
- **一条短信多份文书时按任务逐个确认**：日期来自哪份文书由律师自己看，
  不做跨任务合并——合并会丢失溯源
- **`classification_hint` 目前只会是空串**：短信三档类型都映射到 `other`，
  等于「有提示但粒度不够」。字段先落库，等短信侧分出更细的类型（如传票/判决书）即可生效
- **上诉期锚点是收到日，不是书记员确认的实际送达日**：系统用短信转发到手机的时刻
  作为送达日，与业务方口径一致；若将来接入送达回证时间，改一处锚点即可
