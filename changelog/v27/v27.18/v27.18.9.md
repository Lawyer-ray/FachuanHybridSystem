# v27.18.9 · 多 agent 架构地基：把「只有一个运行时」的隐含假设显式化

> 分支 `feat/agent-multi-backend-foundation`。
>
> **本版不加任何功能，行为零变化**。全部改动都是把「现在只有一个 agent（pi）」这个
> 隐含假设变成显式的接缝，为 12 月接入第二个 agent（DeepSeek Harness）、明年 3 月
> 可能的第三个做准备。
>
> 判断依据：从 1 个到 2 个是**质变**（并行、对比、失败组合都要处理），从 2 个到 3 个
> 只是量变。所以设计目标不是「支持 N 个」，而是**把 2 个做对，让第 3 个是复制粘贴**。

## 一句话定位

原来 `stream.py` 直接 `from ...pi.bridge import stream_events`，pi 是硬编码的唯一路径。
本版把它换成「按 `agent_kind` 查注册表拿后端」，并把三个以后会很贵的东西提前落地：
**统一寻址（run_id）、并发配额分层、后端无关的错误分类**。

# 一、AgentBackend 抽象（新目录 `apps/agent/backends/`）

## 分工边界（这是整层存在的意义）

抽象只把「跑一轮、吐 SSE 事件」收进接口，**其余全部留在编排层**：

| 职责 | 归属 | 为什么 |
|:--|:--|:--|
| 落库（`AgentMessage`） | 编排层 | 后端自己写库会出现两套审计来源，同一轮对话在库里出现两份或零份 |
| 审批（`approval_request`） | 后端自带回调链路，编排层注入事件流 | pi 走 extension → Redis → SSE，别的后端可能走 webhook；**协议不假设传输方式** |
| 池化 / 排队 / 取消 | 编排层 | 后端可以是常驻服务（HTTP）或一次性子进程（pi 就是每请求一进程），协议不假设生命周期 |
| 工具面 / 技能注入 | 编排层配置，`RunContext` 只传选择结果 | 哪个后端用哪些工具是产品决策，不是后端知识 |

## 为什么 `stream()` 只管一轮

pi 是「每次 prompt 起新进程，跑完即关」，DeepSeek Harness 更可能是常驻连接。
把 `start/close` 放进协议会让两者互相迁就——pi 要多一层假常驻，Harness 要为每次
运行重连。只要求 `stream()` 自包含，两种形态都能实现。

## 能力声明而非 `if agent == "pi"`

```python
@dataclass(frozen=True)
class BackendCapabilities:
    streaming: bool            # 有没有增量 token
    tool_calls: bool
    approval: bool             # 支不支持人工审批拦截
    compaction: bool           # 自己管不管压缩
    steer: bool                # 支不支持运行中插话
    concurrent_in_session: bool = False   # 能不能同会话并行（pi 是 False）
```

`concurrent_in_session` 默认 `False` 的保守性很重要：新后端默认不能并发，想并发必须
显式声明。编排层开「双答」时要两个后端都是 `True`，否则**退化为串行**（先跑完 A 再跑 B）
而不是直接拒绝。

# 二、run_id：统一寻址维度

## 为什么这是唯一「以后补很贵」的东西

原来审批 extension 只读 `FACHUAN_SESSION_ID`。同一会话有两个 agent 并行时，
两个进程读同一个 `SESSION_ID`，**审批弹窗无法区分是哪个 agent 的哪次调用**。

批准错 agent 的写入操作 = 用错授权。**这是安全问题，不是体验问题。**

## 格式与改动面

```
run_id = {session_id}:{agent_kind}:{seq}     例：abc-123:pi:1
```

三处改动，全部向后兼容：

| 位置 | 改动 |
|:--|:--|
| `services/chat/env.py` | `session_env()` 加可选 `run_id`，**非空才注入** `FACHUAN_RUN_ID`（不传 = 旧行为） |
| `pi/approval-gate.ts` | 读 `FACHUAN_RUN_ID`，审批请求体带 `run_id`（空串也带，让后端有稳定字段） |
| `sse_types.py` | 12 个运行级事件各加 `run_id: str = ""`，并重新生成前端 TS 类型 |

`seq` 现固定为 `1`：现在每会话同一时刻只有一轮在跑，多 agent 并行上线时再按会话内
并发轮次递增。**这是有意留的扩展点，不是遗漏。**

# 三、并发配额分层（`services/chat/budget.py`）

## 不做的后果

现有只有一个全局信号量（`DEFAULT_POOL_SIZE = 4`）。当同一会话要跑两个 agent 对比、
或主答之外再挂一个审校时，这些运行会与**其他律师的正常提问**抢同一批执行位——

别人什么都没做错却要排队，甚至拿到 `agent 执行位已满` 的报错。
**单人自测永远发现不了**（自己不会跟自己抢），但一上生产就是「开了对比之后大家都变慢」。

## 设计：按角色分档，主答永不被抢占

```
全机执行位总量 (= FACHUAN_AGENT_POOL_SIZE)
├── primary  主答          —— 保证配额，任何情况下不被辅助用途抢占
└── aux      对比 / 审校   —— 可降级：满了就提示「本轮未做对比」，不阻塞主答
```

三个关键取舍：

1. **aux 不是独立池，而是从总量里切一块**。独立池会让总进程数失控（N 个用途 × 各自 size）。
2. **primary 完全不做本地计数**——这是「对现有行为零影响」的保证。主答的并发语义与
   引入本模块前**完全一致**，真正的进程控制仍交给 `pool` 的 Redis 信号量。
3. **aux 满额立即拒绝而不是排队**。对比/审校是增强能力，卡住等 60 秒然后超时，
   体验远差于直接降级并提示。

默认 aux 比例 1/4（总量 4 时 aux 只有 1 席）。保守取值原因：对比功能刚上线时不知道
真实负载，宁可先紧后松。可用 `FACHUAN_AGENT_AUX_SLOTS` / `FACHUAN_AGENT_AUX_RATIO` 调。

# 四、三个后补的缝

抽象第一版完成后，审查发现**三个漏掉的缝**，全部补上：

## 缝 1：运行中控制没有位置

`live_sessions.py` 存的是 **pi 具体对象**，`/steer` 端点直接调 `pi_session.steer()`。
接入第二个 agent 后这张表会混两种不兼容对象。

补 `LiveBackendHandle` 协议（`run_id` / `kind` / `steer` / `follow_up` / `abort` / `get_stats`），
并给出四步迁移路径注释。本版**只定义协议不改造**——迁移放在接第二个 agent 时做，
避免现在扩大改动面。

## 缝 2：错误分类仍是 pi 专属

`stream.py` 靠 `except PiNotAvailableError / PiError / PoolQueueTimeoutError` 选文案，
等于把 `if agent == "pi"` 搬进了 except 子句。

补 `BackendErrorKind`（unavailable / busy / auth / rate_limited / context_overflow / unknown）
+ `BackendError`。**本版暂不切换**：现在统一会让「哪个后端坏了」的信息在翻译时丢掉，
等接第二个后端时再收敛，届时映射关系已写在注释里。

## 缝 3：同会话并发能力没声明

`live_sessions.py` 的注释写得很清楚：

> 同一会话同时只允许一个运行中的 pi 进程（第二条消息会让模型看到两份互相冲突的上下文）。

**这与「同一会话两个 agent 同时回答」直接冲突。** 把约束变成显式的
`BackendCapabilities.concurrent_in_session`。

# 五、会话级 agent 选择

```python
AgentSession.agent_kind = CharField(max_length=32, blank=True, default="pi", db_index=True)
# 迁移 0016，历史数据回填为 pi
```

```python
SessionIn.agent_kind: str = "pi"    # 客户端可指定
SessionOut.agent_kind: str = "pi"   # 前端可显示
```

**为什么 agent 可由客户端指定，而模型不行**：模型由服务端按 `LLMProvider` 解析
（客户端传了也不生效，所以契约里不留诱饵）；而 agent 后端是**用户的选择**——
同一律师可能拿不准的案子开两个会话分别问，偏好级配置表达不了这种意图。

**未注册的 kind 直接拒绝（400），不静默回退到 pi**：用户以为换了后端而实际没换，
会先归因于「新模型效果不行」，白白浪费一轮调试。

# 六、过程中修掉的两个真实缺陷

## 缺陷 A：`PiBackend.result` 挂在单例上会串

第一版把「本轮实际模型 / 上下文水位」放在 `self.result`，但注册表里存的是**单例**
（`apps.py` 启动时 `register(PiBackend())`），而 `stream_chat` 是并发的。

后果：两个并发会话互相覆盖对方的结果——表现为「A 会话看到 B 的模型名」，或成本记到
错误的会话上。**只在并发时复现，极难排查。**

修复：改为按 `run_id` 键控的字典 + `result_for(run_id)`。

## 缺陷 B：协议类型写窄了

`stream()` 声明返回 `AsyncIterator`，但编排层在客户端断开时要调 `aclose()` 主动关闭上游
（否则子进程等到 GC 才收），而 `AsyncIterator` 协议里没有这个方法。

修复：改为 `AsyncGenerator[StreamFrame, None]`，并引入 `StreamFrame = dict | None`
（`None` 是「本 tick 无事件」的让位信号——pi 读取循环必须让出一次控制权，
否则同一协程占着事件循环，审批事件永远进不来）。
