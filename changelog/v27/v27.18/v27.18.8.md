> 分支 `feat/copilot-p0-p1-upgrades`。
>
> 本版不新增功能，修的全是「功能正常但手感崩坏 / 英文环境测不出来」的问题。
> 三处都属于同一类失败模式：**没有任何报错、测试全绿、用户也说不清哪里不对**，

| 问题 | 症状 | 谁会发现 |
|:--|:--|:--|
| 输入法选词 Enter 穿透 | 打拼音时按 Enter 选词，**半句话被直接发出去** | 中文用户（英文用户永远复现不了） |

# 一、输入法 Enter 守卫（PIT-006）

## 根因不是「没判断 isComposing」

原实现（`use-composer-submit.ts:102`）是：

```ts
if (e.key === 'Enter' && !e.shiftKey && !e.nativeEvent.isComposing) {
```

看起来没问题，但 **WebKit 与部分中文输入法会先派发 `compositionend`、再派发同一次选词 Enter 的 keydown**。
等 keydown 到达时 `isComposing` 已经是 `false`，于是这次 Enter 被当成「用户要发送」，走了发送分支。

## 为什么这个 bug 特别难发现

| 原因 | 说明 |
|:--|:--|
| 开发者环境不触发 | 用英文输入法、或只粘贴文字的开发者，**永远复现不了** |
| 不是必现 | 取决于输入法实现与浏览器版本，所以「我试了没问题」不构成反驳 |
| 无报错 | 代码路径完全正常，只是触发的时机不对 |

## 修法：三重判定 + 80ms 尾随窗口

新增 `hooks/use-ime-enter-guard.ts`：

1. `composingRef` —— composition 区间内（事件顺序不可靠时的主依据）
2. `event.nativeEvent.isComposing` —— 标准标志
3. `event.keyCode === 229` —— 老 WebKit 在合成期间把 keyCode 钉成 229；某些输入法干脆不派发 composition 事件，只剩这条可依
4. **`compositionend` 后 80ms 内的 Enter 也算 IME Enter** —— 覆盖「先 end 后 keydown」这个跨事件窗口

两个容易做错的细节：

- **合成中的 Enter 不要 `preventDefault`**（那是输入法在处理，抢了会打断选词上屏）；
  只有 compositionend 后的**尾随** Enter 才吞掉默认行为。
- 窗口只覆盖紧邻事件：正常用户再按一次 Enter 落在窗口外，不受影响。

## 顺带修掉一个真实 bug：Shift+Enter 被 slash 菜单吃掉

`slash.onKeyDown` 的 `case 'Enter'` 不看 `shiftKey`，所以**菜单开着时按 Shift+Enter 会选中菜单项**而不是换行。
现在在问菜单之前就短路：Shift+Enter 是输入法/浏览器的事，不该进入任何业务逻辑。

# 二、流式平滑放字（PIT-007 / PIT-009）

## 为什么不直接渲染 delta

原实现把 `message.content` 原样交给 `<ReactMarkdown>`，于是：

- token 到达频率不受控 → 网络一抖动就「卡一下再猛吐一段」
- **每来一个字就重解析整篇 markdown** → 成本随回复长度线性增长，长回复明显掉帧
- 表格流式吐到一半时，半行 `| a | b` 会先被当成段落，补全分隔行后才变表格 → 每格闪一次

## 做法：按帧节流 + 码点安全 + 表格整行

新增 `lib/smooth-stream.ts`（纯函数）+ `hooks/use-smooth-stream-text.ts`：

| 参数 | 值 | 理由 |
|:--|:--|:--|
| 放字节拍 | 每 2 帧（~30Hz） | 每帧重解析 markdown 太贵 |
| 每拍步长 | `max(2, 积压/8)` | 积压越多放越快，落后不超过约 250ms |
| 直接到位阈值 | 积压 >2000 或全文 >8000 | 切回旧会话 / 网络一次吐一大段 / 长回复不该平滑 |
| 码点推进 | `advanceCodePoints` | **不把 emoji、生僻字（𠮷）的代理对切成半个** |
| 表格行 | `nextStreamCut` 整行放 | 半行表格会闪，见上 |

## 最关键的一处工程细节

放字循环的 `useEffect` **依赖数组只能有 `active`**，全文从 `fullRef` 读。

> 随每段新字重启的话，字来得比两帧密时永远数不到拍点，放字会被饿死。

这是那种「写完看着对、上线才发现不动」的实现陷阱，已写进注释与测试（用例名就叫「不会被饿死」）。

## 硬不变量

**返回值任何时刻都必须是 `full` 的前缀。**

违反它 markdown 会原地重排（甚至把表格结构打乱），视觉上比不平滑更糟。
因此三条逃生通道必须保留：非直播原样返回 / 快照改写（`full` 不再以 `displayed` 开头）直接到位 / 积压超限直接到位。

# 三、流式 Markdown 分块（P1-5）

## 为什么要分块

平滑放字解决了「节奏」问题，但只要每拍仍把**整篇**交给 ReactMarkdown，解析成本就还是随长度线性涨。
分块后成本退化成「一块的长度」。

## 为什么分块是安全的：只在「一定安全」的空行处切

新增 `lib/stream-blocks.ts`。CommonMark 的块级边界只可能来自空行、围栏代码块、容器块（列表/引用）、
链接引用定义与脚注定义。这些来源里只要有一个可能跨越空行，就**放弃切分**（宁可慢，不能错）。

否决清单：

- 围栏代码块内（含未闭合的流式中途）
- 收尾围栏带语言名（` ```js ` 只是块内一行代码，不是关闭）
- 松散列表（项间有空行）、缩进续行、引用块
- 链接引用定义 / 脚注定义
- 原始 HTML 块内部（`<pre>` 等，空行不结束它）

## 修正一个真实 bug：HTML 块被从中间劈开

初版只在**切点处**判断「是否处于未闭合 HTML 块」，漏了「HTML 块开在切点之前」这种形态：

```
a\n\n<pre>\nraw\n\nstill raw\n</pre>
```

被劈成 `["a\n\n", "<pre>\nr", "aw\n\n", "still raw\n</pre>"]` —— 一整块 HTML 碎成四片。
修法是判断切点是否落在**任意** HTML 块（闭合或未闭合）的内部，而不只看未闭合。
已加回归用例锁死。

## 两条不变量（测试逐条验证）

1. `blocks.join('') === text` —— 一字不差，换行不丢不重
2. 各块单独解析的结果拼接，等价于整篇一次解析 —— 保证方式就是上面那份「只在对块级结构确定保守时才切」

# 四、两个长期防线

## 1. 已知坑库 `docs/harness/pitfalls.md`

编号 `PIT-NNN`，**只增不删、只增不改号**；已被根治的改状态而非删条目（复发判断需要知道它曾经怎么发生的）。

三层设计让它不退化：

| 层 | 内容 |
|:--|:--|
| §0.2 八大失败家族 | 假成功比失败更贵 / 错误被吞 / **静默退化** / 双份真相 / **门禁没通电** / 环境与路径 / 契约漂移 / 并行写者 |

关键约束：**代码注释里引用编号**。没有被引用的坑库会退化成没人翻的日志。

已登记 18 条，其中 PIT-006～PIT-010 就是本版修的这几类前端静默退化。

# 五、否决的方案

| 方案 | 否决理由 |
|:--|:--|
| 把 `isComposing` 判据加上 `timeStamp` 负值也拦 | 负值意味着该 Enter 发生在合成结束**之前**，此时合成态已结束、`composingRef` 也为 false。拦它会把「合成结束后用户立刻正常按的 Enter」一起误吞，制造新 bug |
| 为修中文加粗去重写整个 CommonMark 块级状态机 | 那类方案约 500 行，其中 250 行只为「别在代码块里插哨兵」。一个 fence 计数器能覆盖 99% 真实 markdown，代价小得多（PIT-008 已记录取舍） |
| 流式全部改成虚拟滚动 | 与本版三个问题无关，属于另一个量级的改动 |
| 分块时用内容 hash 做 key | 块只会在末尾增长或分裂，下标 key 已能让前缀块稳定 bail out；hash 每次都要重算，反而更贵 |
