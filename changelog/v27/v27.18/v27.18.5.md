## 背景：为什么是 mixin 而不是「拆成同名子包」

这是本版最容易做错的判断，先说清楚。

两个文件都有一批测试用 `patch("...folder_scan_service.Contract")` 这种**按具体绑定位置**打桩的写法
（folder_scan 53 处、oa_sync 7 处）。Python 的模块名字绑定是**值拷贝而非晚绑定**：

```
情形一：子模块自己 from apps.contracts.models import Contract
  → patch("folder_scan_service.Contract") 不影响到子模块 globals → 失效
情形二：Model 留在包顶、子模块 from . import Contract
  → 子模块 import 时把引用拷贝进自己的 __dict__，运行期 patch 包顶不传播 → 失效
```

即「拆成同名包」**两条路都会打掉全部 patch**，需同步改 6 个测试文件。

解法是把方法体搬走、但**保留本模块为业务名的唯一定义点**——mixin 内经 `self._host` 回查宿主模块 globals：

```python
class ContractFolderScanService(_ScanTaskMixin, _ImportMixin, ...):
    @property
    def _host(self) -> Any:
        return sys.modules[__name__]          # 运行期回查，patch 打在模块属性上，能命中

# mixin 内
def _ensure_contract_exists(self, contract_id: int) -> None:
    if self._host.Contract.objects.filter(id=contract_id).exists():   # ← 调用时属性查找
        return
```

这条路在本仓库有大量先例（本次改动前已有 **97 个** `*mixin*.py`，含 `admin/mixins/archive_mixin.py` 765 行、
`automation/services/sms/` 下的 500 行级 mixin），而「同名 `.py` → 包」`git log --diff-filter=D` **零先例**。

本次新增 **9 个 mixin + 2 个类型契约文件**。

> 顺带纠正一个流传的说法：`archive_mixin` 从来不是「mixin 会破坏补丁点」的反例——
> 它的测试 `patch("apps.contracts.admin.mixins.archive_mixin.FinalizedMaterial")` 一直正常工作。

### 三条纪律（已写进每个 mixin 的模块 docstring）

1. mixin 内引用被 patch 的名字**必须写 `self._host.Contract`，禁裸名**——裸名解析到 mixin 自己的 globals，会 `NameError`。
2. `_host` **不要用 `@staticmethod`**——`SERVICE_STATIC_METHOD_RATCHET = 12` 已满额，用 `@property`。
3. mixin 文件**必须与主模块同目录**——`_scan_sunk_function_called_as_method` 按 `pkg_dir.glob("*.py")` 只扫一层。

### mypy 不能退化成 Any

第一版直接把 `_host: Any`，mypy 立刻报 **68 个** `no-any-return` / `attr-defined`——所有
`self._host.Contract.objects...` 全部退化成 Any，等于把这条资金/归档路径的类型检查关掉。

改用两个 Protocol 精确描述：

- `_HostGlobals`：宿主模块 globals 里**被 patch 且被 mixin 引用**的名字（逐个列类型）
- `_ScanServiceContract` / `_OAServiceContract`：跨 mixin 互调的方法签名 + 共享类常量 + `__init__` 注入的协作者

结果：**256 文件 0 error**，与重构前一致。

  - 已有测试直接抓到（`assert PosixPath('None') is None` 失败）。改回保留 `None` 语义：
    `return str(p) if p else None`，与原调用点 `if pdf_path_str: ... else None` 一致。

## 明确没做的（附理由）

- **WS6 局部 N+1 优化：不做**。实测 `_learn_from_import_correction` 里那个关键词循环平均只产生
  **1.4 次** roundtrip（计划估 3–5 次），且它是「用户改了归档项编码」才触发的纠错分支，
  绝大多数导入根本不进循环体。收益比原估计还小。
- **不新建 `contracts/ports/`**：`core/dependencies` 已有 73 个 `build_*` 工厂可复用，
  且 client / reminders 两份已完成计划都明文否决过再引入第三套平行端口机制。
- **intake_scanner 不搬去 message_hub**：它的**产出域**是 contracts（产出 `PaymentIntake`/`IntakeStatus`
  并写 contracts 的表），被 message_hub 调用不改变归属。
- **不动 `contract_match_v2`**：它没有构成 import 环——全仓 2177 模块的模块级 SCC 里**跨 app 环 = 0**，
  依赖是单向的 `intake_scanner → contract_match_v2 → intake_eligibility → contracts.models`（叶），
  6 种 import 顺序实测全 PASS。app 包粒度上确有双向边，但全仓同类有 128 个，不是独有病灶。
