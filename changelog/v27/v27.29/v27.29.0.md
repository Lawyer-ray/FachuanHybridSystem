## 做了什么

### 1. 判定：先分清「硬红线违规」和「该不该拆」

用仓库自带的 `tmp/frontend-audit-v2/guard-v2.py metrics`（与 v27.23.3 审计同口径）先量，再派 5 个只读 agent 分 4 个互不重叠的簇逐文件通读，判定标准是 `docs/harness/frontend/index.md:126`「**单文件是否膨胀** 与 **是否单一职责** 两项同时满足才合资格」，不是行数。

结论：**0 个文件违反硬红线**；23 个软红线文件里 **8 个明确判定不拆**（单一职责、只是长），典型反例已写进各文件头或本合同：

| 不拆的文件 | 理由 |
|---|---|
| `workbench/api/cases.ts`(424) | `api/index.ts:11-15` 已明文决定「归案整条链路留在同一文件」，拆分点=后端域 |
| `demo-nonlit/nl1`+`nl2`(421/382) | 纯字面量数据集，phaseId / revId 的跨块对齐不变式只能一眼核对 |
| `reader/PhaseTable.tsx`(369) | 三处可切出的 cell 各只用一次、无复用，切文件属机械切行 |
| `bank-litigation/ui.tsx`(344) | 12 个视觉原子件，40+ 引用全在本 feature 内；按原子切 12 个 30 行文件正是规范反对的散碎 |

两条**拆分纪律**（比拆本身更重要）：

- **一律保留原导出面**：`types.ts`/`OfficeView.tsx`/`use-assign-launch.ts` 全部 re-export，30+ 处消费方 import **零改动**；只有 `auto-split-helpers.ts` 留了显式 barrel 并写明「新代码请直接引子模块，这个文件不该再长内容」。
- **纯类型文件里不许躺可执行代码**：`material-prep/types.ts` 里混着 `normalizeCloudSelection` / `toggleCloudEngine` / `normalizeSegmentStrategy` 三个运行期函数，没人会去类型文件里找逻辑，一并挪进 `recognition-prefs.ts`。

顺带删掉 `hintNamesOf`（生产代码零调用方，只有自己的测试引用）与对应 9 条用例。

### 3. 诉讼地位英文：根因在后端，不在前端

```
case_schemas.py:127  "legal_status": getattr(it, "legal_status", "")   # 放进 dict 的是代码值 plaintiff
party_schemas.py:55  resolve_legal_status 的 dict 分支 → 直传        # 假设 dict 已是序列化形状
CaseSection.tsx:169  {g.status}                                       # 于是渲染出 plaintiff
```

`get_legal_status_display()` 一直存在，只是「模型 → dict」这一跳没调用。同一张卡的 `status`/`current_stage` 走 `resolve_*` 是中文，所以症状是**半中半英**。新增 `CaseOut._party_status_label()` 在此处翻译，带「无 getter / 空值」降级。

`tests/ci/unit/cases/test_case_schema_party_status.py` 5 条纯函数用例（不建库）钉住：中文标签、空值、无 getter 降级、dict 输入不重复翻译、原有键不丢。

### 4. 规范漂移：测试文件的规模豁免只活在配置里

`eslint.config.js` 的 `max-lines` ignores 了 `**/*.test.*`，但同一 block 的注释写着「硬红线对全仓库无条件生效……不能豁免」，而 `docs/harness/frontend/index.md` 的措辞是「任何单个**源码文件**」——三处口径不一致。

处理：**保留豁免，把理由写进两处**。测试文件长度由**用例数**决定而非职责数（实测源↔测试行数比 2.3–2.5×：346 行 `store.ts` ↔ 876 行测试），拿行数当代理指标会逼人把正常的行为测试切碎；>450 的测试单列 `D3` 台账，按既定的「拆测试属独立工程」处理。配置注释同时把 test/d.ts 标成「适用范围声明，不是 ratchet 条目」。
