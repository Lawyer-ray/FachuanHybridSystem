## ① 成本归属：`LLMCallRecord` / `AgentRun` 加 provider 维度

**问题**：报表只能按「模型 / agent」聚合。同一个模型可能由多个平台提供、同一个平台也被
多个 backend 用 → 「钱花在哪个平台」答不出来；预算与网关账单对不上。

**改动**
- `LLMCallRecord.provider` / `AgentRun.provider`（两个**可空**字段，迁移
  `core/0040`、`agent/0025`，已应用到开发库）。历史行留空串，报表显示「未知」，
  **不按默认平台回填**——回填等于把别的平台的账算到它头上。
- 新增 `apps/core/llm/provider_lookup.resolve_provider_name(model)`：复用
  `_pick_provider`，**与真实发请求的选平台口径完全一致**（不一致的归属比没有更糟）；
  走服务层 60s 缓存，**永不抛**（统计旁路不能拖垮调用记录）。
- `tracking.record_llm_call` / `arecord_llm_call` 集中补 `provider`（4 个调用点无需改动）；
  `persist.persist_run` 落 `AgentRun` 时补 provider。
- `usage_stats.by_provider()`：与 `by_agent` 同构，SQL 里把空串归一成「未知」。

**测试**：`test_provider_attribution.py`（4 例：按模型白名单匹配、未知模型回落、
无平台返回空、解析异常不抛、记录带 provider）+ `test_agent_usage.py` 补 2 例
（按平台分组、空值显示未知）。

## ③ `fallback_models` 运行时接线

配置侧上一轮已修（能加载、Admin 可编辑），但只有 pi 真的降级。现在：非流式
`chat` / `achat` 在**可重试**错误（超时 / 网络 / APIError）时按链换模型重试；
参数类错误不降级（换模型只会同样失败）；排除自身避免空转；**流式不降级**
（已吐出的 token 无法回退，宁可报错）。

**测试**：`test_model_fallback_chain.py`（5 例：超时降级到下一模型、链走完仍失败则抛出、
无链不降级、排除自身、异步同语义）。
