# v27.20.14 — 主对话路径 Key 调度：压测结论「不需要租约」（关闭 TECH-DEBT ⑤）

> 承 `v27.20.13`。**仅压测与文档**，无代码改动。

## 测什么

担心的是：pi / dsh / openai-agents 在外部进程里直连网关，拿不到请求边界，
单栏提问并发一高就会把同一把 Key 压过 `max_parallel_requests=3` → 429。

## 实测（真实网关：10 把 Key × 每把 3 并发 = 30 槽位）

| 同时在飞 | 短请求（16 token，~0.4s） | 真实轮次（~250 字，~2s） |
|---|---|---|
| 10 | 10/10 | 10/10（2.0s） |
| 20 | 20/20 | 20/20（1.9s） |
| **30（= 全部槽位）** | **30/30** | **30/30（2.4s）** |
| 40（超容量 133%） | 3 个 429（`retry-after: 60`） | — |

三种选 Key 策略在 ≤30 并发下**全部 100% 成功**：纯轮转（旧）、健康感知（现状）、
租约（模拟 ⑤）。到 40 并发时租约反而更差（5 vs 3 个 429）——因为
`KeyScheduler.allocate` 在饱和时本就是「循环复用、best-effort」，
它造不出第 31 个槽位。

## 结论

- 出现 429 的瓶颈是**总槽位 = key 数 × 每 Key 并发**，不是"挑得不准"；
  租约（⑤）解决不了容量，只会引入租约泄漏 / 外部进程崩溃 / TTL 兜底这些真实风险 → **不做**。
- 提高容量的正确动作：**加 Key**（每加一把 +3 槽位），而不是改调度算法。
- 重开条件写进 `TECH-DEBT.md`：若出现「并发 < 30 却频繁 429」，说明挑选确实偏斜，再做。
