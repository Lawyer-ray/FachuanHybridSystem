# v27.20.12 — rpm/tpm 额度模型（滑动窗口，默认只观测不拒绝）

> 承 `v27.20.11`。对应 `TECH-DEBT.md` ②。

## 为什么

网关（LiteLLM）除了「每 Key 并发上限」还有每分钟请求数 / token 数限制，我们这边只有
并发一个维度 → 长文档/大 prompt 场景会直接吃 429 而不知道为什么，也无法预判。

## 改动

- **`LLMProvider.rpm_limit` / `tpm_limit`**（迁移 `core/0041`，默认 0 = 不限，已应用到开发库），
  Admin「API 配置」区可编辑；`OpenAIProviderConfig` 与 `LLMProviderService` 同步加载。
- **`KeyPool` 滑动窗口**：每 Key 一条 `deque[(ts, tokens)]`，60 秒窗口求和。
  **刻意不做分钟桶**（LiteLLM 用分钟桶是因为它还有单请求 token 预检兜底；固定窗口在
  12:00:59 与 12:01:01 的瞬时速率可以翻倍）。
- **默认只观测不拒绝**：超限时只 `logger.info` 一次并计入 `rate_snapshot()`；
  `FACHUAN_KEY_RATE_LIMIT_ENFORCE=1` 才真的跳过该 Key。理由：额度没有探测手段
  （网关的 `x-ratelimit-*` 头我们尚未解析），填错就拒绝会误伤正常律师。
- `release(..., tokens=N)` 记录本次消耗（来自响应的 `usage.total_tokens`），供 tpm 统计。
- `shared_pool(...)` 新增 `rpm_limit` / `tpm_limit` 参数并注入池 —— 调用方（`openai_compatible`、
  检索通道）逐参数对齐，避免「参数不一致 → 静默生成第二个池」的老问题。

## 测试

`test_key_pool_policy.py` 补 4 例：观察模式计数但不拦截、执行模式跳过超 rpm 的 Key、
token 计入窗口、0 = 不限。
