## 一、最值钱的一条：`max_retries=0`（S）

`openai` SDK 默认 `DEFAULT_MAX_RETRIES = 2`，且**遵守 `retry-after`**。而律所网关实测
429 会带 `retry-after: 60`（`key_scheduler.py` 里记的 60.96 / 130.20 / 241.02 秒全是 60 的整数倍）
——于是 SDK 在**同一把已限流的 Key 上**睡两轮，**我们自己的换 Key 与 30s 冷却根本没机会执行**。

改：`openai_compatible.py` 两处客户端构造加 `max_retries=0`，把重试权收回本层
（换下一把 Key 才是正确动作）。这一行同时让 `KeyPool` 的冷却第一次真正生效。

## 二、Key 冷却分级（对齐 LiteLLM 的状态码白名单）

旧实现是二值 `release(success=False)`：**任何异常**都让 `(Key, 模型)` 冷却 30 秒。后果是自伤：

- 一次用户超长 prompt 触发 400 → `for _ in range(len(pool.keys))` 把这个坏请求在**每把 Key 上重放一遍**
  → 整池一起冷却 → 下一个正常用户看到「该平台全部 API Key 均不可用」（审计 P0-4）；
- 一次 502 抖动就把一把 Key 停 30 秒，10 把 Key 遇一次峰值会连锁降容。

改（`key_pool.py`）：

- **状态码白名单** `COOLABLE_STATUS = {401,402,403,404,408,429}` + 5xx + 传输层异常 → 才冷却；
  其余 4XX（400/413/415/422）与解析/业务异常 → **不计数、不冷却、不换 Key**（换也只会重放坏请求）；
- **连续 `FAILS_BEFORE_COOLDOWN=2` 次**才冷却（LiteLLM `allowed_fails` 的同族语义），成功即清零；
- **冷却时长可被 `retry-after` 覆盖**并夹在 [5, 300] 秒（网关给 60 就冷却 60，不再 30 秒后回去挨打）；
- 两个阈值都可环境变量覆盖（`FACHUAN_KEY_COOLDOWN_SECONDS` / `FACHUAN_KEY_FAILS_BEFORE_COOLDOWN`）；
- 新增 `KeyPool.snapshot()`：**不含 Key 明文**，只出「第几把 / 在飞数 / 是否冷却 / 剩余秒 / 失败次数 / 原因」。

`openai_compatible.py` 的 8 个 `release` 点全部改为传 `error=`（由池统一判定，
避免每个调用点各写一份漂移的白名单）；**非 Key 故障直接抛出原始错误**，不再换 Key 重放。

## 三、自适应并发补 app-limited 守卫（学 Netflix Gradient2）

`adaptive_limiter.py` 原来只要窗口 p50 贴近底噪就上调。低流量时样本全是「不排队」，
据此加并发 = 凭空调高 → 闲时爬到 30、忙时被打回，来回锯齿（且把 `_base` 污染）。

补：窗口内记录最大在飞数，`peak * 2 < limit` 时**样本不足，不动**（对照
`Gradient2Limit` 的 `inflight < limit/2` 直接返回）。测试改用「先占半个窗口再释放」的方式
模拟真实并发，并新增 app-limited 用例。

## 四、Admin 提示并发口径（不改模型、无迁移）

`concurrency_per_key` 是**按进程**记账的，生产 2 worker + 1 共享 MCP = 实际 ×3。
在 Admin「API 配置」区加说明：填 3 时网关可能看到 9 个在途，撞 429 要按 worker 数折算。

## 五、暂不做（已评估，留档）

| 事项 | 结论 |
|---|---|
| 给 Key 池上 Redis 做跨进程精确并发 | **不做**：LiteLLM 那套预留机制是为无状态多副本网关写的；我们单进程池 + `key_scheduler` 已论证过，最坏只是各 worker 独立记账，不会更差 |
| 照搬 LiteLLM `DualCache` 双层缓存 | **不做**：Redis 回填会把配置生效窗口从 30s 悄悄拉长到 60s，违背「Admin 改完立刻生效」红线 |
| 照搬 `lowest_tpm_rpm` 的分钟桶 | **不做**：固定窗口边界效应明显（12:00:59 与 12:01:01 速率可翻倍）；真要做 tpm 应做滑动窗口 |
| 照搬 Netflix `initialLimit=20` | **不做**：那是长连接 RPC 的参数；我们冷启动首次调用 18s，从「每 key 1 并发」起步更贴合实测 |
| 引入 `circuit_breaker.py` 三态熔断 | **不引入**（且它现在是半死代码：键是后端名，一次 400 累计 5 次能熔断整个后端）——熔断语义已下沉到 per-key |
| 主对话路径绕过 KeyPool（审计 P0-1）、跨进程、成本归属（P1-11） | **下一步**：需要改 pi/dsh/openai-agents 三条路径 + 数据模型，单独排期 |
