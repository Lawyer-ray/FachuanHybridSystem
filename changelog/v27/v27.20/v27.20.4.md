# v27.20.4 — 兜底检索改为复用 Admin「AI 平台」凭据（不再配第二份密钥）

> 承接 `v27.20.3`（联网检索三通道 + 熔断 + 缓存）。涉及 `backend/mcp_server`。

## 一句话定位

| | 上一版 | 现在 |
|:--|:--|:--|
| 网关地址 | `.env` 里配 `FACHUAN_FIRM_SEARCH_URL` | 由 Admin → AI 平台的 `base_url` 换同主机 MCP 路径推导 |
| 凭据 | `.env` 里配 `FACHUAN_FIRM_SEARCH_KEY`（**单把**） | 复用平台配置里的**全部 key**，经与模型调用**同一个** Key 池轮询 |
| 换 key | 要改两处，漏一处就静默失效 | Admin 里改，几秒内生效，无需重启 MCP |
| 并发上限 | 检索另起一套计数 → 与模型调用叠加，翻倍顶穿网关限额 | 共用同一个池实例，限额与失败冷却都共享 |

## 后端

#### 重构 · `firm_search` 的平台配置解析

- 同一台 LiteLLM 网关既提供 `/v1`（模型）也提供 `/WebSearch/mcp`（检索），
  用的就是**同一把 key**——所以再让运维在 `.env` 里配一份密钥是把一个事实写成两处。
- 默认路径：`LLMProviderService.get_providers()` → `_pick_provider(hint)`（与模型调用
  同一口径：`FACHUAN_FIRM_SEARCH_MODEL_HINT` 指定模型名，留空取优先级最高的启用平台）
  → `base_url` 的 `scheme://netloc` + `FACHUAN_FIRM_SEARCH_PATH`（默认 `/WebSearch/mcp`）。
  **只换路径、不动主机端口**：改 host 或补默认端口都是猜；`base_url` 缺 scheme/host
  时宁可放弃这条通道，也不拼一个错地址去撞。
- key 池：`shared_pool(provider.name, provider.api_keys, provider.concurrency_per_key,
  provider.key_model_scopes)`——与 `openai_compatible._key_pool` **逐参数一致**，因此
  落到同一个池实例。参数差一个就会静默变成两个池（限额翻倍、冷却不共享），
  所以有专门的用例断言「两个调用点拿到的是同一个对象」。
- 401/403/429 换下一把 key 重试一次（`release(success=False)` 顺带让该 key 冷却 30s），
  其余错误不重试——避免把一次网络抖动放大成多把 key 一起冷却。
- 环境变量 `FACHUAN_FIRM_SEARCH_URL` + `_KEY` 保留为**逃生口**（指向别的网关 / 本机
  联调 / 单测注入），两者齐备时优先于平台配置；`_KEY` 现支持带不带 `Bearer ` 前缀。

#### 测试

- 新增 `TestConfigResolution`（7 例）：地址推导（含 `/v1/` 尾斜杠、自定义路径、缺
  scheme/host 一律拒绝）、env 逃生口优先且剥离 `Bearer`、平台配置复用（10 把 key →
  全量进池）、平台无 key / 无平台时通道关闭、**Key 池与模型调用同一实例**、
  401 换 key 重试（断言两次 POST 用的是不同 key）。
- `tests/ci/unit/conftest.py` 追加 `_active_providers` 屏蔽：单测的测试库里没有
  `LLMProvider`，真去查库既慢，也会把「查库异常」混进失败原因。

#### 说明

- 平台配置的服务层缓存 TTL 是 5 分钟，但保存 `LLMProvider` 会触发失效，
  所以「Admin 里换 key」的实际生效延迟是**下一次请求**，不是 5 分钟。
- 检索与模型调用共用 Key 池意味着：某把 key 在检索上被限流，会用掉它 30 秒的
  冷却窗口（对模型调用同样生效）。这是刻意的——共用限额的前提就是共用冷却，
  否则会出现「模型侧以为可用、检索侧刚刚被打回」的错配。
