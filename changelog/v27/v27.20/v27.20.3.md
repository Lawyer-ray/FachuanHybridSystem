# v27.20.3 — 联网检索：三通道 + 熔断 + 结果缓存（搜狗 IP 级封禁止血）

## 后端

#### 新功能 · `web_search` 三通道自动切换（桌面 → 手机 → 律所兜底引擎）

- **起因（实测数据）**：搜狗免费 HTML 接口是 **IP 级**封禁——302 →
  `/captcha/?m=1&antip=web_sh2`，页面直接写出被封 IP。共享 MCP 下全所共用一个出口 IP，
  一个人搜得急就是**全所搜索一起挂**。生产库近 7 天真实调用：**33 次被拦 / 6 次成功（15%）**；
  今天本机实测 12 条顺序查询 12 条全拦、8 连发 0 成、6 路并发 1 成，封禁恢复曲线 10 分钟内
  20 次探针全部失败。
- **通道 2 · 搜狗手机**：同一时刻 `wap.sogou.com` + 移动 UA **仍然可用**（307KB 正常结果页）。
  解析按 `div[class*="card_normal_result"]`（CSS Modules 哈希类名只稳定前缀）取标题/摘要，
  真实地址直接从跳转参数 `url=`/`pcurl=` 里解出来——比桌面端的不透明 `/link?url=<token>`
  更可靠；日期从正文尾部（`央广网 2026-01-12`）抽。同一结果的「标题卡 + 正文卡」按 URL 去重。
- **通道 3 · 律所兜底引擎**：律所 LiteLLM 网关上的百炼检索（`FACHUAN_FIRM_SEARCH_URL/KEY`）。
  实测 **15/15 可用**、2–3 秒（首次冷启动 18s）。协议细节按实测定案：响应是 **SSE** 不是 JSON、
  工具名是 `WebSearch-bailian_web_search`、返回体是 `{"status":0,"pages":[...]}`。
  未配置时静默跳过（开发机没有网关不该报错）。
- **兜底结果的权威性问题在工具层解决**：实测 148 条结果里 gov.cn 只有 9 条，首位常是
  百家号/头条/搜狐。因此按 **URL host** 分四层（官方/法院 → 专业法律库 → 自媒体 → 其他）
  稳定重排；**没有任何官方或专业来源时**在结果里插一行显式提醒「不得直接作为法源」。
  分层必须看 URL 而不是展示名——`source` 是「百度」「人力资源和社会保障部」，拿它匹配
  `gov.cn` 恒不命中，会让「官方优先」静默失效（写测试时先踩了一遍）。
- **体量纪律**：兜底引擎单条 `snippet` 实测可达 **47,964 字**（整篇法条/文章）。统一按
  600 字/条截断（附「全文请用 fetch_url 读原文」，正文本来就该走分块续读），整段输出再按
  18KB 字节预算收口——超预算时**减少条数并改写口径**（「已保留前 N 条」），不拿一半冒充全部。

#### 新功能 · 通道熔断 + 结果缓存（`tools/web_search/resilience.py`）

- **熔断**：反爬 10 分钟 / 解析 0 条 5 分钟 / 瞬时网络错误 1 分钟 / 兜底引擎 2 分钟，
  冷却期内**不再发请求**。此前没有熔断时，模型看到「被反爬」会按技能提示「换个关键词重试」——
  生产库会话 268 在 3 分钟内连打 **20 次全部被拦**：既烧掉进程级 20 次/分配额，又持续往
  封禁页送请求、延长封禁。
- **结果缓存**：`(query, page, max_results)` 规范化后 TTL 10 分钟。多答双 lane（pi +
  openai-agents）对同一问题各搜一次（实测同秒并发），现在只真正检索一次。
- 两者都是**优化性状态**（丢了只退化成多打一次请求，不会给出错误答案），因此进程内、不持久化。
- **全部通道失败时如实归因**：逐条列出「哪个通道、因为什么失败」，并明说「这不代表互联网上
  没有相关信息」——本系统文本不套外部内容包裹（与 `fetch_url` 的 `_WRAPPER_HEADER` 纪律一致）。

#### 修复 · `fetch_url` 抓搜狗 `/link?url=` 失败时**静默返回搜狗首页**

- 实测：跳转 token 失效或与检索会话不绑定时，搜狗 302 回自家首页，老实现把首页导航当正文
  返回 `{"ok": true, "text": "<494 字：网页 微信 知乎…>"}`——模型会把它当判决书摘要。
  这是 `fetch_url` 模块 docstring 里明令禁止的「静默错内容」，比失败更糟。
- 新增 `reason: "unresolved_redirect"`：仅当「输入本身是 `/link` 形式」且「最终落在搜狗域名」
  且「没解析出真实地址」时才判定——跳转解析成功但目标站抓取失败、以及用户直接要读某个
  搜狗页面（非 `/link`）都不受影响（后两条各有回归用例）。

#### 配置

- `.env.example` 新增 `FACHUAN_FIRM_SEARCH_URL / _KEY / _TIMEOUT`（含「建议用所级专用 key
  而非个人 key」的说明：实测该 key 是 `user:xxx/main` 个人 key，`max_parallel_requests=3`）。
- 熔断时长与缓存 TTL 可用 `FACHUAN_SEARCH_COOLDOWN_*` / `FACHUAN_SEARCH_CACHE_TTL` 覆盖，
  默认值即本次实测定档。

#### 说明

- **手机通道只支持第 1 页**，兜底引擎无翻页：`page > 1` 只有桌面通道参战（返回 None 表示
  「通道不适用」，不算失败、不熔断）。
- **通道顺序刻意串行**而不是并行：桌面 0.3s 且来源最权威，先试最划算；串行还能避免一次问题
  打三个出口（封禁暴露 ×3）。
- 未接 `webparser`（律所网关的另一个 MCP）：实测 10 个目标 6 个失败，其中 `court.gov.cn`
  挂 122 秒后 500、PDF 直接 500、微信公众号把连接打断；唯一看起来成功的
  `flk.npc.gov.cn` 抓回来的是**首页导航壳**（16KB、`第X条` 匹配 0 条）——又一处「看起来成功、
  实际什么都没给」。要读 JS 站点应仓库内已有的 CloakBrowser 写站点适配器，而不是接这个远端解析器。
