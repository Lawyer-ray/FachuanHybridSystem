# v27.31.1 · 技能从「只能自己用」到「全所可用、审批发布、模型能自己找到」

> **版本判定**：§1.2 同一条主题线的延续。前一条 `v27.31.0` 建的是**个人技能**骨架
> （注册表 / CRUD / 抽屉 / `/skill:` 点名）；本次是同一个能力轴上的下一步——把技能
> 从「个人 + 落盘注入 pi」升级为**三级作用域 + 双轨审批发布 + 全后端统一 DB 直出**，
> 用户动作、文件集合、验收口径都是上一条的延续（`apps/agent/services/skills/**`、
> `frontend/src/features/copilot/**`）→ 第三位 +1。

## 一句话

以前技能只能自己写自己用，而且只有真在 pi 里才能生效；现在律师可以把自己的做法提交到
所里、由管理员看过 diff 后发布，**全所下一轮对话就能用**；模型不再需要律师每次点名——
系统提示里有一份技能索引，它会自己决定去读哪一份全文。

## 用户拿到的四件事

| 之前 | 现在 |
|:-|:-|
| 技能属于个人，想给同事只能让人复制粘贴 | 三级作用域：个人 / 团队 / 所内；本所全员可见，提交后由本所管理员审批发布 |
| 改了就是改了，线上立即换成没审过的内容 | **双轨发布**：编辑只改工作区，审批通过才换线上；驳回后旧版毫发无损 |
| 只有 `/skill:名字` 点名这一条路，且**在案件/合同详情页根本失效** | 详情页也能用（编排层展开，不再依赖 pi 原生前缀匹配）；另外模型会自己看索引调 `get_agent_skill` 取全文 |
| 技能是否生效取决于律师背没背得住英文 slug | `/` 菜单按中文显示名搜索；被同名技能覆盖时明确标出「被「我的」覆盖」 |

## 六个架构决策（为什么这么切）

1. **取消用户/共享技能的磁盘物化，全后端统一 DB 直出（方案 A）。**
   2026-11-28 的二轮审计在 `pi 1.6.0` 真源码里确认了两件事：没有 `read`/`bash` 工具时 pi
   **根本不生成** `<available_skills>`（`dist/core/system-prompt.js:101-108`），所以
   `--skill` 带不来任何自主发现能力；而原生 `/skill:` 只认 `text.startsWith("/skill:")`
   （`dist/core/agent-session.js:1820-1822`），案件/合同详情页每轮前置的 `[当前业务：…]`
   会让它**静默失效**。同时 `codex` 与 `cline` 两个后端并未封住内置文件读取工具，把别人的
   技能目录落到同 UID 磁盘上就是一条真实的跨用户泄密面。
   → 结论：技能不落盘，交付走三条通道（点名展开 / 系统提示索引 / MCP 按需读取）。
   顺带删掉 `store.py`（150 行）与 `skills_reconcile`（69 行）以及 `on_commit` 写盘竞态、
   目录迁移、symlink 防御这一整类运维负担。

2. **`status` 与 `review_status` 正交，`published_revision` 指向线上生效版。**
   如果把新正文直接写进 `AgentSkill` 再置一个「待审」状态，`resolve` 里一句
   `status=ACTIVE` 就把这条技能**当场下线**——作者改一个错别字，全所 AI 立刻失去这条指令，
   而界面显示「待审核中」，没人看得出线上已经断了。所以：`status` 只表示线上槽位
   （`draft`/`active`/`archived`，永不出现 `pending`），修订流状态单独一个字段，线上正文
   由 `published_revision` 唯一决定。

3. **先按偏好过滤，再按名字级联（顺序不能换）。**
   律师把自己那份同名个人技能关掉，期望的是「回落到所内版」。先去重再过滤的话，个人版
   赢了级联之后被 `enabled=False` 踢出，所内版早在去重时被判负删掉——两边一起没了。P0 的
   `visible_skills` 正是这个写法。

4. **解析拆成两个出口，服务两类完全不同的消费者。**
   `resolve_for_user` 是**运行时交付面**（只有真会交给模型的，共享取已审批版）；
   `list_visible_skills` 是**管理抽屉面**（含被遮蔽条目、本人草稿/待审）。P0 只有前者，
   于是「被我的同名技能遮蔽的所内技能」在抽屉里凭空消失——律师会以为所里根本没发过。

5. **权限独立成模块，只认 `lawyer.is_admin`，未知作用域 fail-closed。**
   **没有**照抄 `services/memory/scopes.py:can_curate_scope`：那段在 `scope=TEAM` 时只要
   `is_admin` 就放行，既不校验团队所属律所也不校验团队类型，且未知 scope 默认返回 `True`。
   技能是行为指令，一次跨所发布会让外所的 AI 按别家流程办事且当事人无从察觉。
   另外**不要求双人会签**：生产存在只有 0/1 名管理员的律所，强制 `author != reviewer` 会
   让这类律所永久死锁；代价是管理员可自审自发，所以自审时必须勾选「已确认全所生效」。

6. **安全闸门重写，不复用 `memory/curation.py:scan_pii_risk`。**
   那个函数在 Python 3 的 Unicode 语义下，`\b` 对「手机号13800138000」**实测漏报**，
   同时误杀「律师事务所 / 有限责任公司 / 法律援助中心 / 依据（2024）第1号通知」。
   新的 `safety.py` 用 `(?<!\d)…(?!\d)` 修漏报、给身份证加 GB 11643 校验位、给卡号加 Luhn
   校验（两者把随机长数字的误报压到 1/10 以下），并对主体名、案号序号一并打码。

## 顺手修掉的七个既有缺陷

| 位置 | 缺陷 | 现在 |
|:-|:-|:-|
| `pi` 原生 `/skill:` | 被 `[当前业务：…]` / `[已引用选段：…]` / `[已引用文件：…]` / `[已引用目录：…]` / `[当前页面：…]` 五种锚点顶离行首后静默失效 | 编排层展开，五种锚点全部感知；**HANDOFF 只列了三种**，漏的两个由前端真实拼接点反查补上 |
| `/skills/validate` 与 `POST` | 归档技能占着数据库唯一约束，但 `_taken_names` 排除了 `ARCHIVED` → 校验说「可以用」、创建撞 409 | 口径统一：归档占名，要复用就 `restore` |
| `_own_skill` | 不过滤 `status`，一次 `PUT` 能把已下线的技能写回可交付态 | 已归档一律不可编辑/启停 |
| `_resolve_skill_row` | `select_for_update()` 与 nullable `select_related` 共存 → `NotSupportedError: FOR UPDATE cannot be applied to the nullable side of an outer join`，**除 create/read 外所有写端点 500** | `select_for_update(of=("self",))`，保留 join，一条 SQL |
| 迁移图 | 并行会话的 `0032`（UI 动作）从 `0030` 分叉、绕过 `0031`，出现两个 leaf，`migrate` 直接报 Conflicting migrations | `0033` 同时依赖两条，作为汇合点收拢 |
| `list_visible_skills` | 缺 `shadowed` 字段 → `GET /skills` 500；`effective` 把已归档/未发布条目算成「生效中」 | 补齐字段；`effective` 改成「本轮真会交付」 |
| `ApprovalCard` 拒绝理由框 | 直接判 `e.key === 'Enter'`，中文输入法选词时的尾随 Enter **不可逆地拒批**（PIT-006） | 接 `useImeEnterGuard`，80ms 尾随窗口回归测试 |

## 交付面（谁在什么情况下看到什么）

| 通道 | 实现 | 覆盖范围 |
|:-|:-|:-|
| 显式点名 `/skill:名字` | `services/skills/expand.py`，在 `render_transcript` **之前**展开 | 普通对话 / regenerate / continue / tasks / scheduled / subtask / steer / follow-up（7 条入口） |
| 自主发现（索引块） | `services/skills/prompt_block.py` → pi `--append-system-prompt` | 4000 字预算，两轮裁剪（完整行 → 只留名字 → `not_injected`）；块首固定 `## 可用技能（法穿）`，避免 pi 把实参当文件路径去读 |
| 按需读全文 | MCP `get_agent_skill(name, start=0)` → `GET /agent/skills/resolve/{ref}/content` | 16KB 字节分段（pi 侧 20480B 拦腰截断线之前留包装余量），UTF-8 安全切分 |

`isolated=True`（综合结论这类一次性任务）默认**不注入任何技能**；将来做发布前试跑时走显式
`skill_block_override`，测的就是生产同一条渲染链路，而不是另建一套。

前端对应面：抽屉 4 个 tab（我的 / 所内 / 团队 / 系统，可见性全由服务端 `can_*` 与条目存在
驱动，前端不判 `is_admin`）、双轨状态徽标（已生效 / 草稿 / 待审 / 已驳回 / 已下线）、
覆盖关系行内提示（「被「我的」同名技能覆盖」/「覆盖了所内版」）、按作用域的配额条、
正文字节数两档提示（>16KB 提示分段读取、>32KB 标红）。

**发布前试跑**（`POST /skills/{key}/trial`）：把工作区正文内联进
`skill_block_override`，用 `isolated=True` + 只读工具面真跑一轮，把模型回复与
「实际注入了什么」一起交给审批人。不写会话历史、不可能触发写操作。它验的是
**指令语义**（这段正文被照做之后是什么效果），不是「模型会不会自己想到去读它」——
后者只能靠已发布技能在日常使用中观察。

审批侧：`SkillReviewPanel` 用 `<ins>`/`<del>` 渲染行级 diff（`equal` 段超 6 行折叠），
驳回理由**必填**（作者只有这一条依据）；「已确认全所生效」**不在默认路径上**——先不带
提交，仅当 422 且原因含「全所」时才亮出勾选（默认勾选会把确认变成盲点）。
`SkillPromoteDialog` 的目标层来自服务端 `promotable_scopes`，slug 可编辑并实时查重。
同名赢家跳层时首次弹一次提示（`localStorage` 按 user+name 去重），判定只用服务端的
`effective` / `shadowed_by`。

> **提审可改名**：`POST /skills/{key}/submit` 接受可选 `name` 与 `team_id`。不这么做的话，
> 把一条与目标层同名的个人技能提升上去会直接撞 `uniq_agent_skill_{firm,team}_name`
> （原先抛未捕获的 `IntegrityError`，前端只看到 500）。

## 总开关与回滚

`FACHUAN_AGENT_USER_SKILLS` = `on`（缺省）/ `dry` / `off`。
`dry` 保留解析、API、抽屉、点名展开，**只**停掉索引块注入——用来快速判断「是不是索引块
把某一轮弄坏了」而不影响律师点名使用。`off` 时写接口 503、解析只返内置、索引块为空、
`expand` 只认内置，DB 数据完整保留。环境变量名刻意与 `FACHUAN_AGENT_SKILLS_DIR`（内置目录
路径）区分：同名会让人在排障时改错一个。

## 迁移

`0033_skill_review_publish`：仅**新增**空列与一个索引（`review_status` / `review_note` /
`published_revision` / `reviewed_by` / `reviewed_at` / `activated_at`），零数据回填。
开发库需手动 `migrate`（本批不代跑）。

该迁移**同时依赖 `0031_personal_skills` 与 `0032_uiaction_session_setnull`**：后两者都从
`0030` 分叉（并行会话写 `0032` 时 `0031` 还没入库），只依赖其中一个会让迁移图出现两个
leaf，`migrate` 直接报 `Conflicting migrations detected`——单看任何一个迁移文件都正常，
只有跑起来才炸。

## 已知缺口（如实记录）

- **`codex` / `cline` / `dsh` 仍锁 `skill_delivery=tool_only`**：前两者未封住内置文件读取
  工具、`dsh` 无人工审批。在封洞之前不给它们注入索引块。
- **`opencode` 的 `agent.<name>.prompt` 字段尚未真机验证**（本仓踩过顶层 `tools` 字段被
  静默忽略的先例），点亮前必须先跑探针。
- **试跑没有限流与成本入账**：每点一次是一条真模型调用（实测 3-6 秒），但试跑不走
  `stream_chat`，所以不计入 `AgentRun`/`/usage`。要接成本账本需另开一条轻量记录，
  不在本批范围。
- **试跑验不出「自主发现」那一层**：待审技能还不在 `resolve_for_user` 的交付面里，
  所以试跑是把正文**内联**进去的。它验的是「这段指令被照做之后是什么效果」，
  而不是「模型会不会在合适场景自己想到去读这条技能」——后者只能靠已发布技能在日常
  使用中观察。别把一次通过的试跑当成「上线一定没问题」的证明。
- **试跑时模型若主动调 `get_agent_skill(这条待审技能)` 会 404**（它还不在交付面）。
  默认探针问法不引导它这么做，但审批人自己写的问题可能会。
- **内置技能不可试跑**（422 + 明说原因）：它们随代码发布、不走审批，本来就没有
  「发布前试跑」这个场景。回 404 会让前端以为数据不一致（列表里有、点进去没有）。
- 开发库实测回执里 `model` 是 `kimi-2.6`；测试库没有 `LLMProvider` 行、`models.json`
  回退用户级凭证，那时 `model` 为空。**回执如实反映，不是缺字段**——前端应整行隐藏
  而不是显示 `null`。
- 团队层审批机制（团队维护人表 vs 团队内任一管理员）留待有真实需求时裁定。
- `pinned`（常驻全文）与调用频次统计未做。
- 抽屉的多栏 `answerAgents` 三态提示只做到「开 `/` 菜单时提示一次」；常驻角标未做。
