# v27.13.13 · CodeQL 第二轮：真断 cyclic-import + 告警数门禁上线

## 需求

`v27.13.12` 把 101 条清到 16 条，但合并后重跑 CodeQL 发现——**其中 4 条 `cyclic-import` 根本没修好，还多出 2 条**。

本轮做两件事：把这 16 条真正做干净；补上让存量能攒到 1100+ 的根本缺口——**告警数门禁**。

## 后端

### `cyclic-import` 4 条：上一轮判断错了

上一轮的做法是「把模块级 import 下沉到函数内」，以为这样断了环。但 **`py/cyclic-import` 看的是模块间的 import 依赖图，函数内 import 照样计入**。所以 4 条一直在，而且因为新增了下沉点，反而多报 2 条。

真实的依赖形状是**互为依赖**：

- `manual_upload_service` 要 `archive_extract_service` 的 `is_archive_filename` / `is_multipart_filename`
- `archive_extract_service` 又要 `manual_upload_service` 的 `validate_manual_upload_file`

**延迟导入对互为依赖无解**——两边都延迟，依赖图上的边一条没少。

本轮新建 `backend/apps/message_hub/services/upload_policy.py`，把两边共用的口径整体下沉：

| 下沉内容 | 说明 |
| --- | --- |
| `ARCHIVE_EXTENSIONS` / `_MULTIPART_RE` | 压缩包扩展名与分卷命名 |
| `is_archive_filename` / `is_multipart_filename` | 两个谓词 |
| `MANUAL_UPLOAD_ALLOWED_EXTENSIONS` | 直传白名单 |
| `MANUAL_UPLOAD_MAX_SIZE_BYTES` / `..._ARCHIVE_MAX_SIZE_BYTES` | 两个大小上限 |
| `validate_manual_upload_file` | 校验入口（要连带常量一起搬） |

新模块**只依赖 `pathlib` / `re` + `ValidationException`**，不引 Django、不引任何业务模块——任何一处向上依赖都会把环重新引回来，这点写进了模块 docstring。

依赖形状变为 `archive_extract → upload_policy ← manual_upload`，两个 service 之间**零 import（含函数内）**。AST 实测确认 `archive_extract_service` 已不再 import `manual_upload_service`。`expand_upload_files` 的签名与 `main` 完全一致。

### 一个被测试抓住的 fail-open 设计

第一版实现把校验器做成**可注入参数、默认 no-op**：

```python
def expand_upload_files(files, on_inner_file=lambda f: None):  # ← 危险
```

这个默认值意味着**裸调 `expand_upload_files(...)` 会静默跳过白名单**——解压出来的内层文件不做任何校验就进库。`test_inner_file_fails_same_whitelist` 当场报红。

改成把白名单本身下沉、无条件生效后，签名不变、语义不变、fail-closed。**「默认值是 no-op」这种设计在安全校验路径上永远是错的**，哪怕当前所有调用点都显式传了参数。

## CI

### `alerts-gate`：终于有门禁了

在此之前 `codeql.yml` 只有 `init` + `analyze`，**没有任何告警数门禁**；`main` 分支保护的 `required_status_checks` 也是空的。

所以「Security tab 有 open 告警」完全不会让任何 workflow 变红——这正是存量能攒到 1100+ 的原因，也是上一轮我敢在 PR 里写错数字而无人拦截的原因。

新增 job `alerts-gate`（`needs: analyze`，`permissions: security-events: read`）：

| 设计点 | 决定 | 理由 |
| --- | --- | --- |
| 卡哪些等级 | 只卡 `error` / `warning` | `note` 是存量主体，全卡等于门禁上线即全红，等于没上线 |
| 用过哪个字段 | `rule.severity` | **不是** `rule.security_severity_level`——后者是 CVSS 分值字符串（如 `"8.0"`），拿它比 `error/warning` 会把所有告警漏掉 |
| 分页 | `jq '[inputs \| .[]]'` | **不是** `jq -s`——`-s` 只 slurp 第一个顶层值，`gh --paginate` 多页时后面的页会被静默丢掉 |
| fork PR | 全部 `degrade()` + `exit 0` | fork 上 `GITHUB_TOKEN` 读不到 alerts，硬失败会让所有 fork PR 全红 |
| 降级条件 | 无 token / API 失败 / 无 jq / 阈值非法 / 结构异常 | 阈值非法也降级，否则 `[ -gt ]` 会变成运行时报错冒充门禁失败 |
| 失败输出 | 逐条明细 + step summary 表格 | 直接定位，不用去 Security tab 翻 |

阈值 `MAX_OPEN_ALERTS=2`，按**实测基线**定（当时 `error/warning` 恰好 2 条，且正是本次要修的 6894 / 6895）。合入后应归零，届时把阈值调到 `0`。文件内注释写明「只准往下调，不准往上调」。

局限也要说清：**PR 上不做「不增加」检查**，只在 `main` push / `schedule` 上做强校验。做 PR 级增量检查需要对比 base 分支告警集，实现复杂且容易误伤，本轮不做——写一个会误伤的门比没有门更糟。

## 说明

### 这轮最该记住的教训

上一轮我把「静态检查全绿」当成了完成标准：`compileall` / `ruff` / `mypy` 全过，就宣布 98 条清零。结果 PR CI 报了 8 个用例失败，合并后重跑 CodeQL 又发现 4 条根本没修。

两次都是同一个根因：**没有在真实环境里验证「我以为修好了」这件事。**

- 静态检查抓不到 `monkeypatch.setattr` 的字符串目标
- 静态检查抓不到「函数内 import 仍然算环」
- 推理抓不到「我自己加的 `del exc` 会触发另一种规则」

所以本轮的验收标准改成：`cyclic-import` 必须用 AST 实测两个文件之间零互相 import；测试必须真跑；合并前必须等 CodeQL 在 main 上重跑完、拿到实测数字再写文档。

### 数字

- 第二轮前：16 条 open（14 note + 2 warning）
- 本轮修 10 条（4 cyclic + 5 unused/unnecessary + 1 注释类不消除但满足规则）
- 保留 4 条误报（已加注释说明）
- 预期合入后：**12 条**，其中 `error/warning` 级 **0 条**（门禁阈值即可下调至 0）
