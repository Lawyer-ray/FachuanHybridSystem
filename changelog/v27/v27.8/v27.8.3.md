# v27.8.3

多 worker 部署下的 agent 审批链路打通：单 worker 时全部正常的两个缺陷，只在生产拓扑（uvicorn 多进程）下暴露。

## 后端

`apps/agent`

#### 修复

- **会话上下文未传给 pi 子进程**（`services/chat_service.py`）：`_session_env()` 定义了却从未被调用，池复用的 pi 进程里没有 `FACHUAN_SESSION_ID`，extension 审批回调时 `session_id` 为空 → Django 判定「无订阅者」→ 直接拒绝，SSE 流里连 `approval_request` 都不出现，前端无从弹窗。改为按会话新建 pi 进程并注入会话级 env（`FACHUAN_SESSION_ID` / `FACHUAN_USER_ID` / `FACHUAN_APPROVAL_URL` / `FACHUAN_INTERNAL_TOKEN`）。不复用进程是因为环境变量在进程启动时固定，同一进程无法服务两个会话，否则审批会推给错误的前端；pi 本身很轻（MCP 已共享为一份），池的作用退化为限制并发数。

- **审批决定跨不了 worker**（`services/approval.py`）：等待审批的 HTTP 请求可能落在 worker A，「用户点同意」的请求落在 worker B，而 `_ApprovalWaiter` 是进程内结构 → A 永远等不到 B 的决定，只能超时走 fail-closed（表现为「已审批但工具没执行」）。改为「本地 `asyncio.Event` 立即唤醒 + Redis 决策键轮询」双路：同进程零延迟，跨进程由 200ms 轮询兜底，决策键带 600s TTL 自动过期。

- **Django 5.x 的 `RedisCache` 没有 `cache.client`**（`services/event_bus.py`）：原写法 `cache.client.get_client()` 在 Django 5 上直接 `AttributeError`，异常被 `except` 吞掉后跨进程分发全程静默失效。改为兼容两种布局的 `_redis_client()`（优先 `cache._cache.get_client()`，回退 `cache.client`），拿不到时抛明确的 `RuntimeError` 而非静默降级。

- **共享 MCP 未自动拉起**（`services/chat_service.py`）：`ensure_shared_server()` 只有定义没有调用，需人工手动启动；漏了会静默退回「每个 pi 各起一份 stdio MCP」（实测单份 225MB / 冷启动 6s，20 并发即 4.5GB）。改为首次创建进程池时自动检测并拉起，已在跑则复用。

#### 新功能

- **事件总线跨 worker 分发**（`services/event_bus.py`）：`publish()` 先投递给本进程订阅者（同 worker 零开销快路径），同时写入 Redis list 供其他 worker 消费；每个 worker 一个 relay 协程把 Redis 事件转发给本进程订阅者。无 Redis（开发环境 `InMemoryCache`）时自动退化为纯进程内，行为不变。事件带 `_origin` 标记避免本进程双发；list 有 500 条上限与 60s TTL，无人消费时不会无限堆积。

#### 优化

- `pool.acquire()` 语义改为「每请求进程 + 并发闸门」，不再维护空闲队列/复用路径——复用会串审批路由与跨用户上下文。
- 新增 `pi/model_config.py`：从数据库 `LLMProvider` 渲染 `models.json`（baseUrl / apiKey / 模型白名单），Admin 修改即时生效；Key 在会话间轮转以分散压力。支持 `FACHUAN_PI_GATEWAY_URL` 走自建网关（pi 不持有真实 Key）。
- `rpc_client._clean_env()` 剔除两类会破坏 pi 子进程的继承变量：`PI_PROVIDER`/`PI_MODEL`/`PI_SESSION_*`（会覆盖生成的 `models.json`），以及 `HTTP_PROXY`/`HTTPS_PROXY`/`ALL_PROXY`（内网 LLM 网关经代理会绕死，表现为 `Connection error` 重试 3 次）。

#### 测试

- `tests/ci/unit/agent/` 新增回归用例：
  - `_clean_env` 剔除 `PI_*` 与代理变量、保留无关变量；
  - `DeltaTracker` 的 `note`/`diff` 水位不重复发同一段文本；
  - `_redis_client()` 兼容 Django 5.x 布局（拿不到时抛 `RuntimeError` 而非静默）；
  - 服务端与 extension 两份高危工具清单一致性、`Permission` 五种结果中仅 `approved` 放行。

## 验证

按生产拓扑（uvicorn 3 workers + 共享 MCP + Redis）实测：

- SSE 流出现 `approval_request` 且带正确 `approval_id`；
- 在另一连接上 `POST /api/v1/agent/approval/{id}/decide` → 阻塞中的 `/approval/request` 立即返回 `approved: true`；
- 6 路并发对话 5 秒全部完成，零错误；
- 无 Redis 时退化为进程内总线，单 worker 行为不变。
