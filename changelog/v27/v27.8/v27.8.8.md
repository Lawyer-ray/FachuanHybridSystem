# v27.8.8

推理模型真正开启思考模式（并把推理过程展示给用户），修复 MCP 分页类工具 4 个必然失败的方法，以及 Copilot 回复「(无内容)」的三个真因。

## 前端

#### 新功能

- **思考过程可见**：assistant 气泡上方新增 `ThinkingBlock`（`MessageList.tsx`）——思考中自动展开、实时显示推理文本；正文开始输出后自动收起为「已深度思考（N 字）」，可手动展开复核；与正文同款灰字等宽样式，不打断阅读节奏。
  - `AgentStreamEvent` 新增 `{ type: 'thinking'; content: string }`，store 累积进 `ChatMessage.thinking`；首个正文 delta 到达即置 `thinkingDone`；
  - 思考内容**只用于展示**，不计入正文、不进落库历史、不参与 tok/s 估算。

## 后端

#### 新功能

- **AI 平台新增「开启思考模式」开关**（`LLMProvider.enable_thinking`，Admin「模型配置」区勾选，默认关闭）。迁移 `core.0034`。
  - 关闭（默认）：下发 `chat_template_kwargs.thinking=false`，直接作答；
  - 开启：下发 `thinking=true`，模型先输出推理再作答（延迟与 token 消耗显著上升）。
  - 仅对推理模型生效（`kimi` / `mimo` / `deepseek-r1` / `qwq` / `reasoner` / `glm-z`），普通模型（`glm53` 等）不下发任何开关，避免污染请求体。
  - **修掉模型名匹配失效**：原判断集合是 `{"kimi26", "mimo"}`，而实际配置的模型名是带连字符的 `kimi-2.6`，`"kimi26" in "kimi-2.6"` 为 `False`——思考开关从未真正下发过。改为归一化匹配（去 `-` `_` `.` 括号），`kimi26` / `kimi-2.6` / `kimi-2.6(Anthropic)` 命中同一规则。

#### 修复

- **Copilot 回复「(无内容)」**（三个真因，均与思考模式无关）：
  1. `rpc_client._clean_env()` 的 `noisy_prefixes` 含 `"PI_CODING_AGENT"`，把**我们自己用来指定隔离配置目录**的 `PI_CODING_AGENT_DIR` 一并清掉了 → pi 回落用户级 `~/.pi/agent`，我们写的 `models.json`（`fachuan` provider）被完全忽略，pi 报 `Error: Unknown provider "fachuan"` 并以退出码 1 秒退，前端收不到任何 delta。
  2. pi 的 response **不回传请求 `id`**（只回 `{"type":"response","command":"prompt"}`），而 `_send()` 只按 `id` 匹配 future → `prompt()` 必然等到超时（实测每次都卡满 180 秒）。改为 `id` 优先、`command` 兜底双重匹配。
  3. 思考参数与网关格式不匹配（见下条）。
- **思考模式开了但永远不思考**：`models.json` 声明 `reasoning: true` 并不足够——pi 还需知道往请求里写什么。本仓库 LiteLLM 网关认的是 `chat_template_kwargs.thinking`（布尔），在模型条目上补 `compat`：
  ```json
  { "thinkingFormat": "chat-template",
    "chatTemplateKwargs": { "thinking": { "$var": "thinking.enabled" } },
    "supportsReasoningEffort": false,
    "maxTokensField": "max_tokens" }
  ```
  缺 `chatTemplateKwargs` 时 pi 什么都不发；`supportsReasoningEffort` 为真时网关直接 400（`DeepSeek V4.1 reasoning_effort must be low, high, xhigh, max...`）。
- **MCP 分页类工具必然失败（4 个）**：REST 端点改为服务端分页后返回 `{items, total, page, page_size}`，但工具签名仍声明 `list[...]`，MCP 框架在输出处做 pydantic 校验直接拒绝（`Input should be a valid list [type=list_type]`）。实测确认必然失败：
  - `list_contracts`（v27.8.7 遗留项，本版修掉）
  - `list_case_parties`
  - `list_case_logs`
  - `list_court_sms`

  新增 `mcp_server.client.as_items()` 统一归一化（裸数组包一层分页壳，已是分页结构则原样返回），四个工具改用它并修正返回类型标注；`list_contracts` 补 `page` / `page_size` 参数。

#### 优化

- **`_write_settings_json`：写会话隔离目录的 `settings.json`**，pin `defaultProvider` / `defaultModel` 并写入 `modelThinkingLevels`（形如 `{"fachuan/kimi-2.6": "medium"}`）。不写这份文件时 pi 会沿用用户级 `~/.pi/agent/settings.json`，那里的 `defaultProvider` 会胜出、我们的 `models.json` 被静默绕过——排查时极易误判为网关或网络问题。
- `model_config._load_provider()` 的失败日志从 `debug` 提到 `warning`：它最典型的失败是在 async 上下文读库（`SynchronousOnlyOperation`），吞成 debug 会让「思考模式莫名不生效」「models.json 没生成」这类问题彻底无迹可查——本次排查卡住的主要原因之一。
- 流式 delta 补读 `reasoning_content`（`_delta_text()`）：部分推理模型把增量放在该字段，不兼容读取会让流式调用表现为空回复。

#### 测试

- 新增 `tests/ci/unit/agent/test_model_config.py`：覆盖 `reasoning` 声明（开/关、非推理模型不虚报）、`settings.json` 写入（含思考等级、关闭时不写等级但仍 pin provider/model、无 provider 时不产出文件）。
- `test_agent_runtime.py` 补 `thinking_delta` 转换、空增量丢弃、**思考内容不推高正文水位**（否则后续正文会被 diff 吞掉）。
- 修复 `test_social_auth_coverage.py` 的全局状态污染：`TestProviderRegistry.setup_method` 把 `ProviderRegistry._providers` 置空却未恢复，导致同进程内后续测试看不到已注册的 provider（表现为 `provider-catalog` 只剩 feishu，并连带打挂 `test_execution_request_rules` 数个用例）。改为 setup 快照 / teardown 还原。
- 后端 `tests/ci/unit` + `tests/ci/integration` 全量混跑零失败。

#### 说明

- **实测结论：`kimi-2.6` 后端确实是 DeepSeek V4.1**（网关报错原文 `Available Model Group=kimi-2.6` + `DeepSeek V4.1 reasoning_effort...`），此前的「表面 kimi、实际 DeepSeek」判断成立。
- **开启思考后延迟与 token 消耗明显上升**（实测同一道法律问题 `reasoning_tokens` 达 3240）。短任务（自动命名、OCR 打标等）如不想思考，建议按平台单独配置；当前开关是**按平台**生效，尚无按调用方覆盖的能力。
- 本版不改用本地 magpie 网关统一管理：`models.json` 由 `LLMProvider` 表渲染（Admin 改了就生效），交给个人本地代理会绕过这套配置体系。
- v27.8.7「说明」中的遗留项 `list_contracts` 已在本版修复；`get_finance_stats` 的归属过滤问题仍待单独审计。
