# v27.5.8

`ensure_postgres.sh` 自愈脚本崩溃恢复误判修复（2026-10-15 事故日）：`make backend` 因 PostgreSQL 崩溃恢复耗时超过 30s 等待窗口而误报失败，脚本退出 2 秒后数据库即就绪。

## 后端

#### 修复：PostgreSQL 自愈脚本区分「崩溃恢复中」与「服务未起」

- 事故链：异常关机（同 10-14 强制睡眠断电事件）残留死 PID 的 `postmaster.pid` → 自愈脚本删锁文件并 `brew services restart` → PG 15+ 崩溃恢复在回放 WAL 前先对整个数据目录 fsync（本机实测 10s+）→ 固定 30s 等待耗尽误报「自愈后仍无法连接」→ 脚本退出 2 秒后数据库就绪（日志 21:06:42 报败、21:06:43.804 ready）
- 探测改三态：`probe()` 利用 `pg_isready` 退出码区分 accepting(0) / rejecting(1) / no response(2)——rejecting 正是「进程存活、正在启动/崩溃恢复」的形态；无 `pg_isready` 时 `/dev/tcp` 兜底按无响应处理
- 恢复期保护：检测到 rejecting 时**绝不重启**（重启会打断 WAL 回放从头再来，还会重新 fsync 全目录，越重启越慢）；原「服务 started 但未就绪等 8s 即强制重启」逻辑改为仅在 no response 时触发
- 延长等待：基础窗口（`ENSURE_PG_TIMEOUT`，默认 30s）耗尽后若仍 rejecting，延长等待 `ENSURE_PG_RECOVERY_TIMEOUT`（默认 180s）再判死；两窗口全耗尽才报错并输出日志尾部
- 沙盒回归测试 4 场景（mock brew / pg_isready，不碰真实服务）：事故复现（stale pid → restart → 恢复中 → 延长等待后成功）、started + 恢复中绝不重启、无响应走强制重启、dry-run 只诊断
- `backend/CLAUDE.md`「PostgreSQL 自愈预检」章节同步补记事故与三态行为（本地规范文件，不入库）
