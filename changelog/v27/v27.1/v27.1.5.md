# v27.1.5

本版本修复**批量 AI 功能因 Ollama 硬编码而全线下线**的问题，重构法院文书智能识别的 LLM 分析管线，并完成 Ollama 全面下线与前端审计修复。此前 9 处 LLM 调用硬编码 `backend="ollama"` + `fallback=False`（只试本地 Ollama、禁止回退），本机卸载 Ollama 后文书识别、材料分类、自动命名、图片重命名、执行申请解析等功能全部失败。现全部接入统一 LLM 路由（AI 平台表），运行时模型配置由 `/admin/core/llmprovider/` 管理，换供给只改配置不改代码。**后端含一次加列迁移（本地开发库已应用；合并部署到其他环境时需 migrate），前端无迁移。**

## 前端

#### 修复

- 要素式转换下载后补 `URL.revokeObjectURL`：`convertDocument` 创建的 Blob URL 此前每次转换泄漏一个（文档解析下载路径已正确 revoke，转换路径漏了）

#### 优化

- **material-prep 路由懒加载 + 首屏包瘦身**：`App.tsx` 对材料预处理整域 `React.lazy` + `Suspense`（pdfjs-dist ~520KB 随之移出入首屏关键路径，入口 chunk 降至 ~104KB，仅在进入该路由时下载）。排查中发现 Vite(Rolldown) 的动态 import 预加载 helper（`\0vite/preload-helper.js`）被默认分桶塞进自定义 pdfjs chunk，形成「入口 → helper → pdfjs」静态边使懒加载失效——虚拟模块现归入首屏必加载的 vendor-react，并放弃 pdfjs 单独 chunk（归入懒加载 chunk 同样不进首屏）
- **新增路由级 ErrorBoundary**（`components/shared/ErrorBoundary.tsx`）：渲染异常与 chunk 拉取失败（如发版后旧资源失效）给可恢复的兜底页而非白屏，chunk 类错误有专门文案
- 3 处散落的裸 query key 收口为常量（`SOCIAL_PROVIDERS_KEY` 随 `social-auth` API 定义、`ORG_ME_KEY`/`GLOBAL_SEARCH_KEY` 就近定义），与 `calendarKeys` 等既有口径一致
- **启用 `noUncheckedIndexedAccess`**（tsconfig strict 加严）：清除全部 85 处索引访问可能为 undefined 的报错。修法纪律：守卫优先（如 `splitOutPages` 补 `!sg` 数据不变量守卫、`parseJwtPayload` 显式判空、QuickAdd 改 `!p` 守卫），类型收编次之（`buildLoginMethods` 返回 `NonEmptyArray` 表达恒非空、`CATEGORIES`/`SEG_COLORS` 改封闭联合/常量元组），非空断言仅用于相邻行有长度/范围守卫证明的位置（约 24 处，均带注释）
- **页卡视口懒渲染**：`PageCell` 的 `PageBody` 用 IntersectionObserver（上下各预渲染约两屏）视口外只挂骨架占位，滚近才真正取附件并渲染 canvas。92 页大包此前打开即全量渲染 92 张 900px canvas——实测现在打开只渲 2 张、滚动渐进加载且已渲染的保留
- **归案弹窗焦点管理**：手写 DOM 弹窗（AssignModal）补 `role="dialog"` / `aria-modal` / `aria-labelledby`、打开自动聚焦输入框、Tab 焦点陷阱（圈在弹窗内循环，不再逃逸到被遮背景）
- **日历格键盘可达**：日期格改 `role="button"` + `tabIndex` + `aria-label`（含当日安排数），Enter / Space 等价点空白处打开该日「新增安排」，并补 `focus-visible` 焦点环

## 后端

#### 修复

- **拆除 9 处 `backend="ollama"` / `fallback=False` 硬编码**，涉及文书识别（分类、提取）、材料分类（sync/async 两处）、图片旋转自动重命名、自动命名工具（admin 表单默认模型 `qwen3:0.6b` 改 `kimi-2.6`、调用不再锁后端）、automation AIService、ollama_client 兼容层、文书模板执行申请 LLM 兜底（连带移除死常量 `OLLAMA_FALLBACK_MODEL` 及其 ClassVar 转出）。调用不再指定 backend，按路由优先级自动选择后端与 AI 平台默认模型
- 文书识别构造器不再在初始化时读取系统配置（`get_ollama_model` 触发 DB 访问），修复全量单测中无 `django_db` 标记用例被数据库阻断拦截的交叉污染

#### 新功能

- **Ollama 全面下线，LLM 供给统一收敛到 AI 平台表（`/admin/core/llmprovider/`）**：
  - 路由层：本地 ollama 后端**默认禁用**（SystemConfig 显式设 `LLM_BACKEND_OLLAMA_ENABLED=true` 才启用），fallback 链不再附加本地后端；删除「模型名含 `:` 走 ollama」的名字路由规则，所有模型名（含 `qwen3:0.6b` 这类旧格式）统一路由到 AI 平台
  - 判决书 PDF 提取（judgment_pdf_extractor）：删除 `OllamaBackend` 直连，改经统一 LLM 服务路由（正则失败后的兜底软降级保留）
  - 证据整理 `llm-options`：移除硬编码的 Ollama 后端探测（不再对 11434 端口发起探测请求），仅列出已启用后端
  - 模型列表服务：ollama 禁用时不再把其默认模型合入展示列表
  - workbench Agent：删除 ollama 模型构建分支，全部按 AI 平台多 Key 配置构建
  - 自动命名 API 默认模型 `qwen3:0.6b` → 空（走平台默认）
  - `apps/core/llm/backends/ollama.py` 后端本体保留（显式启用后仍可用），但生产代码已无任何调用路径
- **文书识别单次结构化分析**（`document_analyzer.py`）：分类 + 案号 + 关键时间合并为一次 LLM 调用，pydantic schema 严格校验（`apps/core/llm/structured_output`），解析失败带错误反馈自动重试；同一份识别内分类与信息提取**共享同一次调用**（此前两次串行调用，延迟与 token 减半）。实测 kimi-2.6 单次调用约 0.9 秒完成全部分析
- **降级阶梯**：LLM 不可用或输出始终无法解析时，文书分类降级为关键词规则（传票/执行裁定书/其他），案号与时间继续走正则，任务不再整体 FAILED；降级结果在任务记录与识别工作台标注「⚠ 降级」
- **识别可观测性**：`DocumentRecognitionTask` 新增 `llm_model` / `llm_backend` / `llm_latency_ms` / `degraded` 四列（迁移 `0003`），API `/court-document/task/{id}` 同步返回，admin 任务详情与识别工作台展示实际使用的模型、耗时与降级状态

#### 优化

- Django-Q 识别任务提交显式 `timeout=600` 秒，覆盖 LLM 分析最坏耗时 + 文本提取 + 绑定通知，防止慢识别被集群默认超时误杀；识别工作台「提取方式」旁新增「识别引擎」行
- admin 自动命名工具表单默认模型改为律所 kimi 平台的 `kimi-2.6`，帮助文案说明模型名路由规则
