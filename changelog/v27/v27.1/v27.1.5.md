# v27.1.5

本版本修复**批量 AI 功能因 Ollama 硬编码而全线下线**的问题，并重构法院文书智能识别的 LLM 分析管线。此前 9 处 LLM 调用硬编码 `backend="ollama"` + `fallback=False`（只试本地 Ollama、禁止回退），本机卸载 Ollama 后文书识别、材料分类、自动命名、图片重命名、执行申请解析等功能全部失败。现全部接入统一 LLM 路由（AI 平台表 + 默认后端优先级 + 熔断回退），运行时模型配置由 `/admin/core/llmprovider/` 管理，换供给只改配置不改代码。**仅后端改动，含一次加列迁移（未应用，部署时需 migrate）。**

## 后端

#### 修复

- **拆除 9 处 `backend="ollama"` / `fallback=False` 硬编码**，涉及文书识别（分类、提取）、材料分类（sync/async 两处）、图片旋转自动重命名、自动命名工具（admin 表单默认模型 `qwen3:0.6b` 改 `kimi-2.6`、调用不再锁后端）、automation AIService、ollama_client 兼容层、文书模板执行申请 LLM 兜底（连带移除死常量 `OLLAMA_FALLBACK_MODEL` 及其 ClassVar 转出）。调用不再指定 backend 时按路由优先级（openai_compatible → ollama）自动选择；模型名仍按名字规则路由（含 `:` 走 Ollama，其余走 AI 平台）
- 文书识别构造器不再在初始化时读取系统配置（`get_ollama_model` 触发 DB 访问），修复全量单测中无 `django_db` 标记用例被数据库阻断拦截的交叉污染

#### 新功能

- **文书识别单次结构化分析**（`document_analyzer.py`）：分类 + 案号 + 关键时间合并为一次 LLM 调用，pydantic schema 严格校验（`apps/core/llm/structured_output`），解析失败带错误反馈自动重试；同一份识别内分类与信息提取**共享同一次调用**（此前两次串行调用，延迟与 token 减半）。实测 kimi-2.6 单次调用约 0.9 秒完成全部分析
- **降级阶梯**：LLM 不可用或输出始终无法解析时，文书分类降级为关键词规则（传票/执行裁定书/其他），案号与时间继续走正则，任务不再整体 FAILED；降级结果在任务记录与识别工作台标注「⚠ 降级」
- **识别可观测性**：`DocumentRecognitionTask` 新增 `llm_model` / `llm_backend` / `llm_latency_ms` / `degraded` 四列（迁移 `0003`），API `/court-document/task/{id}` 同步返回，admin 任务详情与识别工作台展示实际使用的模型、耗时与降级状态

#### 优化

- Django-Q 识别任务提交显式 `timeout=600` 秒，覆盖 LLM 分析最坏耗时 + 文本提取 + 绑定通知，防止慢识别被集群默认超时误杀；识别工作台「提取方式」旁新增「识别引擎」行
- admin 自动命名工具表单默认模型改为律所 kimi 平台的 `kimi-2.6`，帮助文案说明模型名路由规则
