# v27.16.7 · 大卷宗预处理：从「必死」到「能跑完并可信」

> 分支 `fix/pdf-split-stuck-recovery`（5 个提交，68 文件 +6277/−361）。
>
> 前置：`v27.16.6` 之后，用一份 **164 页真实银行卷宗**（68.9MB 扫描件、零文字层）
> 首次跑真实大材料，连续失败。
> 本版把「跑不完」「看不到」「改不动」「切不开」四类问题逐个解决。

## 背景：三次失败跑出来的问题

同一份 164 页材料，前后失败四次，每次都死在不同地方：

| 次 | 死法 | 根因 |
|:-:|:--|:--|
| 1 | 卡在 135/164，`segs=0` | `DJANGO_Q_TIMEOUT=600s` 杀 worker，OCR 成果全丢 |
| 2 | 卡在 164/164，`segs=0` | 同上，死在分段阶段 |
| 3 | 报「LLM 输出没有任何可用分段」 | 分批切片后 **未重编号 `page_no`**，页码超出范围被丢弃 |
| 4 | 46 段但质量差 | LLM 被静默降级为规则引擎（因第 3 条的连带后果） |

四个问题里，**只有第一个是超时，后三个都是我自己引入的**——这条记在这里，
因为它说明「分期改造」比「一次改对」更容易出事。

## 一、任务链拆成两段（解决 600s 铁闸）

`DJANGO_Q_TIMEOUT` 是**整个任务**的阈值，不是单次调用的。164 页实测：

- 取字（云端 OCR，25 页/批 × 5 并发）≈ 200s
- LLM 分段 ≈ 300s+

合起来 499s / 476s 两次逼近 600s 被杀。

拆成两个独立任务，各自拥有完整的 600s 预算：

```
extract（取字） → pages.json + 逐页 OCR 缓存 → segment（分段）
```

关键收益：**分段被杀不用重跑 OCR**。取字产物落盘，第二阶段从 `pages.json` 读回。

## 二、云端 OCR 分批 + 断点续传

原来整本一次性交给 MinerU：一个 HTTP 上传、一次排队、一次等全部返回。
进程一死，135 页成果全在内存里，`analysis/` 目录是空的——**从第 1 页重来**。

改为 25 页/批 × 5 并发，**每批完成立即逐页写缓存**。断在哪补哪，
重跑时先读缓存跳过已完成页。实测 164 页从「必死」变成 2 分钟跑完。

## 三、LLM 分段分批（重叠窗口）

分段是**跨页语义**任务：判断「第 41 页是新材料的开头」需要看第 40 页结尾。
按 40 页硬切会把跨批的段切成两截。

所以用**重叠窗口**：每批向后多看 8 页当上下文，但**只采纳落在本批负责区间的段**。

```
批1 负责 [1..25]，实际送 [1..33]
批2 负责 [26..50]，实际送 [26..58]
```

⚠️ **踩坑记录（本版最贵的一课）**：切片后没把 `page_no` 重编号成批内相对值，
摘要里写的是全局页号（「第26页」），LLM 就返回 `page_start=26`，
而 `parse_llm_segments(total_pages=33)` 只有 33 页可用——一半被丢弃，
再加上外层 `+ offset` 二次偏移。最终表现为「LLM 输出没有任何可用分段」，
然后是**静默降级规则引擎**（82 段碎切，且 `segment_backend` 悄悄变成 `rule`）。

这个 bug 之所以难查：单独调 `detect()` 连跑 3 次全成功（12-15 段），
只有走并发分批路径才失败。

## 四、任务卡死自救 + 前端进度

`QuerySet.update()` **绕过 `auto_now`**，所以进度回写从来没更新过 `updated_at`
——看门狗和前端都无法区分「在跑」和「已死」。

- 新增 `heartbeat_at` / `recovery_attempts`，进度回写显式写时间戳
- `sweep_stale_pdf_splits` 巡检：无分段→重排、有分段→转待复核、超次数→标记失败
- 前端显示「正在识别 41/164 页（25%）」；心跳停超阈值立刻报「已中断」并给重试入口，
  不再空转 420 次 × 2 秒 = 14 分钟

判据刻意保守（600s）：误判把活任务标成死，比晚发现更糟。

## 五、只看得到「整份」——复用已算好的结果

后端有 46 段，`draft_state` 只有 1 段整包，中间没有任何桥。
前端只在点「自动识别」时回写，而点它**从零重跑**——前面的钱和时间全白费。

新增 `GET /pdf-splitting/reusable-job`，三重匹配（原始文件名 + 页数 + 已出结果状态），
命中则直接拉 segments、不建任务、不轮询。

**刻意不用文件 hash**：拆分任务的 source 是任务目录副本，与材料包附件算不出同一个
hash，还得先下载 68MB 才能比——代价比收益大。

## 六、分段后处理：续页合并 + 同名去重

LLM 会把同一份材料从中间切开。实测两处：

```
p116-125 / p126-140  个人房产抵押贷款合同   ← p125 结尾 3.9、p126 开头 5.4，条款连续
p24-28               居民户口簿            ← 原来切成 p24-25 + p26-28
```

`segment_merge.py` 判据是**条款序号推进 + 后段首页无标题**，不是靠长度猜。
反例验证：p51-63 与 p64-69 都是 `bank_statement`，但那是两个不同当事人的流水
→ **不合并**（正确）。

同名去重：原来只在**导出**时 dedupe，数据库里仍重名。前端列表、归案建材料、
下游消费读的都是库里的名字，所以改在落库前消歧。

**最终结果**：46 段 → 36 段，`segment_backend=llm`，零降级，覆盖 164/164。

## 七、可疑点标记（本版的产品核心）

按律所口径——「预处理阶段拿到精准 Markdown，**支撑诉讼的部分**准确即可」——
把精力放在**让律师能发现并修正错误**，而不是「自动给出正确结论」。

实测一份流水段（92 行）的确定性错误：

| 形态 | 例 | 数量 |
|:--|:--|:-:|
| 金额混入借贷标记 | `D3.00` / `C3159.44` | 93 处 |
| 日期丢位 | `170201`（应 `20170201`） | 24 处 |
| 表头残缺 | `通借记卡…明细表`（缺首字） | — |

五条判据（纯正则、无模型），取向「宁可多标不可漏标」：
`amount-prefix` / `date-short` / `table-columns` / `digit-width` / `header-truncated`。

两条判据经过实测修正，值得记下：

- `date-short` 要求 8 位日期在**同一列**，同表即可会误伤卡号尾数；
- `header-truncated` 原本想用「短表名」，但实测 `…明细表`（14 字，残缺）
  vs `恒通…明细表`（15 字，完整）**纯长度切不开**——果断放弃长度启发，
  改用结构判据（表头与列名粘连 / 列名独立成行 / 表头无分隔但首行多列）。

**UI 是清单而非行内打点**：`md` 行号与 `blocks` 下标无对应关系
（一个表格块在 md 里展开成几十行），按行号画必然指错行——**标注指错比不标注更糟**。
改为面板底部可折叠清单，每条显示 hint + 命中原文 + 「查看原页」
（文本匹配定位，匹配不到不显示按钮，不给假跳转）。

真实数据验证：上述 4 处全部命中且 `severity=high`。

## 八、人工修改保护

`Segment.manualEdit`（md/name/type）追踪人工动过什么。重跑前
`detectAutoSplitConflicts` 算出会覆盖掉哪些修改，弹窗询问
「保留我的修改 / 用识别结果覆盖」，**取消则完全不提交、不花钱**。

按律所反馈「同案极少先模糊后清晰，通常是 A 案不清晰、B 案清晰」，
所以做成弹窗问而不是默认为其中之一。

## 九、归案物理切分

此前整包上传一次、按页范围标记，归案后点开任何材料都是完整 164 页——
律师原话「开庭的时候不好找相关文件」。

新增 `POST /pdf-splitting/extract-pages` 按页切出小 PDF，前端逐段上传切后文件。

### 顺带修掉一个会丢证据的 P0

核查发现：跨素材段（A素材1-10 + B素材1-6 合并）归案时，
取 `refs[0].mi=A`、`refs[last].p=6` → **只切出 A1-6，B 的 6 页凭空消失**且无提示。

`{partIndex, pageStart, pageEnd}` 三字段模型本质上只能表达「单素材内一段连续页」，
所以加 fail-closed 校验：跨源/跳页的段**拒绝归案**并提示先拆开。宁可挡住，不丢证据。

## 十、两个 P0 修复

**归案必撞 429**：`UPLOAD_REQUESTS=20/60s`，而归案一次传「段数」个附件
（36 段 → 第 21 次起全 429，且前端静默 continue：律师看到「已归案」，材料成批缺失）。

本系统本地/内网部署、同一律所自用，该阈值只误伤正常业务。按确认放开：
UPLOAD/EXPORT/OCR/TASK → 600/60s。**AUTH 保持 5/60s**——登录是唯一
「猜密码」有意义的入口，内网也不该放开。

**`source.pages` 假性为 1**：页数读不出来时兜底 `pages: 1`，归案据此判断
「这段是否覆盖整份」→ 68MB 整卷当 1 页材料上传，还标 `degraded: false` 不提示。

第一版把兜底改成 `pages: 0` 是**错的**：`initialSegments` 的
`for (p=1; p<=pages; p++)` 会产出空 refs 的空段，阅读器直接挂。
改为保留 `pages: 1` + 新增 `pagesUnknown` 标志表达「这个 1 是猜的」。

## 十一、阅读器三处体验

- **左栏可拖宽**：手柄在右缘（与中栏接缝），180–520px，键 `mp.rail.width`。
  拖拽期间不写盘（pointermove 每帧写会卡）
- **删掉彩色类型圆点**：左栏是「找材料」的目录，彩点把视线从段名上拽开；
  类型信息仍在行内胶囊与右键菜单里
- **双击定位框 → Markdown 对应那条高亮并进入修改**：律师的动作是
  「在原件上看到这行不对，想就地改」，不是先去右栏找

第三处用独立的 `editRequestKey` 而非复用 `focusedBlockKey`——
后者也表示「从 Markdown 侧选中」，那种情况不该自动弹输入框。

## 十二、修刷详情页闪烁

`/material-prep/:id` 刷新时，URL 里的 `:id` 首帧就位，但 `openId` 要等
route-sync 的 effect 异步打开才变。DeskPage 只看 `openId` → 首帧渲染完整列表
→ 阅读器才盖上来。

改用 `routeId != null || openId != null` 判「详情意图」，意图成立时整块列表不挂载。
两个都要看：只看 `openId` 会闪列表；只看 `routeId` 则关闭阅读器时（navigate 异步）慢一拍。
