# v27.16.1 · 收法院短信卡支持客户转交材料（拖拽多文件走同一套归档链路）

> 分支 `fix/material-prep-upload-error`。

## 背景

案件材料并不总经法院通道送来。常见情形是客户先收到法院/对方发来的材料，再通过微信
转给律师。这类材料同样需要「解析 → 匹配案件 → 重命名归档 → 群通知」，但此前只有
「粘贴法院短信」一个入口——材料只能先想办法走法院下载爬虫，或者手工往案件文件夹里丢。

本版在**不新建流水线**的前提下打开第二个入口：拖入多个文件即走同一条后端链路。

## 后端

### 新功能

#### `POST /api/v1/automation/court-sms/upload`（客户转交材料）

- multipart：`files[]`（必填，可多个）、`content`（可选备注）、`received_at`（可选）。
- 扩展名白名单 PDF / DOC / DOCX / JPG / JPEG / PNG / BMP，单文件 50MB 上限，
  与文档解析模块同口径。
- 落盘走 `storage_service.save_uploaded_file`（文件名清洗 + 扩展名白名单 +
  大小上限 + 可执行文件魔数检测 + 路径收敛在 `MEDIA_ROOT` 内），落 `automation/uploads/`。
- 落盘后直接写入 `CourtSMS.document_file_paths`，状态置 `matching`，
  随后交给**既有的** `process_sms` 异步任务。
- 响应 `data.materials` 回报 `saved`（已入库文件名）与 `skipped`（跳过原因），
  部分文件不受支持时**不整批拒绝**——微信导出的 `.heic`、录屏混进来是常态。

#### `CourtSMSDocumentIntakeService`

新增 `apps/automation/services/sms/court_sms_document_intake.py`，只负责**来源**：
文件 → 清洗/校验/落盘 → 写入 `document_file_paths`。等级复用点：

| 环节 | 现有代码如何接上 |
|---|---|
| 下载 | `_process_downloading_or_matching` 见 `download_links` 为空 → 直接进 matching |
| 提取案号/当事人 | `_get_document_paths_for_extraction` 已优先读 `document_file_paths` |
| 重命名归档 | `_process_renaming` 无 `scraper_task` 时回落到 `document_file_paths` |
| 文书引用/下载 | `CourtSMSDocumentReferenceService._collect_from_sms_paths` 已支持 |

另含：
- `build_content_placeholder`：文件通道没有短信原文，用「客户转交材料 + 文件名清单」
  填充 `CourtSMS.content`，避免归档 markdown 出现「短信原文: (空)」、后台 trigram 检索无内容。
- `is_meaningful_filename`：识别 `微信图片_2026…` / `mmexport…` 这类无语义文件名
  （供重命名降级时判断，不把流水号当文书标题）。
- `cleanup_paths` / `_is_intake_path`：只清理本通道目录下的文件，不越权删下载原件。

### 修复

- `submit_sms` 增加 `materials` 参数，`content` 可空（两者不能同时为空）。
  幂等键覆盖「文件名清单 + 时间戳」，同一批材料 10 分钟内重复提交被拦下。
- `process_sms` 的状态分发允许 `MATCHING` 直接进入 `_process_downloading_or_matching`：
  文件通道建记录即 `matching`，原来只认 `PARSING`，会让记录永远停在 matching。
- `_process_parsing` 仅在 `document_file_paths` 为空时覆盖 `case_numbers`/`party_names`，
  避免重复进入时冲掉文书抽取结果。
- 新增 `post_delete` 信号 `cleanup_court_sms_intake_materials`：删除/终止短信记录时
  清理客户材料落盘文件（下载原件仍由 `ScraperTask` 信号管理，两条通道互不越权）。

### 测试

`tests/ci/unit/automation/sms/test_court_sms_document_intake.py`（22 例）：
落盘与状态流转、部分失败保留好文件、全不可用拒绝、去重、占位正文、文件名语义判定、
清理不越权、`submit_sms` 的文件通道与短信通道语义、无链接时跳过下载。

## 前端

### 新功能

- `CourtSmsCard` 增加「法院短信 / 客户材料」分段切换，两个入口共用同一套弹窗与轮询。
- `MaterialDropZone`：拖入或点选多个文件、单件移除、实时大小、禁用态、键盘可达；
  扩展名/大小前端先拦一道（与后端常量对齐），不支持的文件即时提示而不入列。
- `material-files.ts`：纯逻辑（校验/合并去重/大小格式化）抽出可单测；
  去重用「名称+大小+修改时间」三元组，不读文件内容（大 PDF 读取会卡主线程）。
- `uploadCourtSmsMaterials`（`api/court-sms.ts`）：multipart 提交，`materials` 缺省字段补齐。
- `useCourtSms` 增加 `submitFiles` 与 `source: 'sms' | 'material'`、`intake`；
  提交→轮询→终态的编排完全复用。
- `CourtSmsFlowDialog` 按来源切换文案与步进器：文件通道用四步表
  （`MATERIAL_STAGES`，无「下载文书」），并展示入库明细（跳过哪些文件、为什么）。

## 说明

- **不改状态机**：`CourtSMSStatus` 十态与 `use-court-sms` 轮询完全复用，无新表、无迁移。
- 重命名仍依赖 LLM 识别文书标题；失败时降级为**原文件名**。微信导出的
  流水号文件名（`微信图片_…`）作为标题无信息量，`is_meaningful_filename` 已提供判定口径，
  后续可接到降级链路上。
- 本接口暂未进 MCP 工具面（纯前端入口），故不涉及 `make mcp` 重启。
