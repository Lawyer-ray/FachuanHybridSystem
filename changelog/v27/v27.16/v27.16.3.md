# v27.16.3 · 后端代码质量审查：四层架构补守卫、删重复实现、修资源与事务缺陷

> 分支 `chore/frontend-code-quality-audit`（4 个提交，全部只动后端）。
>
> 本版来自一次**全量后端代码审查**（2194 个文件 / 31.4 万行，7 个审查 agent 分片 +
> 横向 AST/ruff 机械化核验），然后按「先复现、再改、改完验」的纪律修掉其中
> **已确认成立**的问题。

> 本版只采纳经复现确认的部分；被推翻的结论记在最后一节，供后续会话引以为戒。

## 背景

审查给出了一份很长的清单，但代码库整体工程素养并不差——它已经有一些真实的机制：

- `tests/ci/structure/test_four_layer_architecture.py` 用**棘轮基线**守架构，
  API 层 `Model.objects` 已全量清零（基线 0）；
- Service 层 `@staticmethod` 从 264 压到 12；
- `transaction.atomic` 覆盖 111 个文件，生产代码 `print()` 零残留，可变默认参数零。

但在同一份审查里也暴露了三个系统性的洞：

1. **同一业务常量会在多处各写一份，然后漂移**；
2. **四层架构只守了一半**——API/Service 两层有守卫，Admin/Model 两层没有任何守卫，
   于是这两层的历史违规只增不减；
3. **重复实现没人收**——同一段逻辑复制两三份后，修 bug 必然漏掉一处。

本版按这三条线展开。

## 后端

### 修复

#### 诉讼地位判定四处各写一份且已漂移，收敛为唯一权威

生产库 `cases_caseparty.legal_status` 是**中英文混存**的（英文枚举 + 早期录入的中文，
实测 `defendant 73 / plaintiff 45 / 被告 3`）。这套「哪一方」的判定曾在**四处**各写一份：

| 位置 | 是否含中文 |
|---|---|
| `plugins/court_automation/filing/schemas.py` | 含（已修过） |
| `plugins/court_automation/guarantee/schemas.py` | **仅英文** |
| `apps/cases/services/case_readiness_service.py` | 含中文但**少了「原审原告」** |
| `plugins/court_automation/guarantee/helpers.py` | 又一份仅英文的局部副本 |

`filing/schemas.py` 的注释自己写着「两处的状态白名单必须保持一致口径」——
规范识别到了，但只修了一处。

新增 `apps/cases/domain/party_status.py` 作**唯一权威**（中英文并列 + 三个判定函数），
四处改为引用同一对象，删除 `guarantee/helpers.py` 的局部副本。

**真实影响**（复现确认，不是 500）：`guarantee/api_endpoint.py` 的
`our_party_is_plaintiff_side` 直接拿原始集合做 `in` 判断、**没有 fallback**，
对 `legal_status="原告"` 的案件会返回 `false`，前端据此提示「我方不是原告方，
本页只处理起诉立案」——律师被误导，而实际我方就是原告。修复后正确返回 `true`。

新增 `tests/ci/structure/test_party_status_single_source.py` 防再次漂移（4 项检查：
权威模块必须双语齐备、消费方必须引用同一对象、消费方不得自建字面量集合、
全仓扫描新出现的字面量集合）。做过负向验证：注入一份副本后守卫如期失败。

#### 确认归档跨模型双写无事务

`apps/contracts/api/archive_api.py` 的 `confirm_archive` 原本在 API 层直接改两个模型：
先把合同置 `archived`，再循环把关联案件置 `closed`。中途失败会留下
「合同已归档 / 案件未结案」的脏状态。

逻辑下沉到 `archive_query_service.confirm_archive`，事务边界收在一个**同步函数**内
（async 上下文里不走 `transaction.atomic`，用一次 `sync_to_async` 跨过整个原子块），
写入改用 `QuerySet.update()` 避免触发 `post_save` 信号与 history 行。

补 `tests/ci/unit/contracts/test_archive_confirm_service.py`，其中
`test_confirm_archive_rolls_back_contract_when_case_update_fails` 用
`patch(QuerySet.update, side_effect=[1, RuntimeError])` 让第二步失败，
断言两行都回滚到 `active`——验的是真 `atomic` 块，不是 mock 事务。

#### 询价「删旧 + 写新」无事务，异常会永久丢失旧报价

`plugins/court_automation/preservation_quote/service.py` 的 `execute_quote` 里，
`InsuranceQuote.objects.filter(...).delete()` 与随后的 `bulk_create` 各自 autocommit。
写新失败 → 旧报价已删、新报价未落库 → 任务停在 RUNNING，历史询价数据永久丢失。

改法：新增 `_replace_quotes_sync`，把「删旧 + 批量写新」收进单个 `transaction.atomic`，
async 侧一次 `sync_to_async` 调用它。同时把 `_save_premium_results` 的内部实现
收敛为同步的 `_save_premium_results_sync`（原名保留为薄包装），避免与 service 形成双副本。

**状态机刻意留在事务外**：`RUNNING → COMPLETED/FAILED` 的迁移与 `except` 置 FAILED
保持原样，否则「失败置 FAILED」会被一起回滚掉。新增 `test_quote_replace_atomic.py`
用 AST 守卫这一点。

#### 担保自动填表用伪造身份证号兜底

缺证件号时，`data_mixin` 会填 `DEFAULT_NATURAL_ID_NUMBER`（`110101+19900307+7715`）
与 `DEFAULT_LEGAL_ID_NUMBER`（`91440101MA59TEST8X`）；浏览器侧
`dialog_field_filling.py` 的 4 个 JS 填充点又各自独立兜一次（`defaultNaturalId`）。
这是**向法院提交虚假身份信息**的风险。

只改 Python 侧不够——JS 的 `^\d{17}[\dXx]$` 不匹配空串会再次回落到假号，
所以两层一起改：证件号为空或格式不合法时**留空**，由法院表单自身的必填校验暴露，
人工补全后重跑。删除 `DEFAULT_*` 常量、`defaultNaturalId` 变量，以及
`plugins/.../guarantee/schemas.py` 里已无引用的同名死常量。

### 优化

#### ruff 的 requests 禁令被自己的配置架空

`backend/ruff.toml` 同时存在两处：

- `[lint.flake8-tidy-imports.banned-api]` 把 `requests` 设为禁用（要求用 httpx）
- `[lint] ignore` 列表里又全局 `ignore` 了 `TID251`

结果禁令**永远不触发**——`ruff check .` 静默放过所有 `import requests`，
而显式 `--select TID251` 能检出。移除该 ignore 后，唯一的违规文件
`apps/cloud_storage/webdav_provider.py` 迁移到 httpx：

- `requests.Session` → `httpx.Client`（连接池语义等价，`close()` 用 `is_closed` 守卫）
- `requests.auth.HTTPBasicAuth` → `httpx.BasicAuth`
- 认证与 header 从「构造后赋值」改为构造参数
- 对应 8 处 `patch("...requests...")` 装饰器一并迁移，测试不留在断掉的状态

#### 归档分类的死代码与假覆盖

`apps/core/services/material_classification_service.py` 里的 `classify_archive_material`
及其 5 个专属 helper、2 张关键词表（约 325 行）**零生产调用方**——归档分类的真实入口
是 `apps/contracts/services/contract/integrations/archive_classifier.py`（含跳过规则与
证据文件夹特判，两份实现已语义漂移）。

删除后文件 990 → 665 行。连带清理 6 个测试文件里的 archive 专属区块（约 437 行）：
它们此前只在给这份死代码喂覆盖率。其中 `test_round8_more_helpers.py` 整个文件
都在 `patch` 一个**不存在的属性路径**，用例只断言 mock 自己——留着比删掉更糟，
因为它给出「这里有测试」的错觉。

#### cloud_storage 的 walk() 五份复制

`s3` / `onedrive` / `dropbox` / `webdav` 四份 `walk()` 经 AST 比对**逐字相同**
（差异仅 webdav 一行 docstring），抽为 `_RecursiveWalkMixin`。

三份**刻意保留**，因为差异是真实的：

- `gdrive_provider`：委托 `_walk_recursive(path, visited)` 并做环路检测，
  还必须先 `self._resolve(path)` 解析 Drive file ID——套 mixin 会丢掉环路保护；
- `local`：用 `os.walk`，带 `is_relative_to(self._root)` 越界保护与 stat 失败跳过；
- `null_provider`：只有 `self._fail()`，无需 mixin。

#### LLM JSON 解析：替换 2 处、保留 4 处

`apps/core/llm/structured_output.py` 的 `extract_json_text` / `parse_json_content`
是权威实现。下游有 6 份自签解析：

- **替换 2 处**（语义等价、失败返回值一致）：`document_recognition` 的
  `_response_parser_mixin` 与 `document_classifier`；
- **保留 4 处**（实测功能不等价，仅加 docstring 注明差异与原因）。

保留里最要紧的是 `legal_research/services/similarity/json_utils.extract_json`：
对 `'note: use { } braces {"a":1}'` 这类输入，权威实现返回 `{}` 而旧实现返回 `None`。
空 dict 会让上层 `coerce_score(payload.get("score", 0.0))` 直接判 **0 分**，
并绕过 `_repair_json_payload` 修复路径——这是**静默的错误评分**，比解析失败难发现得多。
为「统一」引入这种风险不值得。

新增 `tests/ci/unit/core/test_llm_json_extraction_contract.py`（21 类输入）固化权威实现
当前行为，未来有人想改它就能立刻看到哪些下游语义会变。

#### 案由列表 N+1

`CauseOfAction.full_path` 是沿 `self.parent` 逐级向上的 `while` 循环，
而 `cause_court_repository.get_causes_by_parent` 返回的 queryset 没有预取父级。
每次列表请求对每个案由都触发额外查询。

加 `select_related("parent__parent__parent")`（实测案由层级最深 4 级，预取 3 层覆盖全链）。
实测 12 个案由从 12+ 次查询降到 **1 次**。

#### 文件夹生成服务里的 zip 死代码

`folder_generation_service._create_folders_in_zip` 只被自身递归调用、外部零引用，
真实打包路径走 `pipeline/packager.py` 的 `ZipPackager`。两处逻辑逐字重复。

删除死的那份，并把 3 个测试文件里 9 个「测死代码」的用例改为测 `ZipPackager`——
zip slip 防护（`safe_arcname` 清洗 `../` 与绝对路径）的断言全部保留。

### 测试

#### 给 Admin / Model 两层补四层架构棘轮

`four-layer.md` 规定了四条禁令，但守卫只覆盖了两条（API 层禁 `Model.objects`、
Service 层禁 `@staticmethod`）。Admin 层「禁止直接实例化 Service」与 Model 层
「禁止业务方法与自定义 save()」一直无守卫，于是只增不减。

新增 `tests/ci/structure/test_admin_model_layer_ratchet.py`，四条**只减不增**的基线：

| 检查 | 基线 | 说明 |
|---|---|---|
| Admin 层 `XxxService(...)` 实例化 | 91 | 应走 wiring 工厂 |
| Model 层自定义 `save()` | 9 | 写逻辑属 Service |
| Model 层写操作方法 | 9 | 方法体含 `self.save` / `.objects.` / `transaction.atomic` |
| Model 层只读派生写成普通方法 | 16 | 风格债（该改 `@property`），非违规 |

**特意把「写操作」与「只读派生」分开计数**：前者是架构红线，后者只是该改 `@property`。
混在一起会让基线失真，也会让「清理」失去指导意义。

两处显式豁免并写明原因：

- `ClientIdentityDoc.validate_doc_type_for_client` —— 受 Django formset 调用时机约束。
  `full_clean()` 对每一行（含标了删除的行）都调 `clean()`，而 DELETE 标记要等
  `save_existing_objects()` 才生效；校验放进 `clean()` 会让一行历史脏数据导致整个
  表单集**既存不下去也删不掉**（2026-11-06 实爆）。
- `CloudStorageAccount.encrypt_sensitive_fields` —— 字段级幂等加密变换，
  无跨模型编排、无外部 IO。放 Model 反而比放 Service 更难写错（不会有人忘了加密就写库）。

负向验证：注入 1 处 Admin 实例化后违规数 92 > 基线 91，守卫如期失败。

#### 拆分 1048 行的 admin mixin

`apps/cases/admin/mixins/views.py` 是 backend 里最长的 admin mixin：一个
`CaseAdminViewsMixin` 塞了列表列展示、详情页、材料视图、4 个文书解析视图、

按职责拆成 5 个兄弟模块，`views.py` 只留聚合入口（**1048 → 41 行**）：

| 文件 | 行数 | 职责 |
|---|---|---|
| `views_list_display.py` | 95 | 9 个列表列展示 |
| `views_detail.py` | 456 | 13 个详情 / 材料 / changeform |
| `views_document_parse.py` | 333 | 5 个文书解析 |
| `views_folder_import.py` | 185 | 2 个文件夹与邮件导入 |

**只搬家不改逻辑**：AST 逐成员比对确认 29 个类方法 + 6 个模块函数逐字节等价，
唯一变化是 `_coerce_optional_*` 按 `code-style.md` 从 `@staticmethod` 改为模块级

## 说明

### 审查里被推翻的结论（记录以免后来者重犯）

审查报告初稿把「诉讼地位白名单漂移」判定为**担保接口 500**，并给出了完整因果链。
按这条链去复现时，**修复前的旧代码也没有崩**——`_list_party_payloads` 有三级 fallback
（先按状态+我方侧匹配、再只按状态、再只按 `is_our_client`、最后取第一个当事人），
中文 `legal_status` 在旧集合里不命中第一级，但命中第三级，照样选对。

真实影响如上一节所述，是 `our_party_is_plaintiff_side` 误判 `false`，不是崩溃。
这类「没读完 fallback 分支就下结论」的误判在审查里出现了不止一处，
因此本版所有改动都执行「**先复现、不成立就不改**」：
`execute_quote` 的事务缺失就是经四条独立证据（无 atomic、无内部事务、四个调用方都无外层事务、
`ATOMIC_REQUESTS=False`）确认后才动手的。

### 已知未修（记录在 `tmp/audit/02-REMAINING-ISSUES.md`）

- **云存储 provider 连接泄漏**：`close()` / `aclose()` 全仓零调用方，
  每次扫描/归档泄漏一个 `httpx.Client` 连接池。修它要改 4 个调用点的生命周期，
  单独 PR 更安全。
- Admin 层 91 处直连 Service、Model 层 9 处写方法：已建棘轮锁住，未清理。
- 仍有 8 个 >1000 行的文件（`guarantee/helpers.py` 1489、`agent_api.py` 1478、
  `mcp_server/server.py` 1329 等）。
