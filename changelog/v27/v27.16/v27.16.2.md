# v27.16.2 · 材料预处理整条链路：大卷宗、混合材料、导航与工具栏重排

> 分支 `fix/material-prep-upload-error`（14 个提交）。
>
> 本分支从「上传 65MB 卷宗时页面显示『请检查后端连接』」这个看起来像后端宕机的
> 报错开始排查，最后连带改掉了整条材料预处理链路：体积上限、多格式取字、
> 识别定位、云端选择与容灾、收件箱与材料包的结构，以及阅读器工具栏。
>
> 同分支上并行会话的其他改动见 `v27.16.1`（法院短信客户转交材料）。

## 背景

律师交进来的材料不是「一份文档」，是**整卷**：

- 一份 164 页全彩扫描的诉讼卷宗实测 66MB，客户一次交几十卷是常态；
- 一个材料包里同时有扫描 PDF、电子版 PDF、图片、Word/Excel，四类正确路径各不相同；
- 「电子版 PDF」虽然能直接读到文字（快、免费、准），但文本层**不带坐标**，
  恰恰是判决书、合同这类最需要「指着原文说事」的材料定位不了。

而入口侧的问题更基础：报错把可自行处置的 400 伪装成服务故障，导航把「东西从哪来」
和「走到哪一步」两个正交维度混成四个并列页签，工具栏常驻区被 5 个同等权重的
描边控件占掉 175px。

本版按「先把链路打通，再把入口收干净」的顺序处理。

## 后端

### 修复

#### 上传失败的报错把 400 伪装成服务故障

超限时后端已正常返回 `400 + {code: ATTACHMENT_TOO_LARGE, message: "附件过大…"}`，
但前端 `catch` 不读响应体，直接弹硬编码的「上传失败，请检查后端连接」。
可自行处置的错误被讲成「后端挂了」，用户唯一的动作是去重启服务。

`DeskPage.handleFiles` / `store.appendFiles` / 状态更新 / 删除共四处改用
`lib/errors` 的 `errMessage`：优先透出后端 `message`，无可用文案才回落通用提示。
体积预检（按后端同口径在发请求前拦住）一并加进 `constants.ts`，
理由不是「多一道保险」，而是 66MB 传满整条链路才被拒既浪费时间也白吃上行带宽。

> 该次修复**没有**放宽 50MB 上限——当时该阈值是仓库内多处共用的既有约定，
> 放宽属策略变更，留到下一版单独处理（即下面的 1GB）。

### 新功能

#### 体积上限 50MB → 1GB（四处口径必须同步）

只改一处会出现「能传进来、却在下一步被拒」，因此四处一起放开：

| 位置 | 原值 | 新值 |
|---|---|---|
| `upload_policy`（单文件 / 压缩包） | 50MB / 200MB | 1GB / 1GB |
| `archive_extract`（展开总量 / 条目数） | 200MB / 200 | 8GB / 1000 |
| `pdf_splitting`（大小 / 页数） | 150MB / 300 页 | 1GB / 1000 页 |
| `nginx`（`client_max_body_size`） | 200m | 1024m |

压缩包与单文件同额，避免「直传被拒、打包反而能过」的怪事；`archive_extract`
的单条上限改为直接引用 `upload_policy` 常量，两处数字不再各写一份。
nginx 会先于 Django 拦截，小于后端口径就只会得到 413 而非可读提示。

内存侧无新增风险：Django 对 multipart 的 FILE 项是流式落盘，
`DATA_UPLOAD_MAX_MEMORY_SIZE` 只管非文件字段。

#### Word / Excel 接入（`OfficeBackend`）

新增 `document_parsing/services/backends/office_backend.py`（docx / xlsx / xls），
已注册进 `ParserFactory`。

**为什么不用 OnlyOffice**：DS 是编辑器画布——渲染给人看、保存时回调。拿它抽文本要绕
三处：① 容器内取文件必经签名回源 + 转换，比本地读 OOXML 慢一到两个数量级；
② 它返回渲染结果，拿文字还得再 OCR 一遍，而 Word 里的字本来就是结构化的，
OCR 反而把可靠的字变成可能认错的东西；③ 1GB 卷宗整份传给 DS 纯属浪费。
故：OnlyOffice 负责「给人看和改」，office 后端负责「给机器读」，两者不重叠。

实现要点：

- 按 `document.element.body` 的**子元素顺序**遍历，而非先读 paragraphs 再读 tables
  ——Word 里正文与表格是交错的，分开读会把表格整块挪到文末；
- 标题层级：样式名（`Heading` / `标题` + 数字）优先，再读 `pPr/w:outlineLvl`
  （`python-docx` 的 `ParagraphFormat` **没有** `outline_level` 属性）；
- Excel：`read_only + data_only` 取公式计算结果而非 `"=SUM(...)"` 字符串；
- 产出文本 + GFM 表格 Markdown + 结构 locator（段落序 / `sheet+行`）。

顺带修两个会让 Excel 直接失败的上游缺口：`parsing_api` 扩展名白名单漏了
`.xlsx/.xls`（传 Excel 会 400，看着像不支持）；该入口大小上限 50MB 与收件箱
1GB 不一致（传得进材料包却解析不了）。

#### 识别定位：bbox 归一化

新增 `pdf_splitting/services/split/bbox.py`，把三家后端坐标统一成前端能直接画的
0–1 矩形：

| 来源 | 坐标形态 | 处理 |
|---|---|---|
| MinerU | 千分比，**不返回页面尺寸** | 按 1000 基准换算 |
| Textin | 绝对坐标 | 必须有 `page_width/height`，缺失返回 `None` |
| 四点多边形 | — | 取外接矩形，越界夹紧，宽或高为 0 视为无坐标 |

核心原则：**算不出来就返回 `None`，绝不编一个框**。错框比没框更糟——会让人指着
A 处说 B 处的内容。Office 同理：只给整页框并标 `approx=True`（前端画虚线），
精确定位走结构 locator。

链路：pipeline 按 `ocr_provider` 传入 bbox_backend → `markdown_builder` 产出
`positioned` → `segments_md.json` **同文件**（正文与坐标同源，分两文件迟早对不上）
→ `SegmentOut.positioned` 透出。

#### 云端补版面开关（`layout_mode`）+ 云端平台可选与容灾

两条都是**真正的成本/能力权衡，不替用户选**，因此做成显式开关而非改默认：

```
layout_mode
  fast_text（默认）  电子页只抽文本层，不调云端  → 无坐标、免费
  layout             电子页也上云端拿版面块      → 可定位、按页计费、更慢

cloud_backend
  auto（默认）   按优先级尝试，失败切下一个   → 容灾
  仅 MinerU / 仅 Textin  锁定，失败即失败     → 不降级
```

关于「是不是随机」的排查结论：**不是随机**。`auto` 是确定性优先级排序
（`sorted by priority, pk`），MinerU priority=5 / Textin priority=10，
所以永远选 MinerU。感觉「随机」来自同一平台下的**多 Key 轮询**（3 个 Key 按游标
轮转 + 失败冷却 30s），变的是 Key 不是平台。而更早的问题是 MinerU 失败只记录错误
就降级本地 OCR、**不切 Textin**——所谓「双平台」其实只是「主 + 手动备用」。

**关键设计：锁定不等于「优先」，而是「不许换」。** 用户选 MinerU 往往是为了固定口径
做比对/复核；若偷偷降级到 Textin，结论失效、计费还会落在他没选的平台上。所以锁定
时候选表只有它自己，失败就走「回落文本层 + 说明原因」。

四个不写就会静默出错的实现要点：

1. `want_layout=True` 时**故意不拿文本层定稿**，把电子页留给云端——这是唯一能让
   电子页拿到 bbox 的办法；
2. 云端不可用/失败时**回落文本层**，而不是让页面变空、也不是丢给本地 OCR：
   文本层是机器真值，拿它喂 OCR 等于把可靠的字重新猜一遍；
3. **缓存档案名带策略后缀**（`_text_v2` / `_layout_v2`）。不隔离的话，先开补版面
   再关掉，第二次仍命中带坐标的旧缓存，开关形同虚设；
4. `summary.layout_unavailable_reason` 显式说明「开了但没生效」及原因，
   以及 `cloud_candidates` / `cloud_failover_from` 让容灾可回溯。
   这是最容易被误判成「开关有 bug」的情形，必须在数据里说清楚。

实现：`parser_factory.resolve_cloud_backends()`（auto → 有序多值去重；锁定 → 单值；
平台未启用 → 空表并明确报不可用，不静默换）+ `pipeline._parse_cloud` 按候选逐个
尝试（**异常与空结果都算失败**），命中后把实际平台与 `cloud_failover_from` 写进 stats。

#### 混合材料包按附件分派取字（新增 `DISPATCH.md`）

一个包里同时有扫描 PDF / 电子版 PDF / 图片 / Word 是常态，四类正确路径不同，
调度必须按**附件粒度**逐份选路，不能按整包一刀切。

- 图片接入自动识别：单页 OCR 取字回填段正文。图片本就单页、谈不上「分段」，
  故新增 `fillSegmentText` 而非套用 `applyAutoSplit`——后者的完整性校验会把单页
  材料误判成「覆盖不全」而整份丢弃。单独一轨，图片失败不拖垮 PDF 分段主线；
- 新增 `classify_pdf_material`：抽样首/中/尾至多 3 页判定
  `digital / scanned / mixed`，写入 `summary.material_kind` 供排障；
  **不参与选路**（真正的选路是逐页的，抽样只给可读标签）；
- `summary.cloud_used` 区分「真调了云端」与「云端没配走了本地 OCR」——
  排障时最容易被误判成「云端很慢」的就是后者。

## 前端

### 材料预处理：结构重排

#### 收件箱与材料包合并为同一页面

`/material-prep` 与 `/material-prep?stage=todo` 本是同页的两个阶段（只差 `?stage=`），
但主区域是两套视觉语言，切换像换了个页面：收件箱外包圆角描边卡片、材料包网格裸铺；
收件箱有二级筛选条、材料包没有；密度差 3 倍；空态是两种完全不同的东西；
材料包阶段有两个上传入口。

改为**一个容器 + 一条统一工具栏 + 同一批数据的两种呈现（列表/卡片可切换）**：

- 新增 `desk-toolbar-types.ts` 作为共享契约（`DeskViewMode`、`STAGE_DEFAULT_VIEW`、
  `toolbarSlotsFor`、`DESK_SURFACE_CLASS`）
- 新增 `DeskToolbar`：按 stage 决定渲染哪些槽位，各阶段不再各造一套筛选条
- 筛选状态与 `viewMode` 上提到 `DeskPage`，`InboxView` 改为纯受控
- `PackGrid` 支持 `viewMode='grid' | 'list'`，list 形态与收件箱列表同密度
- 删掉网格里的虚线上传槽：顶部「新建材料包」+ 全局拖放层已是入口

默认视图按阶段区分（`STAGE_DEFAULT_VIEW`）：收件箱是消息流，要扫过几十条按时间分组，
列表才扫得动；材料包是待办对象，缩略图帮助辨认，网格更合适。用户仍可随时切换。

#### 导航改为两级：收件箱 / 材料包

原来四个页签混了两个正交维度——「收件箱」回答**东西从哪来**，「待处理/已归案/不接归档」
回答**材料包走到哪一步**。它们不是并列关系，后三个是第一个的子集的一种切分。

后果不只是概念不清：**同一份材料被数了两次**——收件箱「全部」是 `listInbox({})`，
包含 `manual_upload` / `client_upload`；而「待处理」拉的正是
`source_type=manual_upload,client_upload`。同一份上传在两边各出现一次，两个角标互相矛盾。

```
一级：[收件箱] [材料包]
二级（仅材料包）：待处理 / 已归案 / 不接归档
```

- 「材料包」升为一级导航，收件箱下的「材料包」来源档位取消
- 收件箱只收外来来源：显式传 `court_inbox,imap,court_sms,court_schedule`
  （**不能省略参数**——省略会让后端返回全表，把材料包一起捞进来）
- 一级角标：收件箱=收件箱数；材料包=三态之和

材料包三态**用同级页签而非下拉**：下拉会把三个角标藏起来，而它们正是
「今天还有几包没处理」的主要线索。点「材料包」时若已在某状态则保持该状态。

### 材料预处理：修复

#### `?stage=` 三处失效

**关阅读器被弹回收件箱**：关闭时 `navigate(materialPrep())` 不带阶段，回落到首段
「收件箱」。stage 是这个页面的状态而非临时筛选，回退时必须原样带回。改为从当前
`location.search` 解析后构造目标地址（读 router 的 location 而非 `window.location`，
测试跑在 MemoryRouter 下没有地址栏）。

**切阶段抹掉其它 query**：`setParams({ stage: s })` 整体替换 query，把收件箱的深链接
`?message=<id>`（从到账短信点「详情」直达原始邮件）一并抹掉。改为函数式更新。

**点材料包会先闪一下列表**：`openAt` 里 `navigate(materialPrepDetail(id))` 只给出
`/material-prep/571` 不带 stage，于是那一次渲染先按 'inbox' 渲染收件箱列表，
下一拍阅读器才盖上来。同根因的另外三个入口一并修：
`InboxView.goPack`、`MessageDrawer.openPack`、`HomePage.goPack`（一律带 `?stage=todo`，
转出来的包必然是待处理）。从「已归案」点开的包，退出时应回「已归案」而非写死 todo。

> `GlobalSearch` 的 inbox 类别**未动**：它可能命中未经转换的收件箱消息，
> 强行加 stage 会把用户带到错误的分区。

#### 材料包阶段贴边且不能滚动

卡片化后两件事没跟着改：① 旧布局靠 `main` 的 `px-7` 内缩，网格自身不需要 padding，
卡片化后不内缩就贴边（收件箱列表一直有 `px-4`，所以只有「待处理」看着突兀）；
② 卡片是 `overflow-hidden` 而卡身没有 `overflow-y-auto`，旧布局靠页面整体滚动的
路径断了，内容超出即被裁掉。

`PackGrid` 根节点加 `p-4`，loading 占位改 `m-4`、错误块加 `p-4`，卡身加
`overflow-y-auto`。

> 这一轮当时的 725 条测试全绿却漏掉了这个视觉回归——现有断言只查结构类名
> （`data-pack-idx`、离场类），没有一条校验内边距/滚动。已补一条锁住
> 「根节点必须有内边距」。

#### 材料包默认名改为第一个文件名

上传后卡片标题是「前端材料预处理上传材料」，和右上角来源标签「前端材料预处理上传」
几乎重复，律师在一堆材料包里分不清谁是谁。

来源标签表达的是「这份材料从哪来」，再拿它当标题等于同一句话写两遍。默认名改为
**第一个文件的显示名（去扩展名）**，与列表第一张缩略图对应。细节：只取 basename
（压缩包展开的展示名带「子目录/文件.pdf」，标题不该带路径）；去扩展名只在
「点号前有名字且扩展名像扩展名」时做（`3.5亿借款合同.docx` → `3.5亿借款合同`，
不会把 3.5 当扩展名切掉）；空名兜底回原来源名，不返回空串。来源标签本身未改动。

#### 1GB 才会暴露的字节缓存隐患

`fetchAttachmentBytes` 的字节缓存原为无限增长，每打开一份附件就整份常驻。
50MB 时代已偏危险，1GB 会直接把标签页内存顶爆且毫无迹象。改为按
「总量 256MB + 单条 64MB 不进缓存 + 条目 FIFO 剃除」的有界缓存。

### 阅读器：工具栏

#### 自动分段改为 split button

原来的 `⋯` 菜单把**动作**（自动分段）、**设置**（版面策略/解析平台）与
**破坏性操作**（恢复初始分段）挤在同一串列表里：既难找，也看不出哪些选项会改变
「下一次识别」的行为。

```
点主体「自动分段」 → 立刻执行
点右侧小三角       → 打开设置下拉
```

`⋯` 按钮随之移除（它唯一的内容就是这些设置）。下拉里每个选项补一句**后果**而非
只写名词——它们直接影响计费与结果可信度：

```
仅文本层  电子版不上云 · 最快 · 无坐标
补版面    电子页也上云 · 可定位 · 按页计费
自动 / 仅 MinerU / 仅 Textin  失败自动切换 / 锁定 · 失败不降级
```

勾选位改为固定宽度的左侧 Check（而非标签后拼 `✓`），让两行文案左对齐。主按钮
tooltip 带当前策略摘要（「补版面 · 自动容灾」），不展开菜单就知道这次会怎么跑。
识别进行中时主体与设置入口**同时**禁用，避免改到正在运行的那次策略。

#### 缩放与列数收进单个视图入口

常驻区原是 5 个描边控件平铺（`−` / `100%` / `+` 三个框 + 列数框 + 分隔线），
占 ~175px。问题不是控件多，而是三件事被拆成五个同等权重的按钮：缩放本质是一个控件
却画成三个框；百分比是只读状态却做成可点按钮（点它归 100%，这个隐藏功能几乎没人
知道）；列数跟缩放无关却紧贴在一起。

改为一个「`100%▾`」入口：

- 常驻只显示当前倍率，**实测 175px → 59px，省下 116px** 给内容
- 点开才有 `−` / `+` / 「恢复到 100%」，重置成为明确的菜单项而非伪装成状态
- 列数按窗口上限逐项列出（单页 / 2 列 / 3 列），**点哪列就是哪列**
- 窗口不够宽时只列「单页」并说明原因

顺带修掉两个隐患：

- `changeCols` 的 `1→2→3→1` 循环语义在菜单里没有意义（三列时循环出的下一项是 1 列，
  点「2 列」却拿到单页），已随 `onChangeCols` 整条退役
- `zoomVal >= ZOOM_MAX * 100` 有浮点误差（`2.2 * 100 = 220.00000000000003`），
  导致 220% 时放大按钮**仍可点**（点了没反应），改为四舍五入后比较
