# v27.16.5 · 发票冲红重开（红字发票）：待认领链路完整支持作废与重开

> 分支 `feat/invoice-red-reenact`（2 个提交，后端 15 个源码文件 + 前端 10 个 + 7 个新测试）。
> 前置：`v27.16.0` 建立了发票待认领（邮件解析 → 首页确认绑定）。
> 本版补上那条链路此前完全没处理的业务：**财务把一张已开的票冲红、再重开一张**。

## 背景

`v27.16.0` 的待认领假设「一张票 = 一个独立待办」。真实业务里这个假设会破：
客户信息开错、金额开错、项目选错，财务的动作是**开红字发票冲掉原票，再重开一张蓝票**。

真实样本（`fachuan_dev`，2026-11-11）：

| 时间 | 事件 | 票号 | 金额 | 状态 |
|---|---|---|---|---|
| 11-10 | 开蓝票 → 律师确认 → `Invoice #13` | …368336 | ¥40,000 | 已入账 |
| 11-11 17:24 | 财务发重开的蓝票 | …185941 | ¥40,000 | 待认领 |
| 11-11 17:34 | 财务发红票（冲 …368336） | …102001 | **解析失败 → NULL** | 待认领 |

在旧版界面上，这是**两行长得一模一样的绿标「确定性匹配 ✓」**。

### 旧版的实际后果

| 后果 | 原因 |
|---|---|
| 律师按界面「正确点击」两次 → **多出一张重复的发票** | 两行各自可「确认绑定」，都挂到同一笔收款 |
| 合同文件夹里多一份**同名不同号**的 PDF | 红票与重开票同天同合同名，命名规则无区分 |
| 收款 `invoiced_amount` 数值**碰巧正确**（`Sum=80000` → `min(80000, 40000)=40000`） | 账面上看不出来，问题被掩盖 |
| 红票显示「金额与收款不符」 | 真实原因是**没识别出来**（`total_amount=NULL`），提示指错方向 |

## 后端

### 一、解析层：负号

`_TOTAL_PATTERN` / `_AMOUNT_PATTERN` 的字符类是 `[\d,]+`，**不认负号**。
红票票面是 `价税合计（大写）（负数）肆万圆整 （小写）¥-40000.00`，三个金额全部抽成 `None`。

```diff
- r"[（(]\s*小写\s*[）)]\s*[¥￥]\s*([\d,]+\.\d{2})"
+ r"[（(]\s*小写\s*[）)]\s*[¥￥]\s*(-?[\d,]+\.\d{2})"
```

同时新增两个票面事实（备注栏里本来就有，此前无人读）：

- `red_against_number`：被红冲蓝字数电发票号码
- `red_confirmation_no`：红字发票信息确认单编号（有法律效力的变动依据，审计留痕）

### 二、数据模型

`InvoiceIntake` 新增 4 个字段（迁移 `0054_invoice_intake_red`，纯加列，无回填）：

| 字段 | 用途 |
|---|---|
| `red_against_number` | 红票冲的原票号 |
| `red_confirmation_no` | 红字确认单编号 |
| `offset_invoice` (FK `Invoice`) | 原票在本库的记录（扫到即绑定） |
| `supersedes_intake` (FK self) | 重开蓝票 → 被它替代的**原票 intake** |

`is_red` **不落库**，用 `@property` 派生：`bool(red_against_number) or total_amount < 0`。
理由：存布尔位会与两个事实漂移；派生永远自洽。

`InvoiceStatus` 新增 `VOIDED_PENDING_REISSUE`（已冲红待重开）——净额口径下
「财务主动冲红」与「从没开过票」会同时是 `UNINVOICED`，必须区分。

### 三、扫描层

| 改动 | 说明 |
|---|---|
| 红票事实落库 + `offset_invoice` 绑定 | 按票号查 `Invoice`，命中即绑定 |
| `_refresh_red_links(project_code)` | 「红票→原票」「重开票→被替代 intake」双向配对，幂等、一对一 |
| **入池判据收窄** | 去掉裸「请查收」；新增 `_NON_INVOICE_FILENAME_PATTERNS`（检验报告/测试报告/联络函/对账单/质检/检测报告），**仅在全部 PDF 附件都命中时**才否决整封邮件 |
| 历史脏数据回填 | 只补空字段，绝不覆盖人工改过的事实 |

**配对只认红票作证**，不做「同项目同金额」的推测——分期开票、同额多期是常态，
擅自推测会把合法旧票误判为已作废。

### 四、匹配层

红票**永不预选收款**（冲销不是新的记账动作，预选会诱导人把红票当新票挂上去）。
置信度分两档：`red_offset` / `red_unmatched`。

被冲票号与「是否命中本库」由**扫描层显式传入**：

> 旧实现试图从「该合同唯一那笔收款已挂的发票号」推导被冲票号。但收款上的票号
> 是**收款自己的票**，不是红票要冲的票——推导结果**恒为空**，于是所有红票都被
> 判成 `red_unmatched`（「原票不在系统里」），把「可一键冲红」误报成「需人工处理」。

### 五、裁定层（核心）

一次原子事务完成整组：

```
confirm_red_reenact(red_intake_id, new_intake_id, user, note, amount_override)
  ① 落红票（金额为负）→ ② 原票移入 已冲红/ → ③ 落重开蓝票 → ④ 重算收款开票额
```

**六条硬守卫**（全部是错误，不是提示）：

| 守卫 | 条件 | 错误码 |
|---|---|---|
| G1 | 原票不在本库 → 禁止一键冲红 | `INVOICE_RED_OFFSET_NOT_FOUND` |
| G2 | 原票所属合同 ≠ 建议合同 | `INVOICE_RED_CONTRACT_MISMATCH` |
| G3 | 重开票金额非正 | `INVOICE_REENACT_NOT_POSITIVE` |
| G4 | 重开金额 ≠ 被冲金额（可 `amount_override` 放行，但留痕） | `INVOICE_REENACT_AMOUNT_MISMATCH` |
| G5 | 重开票号已在库 | `INVOICE_NUMBER_DUPLICATED` |
| G6 | 原票已被别的红票冲销 | `INVOICE_RED_ALREADY_APPLIED` |

另有 `confirm-red-only`（只冲红不重开：客户不要这张票了），走同一套守卫。
`confirm_invoice_intake` 拒绝红票走老入口（`INVOICE_RED_USE_DEDICATED_ENDPOINT`）。

**撤销是整组回滚**：删红票 + 删重开票 + 原票从 `已冲红/` 移回原位。
半截状态（红票删了、原票还在 `已冲红/`）比错账更难查。

### 六、记账层：净额

```python
total = Sum("total_amount")                      # 净额，含负数
if invoiced > 0:
    invoiced = min(invoiced, payment.amount)     # 上限只对正数成立
invoiced = max(invoiced, Decimal("0"))           # 满足 nonneg 约束
```

`min()` 若不加正数条件，会把「已冲红、待重开」错算成「已全额开票」。
派生的三个数供 UI 解释：净额 / 正票累计 / 已冲销额（不落字段）。

### 七、归档：物理目录隔离

> 用户口径：**「归档的时候是不需要已经作废的发票的，只需要保留合法发票即可」**

实现手段不是「归档期过滤」，而是**落盘时就分家**：

```
1-律师资料/3-发票/
  发票（…）_20261111开具.pdf        ← 唯一一份有效票，归档带走
  已冲红/                          ← 按需创建（无冲红则不存在）
    发票（…）_20261111红字开具.pdf   ← 红票
    发票（…）_20261110开具.pdf       ← 原票，已从根目录移出
```

查清的事实：归档材料走 `FinalizedMaterial` 表（`category="invoice"` → 清单项「收费凭证」），
`Invoice` 表的票**不会自动进归档**。所以只要扫描时看不到作废票，归档天然干净，
**归档代码一行判断都不用写**。

三道闸（从落盘到交付）：

| 闸 | 位置 | 规则 |
|---|---|---|
| 1（治本） | `_mirror_to_contract_folder` | 红票落 `已冲红/`；确认冲红时原票**移动**进去 |
| 2（防误选） | 合同文件夹扫描 | 跳过 `已冲红/`；「红字开具」候选不导入 |
| 3（兜脏数据） | 归档材料生成（两个消费端） | 文件名含「红字开具」永不进「收费凭证」 |

闸 3 不查 `Invoice` 表（`FinalizedMaterial` 只有 `file_path`，反查不回发票），
判据取文件名——这让 §「红票文件名加红字」从「防撞名」升级为「归档安全依据」。

## 真机验收抓出的 6 个缺陷

单测全绿但真机有问题，全部修复并加回归测试：

| # | 缺陷 | 后果 |
|---|---|---|
| 1 | 从「收款上的发票号」推导被冲票号 | 恒为空 → **所有红票**都误报「原票不在系统里」 |
| 2 | `reparse_invoice_intake` 缺 `@transaction.atomic` | `select_for_update` 直接抛错，**「重解析」一点就 500** |
| 3 | 回填只补字段、不重算 `payment_pick` | 红票仍显示「金额与收款不符」 |
| 4 | 重开票查找限定在本批 pending | 重开票指向**已确认**的原票 → **组永远拼不起来** |
| 5 | 组事实只发给红票 | 重开票被当独立行 → **组卡片 + 一条重复的新票** |
| 6 | 详情端点单张查询重开票 | 弹窗里三段信息凭空消失 |

### 撤销链路的三个缺陷（真机连续点两次才暴露）

| 缺陷 | 后果 |
|---|---|
| `supersedes_intake` 语义两套并存（确认时指向红票，扫描/装配层按原票反查） | 确认后组卡片缺 `reissue` 段；一个项目里有多组冲红重开时**跨组错配** |
| 撤销时清空 `supersedes_intake` | 两票回到 pending 却失去配对，首页退化成两行，重开票能被当普通待办**再确认一次（多开一张票）** |
| `_red_group_of` 拿 intake pk 比 `Invoice` pk | 从重开票端撤销时**拿错票**（实测 93 vs 92），整组只回滚一半 |

第二条尤其隐蔽：单测里的 `_red_triplet` 写的就是「指向红票」——**测试和实现一起错了**，
只有真机操作才能对出来。现统一为「重开票 → 被替代的原票 intake」，
并加 `test_group_lookup_is_symmetric` 锁死两端对称性。
