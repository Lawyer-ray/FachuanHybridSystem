# v27.23.7 · AI 助手「会话不存在」被报成未知错误：流式层吞掉 code/scope/detail + 前端码表缺 4 个后端码

## 一句话定位

| 之前 | 现在 |
|:--|:-|
| 律师点开 AI 助手，看到 `错误码：unknown` + `原文：会话不存在`，**卡片上没有任何可点的动作**，只能复制诊断找人 | 同一条错误显示为「会话在原位置已不存在」+ **「新开会话」按钮**，一键重开 |
| 诊断文本只有 3 行（时间 / 错误码 / 原文），连是哪个会话都看不出 | 恢复 `范围` / `来源` / `详情：session_id=…` 三行——**这正是当时查不下去的原因** |
| 后端 `errors.py` 有 11 个稳定错误码，前端码表只认得 7 个，其余一律折成 `unknown` | 补上 `session_not_found` / `auth_failed` / `too_many_agents`，并把后端拼写 `quota_exceeded` 接到表中的 `quota_exhausted` |

## 症状与取证

用户报的是一段「复制诊断」文本：

```
时间：2026-11-24T06:39:56.073Z
错误码：unknown
原文：会话不存在
```

**缺的三行就是线索**：`diagnosticsOf` 的字段顺序是「时间 / 错误码 /〔后端原始码〕/〔范围〕/〔来源〕/〔连续次数〕/〔详情〕/ 原文」，缺 `后端原始码` 说明 `rawCode` 是空串，缺 `范围` 说明 `scope` 也是空——**但后端明明给了**。

顺着两条链各自查到根：

**① 后端是对的，前端流式层把三件套扔了**

```
backend/apps/agent/api/chat_api.py:258
  iter([_sse(frame_for(SessionNotFoundError, detail={"session_id": session_id}))])
      → code="session_not_found", scope="request", detail={session_id}

frontend/src/features/copilot/streaming.ts:252（修前）
  h.onError(event.message, origin)      ← 只转发 message
```

`lane-lifecycle.ts` 再 `set({ lastError: message })`，于是 store 里只剩一段裸文案；
`classifyError` 拿不到 code，只能按文案兜底，最后落 `unknown`。**信封机制（`encodeError`）
本来就在，只是这条写入路径没接上。**

**② 即使 code 没丢，也认不出来**

后端 `ERROR_CODES` 11 个 vs 前端 `CODE_TABLE` 7 个，缺 4 个：

| 后端 code | 修前前端 |
|:--|:--|
| `session_not_found` | 无 → unknown |
| `auth_failed` | 无 → unknown |
| `too_many_agents` | 无 → unknown |
| `quota_exceeded` | 表里写的是 `quota_exhausted`（拼写不一致）→ unknown |

所以这张卡是**结构性死路**，不是偶发。

## 改了什么（6 个文件）

| 文件 | 改动 |
|:--|:--|
| `streaming.ts` | `onError(message, origin)` → `onError(err: ErrorInput, origin)`，把 `message/code/scope/detail` 整包转发；补注释记录为什么不能只传 message |
| `handlers/lane-lifecycle.ts` | 写入改走 `encodeError({...err, message})`；多答前缀仍拼进 message（`splitLanePrefix` 靠它拆「来源」，两处口径必须一致） |
| `domain/error-codes.ts` | 补 3 个 code（含 kind/severity/hint/resendable）+ `quota_exceeded → quota_exhausted` 别名 |
| `domain/error.ts` | 新增动作 `new_session`；`session_not_found` → 返回「新开会话」 |
| `components/ErrorNotice.tsx` | 接上新动作（`clearError()` + `switchSession(null)`），图标/文案补齐 |
| `store/session.ts` | 拉历史 **404** 不再笼统报「加载会话历史失败」，改报 `session_not_found` + `detail.session_id`（网络抖动仍走原文案） |

**为什么 hint 里不写「请联系管理员」**：会话没了是律师自己能解决的事（重开一个）。
写「联系管理员」等于把一个 5 秒能自解的问题转成一次求助；而 `resendable` 也必须是
`false`——会话都不存在了，原样再发只会再撞一次 404。

新增测试 4 条（`domain/error.test.ts` 3 条 + `store.streaming-events.test.ts` 1 条）：

1. **码表对齐守卫**——把 `errors.py` 的 11 个 code 快照成一张名单，逐个断言
   `rawCode` 原样带出且**不得落 `unknown`**。修前 `session_not_found` 必然红。
   > 已知局限：两份表不在同一语言里，后端新增 code 这条用例不会自己红。所以
   > 「新增后端 code」那次改动必须同步这张名单——已写在用例注释里。
2. `session_not_found`：kind/severity/`resendable=false`/hint 含「新开会话」/动作正确。
3. `quota_exceeded`（后端拼写）→ `quota_exhausted`（表内拼写），防拼写漂移复发。
4. **端到端信封**：喂一条带 `code/scope/detail` 的 SSE 错误帧，断言 `lastError`
   里真的带着 `session_not_found` 与 `session_id`——这一条直接锁住 ① 那个丢字段的 bug。

## 顺带一个反直觉的点

`detail.session_id` 的丢失让排障**变难**而不是变简单：本来一条诊断就能看出是哪个会话、
在哪台环境没了，结果只剩一句「会话不存在」。所以「少传几个字段」不是性能优化，
是把可诊断性换成了不可诊断性。

## 会话为什么会真没了（没改，属正常）

浏览器 localStorage 里存的 `session_id` 撞上服务端不存在的记录：DB 重置/重新迁移、
换环境（本地↔测试）、或在别处删了会话。这本身是正常状态，**不正常的是前端不自愈**——
这才是本版修的东西。原会话内容不会因此找回，也不会自动跟到新会话。
