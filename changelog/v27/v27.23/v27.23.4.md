# v27.23.4 · CodeQL note 级告警上棘轮：门禁从「只卡 error/warning」扩到 note，并拆掉 required check 会锁死仓库的触发陷阱

> **版本判定**：按 `docs/harness/changelog.md` §1.1 最后一条——「护栏、脚本、门禁、脚本化检查
> 是公共基础设施，不构成独立能力轴，**一律只加第三位**」。故为 `v27.23.4`，不开 `v27.24.0`。

## 一句话定位

| 之前 | 现在 |
|:--|:-|
| `Alerts gate` 只卡 `error`/`warning`，note 级**无人看管**。实测 note 从 #564 收尾时的 **6 条涨到 235 条**，其中 **153 条是最近 7 天新增** | note 级上棘轮：**强制执行层 94 条**（客观真阳，PR 新引入即失败）+ **观察层 141 条**（已知误报类，只报告） |
| 「main 上新增 error/warning 会让 main 立刻变红」被当成拦截，**实际一条 required check 都没配**（API 返回 `Required status checks not enabled`） | 实测事实写进 SKILL 与 workflow 注释；「变红」与「拦截」两个概念彻底分开写 |
| `codeql.yml` 的 `pull_request` 带 `paths: [backend/**, scripts/**]` | **去掉**——否则一旦 `Alerts gate` 被设为 required，纯前端/纯文档 PR 的 check 永不上报，`enforce_admins: true` 下**连 owner 也合不了** |
| `.agents/skills/fachuan-protected-main-workflow/SKILL.md` 写「Required check for merge: `backend-security-guard`」——**是假的**，全仓库 AI 会话都在按不存在的保护行事 | 按实测订正，并补 Common Fix Paths D2「设 required 前必须确认 workflow 每类 PR 都触发」（⚠️ 该文件被 `.gitignore:90` 忽略，**不进版本库**，详见下节） |

## 做了什么

### 1. 先量事实，再动门禁（2026-11-24 实测）

```
open 告警 total           235   （全部 rule.severity = note；error/warning = 0）
most_recent_instance.ref  235 条全部 refs/heads/main
最近 7 天新增             153 条
```

按规则分布，并据此确定「哪层能卡」：

| 规则 | 数量 | 层级 | 依据 |
|:--|-:|:-|:--|
| `py/ineffectual-statement` | 72 | 观察 | 抽样 `def tool() -> None: ...` 的省略号体被判无效果语句——**idiom，误报** |
| `py/unused-import` | 71 | **强制执行** | 无任何误报可能 |
| `py/unused-global-variable` | 51 | 观察 | 抽样 `_pool_lock = _LoopScopedLock()` 经模块属性访问被判未使用——**误报** |
| `py/catch-base-exception` | 13 | 观察 | 线程边界的 `except BaseException` 有意为之（收窄会丢异常，#564 已记录） |
| `py/unused-local-variable` | 12 | **强制执行** | 无误报可能 |
| `py/unnecessary-lambda` | 8 | **强制执行** | 无误报可能 |
| `py/empty-except` | 5 | 观察 | 多为有意吞异常，需人判断 |
| `py/mixed-returns` | 2 | **强制执行** | 无误报可能 |
| `py/import-and-import-from` | 1 | **强制执行** | 无误报可能 |

**强制执行层 94 条 / 观察层 141 条 = 235。** 不搞「note 全卡」的理由就是 #564 自己写过的
教训：note 占存量绝大多数，全卡 = 上线即全红 = 等于没上线。

### 2. note 棘轮独立成 step，不并进已有的 error/warning 门禁

`alerts-gate` job 里新增第二个 step `Enforce note-level alerts`（162 行脚本），
**刻意不复用、不修改**上面那段已验证可用的 error/warning 逻辑（它自 2026-11-23 起在 main 上
真抓到过 5 次告警）。动机是隔离失败：note 逻辑写错最多多一个红 step，不会连坐把
error/warning 门禁一起搞哑。

两条路径语义**不同**，注释里写死了，避免以后被当成同一件事：

| 事件 | 统计范围 | 失败条件 | 是不是真拦截 |
|:--|:--|:--|:--|
| `pull_request` | 只算落在**本 PR merge ref**（`refs/pull/N/merge`）上的执行层告警 | `> 0` | ✅ 是（前提：配进 required checks） |
| `push` / `schedule` | 全仓 note 总量 | `> MAX_OPEN_NOTE_ALERTS`（235） | ❌ 不是——main 的 push 不受 required checks 约束，只是**可见化** |

新增环境变量：

```yaml
MAX_OPEN_NOTE_ALERTS: "235"     # 只准下调；上调须在同 PR 写明理由（如 CodeQL 版本漂移）
NOTE_RULES_ENFORCED: "py/unused-import, py/unused-local-variable, py/import-and-import-from,
                      py/unnecessary-lambda, py/mixed-returns"
```

### 3. 拆掉 required check 的触发陷阱（本 PR 最容易造成事故的一处）

`codeql.yml` 原本：

```yaml
pull_request:
  paths: ["backend/**", "scripts/**", ".github/workflows/codeql.yml"]
```

这条 path 过滤意味着**纯前端/纯文档 PR 不触发本 workflow**。GitHub 不会把「未触发的
required check」当作通过，而是永久停在 `Expected — Waiting for status to be reported`；
再叠加 `enforce_admins: true`，结果就是**任何人（包括 owner）都无法合并任何前端/文档 PR**。

所以本 PR 去掉 `pull_request` 的 path 过滤（`push` 侧保留）。代价：纯文档 PR 也跑一次
CodeQL analyze（实测 5–8 分钟，与其它 job 并行）。**用这个代价换「门禁真的会拦」而不是
「门禁看着像会拦」，值。**

为什么不是「把门禁拆成独立轻量 workflow 来省掉 analyze」：那样会失去 `needs: analyze`，
门禁可能在同一 PR 的扫描完成前就跑完——此时 `refs/pull/N/merge` 上还没上传任何告警，
计数自然是 0，**静默报假绿**。宁可多烧几分钟 CI，也不要一个会假绿的门。

## 怎么验的（本地真跑，不是读一遍觉得对）

把 step 里的脚本从 YAML 里 `yaml.safe_load` 抽出来，用**真实 235 条告警数据**喂进去，
`gh` 打桩成 `cat <json>`，跑 11 个场景：

| # | 场景 | 期望 | 结果 |
|:-:|:--|:-:|:-:|
| A | push main，235 vs 基线 235 | PASS | ✅ |
| B | push main，235 vs 基线 234 | FAIL | ✅ |
| C | PR，235 条存量全在 `refs/heads/main` | PASS | ✅ |
| D | PR 新引入 2 条 `unused-import` | FAIL | ✅ |
| E | PR 新引入 1 条 `empty-except`（观察层） | PASS | ✅ |
| F | 无 `GITHUB_TOKEN` | PASS（降级） | ✅ |
| G | 基线写成 `abc` | PASS（降级） | ✅ |
| H | API 返回结构异常 `{}` | PASS（降级） | ✅ |
| I | API 返回空数组 `[]` | PASS（不能误降级） | ✅ |
| J | 多页拼接（235 条拆 3 个顶层数组）vs 234 | FAIL（证明没丢页） | ✅ |
| K | `schedule` 事件走全仓路径 | PASS | ✅ |

**自测过程中抓到两个会发假绿灯的真 bug，都修了：**

1. **规则分布表静默渲染成 0 行**。原因是 jq 写成 `$enf | index(.rule)`——`.` 落在 `$enf`
   （字符串数组）上取索引，jq 报 `Cannot index array with string "rule"` 后中止，表格只剩表头；
   而 step 照样 exit 0，肉眼很容易放过。修法：先把当前行绑成 `$row` 再用 `$row.rule`，并加
   一条自检——`repo_total > 0` 但表格为空时打 `::warning` 并写 `_渲染失败_`。
2. **API 返回 `{}` 时判「0 条，通过」**。`[inputs | .[]]` 把对象遍历成空，于是零计数通过，
   注释却写着「结构异常会降级」。修法：响应里连一个 `[` 都没有就降级（`[]` 仍正常走通过）。

## 顺带查出：规范文档全在 `.gitignore` 里，写错了没人兜

为了订正「`backend-security-guard` 是必需检查」这句谎言，扫描了全仓文档，并用
`git check-ignore -v` 逐个核实（不靠推理）：

| 文件 | gitignore 依据 | 能否被 commit |
|:--|:--|:--|
| `.agents/skills/**/*.md` | `.gitignore:90` `.agents/` | ❌ |
| `docs/**` | `.gitignore:257` `docs/` | ❌ |
| `CLAUDE.md`（含各子目录） | `.gitignore:321` `**/CLAUDE.md` | ❌ |
| `.github/workflows/**`、`changelog/**` | — | ✅ |

后果：**全仓库工程规范都是本地文件，不进版本库、不被 CI 校验、不被 review 看见**。
所以「文档说某 check 是必需的」这类断言可以长期假下去而无人发现——本次就是例子：
`CLAUDE.md:197/205`、`docs/harness/pr-flow.md`、`.agents/skills/*/SKILL.md` 都在说
`backend-security-guard` 是必需检查，而实测一条 required check 都没有。

本轮**一并订正了 5 个本地文件共 14 处**（均不入库，仅本机生效）：

| 文件 | 处数 | 订正内容 |
|:--|-:|:--|
| `CLAUDE.md` | 3 | 「铁律」里加「关键 job ≠ required checks + 实测 404 + 自查命令」；流程第 6 步把
`backend`（ruff/mypy/pytest/bandit/pip-audit）与 `backend-security-guard`（增量行敏感模式）拆开；§CI 等待上限删「（必需检查）」并补「纪律约束 ≠ 平台约束」 |
| `docs/harness/pr-flow.md` | 6 | 「四道必需检查」→「四道把关 job」；**决策树去掉空集陷阱**（`全部 required 已 pass` 对空集恒真 → 改为「关键 job 全部 pass（须非空）」）；「这那么认 required」整段重写为「先查 API 配置，404 才退回自觉名单」；§3 理由、§5 检查单、§9 收尾同步改词与职责归属 |
| `docs/harness/index.md` | 1 | 每周快捷清单第 7 条同步 |
| `.agents/skills/fachuan-protected-main-workflow/SKILL.md` | 3 | Required checks 改为实测事实；新增 Common Fix Paths D2「设 required 前必须确认 workflow 每类 PR 都触发」 |
| `.agents/skills/fachuan-django-ninja-backend-patterns/SKILL.md` | 1 | 「merge 终点是 `backend-security-guard`」改为「PR + key CI jobs green」 |

**最值钱的一条是 `pr-flow.md` 决策树里的空集陷阱**，不是措辞问题：原文写
「以 `gh pr checks` 里标为 required 的为准」+「全部 required 已 pass → 立刻合并」。
required 集合为空时，「全部通过」**恒真** → 照字面执行就是**一次 check 都没看就直接合并**，
连 5 分钟都没等。这就是这套幻觉能活一个月的真正原因：流程自己证明了自己。
改完后新增一道前置：**先 `gh api .../required_status_checks` 确认平台到底配了什么**
（返回 404 即空集），而不是先看一份硬编码名单。这样以后真配上 required checks 时，
这几处文档**不需要再改一遍**。

> 顺带一个独立的事实错误：`CLAUDE.md:197` 把 `backend-security-guard` 描述为
> 「ruff / mypy / pytest / bandit / pip-audit」，实际该 job 只跑
> `devtools/security_guard.py --check sensitive`；那些检查在 `backend` job 里。

## 边界（明确不做）

- **不清理那 235 条存量**。本版只上棘轮，让「不再增长」可被机器发现。存量里 141 条是误报类，
  清它等于跟 CodeQL 的视线较劲（`global` 读取、`...` 函数体、`except BaseException` 边界）。
- **不改 error/warning 门禁的任何一行逻辑**，只在它后面加新 step。
- **不在本 PR 改仓库设置**。`required_status_checks` 是 `PATCH /branches/main/protection`，
  改不了代码仓；配置动作在其后单独执行，并先用一个纯文档 PR 实测「check 真的会上报」再设，
  避免一设就锁死。
