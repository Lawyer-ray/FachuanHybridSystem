# v27.21.1 — 四栏验收发现的三个缺口全部修掉（dsh 证据链 / openai-agents 成本与 done / 平台解析不再读同步 ORM）

> 承 `v27.21.0`。上一版把第四个 agent 接进来后做真机验收，暴露出三个**既有**缺陷
> （记在 `TECH-DEBT.md` ⑥）。本版把三条全部闭掉，并复跑全量四栏验收。

## 修了什么

### 1. `dsh`：工具结果整条链路缺失（前端看不到检索证据、引用抽不出来）

**证据（真机 census，SDK 0.2.2rc2，一次 8 次工具调用的联网检索轮）**：

```
{'session/title': 1, 'session/context': 1, 'assistant/message': 6,
 'tool/call': 8, 'tool/result': 8, 'step/end': 6, 'turn/end': 1}
```
`tool/result` **一直存在**，只是 `_translate_event` 没写这个分支——所以「一轮 8 次调用、
0 条结果」不是 runtime 缺数据，是我们自己把结果丢了。

**改法**（`dsh_backend.py`）：

- 新增 `tool/result` 分支 → `tool_result` 帧。字段形状逐字取自实测：
  `data.message.{toolCallId, content[], isError, source.callId}`；
  名字不在结果事件里，靠 `tool/call` 记下的 `callId → name` 配对表补（取用即 pop）。
- 结果文本只取 `text` 块、截断到 **2000 字**（与 `pi/bridge.py` 同一上限——
  `services/chat/citations.py` 的兜底解析按「结果前 2000 字」写死，两条通道长度不同
  会让同一份 `search_cases` 结果一边出引用、一边一条都出不来）。
- 失败是 `isError` 布尔：映到 `is_error=true`，且无错误正文时补一句可读文案。

### 2. `dsh` + `openai-agents`：都不发 `usage`，成本账恒记 0

- **dsh**：用量其实一直在 `assistant/message` 的 `data.usage` 上
  （`{inputTokens, outputTokens, totalTokens, cacheReadTokens}`，每次模型调用一份）。
  模块注释里那句「待 SDK 暴露 usage/stats」是**错判**——`totalTokens` 是累加后的
  上下文大小（实测同轮 11348 → 38986），不能当用量，但 `inputTokens` /
  `cacheReadTokens` 是**未含缓存**的真实计费量，直接逐次上报。
- **openai-agents**：`RunResultStreaming.raw_responses[*].usage` 恒 `None`。根因不在
  SDK：**律所网关（LiteLLM → vLLM）流式默认不回 usage**，要显式带
  `stream_options: {"include_usage": true}`。网关侧对照实测：

  | 请求 | 流式末块 |
  |:-|:-|
  | 不带 `stream_options` | `usage=None` |
  | 带 `{"include_usage": true}` | `{"prompt_tokens": 8, "completion_tokens": 2, "total_tokens": 10, ...}` |

  改法：把 `stream_options` 与思考参数合并进同一份 `extra_body`（两者都是「网关要、
  SDK 默认不发」的字段，分两处构造会互相覆盖），收尾从 `raw_responses` 累加成
  **一帧** `usage`（`input_tokens` 减掉缓存读/写、缓存单列）。

### 3. `openai-agents`：单栏发两条 `done`

后端 `_run` 自己 `yield done` + 编排层 `stream.py` 又铸一条 → 实测 `done=2`。
删掉后端那条，与 `pi_backend` / `antigravity_backend` 同口径（单测改成断言
**后端不发 done**，done 由编排层铸造）。

### 4. 平台解析在异步上下文读同步 ORM（四栏（含未改动的 pi）每轮都刷一条 WARNING）

```
[LLMProviderService] 读取平台配置失败
django.core.exceptions.SynchronousOnlyOperation: You cannot call this from an async context
```

**调用链**：`services/chat/persist.py::_record_run`（async）→
`core/llm/provider_lookup.resolve_provider_name`（同步）→
`LLMProviderService.get_providers()`（同步 ORM）→ 抛错被 `_load_from_db` 吞成空列表
→ `AgentRun.provider` **静默变成空串**（不只是日志噪音，是成本归属丢数据）。

**改法**：`provider_lookup` 新增 `aresolve_provider_name()`（内部 `await aget_providers()`，
即 `sync_to_async` 版），`_record_run` 与 `core/llm/tracking.arecord_llm_call` 改走它；
**同步版原样保留**给真正的同步调用者。新增护栏单测：把同步访问器 monkeypatch 成
「被调即 AssertionError」的哨兵，再 await 异步链路。
