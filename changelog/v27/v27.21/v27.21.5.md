# v27.21.5 — 网关协议层：思考开关与降级语义收敛到唯一来源

> 承 `v27.21.4`。本版不加功能，只修「同一个开关在不同入口产生不同行为」——
> 一个已经在产生**静默质量差异**的分叉，以及一个在产生**无效计费**的降级条件。

## 病因（都有实测证据，不是推测）

网关「认哪些字段、认哪些档位、认哪些模型能思考」这三件事被复制在 5 处：

| # | 位置 | 内容 |
|---|---|---|
| 1 | `models/llm_provider.py` `_THINKING_CAPABLE_MARKERS` | `("kimi", "mimo", …)` —— Agent 通道用，**宽**匹配 |
| 2 | `backends/openai_compatible.py` `_DISABLE_THINKING_MODELS` | `{"kimi26", …}` —— 服务通道用，**窄**匹配 |
| 3 | `pi/model_config.py` `_GATEWAY_EFFORT_MAP` | `minimal→low` / `medium→high` |
| 4 | `agent/backends/dsh_config.py` | 自写 `("off","low","high","xhigh","max")` |
| 5 | `openai_compatible._fallback_models_for` + `pi.resolve_fallback_models` | 两份近似的降级链解析 |

### 后果 A：`kimi-k2` 在两个入口思考与否相反

`"kimi"` 命中 → Agent 通道判为可思考，下发 `thinking=true` + `reasoning_effort=max`；
`"kimi26"` 不命中 `kimi-k2` → 服务通道**一个字段都不发** → 不思考。

同一平台、同一模型、同一个 `enable_thinking` 开关：copilot 里深度推理，诉状生成 /
合同审查 / 短信解析不推理。因为「不下发开关 ≠ 关闭思考」（本仓 `v27.20.x` 已实测），
**没有任何报错**，只有质量差异。

反方向同样成立：即便命中窄表，服务通道也只发开关不发 `reasoning_effort`——而
`pi/model_config.py` 自己的注释写着「只发前者等于永远停在默认深度」。

### 后果 B：400 参数错也会触发降级重试

`openai_compatible.py:408-418` 把**所有** `APIStatusError`（含 400）映射成
`LLMAPIError(status_code=…)`，而 `_FALLBACK_TRIGGER_ERRORS` 含 `LLMAPIError`。
于是一次坏 prompt 会把降级链上每个模型各打一遍（3 个 fallback = 4 倍计费，
结果必然一样是 400）。原注释「参数错（400）不在其列」是**假的**。

### 后果 C：`rpm_limit` / `tpm_limit` 对最耗量的入口不生效

两个字段的唯一消费点是 `key_pool.configure_limits`，唯一调用方是服务通道
（`openai_compatible.py:164-165`）。`rg -rn "rpm|tpm" apps/agent/` **零命中** ——
copilot 主对话完全不看这两个字段，而 Admin 上它们看起来是生效的。

## 改法

### 新增 `apps/core/llm/gateway_profile.py`（唯一权威）

纯函数模块，零 IO。对外：`normalize_model_key` / `model_supports_thinking` /
`GATEWAY_EFFORTS` / `DEFAULT_THINKING_LEVEL` / `gateway_effort` /
`selectable_efforts` / `ThinkingDirectives` / `resolve_thinking` / `wire_fields` /
`RETRYABLE_EXCEPTIONS` / `is_retryable` / `fallback_chain` / `RATE_LIMIT_CHANNEL_NOTE`。

关键设计：`ThinkingDirectives` 是**与传输格式无关**的中立指令，5 个 adapter 各自
只做序列化——服务通道→`extra_body`、pi→`models.json` 的 `compat` 段、dsh→YAML
patch、openai-agents→`ModelSettings`、antigravity→loopback 代理注入 JSON body。

`resolve_thinking` 收 `level` 入参：`enabled = supported and enable_thinking and level != "off"`，
档位→白名单的映射只此一处（否则 pi/dsh 的会话档位映射又会散回各处）。

### 各 adapter 变薄

| 文件 | 改法 |
|---|---|
| `backends/openai_compatible.py` | `_build_extra_body` 走 `resolve_thinking`+`wire_fields`；删 `_DISABLE_THINKING_MODELS` / `_normalize_model_key`；降级链走 `fallback_chain`，`except` 分支加 `is_retryable` 二次过滤 |
| `pi/model_config.py` | 档位常量改为从权威模块再导出；`reasoning` 由 `resolve_thinking` 驱动；`resolve_fallback_models` 走 `fallback_chain`（**去掉 `str()`**，否则 `list[str]` 会被字符串化成 `"['glm53', …]"`） |
| `backends/dsh_config.py` | 档位集合改 `selectable_efforts()` |
| `backends/openai_agents_backend.py` | `_thinking_settings` 走 `wire_fields`，与 `pi.model_config` 解耦 |
| `backends/antigravity_backend.py` | `thinking_extra` 走 `wire_fields`，与 `pi.model_config` 解耦 |
| `backends/antigravity_gateway.py` | 只负责把上层算好的 dict **只补缺不覆盖**地合并（红线未动） |

### 校验

- `models/llm_provider.py` 的 `supports_thinking` 改为**函数内**延迟 import 并委托
  （模块顶层 import `apps.core.llm.*` 会与 models 成环）
- `agent/backends/gateway_cache.py` 改为委托，去掉对 models 私有常量的反向 import

### rpm/tpm：选择「诚实明示」而不是「假装接上」

不接进 `key_scheduler`：rpm 需要观测**请求边界**，而 pi/dsh/antigravity 的 model
调用在外部进程内部，Django 侧只拿得到轮次；按轮次近似会把「一轮 = 20 次调用」
记成 1 次，属误导。且 `TECH-DEBT` ⑤ 已实测「精确在飞计数买不到容量」。

改为：`gateway_profile.RATE_LIMIT_CHANNEL_NOTE` 单一文案，Admin 表单 help_text 引用它，
`key_pool` 模块 docstring 写清原因，结构测试锁死这三处不许被悄悄删掉。

**为什么不写模型字段 help_text**：任何字段属性变更都会让 `makemigrations --check`
判定有待迁移，于是要建 `0042_alter_llmprovider_rpm_limit_and_more`、再在开发库
`fachuan_dev` 上 `migrate`——而 `backend/CLAUDE.md` 硬规则第 3 条是「migrate 必须
用户明确同意」。为一条展示用字串付一次 DB 迁移 + 一次审批 + 一份永久迁移文件，
且正好撞上本仓记录过三次的「迁移文件在、开发库没 migrate、CI 全绿」事故类型。不划算。

## 新增守卫

`tests/ci/structure/test_llm_gateway_protocol_single_source.py`（5 条断言）：

1. 思考能力特征串只许出现在 `gateway_profile.py`
2. `reasoning_effort` 白名单字面量元组只许出现在 `gateway_profile.py`
3. `{"chat_template_kwargs": {"thinking": …}}` 的 dict 字面构造只许出现在 `gateway_profile.py`
4. **计算**字段的 adapter 必须 import `gateway_profile`（纯传输层不在清单内——对
   `antigravity_gateway` 来说守卫是断言 3，不是逼它加一个只为过检查的 import）
5. Admin 表单 `rpm_limit` / `tpm_limit` 的 help_text 必须写明「仅服务通道生效」

## 上线后该盯的一条

开启思考的服务通道请求体现在多了 `reasoning_effort`（此前从不发），而 400 现在
**不降级**。两者组合下，若某个后端不认这个字段，失败会直接冒给调用方而不是被
fallback 掩盖。这是本次唯一需要真机确认的行为变化点。

## 遗留（已记录、不在本版范围）

`is_retryable` 修的是「400 是否降级」。若将来出现「只有某个 fallback 模型支持
该请求形态」的场景，4xx 直接失败会比旧的「继续试下一个」更严格——按契约判定
4xx 换模型必然同错，接受此取舍。
