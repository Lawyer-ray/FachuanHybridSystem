# v27.26.0 · 回传件内容核对：客户悄悄改了起诉状，归档前就报出来

> **版本判定**：按 `docs/harness/changelog.md` §1.1-A，本次做的是另一条能力轴——
> 另一批用户动作（律师核对**客户回传件**是否被改动）、另一批文件（`backend/apps/doc_verify/**`、
> `frontend/src/features/material-prep/doc-verify/**`）、另一个验收口径（漏检/虚警与状态语义，
> 不是界面上看得清不清楚）。上一条线 `v27.25.0` 是「收件箱分诊」（附件元信息 + 首页缩略图 +
> 应用内预览），两者没有共同的用户动作，故新开 `v27.26`。

## 一句话

| 之前 | 现在 |
|:--|:-|
| 律师把起诉状发给客户签字，客户回传扫描件，系统当一份普通材料归档。客户把诉请金额 `998,702.06` 改成 `998,670.21`、删掉一句不利事实，**没有任何提示**——直到开庭念错数才发现 | 出站那一刻冻结基线，回传后自动逐级核对：金额/日期/案号/诉请项数**红线**、段落增删**疑似**、无文本层**不给绿灯**。律师在归案弹窗里就地看到「本案 N 份待裁决」，采纳或退回都留痕 |
| 「核对了」只有两种结果：通过 / 不通过 | **六个状态**：`identical` / `verified_clean` / `no_difference_detected`（灰，只跑了免费层）/ `changed` / `unverifiable` / `not_requested`。把「没花钱核」显示成绿色，等于替系统说一句它没有证据的话 |

## 后端：把「文档比对」降维成「断言回归」

不做全文 diff（中文扫描件 OCR 差异率 3–8%，diff 出来是一屏噪声），而是把出站件固化成
**五级断言**，回传件逐级核对，产出可复核的失败清单：

| 级别 | 断言 | 抓什么 |
|:--|:--|:--|
| 包级 | 页数 / 文书名集合 | 少一页、多塞一份 |
| 页级 | 逐页图像指纹（100dpi 二值化 8px 块墨占比，沿用 `pdf_splitting` 口径） | 整页换掉、抽页、页序调换 |
| **字段级（红线）** | 金额 / 日期 / 案号 / 诉请项数 | 改一个数字、换主体 |
| 段落级（疑似） | 段落存在性 + 首末句锚点 + 段序 | 删一句、加限定语 |
| 覆盖度（灰） | 两侧都取不到文本的页 | 图片页/手写页——**不许给绿灯** |

- `domain/normalize.py`：归一化唯一真源（全半角、空白、页眉页码），`split_pages` 按 `\f`
  切页，三方共用一份
- `domain/compare.py`：字节相同**先短路**（原样回传是硬事实，不白跑断言集）
- `domain/states.py`：状态由 findings + coverage 推导，**`verified_clean` 看「正文是否真的比过」
  而不是 tier**——tier 只说明花了多少钱；`BLOCKING_STATES` 只含 `changed` / `unverifiable`，
  `no_difference_detected` 不进集合（它是「没花钱核」，不是「检出问题」；并进阻塞集合
  会让扫描件回传永久红，结果一定是律师关掉功能）

#### 出站基线：锚在「我们实际发出去的那一份」

`OutboundArtifact` 存三套东西：**逐页指纹**（定位哪几页变了，不 OCR）、**文本层**（判定改了
什么，**基线侧永不 OCR**——两侧都带 OCR 噪声时误报率平方级上升）、**允许变化区域掩膜**
（签名/日期/盖章区，高风险四类默认给「文末签署区」）。幂等键 = 同案 + 同文书 + 同版本 + 同字节。

#### OCR 层（tier ≥ 1）：扫描件才真的能比正文

扫描件没有文本层，免费层一个字都比不了。`services/anchor/ocr_fill.py` 补上这一层：

- **只补没字的页**（已有文本层的页绝不重 OCR）
- **默认全量：每一页都核**。曾按「前 10 页」设过上限，被律师否掉——没核的页恰恰是客户
  最可能动手脚的地方，只核一部分的结论写不进卷宗。剩下的只有病态保护
  `OCR_HARD_LIMIT=500`（超了报灰项 `OCR_BUDGET_EXHAUSTED` + `unverifiable`）
- `hint_pages` 由**页指纹**给出：基线渲染页 vs 回传页面距超 `SAME_PAGE_MAX_DISTANCE` 的页
  先 OCR。它只调顺序、不做筛选——先出可疑页的结论，律师不必等整本 OCR 完才看到红线
- 引擎不可用 → `engine="unavailable"` + 灰项 `OCR_UNAVAILABLE`，**不抛异常、不 500**
- 单页失败不拖垮其它页；输出正文按 `\f` 分页，段数与页码严格对齐

**层数怎么定（`tier` 语义 = 三种不同的钱）**：不传 `tier` = 自动（勾了「回传后核对
内容」且入站件整篇没文本层 → 升 OCR 层）；显式 `tier=0` = 只要免费层，**必须尊重**；
显式 `tier>=1` 原样返回。同一份字节升层时**原地升级同一行**（`run_key` 认「基线 +
字节」，新开一行会让待裁决清单对同一件事重复计数）；已有裁决的不升——`list_unverified`
靠「有 accept/reject 就排除」收敛，改结论会让新红线从清单里消失。

#### 核对运行与裁决

- `VerificationRun.run_key = sha256(artifact.id + 入站字节)`：同一份回传件被邮件/回传链接/手工
  上传三条链路看见，只落一行（否则待裁决清单里同一件事出现三次，清单就没人信了）
- `VerificationDecision` **append-only**：不留痕的「放行」在出事时证明不了律师看过什么
- `VerificationPolicy`（迁移 0002）：案件级策略落库，**库里没记录回落到代码默认**——反过来
  会让新案子默认全关，功能上线第一天就静默失效

#### API（6 条路径 / 8 个操作，运行中服务已可见）

| 路径 | 操作 |
|:--|:--|
| `/api/v1/doc-verify/artifacts` | `POST` 冻结出站基线（幂等）、`GET` 该案基线清单 |
| `/api/v1/doc-verify/runs` | `POST` 提交一份回传件核对 |
| `/api/v1/doc-verify/runs/{run_id}` | `GET` 单次核对详情 |
| `/api/v1/doc-verify/runs/{run_id}/decision` | `POST` 裁决（accept / reject / reissue） |
| `/api/v1/doc-verify/unverified` | `GET` 待裁决清单 |
| `/api/v1/doc-verify/policy` | `GET` 读、`PUT` 写案件级策略 |

## 前端：入口落在归案弹窗

- `AssignModal` 底部（「同时归档到案件文件夹」下一行）加勾选 **「回传后核对内容（起诉状 /
  授权委托书 / 送达地址确认书 / 退费账户确认书）」**，默认勾选，模块级偏好（关掉弹窗再打开
  不该自己弹回来）
- 归案成功后按**归案返回的** `caseId` 落库策略；拿不到就跳过——宁可这次没存上，也不能猜一个
  id 把策略写到别人案子上。失败只 `console.warn`：此刻归案已写库成功，再弹提示会让律师以为
  归案失败而重试建出第二个案子
- 选中既有案件时，弹窗内就地显示该案**待裁决清单**（`PendingRuns`）：文书名 + 状态中文标签 +
  覆盖率（`coverage.pages_no_text > 0` 时明写「N 页无文本层，未核对」）+ 前 3 条发现项
  （红/黄/灰）+ 采纳/退回

## 说明与遗留

- **时间成本是真金白银**：全量 OCR 约 7 秒/页（12 页含模型加载 141s）。40 页扫描件首次
  核对分钟级，之后同字节重传走幂等直接返回。批量案件应按批次评估要不要勾「回传后核对内容」
- **病态保护 500 页**：单份超 500 页时只核前 500 页并报灰项，不静默——真要核更长的文档，
  设 `FACHUAN_DOC_VERIFY_OCR_PAGES`；但要认识到「一页都不许漏」与「不设上限」不是一回事
- **OCR 质量是上限**：全角数字、数字间空格已由归一化兜住（实测 `９９８６７０.２１` 能与
  `998,670.21` 对上），但 OCR 认错字本身无从发现——它是「比对了两个 OCR 结果」还是
  「比对了真实文字」这件事，报告里只能靠 `coverage.ocr` 与 `pages_failed` 如实交代
- **升层不可逆**：同一份字节从免费层升到 OCR 层会原地改写结论；已有裁决的则不升，
  要重核得先作废裁决或换基线
- 指纹容差沿用副本识别的 `0.03`，**未针对「数字渲染 vs 扫描」重标定**：它只能用来**定位**
  变化页，不能用来下「这页没改」的结论。判「改了什么」的是字段级/段落级，不是指纹
- 访问控制目前只校验「有操作人」（`api/_operator.py`），没有按案件授权收敛——仓库现有的
  `CaseAccessGrant` 只在显式授权时建行，直接接会让合法用户 403，需单独设计再上
- 待裁决清单的入口只在「归案 → 选中既有案件」这条路径上；新建案件路径没有清单入口
  （Reader 没有「已归案」区块，要新开）
- 未加 MCP 工具：agent 侧还不能主动「查这个案子有没有没核对过的回传件」
- 前端策略落库失败静默（理由见上），要可见提示需先改既有
  `use-assign-launch.archive.dom.test.tsx` 的 toast 计数断言
