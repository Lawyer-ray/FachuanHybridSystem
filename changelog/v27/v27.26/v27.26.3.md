# v27.26.3 · 进度条不再显示别的材料包的任务 + 「停止识别」终于能真停

> **版本判定**：`v27.26` 线的延续（同一条「界面说的到底是不是真的」主题），只加第三位。
> 具体判据：这一版修的是**界面把一个不属于当前材料包的任务说成是它的**，
> 以及**律师没有任何办法让那个任务真停下来**——两件事都在回答「用户能不能相信并控制眼前这条进度」。

## 一句话

| 之前 | 现在 |
|:--|:-|
| 在材料包 A 上发起识别，切到材料包 B（`/material-prep/<id>`）→ B 的页面底部浮着 A 那份任务的「正在识别文字（0/37 页）」 | 进度面板**按材料包归属**：会话态记着任务属于哪个包，换包立刻撤掉、并且只把本包的任务交给界面（渲染期过滤，不闪一帧） |
| 接管/复用只按「文件名 + 页数」匹配。两个包里各有一份同名同页数的 PDF（真实卷宗里极常见）→ 后端把**别人包的那份任务**交回来 | 新增 `PdfSplitJob.pack_message_id`：提交时落库、查询时按包收敛。不传包主键（老客户端/脚本）才退回旧口径 |
| 浮条上只有「不再显示」——它只收起界面，云端任务照旧跑、照旧计费。**律师没有任何办法让一个跑错了的任务停下来** | 新增「停止识别」（破坏性，二次确认）：打 `POST /pdf-splitting/jobs/{id}/cancel` 真取消 + 停掉本地轮询。取消失败**不伪装成功**：浮条留在原地、进度继续走、错误原因说出来，可以再按一次 |

## 后端

| 文件 | 改动 |
|:--|:--|
| `apps/pdf_splitting/models.py` + `migrations/0018_pdfsplitjob_pack_message_id.py`（新） | `pack_message_id: BigIntegerField(null=True, blank=True, db_index=True)`。刻意**不做** ForeignKey：pdf_splitting 不该依赖 message_hub，包被删时由 `cleanup_service` 回收派生数据。存量任务为 NULL |
| `services/job_service.py` | `create_job` 收并落库 `pack_message_id`；`find_inflight_job` / `find_reusable_job` 新增同名参数，**传了就只认这个包**。传了包过滤时，存量为 NULL 的任务一律不命中（宁可少接管一次，也不能拿别的包的任务冒充） |
| `api/pdf_splitting_api.py` | 提交端点收 `pack_message_id`（Form）；`/inflight-job` 与 `/reusable-job` 收 `pack_message_id`（query）。不传时行为与改动前逐字一致（老客户端不断） |
| `backend/openapi.json` + `frontend/src/types/api-schema.d.ts` | 产物刷新（`export_openapi_schema` + `openapi-typescript`）。注：现有的 `check-openapi-fresh.sh` **只比路径 / schema 名 / schema 字段，不比 query 参数**，所以这次参数级漂移它报的是「一致」（已在下方「记账」里列出） |

**为什么包主键是权威判据**：文件名是律师自己的命名习惯（同一批材料常被叫成「材料.pdf」「1165_001.pdf」），页数是 PDF 的天然属性，两者**组合起来也不唯一**；只有「这份任务是从哪个材料包提交的」是唯一的，而且它本来就是前端唯一知道的事实（路由里的 message id）。

**为什么失败点选在查任务这一层而不是前端过滤**：前端拿不到「这个任务属于哪个包」的任何证据——payload 里没有、文件名+页数也不唯一。前端过滤只能拦「已经知道是错的」那种，拦不住「后端把别人的任务当成这个包的」那种。

## 两名 reviewer 视角的自查（这次没起 reviewer，逐条自审）

| 问题 | 处置 |
|:--|:--|
| 换包时清掉上一个包的会话态，会不会把那个任务的轮询也停掉、白白浪费钱？ | **不会**。轮询随阅读器组件卸载就已失效（`usePollSession` 的 unmounted 闸门），云端任务不受影响；回到原包会按包主键重新接管 |
| A 包的轮询收尾（`finally`）会不会把 B 包刚发起的任务一起清掉？ | **已防**：收尾改成 `clearAutoSplitTask(openId)`，包号对不上不动 |
| 同包重入两次，「停止」会不会停错/停不掉？ | 停机回调按 token 注册，先结束的那次 `release` 不会删掉后开始的那次注册 |
| 取消接口失败时把浮条藏掉？ | **不藏**：先打后端、成功才清本地。失败时浮条与进度都保留（任务确实还在跑），并 toast 出原因，可重试 |
| 接管轮询的旧快照会不会盖掉用户随后发起的新任务？ | 回调额外比 `state.jobId`，替换后旧循环的回报一律丢弃 |
| 「停止」之后那个「任务已取消」的报错会不会弹成故障？ | `isAutoSplitStopping` 抑制；这是用户自己要的结果 |

## 记账（本轮发现但不改）

1. **`check-openapi-fresh.sh` 对 query / form 参数盲**：本轮新增的 `pack_message_id` 三个参数在产物里能刷新出来，但护栏本身**看不见**这类漂移（只比 paths / schema 名 / schema properties）。要真拦住，需把它扩到 parameters / requestBody properties——属于护栏改造，单独一轮。
2. **`cleanup_service.purge_split_jobs_for_attachment` 仍按「同名 + 页数」回收任务**：有了 `pack_message_id` 之后可以收紧成「只回收本包的任务」，但那条链牵到删包主流程，需单独验一轮（同一份文件被两个包共用时的保留判据）。
3. **接管来的任务跑完不回写草稿**（`owned=false`）：它是既有设计（怕覆盖别人的编辑），但意味着「切走再切回」会让结果只留在后端、要靠下一次点按钮的复用查询捞回来。本轮未动。
