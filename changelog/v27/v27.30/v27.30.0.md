# v27.30.0 · 项目主页首屏 356ms → 104ms：一条请求里 150 条假 ERROR + 96 条 N+1 同时被摘掉

> **版本判定**：§1.1-A 换主题线（前一条 `v27.29.x` 是 README 数字校准与前端文件规模，本次是
> **列表接口性能 + 加载态视觉**：另一批文件、另一类用户动作、另一个验收口径）→ 次版本 +1。

## 一句话

| 之前 | 现在 |
|:--|:--|
| `GET /contracts/contracts?slim=true&page=1&page_size=50`：p50 **355.9ms** / p95 565.3ms | p50 **103.7ms** / p95 **153.2ms**（交错 A/B，N=40/边） |
| 一次请求写 **150 条**带完整 traceback 的 `ERROR`（每行 3 条：回款记录 / 归档材料 / 可归档） | **0 条**；同批请求日志体积 11.3MB → **6.8KB** |
| 一次请求 **113 条 SQL**，其中 **96 条**是同一个 `cases_clientidentitydoc` 逐行补查 | **19 条**；`cases_clientidentitydoc` 从 96 降到 2 |
| 项目主页首屏是一块 `py-[90px]` 的手猜转圈（~150px），切到 50 行真列表（~3300px）时视口猛跳 | 换成与真行**同源**的骨架（复用 `DEAL_ROW_SHELL`），300ms 延迟门控 + 读屏播报 |

## 根因一：一条正常的设计路径被记成了 150 次「失败」

`slim=true` 的本意是"列表不要归档材料和回款记录，省 60% 体积"。实现方式是
`_SlimContractView.__getattr__` 对 `finalized_materials` / `client_payment_records`
**抛 `AttributeError`**，指望 pydantic 落到字段默认值
（`backend/apps/contracts/api/contract_api.py:36-45`）。

但 pydantic 之前，schema resolver 先接住了这个异常：

```python
# backend/apps/contracts/schemas/contract_schemas.py（改前）
except Exception:
    logger.exception("操作失败")   # ← 每行每个字段一条完整 traceback
    return []
```

于是**每次刷新项目主页都会写 150 条 `ERROR` + 完整调用栈**（3 个 resolver × 50 行）。
这既是 p50 里最贵的一段，也是更糟的一件事：**真故障会被 150 条假失败埋掉**。

改法：给"源对象没有这条关系"加一个**预期内分支**（`except (AttributeError, TypeError)`），
静默返回默认值；无法识别的异常仍由原来的兜底接住（行为不变，只是不再刷栈）。
顺带把 `resolve_can_archive` 里写在 `try` 内的 `MaterialCategory` import 提到模块级——
否则一次循环 import / 改名会被兜底吞成"这份合同不可归档"，而不是在导入期就炸。

## 根因二：96 条 N+1 在 `identity_docs` 这一层

`get_contract_queryset` 的 prefetch 组只到 `contract_parties__client`，而
`ClientOut.resolve_identity_docs` 读的是 `client.identity_docs`
（`backend/apps/client/schemas/client_schemas.py:60`）。于是每个当事人各发一条
`cases_clientidentitydoc` 查询——实测 50 行页面里 **96 条，占全部 SQL 的 85%**。

补两层：`contract_parties__client__identity_docs` 与
`supplementary_agreements__parties__client__identity_docs`。

> 顺带纠正一个我原本的判断：以为要补 `payments` 预取。**不成立**——`payments__invoices`
> 本来就在 prefetch 组里，Django 按 `prefetch_to` 去重后 `payments` 那一层不会重复下发；
> 三个金额 resolver 走的是 `Subquery` 注解（`service.py` 的 `_total_received` 等），
> slim 下 Python 求和分支根本不执行。真正重复的是证件。

## 前端：骨架屏只在"确实会慢"的时候出现

判据不是"感觉更现代"，是实测：p75 > 300ms 才值得上骨架，且占位必须与真行**同源**。

- `components/shared/Skeleton.tsx`：灰块（`animate-pulse` + `motion-reduce:animate-none`）
  与"播报 + 延迟"壳分两层。`SkeletonStatus` 默认 **300ms** 延迟（对齐 GitHub Primer
  `SkeletonBox` 的 `'short'=300ms`），窗口内返回 `null`——**短请求不该看见骨架**；
  文案走 `sr-only`，因为原来的 `LoadingBlock` 本来就有 `role=status` + `aria-live`，
  换骨架不能让读屏倒退成"什么都不播报"。
- `DealRowSkeleton` 复用 `DealRow` 导出的 `DEAL_ROW_SHELL`；`InboxRowSkeleton` 复用
  `InboxRowItem` 导出的 `INBOX_ROW_SHELL`。骨架与真行共用同一串类，改一行两边一起变——
  手抄平行树就是"半年后必漂"。
- 接入点只有两处：项目主页列表（`WorkbenchPage`）与材料预处理收件箱（`InboxList`）。
  其余 61 处 `LoadingBlock` **一律不动**——小面积、短等待的 spinner 比骨架更诚实。

修完后端后这个接口 p50 104ms，**绝大部分请求落在 300ms 门控内、根本看不见骨架**，
这正是设计意图；骨架只在冷启动、大载荷、慢机器这类长尾上兜底。

## 勘误（三条我自己的断言被独立核验推翻，原样留档）

| 我的断言 | 实测结论 |
|:--|:--|
| 每请求 200 条假 ERROR | **不成立，是 150 条**（3 个 resolver × 50 行；我按 4 个字段估的） |
| N+1 来自 `payments` 未预取 | **不成立，来自 `identity_docs`**（96/113）；`payments` 预取是 no-op |
| 133ms 全是写 traceback | **低估且方法有偏**：`logging.disable` 连 SQL 日志一起关了；改用交错 A/B 后真实收益是 **+253ms** |

## 已知取舍

- **没有改** `_SlimContractView` 的"抛 AttributeError"设计：现有
  `test_contract_slim_serialization.py` 就是钉这个契约的，动它等于顺带改一批消费方语义；
  本次只在 resolver 侧把"预期内"接住，收益一样、风险最小。
- **没有删**那几个 `except Exception` 兜底：收窄成"白名单外一律冒泡"会让 `DatabaseError`
  从"静默返回空列表"变成 500，属于另一件事（资损口径要单独评审）。本次只让它们**不再刷栈**。
- 顺手改了 4 处描述 `exclude_unset` 的注释：实测 slim 响应里 `finalized_materials` **就在**、
  值是 `[]`（`_serialize_contract` 走 `model_dump(by_alias=True)`、不带 `exclude_unset`，
  端点上的 `exclude_unset=True` 无键可剔）。**判 slim 请看请求参数，不要看键是否存在。**
