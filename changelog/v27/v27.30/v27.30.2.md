# v27.30.2 · 案件列表 724KB → 47KB（1.52s → 0.036s）；当事人快照去掉内嵌证件；收件箱 -32%

> **版本判定**：§1.2 同一条线（`v27.30.x` 的「列表接口响应瘦身 + 加载态」）→ 第三位 +1。

## 一句话

| 接口 | 之前 | 现在 |
|:--|--:|--:|
| `GET /cases/cases?limit=200`（真库 115 行） | **724,424 B / 1.52 s** | `slim=true` → **47,547 B / 0.036 s**（体积 −93.4%、耗时 −97.6%），并可用 `with_total=true` 从 `X-Total-Count` 拿总数 |
| `GET /contracts/contracts?slim=true`（50 行） | 119 KB | **102,136 B**（当事人快照不再内嵌证件清单） |
| `GET /inbox/messages?limit=200` | 195.4 KB | `slim=true` → **132.0 KB**（−32.4%），SQL 仍 1 条 |

三个都是**可选增量参数**：不传时与历史响应**逐字节一致**（各 lane 用 sha256 比对自证）。

## 同一个毛病：响应里塞了消费方不读的东西

这一波的三处都不是"接口慢"，是**返回了没人读的字段**，而读这些字段要付查询与序列化的钱。

### ① `/cases/cases` 每行背 7 个嵌套集合
`CaseListPage`（唯一重消费方）只读 `CaseRow` 的 7 个标量字段
（id / name / status / current_stage / cause_of_action / target_amount / filing_number），
`parties` / `assignments` / `logs` / `case_numbers` / `supervising_authorities` /
`chats` / `contacts` 一个都不读。

- 新增 `CaseSlimOut`（`apps/cases/schemas/case_slim_schemas.py`）：标量列与 `CaseOut`
  **完全一致**（同一份 `CASE_SCALAR_FIELDS`），只去掉那 7 个集合。所以一条就能记住：
  **slim = CaseOut 去掉全部嵌套集合。**
- queryset 同步裁预取（不裁则 SQL 一条不省）；序列化前也不再
  `warm_reminder_cache_for_cases`——响应里没有 `logs`，预热只会为每个案件多一次查询。
- `with_total=true` → 总数走**响应头** `X-Total-Count`（实测 115），响应体仍裸数组。
  本端点已有 4 个消费方按数组消费（workbench / material-prep / bank-litigation / MCP
  的 offset 续取），改信封会同时打红四个。
- 两个形状用 `list[CaseOut] | list[CaseSlimOut]` 声明，`CaseSlimOut` 上开
  `extra="forbid"` 让 union 分支互斥——否则 pydantic 的 smart union 会把全量 dict 也
  判进 slim 分支（多余键默认 ignore），**静默吞掉集合字段**，默认行为被无声改掉。

### ② 当事人快照内嵌证件清单（第三次踩同一个坑）
`ClientOut.resolve_identity_docs` 读 `client.identity_docs`，而 `ClientOut` 被内嵌在
`ContractPartyOut` / `CasePartyOut` / `SupplementaryPartyOut` 的 `client_detail` 里。

前两轮（v27.30.0 / v27.30.1）只在 queryset 侧补预取（96→2、239→2 条）。但那只是
**止痛**：只要字段还内嵌，任何一个新调用方忘了预取就会重演。本版从字段层拆掉——

- 新增 `core/api/schemas_shared.ClientBriefOut`：id / name / is_our_client / phone /
  address / id_number / legal_representative。
- 三个内嵌点改用 `ClientBriefOut`，**不含** `identity_docs`（只在客户自身端点出参，
  前端生产代码 0 处消费，只有 test fixture 里出现）与 `client_type_label`（choices
  衍生字段、同样无人读）。
- 客户端自身端点（`GET /clients/{id}` 等）仍用 `ClientOut`，证件能力不受影响。

### ③ 收件箱：先量化，才发现前提是错的
原判断是"接口把整封邮件正文带上了"。**不成立**——`body_text` / `body_html` 只在详情
端点 `GET /inbox/messages/{id}`（`MessageContent.tsx` → `getInboxMessage`）。

真正的水分是 **15 个只服务材料包桌面的行级字段**（`status` / `segs` / `upload_*` /
`created_at` / `read_at` / `compose` …）。`slim=true` 剔掉它们，保留 12 个收件箱真消费的
字段。材料包桌面（`listMaterialPacks`）**不带** slim，形状不变。

## 已知取舍与未做

- **分页 UI 没做**。后端已具备 `limit` / `offset` + `X-Total-Count`，但列表页还没有分页
  控件——那是交互设计（每页多少条、翻页放哪、总数怎么显示），不该塞进这次性能改动里。
  现在默认 200 条上限对 115 件案子够用。
- 合同列表的 `contract_parties` 仍占响应 58%（62 KB / 50 行）。它**是**被消费的
  （行内"我方/对方"、抽屉当事人），不能再剔；要削只能做行级投影（前端得改成两段式
  取数：列表只取行字段、抽屉再拉当事人）。
- 三条 lane 都是"flag + 增量参数"路线，代价是 API 表面多了 `slim` / `with_total` 两组
  开关。若将来所有消费方都切到 slim，应该考虑**反转默认**再删开关。
