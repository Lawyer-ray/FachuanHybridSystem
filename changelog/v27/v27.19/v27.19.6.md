## 一句话定位

| 能力 / 问题 | 之前 | 现在 |
|:--|:--|:--|
| A 在会话里捋出的判断 | 只活在那一次会话，换人就丢 | 点回答下方的书签存成**项目笔记**，挂在项目/案件上 |
| B 接手同一项目 | 零上下文，只能重问 | 会话一开始就注入「本项目同事的判断」，带作者与时间 |
| 模型写的结论 | 与人工结论无法区分 | **必须人点一下**才升为「项目事实」（`confirm_` 前缀 → HIGH 审批） |
| 结论被推翻 | 只能删掉，历史消失 | `supersedes` 指针：旧条保留、不再注入，能回答「当时怎么定的」 |
| 案件会话的归属 | 只有 `case_id`，项目维度是空的 | 建会话时从 `Case.contract` 反查补上，项目页才拉得到 |
| 项目页看本项目 AI 笔记 | 没有入口 | 页头「AI 上下文」抽屉，事实/判断分两组、事实在前 |

## 链路（改之前先读这段）

```
写入  回答下方书签 → POST /agent/memory/notes
        └ 前端只有 sessionId，锚点由服务端按会话反查（前端猜锚点必然写错项目）
      AI 也可直接写：save_project_note / save_case_note（MCP 工具，MEDIUM 留痕）
确认  confirm_project_fact → POST /agent/memory/{id}/confirm（HIGH，人工审批）
注入  pi session_start → GET /agent/memory/snapshot?session_id=
        └ build_snapshot 按会话锚点取同团队成员的笔记
        └ 本项目已确认的事实(1200) → 同事的判断(800) → 个人(1600) → 团队(900) → 律所(700)
读取  项目页 → GET /agent/memory?contract_id= → 「AI 上下文」抽屉
```

三条不可动摇的设计约束（写进 `backend/apps/agent/README.md`）：

1. **锚点与作用域正交**：`scope` 回答「谁能看」（个人/团队/律所），`contract_id` /
   `case_id` 回答「属于哪个项目、注入到哪」。不给 scope 再加 `project` 档——可见性
   真相只有一份（`org_access["lawyers"]` = 同律师团队），加第二套迟早漂移。
2. **快照缓存必须带锚点与版本号**：不带锚点会把 A 案的快照发给 B 案；不带版本号则
   失效只能按人删一个 key，而同一律师现在有 N 个锚点变体（locmem 没有
   `delete_pattern`）。版本号把失效降级成「自增一个整数」。
3. **三层记忆查询排除锚点条目**：否则一条挂 A 案的笔记会同时出现在 B 案会话的
   「个人记忆」里——项目隔离失效，而且同一条会被注入两遍。

## 已知取舍与边界

1. **共享的是判断，不是谈话记录**。把 A 的 pi session 挂给 B，B 会继承 A 的试错与
   措辞偏见，且前缀每轮变、prompt cache 全废。所以只传结论。
2. **谁都能写、谁都能确认**（同团队）。没有审核闸，风险靠 author / 时间 / `supersedes`
   链的可追溯性兜——`superseded` 的旧条不删，被推翻的结论仍可回查。
3. **撤权不可回收**。律师换团队后，快照立即失效、下一轮不再注入；但他已经读到的内容
   收不回来。这是接受的代价（要回收就得「失效重放」，成本高且挡不住截图）。
4. **`Case.contract` 允许为空**（历史/导入案件）。这类案件解不出项目，笔记只能挂
   `case_id`；回填命令会把「案件未关联项目」「案件已不存在」分别计数，不猜。
5. **同一句话不重复建行**（`content_hash` 去重）。代价：同一句结论想挂到第二个项目上
   时不会新增行，只会给原行补锚点。真实场景里极少见，暂不为此改唯一约束。
6. **PII 未加闸**。项目笔记天然含当事人/案号，且每轮进 system prompt；策展闸门
   （`scan_pii_risk`）只作用于团队/律所层提升。**同团队可见**是本期确立的边界，
   跨团队传播没有任何通道。
7. **工具面不带 `DIRECT_TOOLS`**。写工具按既有策略走 `tool_search`（`create_/update_`
   同理）；靠 `AGENTS.md` 的路由让模型知道「有这个工具」，而不是把 427 个工具全塞进
   每轮上下文。
8. **`confirm_project_fact` 用 `confirm_` 前缀**是为命中 `DANGER_PATTERNS` 判 HIGH。
   改名 `promote_to_fact` 会被判 LOW + `readOnly=true`（pi 免审批、前端显示只读徽标），
   等于模型替律师签字——这是本轮唯一一处「名字即安全策略」的地方。

## 并入：多答合并的公平交错（`1556f291`，另一会话）

> 与本版本主段主题线无关，但同分支同期落地。用户实报的现象值得原样记下来：
> **多答时不管哪个 agent 摆在最左列，它永远回答最快**——「快」这件事与模型无关，
> 只与栏的位置有关。

### 一句话定位

| 能力 / 问题 | 之前 | 现在 |
|:--|:--|:--|
| N 栏的事件出场顺序 | 左列（恒为 `agents[0]`）边产边推，其余栏被后端扣住，等左列**整个跑完**再逐栏整批刷出 | 谁先产出谁先上线：右列的 delta 可以在左列还在打字时就到达 |
| 次栏的帧存在哪 | 每栏一个**无界** `asyncio.Queue`，主栏结束后 `for kind in secondaries:` **逐栏串行**抽干 | 所有栏共用**一个**有界队列（256，背压），只阻塞、不丢弃 |
| 某一栏失败 | 只转发**第一条** error（它恒为主栏，因为主栏内联先跑） | 每栏各自一条 error，前端按 `agent` 把那一栏标成「本轮未做」 |
| 用户按停止 | 次栏已流出的正文不落库（重开会话只剩主栏） | 按 `agents` 顺序补落；主栏行不再依赖 GC 补写 |
| 回放时的左右栏序 | 断连路径下由落库**时机**决定，主栏行可能晚于次栏行 → 左右颠倒 | 恒为 `agents` 顺序（先答的在左） |

### 根因（读代码只需要看这一段）

前端本来就是顺序无关的：`streaming.ts` 每帧自己算 `origin={agent, runId}`，
`turn-handlers.ts` 按 kind 路由到对应气泡，`store.multi-answers.test.ts` 甚至有
「次栏 delta 晚于主栏 done」的用例。所以这是**纯后端**缺陷，在 `stream_multi`：

- 修复前 `multi.py:620-645`：`agents[0]` 在合并协程里**内联** `async for` → 每产一帧就
  实时 `yield`；
- 修复前 `multi.py:667-687`：`agents[1:]` 经 `_pump_one` 进**每栏一个无界队列**，而这些
  队列只在主栏的 `async for` 结束后才被吞，且是逐栏串行。

左列恒为 `agents[0]`，于是「谁在最左谁最快」结构性成立。**7 个测试文件全绿**都没抓到：
它们只断言「谁的帧都在、done 有几条、助手行几条」，从不问**相对顺序**——而「实时上线」
只体现在顺序上。已登记 `docs/harness/pitfalls.md` PIT-020（顺序）与 PIT-021（丢正文 / 栏序反转）。

### 改法

1. **所有栏一视同仁**：N 条 task（含主栏）+ 单个有界队列 + 纯消费者
   `while finished < len(agents)`。代码里**刻意没有任何**「主栏优先」的排序。
2. **审批/提问帧**改由 `_pump_external` 搬进同一队列（原来靠「主栏每产一帧就
   `get_nowait()` 一次」捎带；公平交错后主栏不再有「间隙」这个概念）。
3. **每栏各自一条 error**：删掉 `errors` 列表与 `if len(errors) > 1: continue`。
4. **断连也按栏落库** + `_pump_lane` 在 `finally` 显式 `await agen.aclose()`：队列有界之后
   取消点会落到 `queue.put` 上，而 `async for` 提前退出**不会**替你关异步生成器（PEP 525），
   `stream_chat` 的 `finally` 不跑就会丢已流出的正文，并让主栏行改由 asyncgen finalizer 补写
   而反转回放栏序。
5. `_join_lanes` 边等边抽干（不是裸 `gather`）：被取消的栏还要往**满**队列里放哨兵。
6. 收尾硬顺序不变：抽干 → 等 task 收尾 → 按 `agents` 顺序落次栏正文 →
   `_stamp_finish_reason` → 逐栏 `done`（`done` 字段与水位口径一字未改）。

### 已知取舍与边界

1. **不给主栏任何特权**，连「第一个 error 优先」也一起去掉——它原本只是「主栏内联先跑」的
   副产品；公平交错后「第一条」变成到达顺序，保留它就会让最左栏的 error 被次栏占位而
   **静默不发**。代价：全部失败时每栏各一条错误行（`lastError` 是单字段，横幅只显示最后一条）。
2. **有界队列 256 + 慢客户端**会让合并协程被 SSE 写阻塞，整轮继续持着全所唯一的 `aux` 席位
   与 N 把 key。没有加超时或丢弃：正文帧丢一条就是律师看到的正文缺字，宁可排队。
3. **落库仍是串行**（按 `agents` 顺序），没有改成并发：`persist.py` 按 `-created_at,-id` 排序，
   前端用 assistant 行序决定栏的左右，并发落库会让刷新后栏序随机。
4. **单栏路径（`len(agents)==1`）逐字未动**——它本来就不走合并，改它只会多一处
   「`done` 长什么样」的分歧。
5. **未做真机三栏验收**（要真实模型调用）。上线后的确认方式很简单：两栏的正文应当
   **同时**在打字，而不是左栏整段出现后右栏再整段出现。
