## 已知取舍与边界（每条都给「为什么不做」）

1. **不引入任何开源框架**（inspect_ai / llama_index / haystack / dspy / LLM-Blender / MoA 全不装）。
   调研结论：它们解决的是「离线评测一份输出」，不是「在线裁决三份互相冲突的回答」，接口都不对；
   且 40 项 runtime 依赖会污染 Django 依赖树。**只移植了 6 件零件（约 660 行），新增依赖 0 个**。
2. **不碰 GPL/AGPL**（merge3、dulwich 合并层、LexNLP、CUAD 代码、multiagent_debate、opencouncil）。
   diff3 按语义自研约 80 行。
3. **多栏绝不直写正式文件**：即使有审批闸门也不。原因是 `rewrite_folder_file` 要求 `original` 逐字一致，
   第一栏写完后其余栏必然失效或改错位置，且三套修订痕迹叠加后律师无法逐条接受。
4. **不做角色剧场化评审**（10+10 个 persona 开会）：成本 ×20、不可核验、容易被误读成专家会诊。
5. **不做 judge 自由综合终稿**：MoA 的 aggregator 自己都写着候选「可能有偏或错」，把三份丢给它综合，
   等于把三份的幻觉一起融进来。只融合被 rubric 判定为达成的片段。
6. **失败栏刷新后不显示**（保留现状）：`stream.py` 只在正文非空时落库。落一条空回答会让评审去判空文本、
   memory 抽取与用量统计各多一条脏数据；先按「不落空行」处理，修复要求写进计划文档 §20。
7. **真实校准未执行**：需要 40 份真实合同 + 律师标注 + 约 5000 次批量调用。本版只交付骨架与门禁，
   跑不了就说跑不了（`--data` 缺文件退出码 2，不回退合成样本）。
8. **校准数据还没有生产者**：`families_agreeing` / `margin` 需由判定运行侧记录后写进 JSON，
   目前 `/review` 尚未产出该字段——已登记为下一步（避免脚本自己给自己发门禁）。
