# v27.19.4 · 材料预处理：左栏还回宽度 + 复核原因说清楚

> 分支 `fix/material-prep-rail-density`（`main` 之后 **6 个 commit**）。全部是材料预处理
> 阅读器的前端改动，后端零改动。
>
> 起因是四句真实反馈，按顺序推进：
> ①「显示 pdf/md 之后太拥挤了」→ ②「复核两个字也太占位置了」→
> ③「需要复核的材料，为什么没有把复核的问题展示在右边对应 Markdown 处？那我怎么知道
> 什么要复核」→ ④「置信度 90% 你还要我复核？」
>
> ①②是**宽度预算**问题，③是**信息在链路上被丢掉**，④是**把数字当成了理由**。
> 前三件改布局与传参，第四件改的是提示该说什么话。

| 能力 / 问题 | 之前 | 现在 |
|:--|:--|:--|
| 段行里的 PDF / MD | 两个常驻按钮吃掉约 40px | 收进右键菜单，行内不占位 |
| 「复核」标记 | 两个字常驻，40 行 × 22px | 12px 琥珀三角 + tooltip |

| 段名尾部（`-P20.pdf`） | 被 CSS 连尾巴一起裁掉 | `flex-none` 固定显示，永不丢 |

## 一、左栏：把宽度还给段名

### 现状（改前 232px 栏的实际预算）

一行里塞了 8 样东西：勾选框 14 + 段名（剩多少算多少）+ 页范围约 40 + 质量图标 12 +
「复核」22 + PDF 20 + MD 16 + 五处 gap 30。**段名只剩约 66px＝四五个汉字**，而律师
在这一栏做的唯一事情就是「认出这是哪一份材料」。

### 改法

1. **PDF / MD 收进右键菜单**。左栏是「找材料」的目录，「这一段是什么」永远比
   「现在就下载」高频；批量下载已有「全选 → 下载选中（N）」与「整包下载」两条明路，
   「只要这一段」也可以勾一行再点「下载选中（1）」。菜单只覆盖「不打包、只要单一文件」。
   菜单项只在**该段有后端产物**（`splitRef`）时出现——人工拆的段点了必 404。
2. **「复核」→ 12px 琥珀三角**。40 份材料里三十多行都挂着它，每行固定吃掉 22px。
   同一个意思用图标说，置信度百分比与「该核对什么」放 tooltip；图形与右栏
   `SegmentQualityHint` 同一枚 `AlertTriangle`，读起来是一套语言。
3. **段名结构性拆分**（`segment-name.ts`）。以前是 `midEllipsis()` 先按 16 个字挖中间、
   再交给 CSS 截断——16 字的上限远大于栏宽，**CSS 又把尾巴连同省略号一起裁掉**，
   中部省略等于从未生效。现在头部 `flex-1 truncate`、尾部 `flex-none`：
   两份「授权委托书」只差页号也不会认错。
4. **下载工具条压成一行**（`flex-wrap` 兜底），且只在「左栏段数 > 可下载段数」时才解释
   差额——绝大多数包里两者相等，再说一遍「共 40 段可下载」只是把标题的「40 份」重复一次。

净效果：段名可读字数从四五个字到九到十个字，行高与点击热区不变。

## 二、复核：从「四个字」到「说清为什么」

### 根因：不是功能被删，是从来没接上

后端一直在回三个字段：

```python
review_flag        # low_confidence / unrecognized / ocr_failed
review_flag_label  # 低置信度 / 未识别 / OCR 失败
source_method      # layout_title / rule_weak_only / rule_adjacent_start / llm …
```

而 `draft/auto-split.ts` **只映射了 `review_flag` 和 `confidence`**，`source_method`
被整个丢掉；右栏的 `SegmentQualityHint` 只接了「图纸页 / 稀疏页 / 证件页」，压根没接
段级复核信号。于是全站只有一个地方提复核——中栏段头那枚「建议复核」徽标，tooltip 里
只有一句置信度。**「为什么」这个信息后端给了，前端扔了。**

### 改法

- `quality.reviewHintOf()`：`review_flag` → `{ 标签, 原因 }`。原因按 `source_method`
  分开说（版面标题猜起点 / 只命中弱规则 / 与上一段只隔一页 / 合并 / 补空），
  拿不到原因时**留空，不编**。
- 右栏正文面板顶部新增琥珀色复核条，排在证件页、图纸页之前——切错边界等于把别的材料
  末尾混进来，比「这页看不出内容」严重。
- **中栏徽标、左栏三角标、右栏提示条全部改读 `reviewHintOf`**。三处各拼一遍文案，
  迟早出现「徽标说 62%、提示条说 60%」，而律师一旦发现两处对不上，就会连带不信第三处。

### 落点：段级在栏顶，逐页在正文里

第三句反馈的记忆参照物是双引擎分歧——「直接放在对应页面的 Markdown 顶部」。
按同一套重排：

| 信号 | 落点 | 理由 |
|:--|:--|:--|
| 段级复核（切错边界 / 起错名） | 面板顶部 | 错的是整段，不归任何一页，读之前就该知道 |
| 证件页缺字段 / 疑似图纸页 | 该页正文**第一行之前**（与 `EngineDisagreementsInline` 共用 `isFirstOfPage` 判定） | 读到哪页就看到那页的问题 |
| 图纸页没有正文行（一个字都没取出来） | 补在正文之后单独成行 | 挂不上去就等于没提示 |
| 老任务的段级 `quality_flags` | 面板顶部兜底 | 没有逐页画像，只能整段说一句 |

文案跟着粒度改：段级「本段含 2 页疑似图纸（P147–148）」→ 逐页「P147 疑似图纸 / 照片，
正文可能不完整 · 建议核对原页」。

## 三、老材料包：不重跑识别也能看到原因

已存在的草稿里没有 `source_method`（旧前端从没映射过），律师打开手上那份 40 段卷宗
仍只看得到置信度。重跑一次识别是几分钟 + 几十元，只为补一个提示字段，不值。

而 `GET /pdf-splitting/jobs/{job_id}` 的响应本来就带着每段的 `source_method` /
`review_flag_label`。所以打开阅读器时按 `splitRef.jobId` 调一次，按 `splitRef.pk`
回填进草稿（`review-backfill.ts` + `use-review-backfill.ts`）：

- **只补缺、不覆盖**：已有的值一律不动——回填是补数据，不是「以服务端为准重写草稿」
- **每个任务号只试一次**：比该字段更老的后端任务回不来，没有这个闸门就会每次渲染发一次 GET
- **失败静默**：提示条退化成「置信度 62%」，不弹 toast、不影响阅读器

写测试时抓到自己的一个真 bug：`applyReviewReasons` 的「只填空」写反成了「以服务端为准
覆盖」，而这条路**每次打开阅读器都会走**。

## 四、置信度 90% 还要求复核？

### 后端的 6 个触发点

| # | 触发点 | 条件 | `source_method` | 置信度 |
|:--|:--|:--|:--|:--|
| 1 | 规则引擎 | 起点按**版面标题**猜（无强关键词） | `layout_title` | ≈0.5 |
| 2 | 规则引擎 | 只命中 ≥2 个**弱**关键词 | `rule_weak_only` | ≤0.2 |
| 3 | 规则引擎 | 与上一段起点**只隔一页**且同类型 | `rule_adjacent_start` | 压到 ≤0.55 |
| 4 | LLM 分段 | 段类型不在模板枚举里，或模型自报 `< 0.6` | `llm` | 模型自报 |
| 5 | **边界二审** | 疑点边界超复核次数上限 / 二审没结论 | 不改 | **不动** |
| 6 | 段落合并 | 继承两侧「更差」的 flag | 不改 | 取较小 |

**90% 来自第 5、6 条。** 后端那里有一句明确注释：

```python
def mark_unverified_boundaries(...):
    """这是 B6 的保守校准：不动 LLM 自报的 confidence 数值（无校准依据），
    只用**结构信号**补复核标记——批界是已知薄弱点，二审又没给出结论
    （超次数上限 / 调用失败 / 输出非法），那这一段就该让律师看一眼。
    """
```

也就是说：文字识别有 90% 把握，**但这一段的「分界」没被核实**。

### 错在我们把数字当成了理由

前端无条件把 `confidence` 拼进 reason，于是出现「建议复核 · 置信度 90%」这种自相矛盾
的话。现在的规则：**提示里出现的百分比必须支持「要复核」这个结论**。

- 只有 `< 0.6`（与 `llm_segment_detector` 同一阈值）才显示百分比
- 高置信度仍要复核时改说对象：「文字识别置信度 90%，要核对的是分段边界（二审没能给出结论）」
- 规则引擎的结构成因不再追加高置信度数字
- 「模型把握不大」只在 `sourceMethod` 确实是 `llm*` 时说；来源不明只报数字

## 已知取舍与边界

1. **触摸屏没有 hover / 右键**：单文件下载只能走「长按出菜单」或「勾行 → 下载选中（1）」。
   已与用户确认本页面不在手机上使用，故不额外加 `⋯` 入口。
2. **比 `source_method` 更老的后端任务**：回填拿不到原因，提示退化为「自动分段置信度 X%」。
3. **第 5、6 条触发点改不了 `source_method`**：只能笼统说「边界二审没能给出结论」，
   分不清「超次数上限」还是「二审失败」。要精确需给 `PdfSplitSegment` 加 `review_reason`
   字段（后端迁移 + API），本轮未做。
4. **高置信度仍会打「建议复核」**：这是产品口径而非 bug（边界确实没核实），本版只让
   措辞说清对象。若改成「边界二审没结论时把置信度压到 ≤0.55」，数字与结论会更一致，
   但会污染「模型自报置信度」的语义并影响用量统计——留待产品决策。
5. **`segment-name.ts` 的拆法是启发式的**：尾部 = 扩展名 + 紧邻页号（`-P20.pdf`）。
   区分信息不在尾部时（如 `行政复议答复书（盖章版）.pdf`，尾部只剩 `.pdf`）仍会被
   可截断的头部吃掉——这是命名规则本身的局限，不靠猜去补救。
