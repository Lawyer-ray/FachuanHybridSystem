## 后端

#### 新功能

**1. openai-agents 成为第三个 agent 运行时**

走官方 SDK：模型经律所网关（LiteLLM，OpenAI 兼容）用 `OpenAIChatCompletionsModel`，
业务工具经 `MCPServerStreamableHttp` 连共享 MCP（`:8011`，与 pi / dsh 同一个常驻进程）。

能力声明是**事实**而不是愿望，前端按它降级：

| 能力 | 值 | 依据 |
|:--|:--|:--|
| `streaming` | `True` | 真产出 `delta` / `thinking`（逐 token 的 `ResponseTextDeltaEvent`） |
| `tool_calls` | `True` | `tool_called` / `tool_output` 两种 run item |
| `approval` | `False` | SDK 有 `MCPToolApprovalFunction`，本轮不接；前端据此隐藏审批入口 |
| `compaction` | `False` | SDK 不做上下文裁剪，归编排层 |
| `steer` | `False` | `RunResultStreaming` 只有 `cancel`，声明 `True` 会渲染出一个「敲进去就被丢弃」的输入框 |
| `concurrent_in_session` | `True` | 每轮自建 client / agent / MCP 连接，无跨请求共享可变状态 |

工具面**只排除不可逆删除**（`BLOCKED_TOOL_NAMES = ("delete_case",)`），不做任何收窄；
工具名取不到（未连 MCP）时整条过滤器都不传。

注册侧与 dsh 同构：`_register_openai_agents()` 缺包时**静默降级**（`logger.info`），
pi 会话不受影响；`_attempted` 只记「import 失败过」，不当「已注册」的凭据
（注册表可被 `clear()` 清空，用它挡会让该后端永远报「未知 backend」）。

**2. 多答编排 `stream_multi`：编排队列不再认识具体 agent**

`kinds` / `specs` 由调用方给（API 层解析 `agents` 字段），编排层只认 `list[AgentSpec]`。

失败矩阵是本模块的核心设计：

| 情况 | 事件 | 收尾 |
|:--|:--|:--|
| 全部成功 | 各自完整事件流（带 `agent` / `run_id`） | **每栏一个** `done` |
| 部分失败 | 成功的照常输出；失败方**只**发一条带 `agent` 的 `error` | **每栏一个** `done` |
| 全部失败 | 只发**第一条** `error`（不堆 N 条） | **每栏一个** `done` |
| 辅助配额已满 | 只跑主后端 + 一条 `activity{status:"degraded", reason}` | 一个 `done`（`agents` 收窄为单栏） |

首个 kind 在**调用方协程里直接迭代**，其余走队列：主答的异常必须能原样上抛成取消语义，
否则客户端断开时停不下来；其余回答失败只降级成本栏的 `error`。

`MAX_ANSWERS = 4`（成本线性涨 + 四栏并排已接近可读性极限）。超限由 API 层挡成一条
`error` 事件，**不静默截断**——静默截断会让律师以为选中的都跑了。

`normalize_agents` 混收三种形态：纯字符串 `"pi"`（老前端）、字典 `{kind, model}`
（JSON 自然形态）、`AgentSpec` 实例。同一 kind 只跑一次（保留第一个，即先出现那栏的模型）
——同一 kind 跑两遍既花双倍钱，又会让两栏共用同一个 `run_id` 前缀而串栏。

`dual.py` 缩成 47 行**纯转发**薄壳（`stream_dual` → `stream_multi(kinds=None)`），
避免一次性改所有调用点把真正的抽象改动埋进改名噪音里。

**3. 每栏可选模型**

盘点出来的现状是「能力各有一半，缺的是传下去和选出来」：`RunContext.model` 早就存在，
dsh / openai-agents 都读 `model_hint`，但 `stream.py` 写死 `model=None`，pi 后端则完全没读 `ctx.model`。

改动：

- `stream.py` 把 `model` 透传进 `RunContext`，并用 `used_model` 回写 `AgentRun` 与
  助手消息 metadata（不再重新置 `None`，否则「用户选了模型」在成本账与界面上全变空）；
- `pi_backend` 改成 `model = ctx.model or await chat_pool._resolve_model()`——显式选择优先，
  为空才回落平台默认，**老路径逐字不变**；`PiProcessPool` 是「用完即毁」的进程工厂，
  不同模型不会串号；
- `GET /agent/backends` 补 `models` / `default_model`，数据源是现有 `LLMProvider`
  （`default_model` + `extra_models`），复用 `pi.model_config._provider_models`，只查一次；
- `default_model` 取清单第一项，与 `pool._resolve_model()` 的回落口径一致，否则 UI 预填的
  模型和「不指定时实际用的」会对不上。

**4. 轮次级 API Key 调度（把「某栏卡 60 秒」变成可解释的事）**

网关对**每把 key** 限 `max_parallel_requests = 3`，超限返回 429 + `retry-after: 60`，
SDK 自动重试 → 那一栏表现为「卡住 60 秒」（压测里见过 61s / 130s / 241s，全是 60 的整数倍）。

后端的 `_next_key` 是**全局轮转计数**：只保证「先后两次通常不同」，既不保证同一轮的三个
agent 不同，也不知道哪把 key 已经满了。所以「三 agent 用三把 key」必须由编排层按轮次显式分配：

- `key_scheduler.allocate(count)` 一次给出 `count` 把互不相同的 key，优先挑在飞数最少的，
  跳过已达容量（`DEFAULT_CAPACITY = 3`，可用 `FACHUAN_GATEWAY_KEY_CONCURRENCY` 调整）的；
- 全部饱和时仍返回（best-effort）+ WARNING——宁可排队也不让律师的提问失败；
- key 不够时循环复用 + WARNING，**不报错**：少几把 key 是运维配置问题；
- `RunContext.api_key` 有值就照用，后端**不得**再调 `_next_key` 覆盖它；
- `compact_service` 也参与分配（压缩与对话打的是同一批 key，压缩撞上满 key 的表现正是
  「上下文快爆了、最需要压缩的时候压缩卡 60 秒」），并在 `finally` 归还租约。

红线：`KeyLease` 持明文 key（要传给后端），但**任何日志/异常消息里只出现指纹前缀**。

**5. 成本按 agent 归因**

多答一轮会同时落 N 条 `AgentRun`，没有 `agent_kind` 时账上只能回答「这一轮花了多少钱」，
回答不了「**哪个 agent** 花的」——两个 agent 配同一个模型时更彻底无解。

- `AgentRun.agent_kind`（迁移 `0018_agentrun_agent_kind`）：空串 = 引入本字段之前的旧数据，
  **不填 `pi`**——填了就把「不知道」伪装成事实；
- `stream.py` 落库时带 `agent_kind=backend.kind`（本轮实际用的后端，不是会话默认的）；
- `usage_stats.by_agent()`：**在 SQL 里**用 `Coalesce(NullIf("agent_kind", ''), 'pi')` 归一空串。
  只改显示文案不够——`GROUP BY` 会把 `""` 与 `"pi"` 分成两组，逐行改名会出现两行都叫 pi、
  token 各算一半的报表。统计 runs / tokens / cache 命中率 / 失败 / 中止。
  目前是服务层函数 + 单测，HTTP 路由本轮未挂。

**6. 到账通知的 AI 兜底匹配（`contract_match_ai.py`）**

规则匹配靠三个硬信号（案号、付款人命中委托人、代付方命中委托人）。真实到账通知千变万化
——银行改模板、律师把付款方写成简称、一句话塞三家公司——任何一种都会让硬信号全部落空，
整笔钱只剩「金额恰好撞上应收余额」，在待认领页显示成「仅金额吻合」，让人翻十几个无关项目。

兜底层的边界写死在模块 docstring 里，四条都不可妥协：

1. **只在没有任何 `exact` 候选时才调用**（规则已给确定答案时不再花一次模型调用去「复核」）；
2. **AI 只能从给定候选里选**，返回的 id 不在候选集合里一律丢弃（幻觉 `999` 不会变成一行项目）；
3. **`kind` 恒为 `ai_suggested`，排在所有规则候选之后**（`_KIND_ORDER` 里是 3）；
4. **失败静默降级**（模型不可用 / 超时 / 非 JSON 就当地没有兜底）；纯只读，不写数据。

候选池侧补了名称归一化（去「有限公司」等后缀、公共前缀、泛化名判定）与**独立额度**
（`MAX_CANDIDATES + MAX_AI_RESULTS`），避免规则候选的上限把兜底结果挤掉。

#### 修复

**1. 到账匹配漏掉「无『代』字」的付款方说明**

真实样本有两种写法，原正则强制以「代」开头，只认第一种：

- ①「（代某供应链公司付律师费）」 ✅ 一直能认
- ②「（甲方公司支付律师费）」 ❌ **完全不命中**

失败链条：律师先把客户的钱收进自己账户再转入律所账户，银行通知里的付款人是**律师姓名**，
真正的付款方只写在括号里 → `on_behalf_of` 留空 → 唯一能指向项目的强证据消失 →
整笔钱只能靠「金额撞应收余额」落进 `amount_only`。

修法：正则放开「代 / 由」前缀并补 `代付 / 汇付 / 缴付` 等动词；**只在括号片段里找**
（正文任意位置搜「XX支付」会把「向贵公司账户支付」这类描述当成人名，噪声当证据比漏掉更危险）；
新增 `_clean_on_behalf` 剥掉用途后缀（律师费/代理费/服务费…）与指代前缀。

同时补 `looks_like_person_name()` + `TransferNotice.payer_is_person`：律所真实链路是
「客户 → 承办律师 → 律所」，此时付款人是自然人，**不能**拿去和合同的委托人比对
（律师永远不是委托人），否则白白浪费一条实名信号，还可能误命中同名委托人。
判定不写死律师名单（避免跟组织架构漂移），只标识「付款人是自然人」这一事实。

**2. 思考档位：默认 `medium` 等于「一开思考就 400」**

实测（DeepSeek V4.1 走 vLLM）服务端原话：

```
reasoning_effort must be low, high, xhigh, max, or an integer within [1, 100]
```

而 `DEFAULT_THINKING_LEVEL` 就是 `medium`。三处口径一起修：

- pi 侧：默认改 `max`；新增 `_GATEWAY_EFFORT_MAP` 把七档收窄到服务端白名单
  （`minimal → low`、`medium → high`），`thinkingLevelMap` 显式写全七档，
  否则「拖到 Max」会被 pi 静默降成 `high`（看起来调了但没生效）；
- `supportsReasoningEffort`：`False → True`。早先写 `False` 是因为判断「网关不认
  reasoning_effort，发了会 400」，实测证明那个判断错了——`reasoning_effort=max` +
  `chat_template_kwargs.thinking=true` 是 HTTP 200 且 `reasoning_content` 有内容。
  两个参数**互补**：thinking 管「要不要想」，effort 管「想多深」；
- dsh 侧：`reasoningEfforts` 由 `(off, low, medium, high)` 改成 `(off, low, high, xhigh, max)`
  ——`medium` **不能列**（发出去直接 400，等于在 UI 上埋了个必炸档位），`minimal` 不列
  （服务端静默降成 low，不如不给）。而且 key 必须加引号：YAML 1.1 把裸的 `off` / `on`
  解析成布尔，于是 `off: "off"` 会变成 `False: 'off'`，dsh 找不到 off 档 → 用户关不掉思考，且不报错。

**3. `stream_chat` 的 `agent_kind` 落账口径**

`_record_run` 增加 `agent_kind` 参数（截断 32 位），确保多答时每条运行记录归到真正跑它的后端。

#### 优化

**1. 开流前的固定开销，一轮只做一次**

`stream_chat` 会被调用 N 次，而「铸律师凭证 + 探 pi session + 可能补历史」对 N 栏是**同一个答案**。
各栏各算一次不只是白跑：这些都走 `sync_to_async(thread_sensitive=True)`，即在同一线程上排队，
重复 N 次就是串行 N 次；`has_pi_session` 每次还会把会话目录 `mkdir` + `chmod` 一遍。

抽出 `ContextPrep` + `prepare_context()` + `probe_pi_session()`：`stream_multi` 算一次，N 个
`stream_chat` 共用。顺序是「铸造 → 探 session → 补历史」，铸不出凭证就整轮拒绝
（不能让工具退回超管服务账号执行）。

**2. 网关配置 30s TTL 缓存（`gateway_cache.py`）**

每轮现查 `LLMProvider` 付掉一条 `sync_to_async` + ORM 的固定开销（实测首字延迟里约 1.3s 量级）。
两条红线同时成立：

- 用户在 Admin 换模型 / 换 key 必须**立刻生效** → 短 TTL（默认 30s、上限 60s）**且**
  `LLMProvider` 的 `post_save` / `post_delete` 信号直接清缓存（信号只管本进程，
  TTL 兜住多 worker 的最坏情况）；
- key 轮转**不能**被缓存固化 → 只缓存 provider 的静态配置（base_url / 全部 key / 模型清单 /
  思考开关），「这一轮选哪把」仍每轮现算。缓存键里必须含 `model_hint`，否则会把 A 平台的
  key 发给 B 平台的地址。

失效信号挂在 agent app 的 `ready()`（`dispatch_uid` 保证只挂一份，连接失败只 warning
——最坏结果是「最多 30s 后生效」，不该让进程起不来）。

**3. MCP 连接常驻化（`mcp_session_pool.py`）**

裸 SDK 每轮 `async with server` 都要重跑「建连 + `initialize` + `tools/list`」，
实测**约 2.9s**，而工具面在进程生命周期内几乎不变。

池的键是 `(endpoint URL, sha256(token))`——`:8011` 强制每请求 Bearer 且刻意不回退服务账号，
而 MCP 的 streamable-http transport 把 `Authorization` 写在**连接**上。所以不同律师的 token
→ 不同桶 → 不同连接，物理上不存在「拿到别人那条连接」的代码路径；也绝不存明文 token 做键。

按桶做池而不是「每 token 一条」：一条连接断掉会同时毁掉正在用它的所有轮，池里多条时一次只坏一条。
空闲 600s 回收，桶内最多 2 条。连接失效就摘掉、关掉，**下一次取用重新建**，不重试本轮
（重连要几秒，用户已经等着了）；失败一律降级为「无工具但能对话」。

**4. 开流打点（`FACHUAN_AGENT_PROFILE=1`）**

多答时 `stream_chat` 被调 N 次，固定开销全部排在一条线程上，只看总时长分不出哪段占多少、
重复了几遍。`profile.timed()` 给每段单独计时（`prepare.*` / `stream.*`），默认关——
关闭时只多一次 `os.environ` 读取。

## 前端

#### 新功能

**1. 多答：2~4 栏并排，栏头写「agent · 模型」**

- `DualAnswers` → **`MultiAnswers`**：按栏数取 `sm:grid-cols-2 / 3 / 4`（写死两列会把三栏硬塞成
  「上面一对、下面一个」，对照关系就散了）；窄屏上下堆叠——侧边栏面板在笔电上只有 400px 宽，
  硬塞四列会把每栏压成一行三个字的薯条。
- 栏头 `AgentModelHead`：模型这半截是**核心需求**而不是装饰。律师引入多答就是为了比较效果，
  只写 agent 名的话，同一个 agent 换两个模型跑两栏会看起来像同一个人说了两遍不同的话。
  模型名截断到 110px、hover 显示全名（按像素而非字符截断，字宽差异太大）。
- 单栏**不走**分栏容器：套一层会在视觉上暗示「本来可以有几栏」，那是引入多答之前没有的体验。

**2. 本轮问哪几个 AI：多选菜单 + 每行模型下拉**

`ComposerToolbar` 里的 `GitCompare` 双答开关换成 `AnswerAgentMenu`：

- 选项来自部署级清单（`GET /agent/backends`），写死几个开关会在新后端注册后立刻过期；
- 一行 = 勾选框 + 名字（默认徽标）+ 说明 + 模型下拉。两件事都只对**这一轮**生效，
  拆成两个菜单会让「哪家的模型」只能靠位置猜；没勾的行模型下拉置灰（选了也不跑，
  允许改只会让人以为自己已经配好了）；
- 行是 `div[role=option]` 里放两个真按钮——按钮套按钮是非法 HTML，浏览器会把内层甩出外层；
- 清单为空（后端没上线该字段 / 平台没配可选模型）时**整枚下拉消失**，多选 agent 本身照常可用。

store 侧删除布尔 `dual`，新增 `answerAgents` / `answerModels` / `toggleAnswerAgent` /
`setAnswerModel`（`store/answers.ts`）。`reset()` 清空的是**选择**，保留部署级清单
——换账号不该带着上一个账号「某栏跑哪个模型」的配置。

开流前一次性算清：`resolveAnswerAgents`（过滤不可用 / 非流式、截到 `MAX_ANSWERS`）与
`resolveAnswerSpecs`（逐栏挂模型）同源，否则「这一轮几栏」与「每栏哪个模型」会各自跑出不同的栏序。
`model` 只在有值时才出现在请求体元素上——缺省字段 = 平台默认，与发纯字符串 `"pi"` 等价。

**3. `/assistant` 全宽助手页**

抽屉宽 600~1200px，多 agent 并排时每栏只剩一百多像素、工具行也挤成两行。新增独立页：

- `paths.assistant()` + 路由 + 懒加载（**故意不进 `ROUTE_PRELOADERS`**：copilot 域带
  markdown/语法高亮，登录即空闲预载会把它塞进每个用户的首屏余量）；
- 壳层在 `/assistant` 上**不渲染抽屉**、也不留并排 padding：同一段对话出现两个输入框，
  用户不知道该跟哪个说；抽屉开关状态原样保留，离开本页即恢复；
- **不新增任何导航入口**（第一版曾往顶栏导航塞了一个「AI 助手」，已回退）：
  用户原本就有右侧的「AI 助手 ⌘J」抽屉按钮，再造第二个同名入口只会让人点错，
  也会把不属于本功能的导航结构一起改掉。**进出都走抽屉这一条路**：
- 抽屉 header 新增「全屏」按钮（`onExpand`）→ 跳 `/assistant`；
- 独立页 header 新增**带文字**的「退出全屏」按钮（`onExitFullscreen`）→ 回进入前那一页。
  全屏页没有导航入口可以「点回去」，不给出口用户就被困住（真实反馈：全屏之后不知道怎么缩回去）。
  用文字而不是小图标：上一版只给图标没人找到，出口这种「后悔药」宁愿占点地方。
  退回目标按 `location.key` 判：站内进入 → `navigate(-1)` 回上一页；直接粘链接 / 刷新后
  打开（`key === 'default'`）→ 回首页，否则 `navigate(-1)` 会把用户弹出应用。
- `use-active-session.ts`：两个宿主共用的挂载期装配（恢复会话 / 拉后端清单 / 消费业务页启动
  上下文 / 拉待审 / 按业务范围取标题与能力 / 流结束失效缓存 / 后台任务跑完重拉转录）。
  页面若照抄一遍，漏掉的那处就表现为「同一个会话在两个宿主里表现不一样」。

**4. 等待期观感：在律师的注意力焦点上说「正在干什么」**

真实反馈：Pi 2.4 秒就出字（边调工具边吐过程），dsh / openai-agents 却「憋到 16 秒才一次性吐全文」。
根因不在网关（0.28s 就有 chunk），而在这两个后端**先调工具、调完才说正文**，其间界面一片空白
——看到的是「卡死」。

事件链路本来就通，问题全在**位置和措辞**：

- `domain/progress.ts`（纯函数）：`pendingToolCall` 判「这一栏此刻还在等哪个工具」，
  `toolActionLabel` 把工具名说成人话（→「正在查客户信息…」）；
- `StreamActivity.tsx`：把这一行放进**本栏气泡内、正文之前**，用 `copilot-shimmer` 流光表明还活着
  （`prefers-reduced-motion` 下回落静态文字）；
- 工具条**只有一个可见位置**：正文没到 → 气泡内活动行；正文到了 → 气泡下方的紧凑 chip
  （`ToolChips.OwnToolList`）。两者按「正文有没有到」互斥，不会重复渲染成两处。

**5. 待认领页：AI 推断必须显式标注**

`CandidateKind` 增加 `ai_suggested`，`KIND_STYLES` 文案「AI 推断」（`risky: true`）；
`intakeShape` 把它与 `amount_only` 归同一类（都要强提醒核对），`hasUsableSuggestion` 对它返回
`false`（不给「确认建议」按钮），`intakeHeadline` 明写「AI 推断的项目，请核对后选择」。
AI 自己也会判错，不能因为它排第一就默认可直接确认。

**6. 首页日历：按面板净宽降密度**

一律按**面板净宽**判定，不看视口：AI 助手并排让位与分屏会把日历压到几百像素，而视口依旧很宽，
此时 `max-[760px]:` 与 `useMediaQuery` 都不成立，五行卡片塞进 40~90px 宽的格子，每行只剩 1~2 个字。

`calendar-density.ts` 三档 + 每格行数：

| 档 | 条件 | 表现 |
|:--|:--|:--|
| `wide` | ≥ 900px | 原五行卡片（1440/1512 笔电整宽仍在此档，不劝动手感） |
| `medium` | 680~900px | 两行卡片（砍掉地点/律师这类可从详情看的次要信息） |
| `compact` | < 680px | 圆点 + 标题，点格开当日抽屉 |

每格最多 5 / 4 / 3 行（≥1900 / ≥1150 / 其余）。事件行抽成 `DayEventRow`，`DayCell` 净减 44 行
（+76 / −120，剩下的都是密度分派）。

#### 修复

**1. 转录分组从「连续 assistant」改成「一段连续非 user = 一轮」**

这条曾经就是按「连续 assistant」写的，前提是「同一轮各栏的回答相邻写入」——**前提是错的**：
工具调用（`role: 'tool'`）也落在同一段里，而多 agent 的工具是**交错**落库的。

两个用户报的 bug 都由此而来：

- 工具消息各自成组 → 每组只有 1 条 → 走「单条」分支 → 渲染成全宽 `ToolRow` 堆在对话底部，
  分不清哪个 agent 查的、还占满屏幕；
- 同一轮的 assistant 被工具隔开 → 三个 agent 被切成多组 → 刷新后从 3 栏变成 2 栏 + 1 条掉到下面。

轮次语义对这两件事都免疫：user 消息天然是轮次边界，判据也不依赖后端新增字段（消息表没有 turn_id），
历史数据同样成立。

**2. 刷新后栏序被「工具落库顺序」带偏**

`distinctAgentKinds` 只从 **assistant** 取栏序：多 agent 的工具总是先于正文落库（模型先查再答），
若把工具算进栏序，刷新后栏的左右顺序会整排换位——实时视图 pi→dsh→openai-agents，
刷新完变成 openai-agents→pi→dsh，读起来像换了答案。

同时「整轮中断 / 全部失败」时一组里可能只有工具、没有正文：没有正文就没有栏可谈，
此时必须逐条平铺工具行，而不是渲染出一排空白栏（实测见过 `sm:grid-cols-4` 的空栅）。

**3. 同栏多段 assistant 合并、工具归位到各自的栏**

`mergeAgentAnswers`：同一栏的多条 assistant 合成一条（正文/思考按到达顺序拼接），
工具挂回**它自己那个 agent** 名下，再挂在**合并后**的那条上——界面才是「一个人 → 他查过的东西 →
他的话」，而不是「话、工具、话、工具」。已归位的工具 id 由 `attachedToolIds` 统一给出，
转录流里不再重复渲染（否则未完成的工具会同时出现在气泡内和外面）。

**4. 失败那一栏不再留空，改写明「本轮未做」**

只标失败那一栏（`ChatMessage.failed`），其他栏正文照常。留空的话界面上只有一个空白栏头，
看起来像「AI 回答了但内容丢了」，律师会去查是不是系统坏了。

**5. 降级要说话，并且把被丢下的栏就地收尾**

aux 席位满 → 后端只跑主栏并收窄 `agents`，只会给主栏发 `done`，其余栏永远等不到收尾信号
（界面上就是一排转圈的空栏）。新增 `onDegraded`：说明「本轮只跑了主后端」，同时把未跑的栏
`streaming: false, failed: true`。

**6. 日历头部统计行溢出 / 「快速记一笔」被助手盖住**

统计行改为允许折行；「快速记一笔」行宽改 `min(320px,100%)`，助手拉宽时不再被盖。

## 已知取舍与边界

1. **openai-agents 没有审批闸门**（`approval=False`）。SDK 有 `MCPToolApprovalFunction`，本轮
   按约定不接；前端据此隐藏审批入口。**高危工具在这一栏没有人工闸门**，启用该会话前需合规确认。
2. **openai-agents 不支持插话 / 中止**（`steer=False`）：`RunResultStreaming` 只有 `cancel`。
   声明 `True` 会比禁用更糟——渲染出一个敲进去就被丢弃的输入框。
3. **dsh 的流式粒度修不了**：SDK 只发整条 `assistant/message`，无逐 token 增量（等上游更新）。
   本版只保证「等待期界面不空白」。
4. **`by_agent` 只有服务层**：聚合函数与单测已就绪，HTTP 路由本轮未挂，等管理端需要时再开。
5. **`stream_dual` 保留为薄壳**：外部仍有调用点按这个名字 import（含测试），一次性全改会让抽象
   改动淹没在改名噪音里。壳里**不许加逻辑**，否则又会长出第二份实现。
6. **AI 兜底不是答案**：`ai_suggested` 永远排最后、永远不预选、永远要人点确认。模型判错时，
   人的核对是唯一闸门。
