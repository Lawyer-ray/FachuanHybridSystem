# 一、四个真机问题

## 1. 第二轮对话必炸（最严重）

**报错**：

```
deepseek_harness.errors.JsonRpcError: session "<uuid>" already exists
```

**根因**：`harness.run(prompt, session_id=...)` 的内部实现是
`self.start_session(session_id).run(...)`，而 dsh 把会话**持久化在磁盘**
（`$DSH_HOME/sessions`）。同一个 `AgentSession` 的第二次发言必然撞号。

**修法**：先 `resume_session`（恢复磁盘历史）再在那个 Session 上 `run`；
只有全新会话才 `start_session`。`"already exists"` 异常**不吞**——那说明
我们自己逻辑错了，吞掉会把「后端不可用」误报成「新建会话」。

**实测**：

```
第1轮 -> {'dsh': '收到', 'pi': '收到'} 错误: []
第2轮 -> {'dsh': '好的', 'pi': '收到'} 错误: []
第3轮 -> {'dsh': '明白', 'pi': '收到'} 错误: []
```

dsh 第二轮答「好的」而非「收到」，说明它自己的多轮上下文也接上了。

## 2. 双答两栏都「(无内容)」

三个叠加的原因：

**(a) 迁移 0017 未应用** → `column agent_agentmessage.agent_kind does not exist`

这是**同一个坑第二次**（0016 那次是「创建会话失败」）。上次只补了
`makemigrations --check`（防「没生成迁移」），防不住「生成但没应用」。本版补
**CI 第 3c 步 `migrate --check`**，并造真实例验证它会红。

**(b) 前端 `onDone` 收掉全部气泡**

```js
onDone: () => { finishAssistant() }   // 收掉所有 streaming 气泡
```

双答时 pi 先完成 → done 到达 → **dsh 那栏也被收掉** → 后续 delta 无处可写。

修：`onDone` 接收 `origin`，只收自己那栏；全部栏收完才写 `doneAt`。

**(c) 后端 done 只发一个**

原设计「整轮只发一个 done」，注释理由是「两个 done 会让前端提前收尾」。
**这个理由是错的**——前端契约本就是按 agent 分栏。只发一个反而让次栏永远收不了尾。

修：按 `agents` 逐栏发。顺带修降级路径（降级后 `agents` 应收窄为单栏，
否则多渲染一个空栏）。

> **一条值得记的教训**：原测试 `test_done_emitted_exactly_once_with_agents`
> 断言「done 只能有一个」，注释还写着那个错误理由。**测试本身锁住了错误设计**，
> 所以 CI 全绿也发现不了。已连同断言与实现一起改正。

## 3. dsh 不思考

**根因**：`dsh_config` 的 provider patch 只声明了 `id` / `name`，**完全没读**
`LLMProvider.enable_thinking`，也没写 `reasoning` / `compat`。

而 pi 侧（`model_config._model_entry`）早就踩过同一个坑并解决了：

> 律所 LiteLLM 网关把思考开关放在 `chat_template_kwargs.thinking`（布尔），
> 适配器默认探测会误判 → 不发思考参数 → 网关不返回 `reasoning_content` →
> 表现为「平台开了思考但模型永远不思考」。

**修法**（与 pi 同口径）：三件套缺一不可——`reasoningEfforts` /
`thinkingFormat: chat-template` / `chatTemplateKwargs.thinking`。
条件是**平台开关 AND 模型确实支持推理**（只按开关不看模型会给普通模型错报能力，网关直接 400）。

**实测**：

```
修复前: {'pi': 187 字思考, 'dsh': 0 字}
修复后: {'pi': 187 字思考, 'dsh': 221 字}
```

## 4. 生命周期事件噪音

实测一次普通对话带 5 条生命周期事件（`turn/start` / `step/start` / `step/end` /
`user/message` / `request/header`），此前全部透传成 `unknown` 发给前端。

**修法**：白名单静默（不是「凡不认识都不发」——新事件类型若是**内容**，
必须能漏出来被看见）。`turn/end` 刻意不在此列：它有专门分支（`reason.kind=="error"`
要报成 error），且该分支在静默检查之前就已 return。

# 二、工具面分层：每轮省 85% token

## 问题

dsh 把 MCP 的 **424 个工具**全量注册给模型，每轮请求带 **305KB / 约 10.4 万 token**
的 schema（实测）。双答时翻倍。

## 为什么只能在服务端做

两条实测否掉了 dsh 侧的所有方案：

**证据 1：裁剪后模型调不了不在列表里的工具**

```
模型可见工具: ['mcp__fachuan__get_server_time']
要求调 delete_case → "当前会话中并没有 delete_case 这个工具"
```

**证据 2：加 `tool_search` 动态解锁也不行**

做了个探针：`tool_search("delete")` 命中后，在 service 侧把 `delete_case` 加进
下次 `tools/list`。结果：

```
整轮 6 次 tool_search，request/header 始终只有 2 个工具
→ 模型回答："tool_search 命中 delete_case，但实际调用无法发起"
```

**根因**：dsh 在**会话启动时同步一次** `tools/list`，**会话内不重新同步**。

> 这推翻了 `dsh-plugin-evaluation.md:190` 的乐观判断（「用 `tool-addition`
> 激活后按真名调用」）。那需要**自写 Cordis 插件**，不是「MCP 侧多返回几个工具」
> 能做到的。

## 实现

MCP server 侧 ASGI 中间件，按 `X-Fachuan-Tool-Tier` 裁剪 `tools/list`：

| 值 | 返回 |
|:--|:--|
| 不带头 | 全量 424（**老客户端零影响**，兼容底线） |
| `lite` | 61 个（`DIRECT_TOOLS` + `DIRECT_PATTERNS`） |
| `full` | 全量 |
| 未知值 | 全量 + WARNING（**不 fail-closed**） |

**实测**：

```
tier=(无)  -> 424 个工具 / 305 KB / ~104,149 token
tier=lite  ->  61 个工具 /  44 KB / ~ 15,223 token
```

## 两个实测踩到的实现坑

1. **中间件拿到的是 `_serialize` 之后的 wire dict**，不是 pydantic 对象。
   写 `result.tools = [...]` **静默无效**，必须 `result["tools"] = [...]`。
2. **stdio 模式下 `ctx.request` 为 `None`**，直接走全量。

## 未知值为什么不 fail-closed

拼错一个头（`lit` / `Lite `）就返回空工具集，是能想到的最坏体验——模型一个工具
都没有，只会反复说「我做不到」。全量是安全侧默认：多花 token 但功能完整。

## 顺手优化

`mortgage_default_calculate` 的 docstring **7106B → 930B**（单个工具占全量 6%，
因为它把大量银行合同条款写进了 description，而这些细则 48 个参数各自的
`Field(description=...)` 里都有）。

# 四、已知取舍

**dsh 拿到的是静态 61 个工具。** 律师问「创建一份合同」时，如果
`create_contract` 不在直连层，模型会说「我没有这个工具」——**这是真实的能力损失**。

- 回滚：`FACHUAN_DSH_TOOL_TIER=off`（dsh 侧）或
  `FACHUAN_MCP_TOOL_TIER_GATE=off`（服务端总闸），两者独立
- 生产库当前只有测试数据（12 会话 / 47 run），现在切换零风险

**上线后要盯的两个信号**：
1. 律师反馈「AI 说没有某功能」→ 说明该工具应加入 `DIRECT_TOOLS`
2. dsh 会话的 token 消耗是否如预期下降
