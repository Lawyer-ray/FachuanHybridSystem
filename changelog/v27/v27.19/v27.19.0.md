# 一、DeepSeek Harness 接入

## 为什么走 Python SDK 而不是 TS 版

项目已有 `dsh-plugin-evaluation.md` 评过 **TS 版**（Cordis 插件树 + 浏览器前端）。
但我们的编排层、审批服务、SSE 协议、Copilot 面板**全在 Django + React**，
走 TS 版等于把执行权交给 dsh 自己的 Host 进程，前端要重写。

Python SDK（`deepseek-harness-sdk==0.2.2rc2`）是**stdio JSON-RPC 驱动子进程**，
形态与 pi 同构，所以：

| | TS 版路径 | Python SDK 路径（本版） |
|:--|:--|:--|
| 谁驱动 runtime | dsh web 服务 | **我们的 Django 进程** |
| 前端 | 需重写 | **零改动**（协议不变） |
| 工作量 | 5 个 TS 包 1800–2500 行 | **1 个 backend 类** |

## 新增模块

```
backends/dsh_backend.py    DshBackend：同步 SDK → 异步生成器桥、事件翻译、会话池
backends/dsh_config.py     LLMProvider → dsh 配置；安全收紧；网关路由；代理剔除；profile 引导
backends/dsh_mcp.py        法穿共享 MCP（:8011）接入
```

`DshBackend` 的 `capabilities`：`streaming/tool_calls/approval/compaction=True`，
`steer=False`（SDK 未暴露插话/中止），`concurrent_in_session=False`（保守默认）。

# 二、真跑才暴露的五个坑

这一节是本版最有价值的部分。**五个问题全部只有真跑才暴露，静态审查一个都发现不了。**

## 坑 1：dsh 读 cwd 的 `.env`，遇到 `HTTPS_PROXY` 直接退出

**症状**：`TransportClosedError: DeepSeek Harness runtime stdout closed`

**根因**：dsh 启动时读 cwd 下的 `.env`（layered env），且有一条自我保护——
代理类变量只允许由**启动方环境**提供，不允许来自「随仓库走」的 `.env`
（那些变量决定进程去哪里取代码与网络）。Django 进程 cwd 是 `backend/`，里面正有含代理配置的 `.env`。

**修法**：给 dsh 专属干净工作目录（`~/.fachuan-dsh/<uid>/workspace`）。
顺带解决另一个隐患：dsh 会读 cwd 下的 `AGENTS.md` 与技能目录（编码 agent 默认行为）。

**同一个坑在 profile 引导阶段又出现一次**，所以引导用的 subprocess 也显式设了 `cwd`。

## 坑 2：代理劫持内网网关 → 502 no body

**症状**：模型调用返回 `502 status code (no body)`，重试 5 次后空回复。

**根因**：律所网关是内网地址，开发机 `HTTPS_PROXY` 指向本地 Clash，`NO_PROXY` 只含 localhost。
dsh 子进程继承代理变量 → 请求被送到代理 → 代理无法回源内网 → 网关侧 502。

**决定性验证**：同一条 key + base_url，**直连 `chat/completions` 正常回答，走代理则 502**。
这一步把「网络不通」与「路由选错」区分开——否则会一直以为是网关或 key 的问题。

**修法**：`without_proxy_env()` —— 启动前临时从进程环境剔除代理变量。
注意 SDK 是 `os.environ.copy()` 叠加 config.env，**只能加不能删**，必须在父进程环境层动手。

> 这与 `pi/rpc_client.py` 的 `_clean_env` 是同一个坑、同一种解法。
> pi 早就踩过并写在注释里，但**新接入的后端不会自动继承这个经验**——所以本次把它写进了坑库。

## 坑 3：`deepseek-official` provider 不认 LiteLLM 网关

**症状**：`DeepSeek Messages request failed (502)`

**根因**：默认 provider 走 DeepSeek **原生 Messages 协议**，律所网关是
**LiteLLM（OpenAI 兼容）**——认 `/v1/chat/completions`，不认 Messages 形态。

**修法**：用 `llm-pi-ai` 插件声明 provider，走 `openai-completions`。
三个字段缺一不可，每个对应一个真实报错：

| 缺什么 | 报错 |
|:--|:--|
| `api` | `no adapter registered for provider "fachuan"` |
| `models` | `provider "fachuan" resolves no models` |
| `models` 形态错 | `expected array` / `expected object`（正确是对象数组，每项带 `id`） |

## 坑 4：官方 MCP 插件版本落后 runtime 两个 minor

```
dsh: installation rejected: @deepseek-ai/dsh-mcp-client@0.0.1-rc.1
     is incompatible with dsh 0.2.2-rc.2
```

必须 `dsh plugin allow-version ... --accept-risk` 才能装，且装了**不自动生效**
（它不声明 `dsh.bundle`，要手写 patch 层）。

**这是整条接入链最脆的一环**——官方自己都没对齐。

## 坑 5：每个 dsh home 都缺 profile，且 `PATH` 上的 dsh 版本是错的

**症状**：工具面为空（模型能对话但没有 `mcp__fachuan__*`），且不报错。

**根因（两层）**：

1. 每个 dsh home 首次启动只铺 shipped profile（**不含 mcp-client**）；
2. `shutil.which("dsh")` 找到的是全局 npm 版 **0.2.2-rc.1**，而 SDK 配对的是 venv 里的 **0.2.2-rc.2**。
   用错版本报 `returned non-zero exit status 1`，**错误信息完全不提版本不匹配**——排查方向被彻底带偏。

**修法**：
- `_ensure_profile()`：共享一份真实安装（`_shared_profile`，装一次），各 home 的 `profiles/sdk` 软链过去
- `shutil_which()`：**优先用与当前解释器同目录的 `dsh`**（唯一保证配对的那个）

> 软链目标也踩过一次：起初链到 `_shared_profile` 根，实际内容在它下面的 `profiles/sdk/`，
> 结果「装了但工具面为空」——这种失效是静默的。

# 三、MCP 工具面：426 个工具接上了

## 实现要点

`dsh_mcp.ensure_mcp_patch()`：
- 先 `ensure_shared_server()` 确保 :8011 在跑（它原本只在「有人用 Copilot」时才被拉起，
  没人用过就是 `ECONNREFUSED`，而 mcp-client 默认 `failOnStartupError: false` → **静默无工具**）
- 生成 patch：`serverName: fachuan` / `streamable-http` / `Authorization` 头
- **token 不写日志**（只记长度），文件 0600
- 无 token 时返回 None 并 warning（无身份无法调业务工具）

## 实测结果

```
工具总数: 426
mcp__fachuan__*: ['mcp__fachuan__add_case_party', 'mcp__fachuan__add_contract_party', ...]
final: '你好' | finish: completed
```

**工具命名与现网 pi 完全一致**（`mcp__fachuan__<rawName>`），所以现有四级审批能原样命中。

## ⚠️ 必须知道的成本数字

```
426 个工具的 schema 体积: 196 KB ≈ 6.7 万 token / 轮
```

这与 pi 时代的实测（409 工具 ≈ 8.8 万 token）同量级。**dsh 也没有工具分层机制**
（`mcp-client` 一次同步整份 `tools/list`，无过滤配置）。

这意味着：
- 单轮成本显著上升，长会话更明显
- **双答时两份都要付这个前缀**，成本再翻倍

**下一步该做的**：把 pi 的 `tool_tiers.py` 分层策略搬到 dsh（自写 `tool_search` + 按需激活），
本版未做（需要先确认 dsh 的工具激活机制与 cache 影响）。

# 四、安全收紧：37 个插件禁用

dsh 默认是「给程序员用的编码 agent」，开着一整套 shell / 文件 / 技能 / 联网能力。
法务场景必须关掉——它们的共同后果是「提示注入 → 读写宿主文件 / 执行命令 / 外发」。

**实测效果**：暴露给模型的工具从 **16 个降到 2 个**（只剩 `ask_user_question` 与 `working_directory`），
**宿主机 204 个 skill 不再注入**。

| 禁用类别 | 插件 |
|:--|:--|
| shell / 命令 | `tool-bash`、`bash-sandbox`、`tool-pwsh`、`pwsh-sandbox`、`tool-jobs`、`shell-env` |
| 文件 | `tool-fs`、`tool-fs-search`、`fs-observation-policy` |
| 技能 | `skill`、`skill-filesystem`、`tool-skill` |
| 指令注入 | `agent-instructions`（不读 cwd 的 AGENTS.md） |
| 插件管理 | `plugin-manager`、`tool-plugin-manager` |
| 子 agent / 工作流 / 定时 | `subagent*`、`tool-workflow`、`schedule*`、`goal*` |
| 联网 | `web`、`tool-web`、`web-search-deepseek`、`web-fetch-http` |

**顺序保证**：收紧层是第一个 patch。有测试锁（`test_lockdown_listed_before_provider_patch`）。

# 五、双 agent 同题并答

## 交互

新建会话选好主后端后，发送区有「同时问两个」开关（**默认关**，因为成本翻倍）。
打开后同一问题同时发给 pi 与 dsh，两栏并列显示，各带后端标签。

## 后端设计（`services/chat/dual.py`）

- 主后端 = 会话自己选的；次后端 = 注册表里第一个不同的
- 事件按到达顺序交错产出，前端按 `agent` / `run_id` 分流
- 配额：主用 `primary`（不限制），次用 `aux`（满额立即拒绝）
- **失败矩阵**（核心）：

| 情况 | 表现 |
|:--|:--|
| 两个都成 | 双栏，各自正常 |
| 一个成一个败 | 成功的照常输出；失败的只发一条 `error`（带 `agent`），**不阻断另一个** |
| 都败 | 只发**第一条** error（不堆两条） |
| 配额不足 | 只跑主后端 + `degraded` 事件，前端提示「本轮未做对比」 |

- `done` 只发**一次**（等两个都结束，带参与方清单）
- 用户消息与标题只写一次（两个后端跑同一条提问，各写一次会让回放里出现两个一样的提问）
- 事件总线只订阅一次（两次订阅会让一条审批只被其中一个消费）

## 数据模型

`AgentMessage.agent_kind`（迁移 `0017`）：**历史数据回填空串**（表示「旧数据/未标注」，
前端渲染时当 pi 处理）——不回填 'pi' 是为了避免猜错。

# 六、修掉的真实阻塞：创建会话失败

## 症状

律师点发送 → 「创建会话失败，请稍后重试」。

## 根因

```
column agent_agentsession.agent_kind does not exist
```

迁移 `0016` 生成了，但**开发库没跑 migrate**。而：
- 前后端 CI 全绿
- 所有单测全绿（**测试库会自己建表**）
- 只有真人一点就炸

## 修法（两层）

1. 应用迁移（治标）
2. **CI 加「迁移漂移检查」**（治本）：`scripts/ci-local.sh` 第 3b 步
   `makemigrations --check --dry-run` —— 模型改了但没生成迁移文件时直接红

> ⚠️ 已知局限：`--check` 只能发现「没生成迁移文件」，发现不了「文件在但没应用」。
> 后者需要连库比对，本版未做（CI 里没有可用的持久库）。
