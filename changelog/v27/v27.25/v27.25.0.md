## 一句话

| 之前 | 现在 |
|:--|:-|
| 「取字成功」的判据就是「有没有字」。复读循环（一页吐 17000 字、98% 是同一句话）与空返回（`finish=stop` 但正文空）都能骗过它，一路进 Markdown、进分段、进归案 | 新增 `page_degeneracy` 四条件判据，把「有字」与「可用」分开 |
| 同一份卷宗里同一个数被读成两版（应补税额 `6529346.56` 在 3 页一致、第 4 页成 `6592946.56`；案号 `民终6121号` 有一页掉了一位成 `621号`），而「错字频次 / 人名聚类 / 证件号结构」三类判据都看不见 | `cross_page_consistency` 增两类**数字判据**，实测在真实卷宗上各报 1 条、都是真错、0 误报 |
| 只有 MinerU / Textin 两个云端解析平台；旋转页它们读成行序反转 + 错字密集，没有任何兜底 | 新增第三个引擎 **DeepSeek OCR**（系统配置里填 Key 即可用），自带页级自愈；可作为 `cloud_backend=deepseek` 单独使用，也在 auto 链末尾兜底 |

## 后端

### `page_degeneracy.py`（新）：把「有字」与「可用」分开

四条判据，都是「除了循环没有别的解释」才判死：

1. 正文为空
2. 同一行重复 ≥5 次（行长 ≥8；真实银行流水同一行最多 3 次）
3. 40 字窗口去重比 <0.25（只看含 ≥12 汉字的窗口，且窗口数 ≥10）
4. `finish_reason≠stop` 且唯一行比例 <0.5

**刻意没有「字数太多=坏页」**。调研期曾用过 `len(text) > 5000`，在 164 页银行流水上把
4 页**完全正常**的交易明细（6300–7500 字、唯一行比例 1.00）全判成坏，由此得出
「退化率 42%」的错误结论；换成上面四条后真实首跑退化率是 20.7%。密度高的表格页本来
就字多，字数不是证据。

第 3 条也返工过一次：先数「某个窗口出现几次」会把合法流水页判死（账号 +
「银联无卡快捷业务联机待清」那段结构串每行都有，单窗口数到 18 次）；改看去重比后
该页 0.89–0.97 vs 真循环页 0.01–0.15，分离度足够。

三份真实卷宗（37 / 93 / 164 页）上的判定结果：10.8% / 5.4% / 22.6%。

### `cross_page_consistency.py`：两类数字判据（都是 medium，只提示不自动改正文）

- `case_number_variant`：同「法院 + 年份 + 案件类型」下，短号码是长号码**删掉 1–2 位**
  的产物。**只认删除不认替换**——实测 `6121号 → 621号` 命中，而 `6121号` / `6122号`
  这两个同年同类的真案件不命中（形态是替换一位）。
- `amount_variant`：同角色标签（应补税额/本金/合同价…，金额前 40 字内）+ 数值编辑距离
  ≤2 + **多数派出现 ≥2 次**。最后那条不是调优是必需：去掉它那份 164 页卷宗会出 4 条
  假阳性（`100000`/`1310000`、`10020`/`100000`、`11700`/`11530` 全是两个真实金额），
  加上后 4 条全滤掉而真错仍在。

没有单位（`元`）的数字一律不参与——页码、账号、流水号进来会盖掉真信号。

### `deepseek_backend.py`（新）：第三个云端解析引擎

`POST /v1/tools/ocr` 的封装。主调用 `text_recognition` → 退化检测 → 退化页逐页换
`rich_layout_recognition` 单页重试（并发 4，约 2.5s/页）→ 仍退化就**清空正文**并记进
`metadata.unrepaired_pages`，交上层走 MinerU / 本地 OCR。

实测（37 / 93 / 164 页三份）：首跑硬退化 10.8% / 5.4% / 22.6%；单页换 purpose 重试能救
**65%–71%** 的残余。空返回是瞬时的（164 页上 11 页空返回，重试一次 11/11 全恢复）。

三个照文档写就会错的地方：

1. **rich 模式的标记语法与文档不一致**：真实形态是
   `‹｜ref｜›image‹｜/ref｜›‹｜box｜›[[213,0,999,999]]‹｜/box｜›` —— 块类型词夹在
   `ref` 与 `/ref` **之间**，坐标在 `box` 那一对标签里；分隔符是**全角竖线 U+FF5C**，
   不是 ASCII `|`。按文档里的半角写法写正则会一条都匹配不到。
2. **坐标是千分比且是原始页帧**：一页 90° 旋转扫描的正文，框是「窄高」的。
   别拿「宽>高」判断坐标轴反了——那会把对的判成错的。
3. **网关体积上限低于文档**：官方写 100 MiB，实测 66 MiB 直接 413（openresty 挡的，
   返回 HTML 不是 JSON）。所以按 48 MiB 预判并给可操作原因。

另有几处配套：`bbox.resolve_bbox_unit` 把 `deepseek` 归 `permille`；
`OCRHandler.resolve_cloud_backends` 原来写死 `{"mineru", "textin"}` 过滤，新增平台
忘了同步会「注册了、也配了，却永远选不到」（不报错，静静回落本地 OCR），改成从
`CLOUD_BACKEND_CHOICES` 派生。

### 凭证：放 SystemConfig，不新增 `DocumentParseProvider` 枚举

系统配置页新增三个默认项：`DEEPSEEK_OCR_API_KEY`（密文）/ `DEEPSEEK_OCR_API_URL` /
`DEEPSEEK_OCR_PURPOSE`。`resolve_cloud_backends` 因此多一条可用性判据：另两个平台看
`DocumentParseProvider` 有没有启用的行，DeepSeek 看 SystemConfig 有没有 Key。
auto 模式下它**追加在最后**（是兜底不是首选；想让它当首选就显式锁定）。

## 前端

- `CLOUD_ENGINES` 增 `deepseek`，但**它不参与交叉比对**（后端 `DUAL_ENGINE_CHOICES`
  里没有它，它没有独立于 `cloud_backend` 的第二条通道）。新增 `DUAL_CAPABLE` /
  `dualEnginesOf`，`dual_engines` 只发可比对的引擎：勾 MinerU + DeepSeek 时正主是
  MinerU、`dual_engines=null`——不能让用户以为开了比对。
- 摘要与菜单副标题单列一套说法：只勾 DeepSeek 时说清「读得更准但约 1/5 的页会整页崩，
  需靠单页重试救回」；勾了 DeepSeek + 别家时说「DeepSeek 仅兜底」。

## 说明与遗留

- **新增迁移 `pdf_splitting/0015_alter_pdfsplitjob_cloud_backend`（仅 choices，无 DDL），
  尚未 `migrate`**——按规范迁移需用户确认。
- 退化判据只认「除了循环没有别的解释」的形态；「安静地读错一个数字」它抓不到，
  那正是案号/金额闸门存在的理由，而闸门只能抓「同一个数写了两版」。
- DeepSeek 的 20% 页级失败率是在三份扫描件上测的，其中两份来自同一批客户
  （银行催收卷宗，扫描特征相近）。换扫描源（手机拍照、彩印）首跑退化率可能不同。
- 金额闸门只有 2 个真错样本，精度 2/2 但统计上没有意义。
