# v27.25.7 · 一句话起草文书：骨架族 + 长正文注入 + 自动落进案件文件夹

> **版本判定**：本 PR 内按功能分段记账的第六段，沿用 `v27.25` 的第三位顺延。
> 能力轴：**文书生成**（前六段都在「怎么把材料读进来」，这一段开始是「怎么把文书发出去」）。

## 一句话

| 之前 | 现在 |
|:--|:-|
| 律师说「帮我写一份管辖权异议申请书」，AI 答不上来：`/doc-workspace/draft` 只有 REST，MCP 工具面里没有对应工具 | 一句话触发：MCP 工具 `draft_document` / `POST /doc-workspace/draft-by-type`，产物落进该案文件夹的指定位置并返回可直开的 `file_url` |
| 长正文塞不进模板：docxtpl 把 `\n` 变成 `<w:br/>`，全落在同一个 `<w:p>`，而 `w:ind/@w:firstLine` 只作用于段落首行 → 起诉状渲染出来是**一整段墙**，第二段起没有缩进 | `\a`(0x07) 断段：docxtpl 把它换成 `</w:p><w:p>{原段 pPr}`，**真断段且完整继承段落属性**，模板零改动 |
| 新增一种文书 = 写新 docx + 写代码分支（谁是骨架、哪个槽交模型、落到哪个文件夹） | 新增一种文书 = **插一行数据**（`DocumentSpec`）。格式由骨架固定，模型没有排版的能力 |
| 起诉状/答辩状的模板路径是硬编码常量；答辩状连 `DocumentTemplate` 记录都没有 | 路径由 `DocumentSpec.skeleton_template` 决定；答辩状补登记为模板（28 → 29） |

## 为什么现在做这个

28 个模板里真正需要 LLM 写长正文的占位符**只有 3 个**（`事实与理由` / `诉讼请求` / `答辩理由`），
其余全是确定性映射或代码拼接。所以缺的从来不是「更会写」的模型，是接缝。

三条硬边界（结构上堵死「AI 异想天开自由排版」）：

| 边界 | 行为 |
|:--|:--|
| `doc_type` 没有 `DocumentSpec` | **不生成**，回「这个文书还没有骨架」——绝不猜格式 |
| 槽位零命中 | 只降级 `other_filing` 并记 warning；再零命中就失败并说清「这个案件的文件夹没有 X 的位置」 |
| 任何一步失败 | **不留半成品文件** |

## 内容

### 一、长正文注入（新增 `placeholders/long_text.py`，253 行）

- `to_body_text`：段落之间用 `\a` 连接；**剥掉除 `\t\n\r` 之外的全部 C0**（尤其 `\f` 分页、
  以及输入里自带的 `\a`）——模型吐一个 `\f` 就能把文书撕成两页、吐一个 `\a` 就能自己断段。
- `markdown_bold_to_sentinel` + `apply_bold_sentinels`：`**x**` 用私用区哨兵穿过 `autoescape`，
  渲染后只处理**含哨兵的段落**，把哨兵区间拆成独立 run 并置 `<w:b/>`——正文不动、模板原有
  加粗一个不碰。无哨兵输入**逐字节相同**返回。
- `DocxRenderer` 与 `draft_service.render()` 出口统一挂钩。

### 二、骨架断言放宽（`draft_service._assert_skeleton_intact`）

从「段落数必须相等」改成「**不含槽位的段落逐字、按序留在成稿里**」。

理由：长正文槽会合法地把 1 段变成 N 段，段落数不再是骨架不变量；真正的不变量是
「模板作者写的那些固定段落一个字都不许变」。反向保护保留：不得减少、不得乱序。

### 三、文书类型层（`DocumentSpec` + `spec_service` + `facts_builder`）

字段：`doc_type` / 骨架 / 各槽来源（`fixed`·`slot`·`llm`）/ `folder_slot` / `ai_brief`。
**prompt 从代码搬进 `ai_brief`**——原来 `prompts.py` 里的 `COMPLAINT_PROMPT` 只有一句
「你是一位专业的法律文书撰写助手」，没有案情结构化输入、没法条、无类案。

`resolve_slot_values` 的四条路径：`fixed` 用文案 / `slot` 取 facts / `llm` 调模型 / 缺的一律进
`pending`，**不得抛异常**。

### 四、一句话入口（`draft_by_type.py` 421 行 + MCP `draft_document`）

六步：取 spec → 组 facts → 取值 → 渲染 → 按 `folder_slot` 解析路径落位 → 快照/未决项。
落位用现成的 `SlotResolutionService.find_slot_paths(folder_template, slot_key)`。

起草**不拍快照**：没有旧内容可留；AI 原稿的基线由律师第一次覆盖保存时自动留下
（`onlyoffice/services/domain_registry.py` 的覆盖前必留底）。

审批分级补 `draft_` 前缀（MEDIUM：会落盘 + 触发模型调用）。

### 五、种子数据（`seed_document_specs`，幂等）

起诉状 / 答辩状 / 管辖权异议申请书三条 spec + `jurisdiction_objection` 槽位。

**管辖权异议复用起诉状的骨架**（两者骨架同构：标题 → 当事人 → 请求事项 → 事实与理由 →
此致 → 法院），**零新增 docx**。答辩状由 `--register-missing-skeletons` 显式开关补登记。

### 六、前端（新 feature `doc-generation`）

项目详情页诉讼分支一个「＋ 生成文书」→ 选类型 → 生成 → 成稿用返回的 `subpath` 走现有
文件夹画布通道。**不用裸 `file_url`**：保存 / 另存为 / 版本都挂在 `kind+owner+subpath` 上，
喂一个 URL 会绕过保存链。失败不关弹窗并原样显示 `reason`。

## 说明与遗留

- **`numId≠0` 是硬边界**：占位符段落若带真实编号（实测 20 个占位符段落 / 6 个模板），
  不能走 `\a`，否则正文会变成 1./2./3. 自动编号。这是**调用方责任**，已在 docstring
  与一条 xfail 用例中记明，未解决。
- **只在案件侧落位**：合同文件夹模板没有对应 `kind` 节点，传 `contract_id` 会返回
  `created=false` + 明确 reason。P0 只覆盖案件侧。
- **档 0 的 19 个模板未接入**本入口，仍走原链路。
- **批注三件事已按用户要求改好**：署名**在起草弹窗里填**（默认 `Lawyer`，随本次请求走、
  不进系统配置）、时间按本地时区带偏移、文案收成「待补：槽名」。
  署名不做成系统配置是刻意的：同一个所里不同案子、不同客户对署名的要求都可能不同。
- **仍未验：`\a` 在真 OnlyOffice 画布里的显示**。本轮用 LibreOffice 把 docx 渲成 PDF 逐页看过，
  首行缩进确实生效（这是渲染器层面的证据）；但 DS 自己的排版引擎是另一套，要验得真开浏览器。
- **事实来源仍不够可靠**：本次联调里 `审理机构` / `当事人信息` / `签名信息` 全部落到未决项
  （填充率 0.33）——`facts_builder` 只能说「能读到就填」，读不到就空着。这不是 bug，是当前
  输入源的边界：案件实体上没有这些字段，材料 Markdown 也没做要素抽取。
- `facts_builder` 的材料来源目前是「按文件名匹配案件材料的解析 Markdown」——按文件名匹配
  本身就不够可靠，因此**不做要素抽取**（据此抽事实等于凭空补量），复杂抽取留待归案时
  把解析任务 id 写到材料上。
