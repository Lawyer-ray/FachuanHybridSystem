# v26.56.26

> 分支：`feat/frontend-doc-parsing`

本版本把社交登录从「扫码即自动建号」改为**只放行已绑定的律师身份**，并补齐「绑定 / 解绑」闭环与后台可查性：管理员在律师页能一眼看出某个飞书身份对应哪位律师。前端登录页同步重构为**可扩展的多登录方式结构**，为后续接 Google 等平台留出入口。**涉及数据库迁移** `social_auth.0002`。

## 后端

### 新功能

#### feat(social_auth): 登录改为「只放行已绑定身份」，不再自动建号

- 新增 `resolve_user_by_social_profile`：按 `(provider, provider_uid)` 解析已绑定律师，未绑定抛 `SocialAccountNotBoundError`，前端提示「请先用账号密码登录，再到账号绑定完成绑定」
- 移除 `link_or_create_user` 与随机账号 / 随机密码生成逻辑——自动建出的 `soc_xxx` 账号对应不上真实律师，后台无法判断「这条飞书记录是谁」，是本次改动的直接动因
- 新增 `bind_social_account_to_user` / `unbind_social_account`，配套 4 类异常区分冲突场景：身份已属他人（`Conflict`）、该律师在此平台已有账号（`ProviderOccupied`）、记录不存在（`NotFound`）、未绑定（`NotBound`）

#### feat(social_auth): 账号绑定 API 与回调双流程

- 新增端点：`GET /social/bindings`（已绑定列表）、`GET /social/provider-catalog`（全部已知 Provider，含未启用，供绑定页显示灰态）、`POST /social/{provider}/bind-session`（发起绑定授权，需登录）、`DELETE /social/{provider}/bind`（解绑）
- 回调视图按 `AuthorizationRequest.extra.bind_user_id` 分流：**绑定流程只关联到已登录用户，绝不新建 Lawyer**；登录流程走「只放行已绑定身份」
- `build_authorization_session` 增加 `bind_user_id` 参数；新增 `_frontend_redirect_url` 统一拼回调 URL，`next_url` 继续走开放重定向校验

#### feat(organization): 律师后台可查社交绑定

- 新增 `SocialAccountAdmin`（只读）：排查「律师说扫码进不去」的第一现场，能反查身份对应哪位律师、替律师解绑换号
- `LawyerAdmin` 新增 `SocialAccountInline`（只读内联）、`social_bindings` 列表列、`SocialLoginFilter` 筛选（已绑定 / 仅账密），并 `prefetch_related` 避免 N+1

### 修复

- social_auth：`transaction.atomic()` 在 Django 6.1 不是 async context manager，原先 `async with transaction.atomic()` 每次调用必抛 `TypeError`。改为把原子逻辑写成同步函数加 `@transaction.atomic`，再用 `sync_to_async` 包装成异步接口
- settings：`FRONTEND_BASE_URL` 与 CORS 默认白名单仍是 Vite 旧端口 5173，改为新一代前端的 5090

### 重构

- social_auth：**「SystemConfig 变更 → 失效 Provider 配置缓存」从 core admin 挪回 social_auth**（新增 `apps/social_auth/signals.py`，监听 `pre_save` / `post_save` / `post_delete`）。原实现写在 `SystemConfigAdmin.save_model` 里，让 core 反向 import 业务 app `social_auth.providers`，被结构门禁 `test_core_no_business_deps` 拦下（该基线只减不增）。改为信号后依赖方向反转，core 不再认识 social_auth；顺带补上**删除配置**时的失效（原先只有保存会清）与「改名后旧键命中前缀」的漏清

### 数据库迁移

- `social_auth.0002_socialaccount_uniq_social_account_user_provider`：`SocialAccount` 新增唯一约束 `(user, provider)`——**一位律师在每个平台只能绑一个账号**，换绑需先解绑；配合既有 `(provider, provider_uid)` 唯一键，同时挡住「同一身份挂两位律师」和「同一律师挂两个同平台账号」

### 测试

- 重写 `tests/ci/unit/social_auth/test_social_auth_services.py`：覆盖未绑定拒绝、绑定幂等、身份被他人占用冲突、同平台第二账号拒绝、一位律师可绑多平台、两位律师各绑各的，以及两条唯一约束在绕过服务层时仍报 `IntegrityError`；解绑测试用 `async_to_sync` 驱动，避免 async ORM 看不到 `django_db` 未提交数据
- 新增 `tests/ci/unit/social_auth/test_social_auth_signals.py`：锁住配置缓存失效行为——本分类键只清对应平台、共用飞书凭证清全部、改名后旧键命中前缀仍清、删除配置清、无关键不动缓存

## 前端

### 新功能

#### feat(auth): 登录页重构为可扩展的多登录方式结构

- 新增 `login-methods.ts` 登录方式注册表（`password` / `embedded_qr` / `redirect`），`buildLoginMethods` 把账密与后端返回的 Provider 合并成统一列表，后续接新平台只需后端加 Provider
- `LoginPage` 改为左右分栏：左侧品牌面板，右侧按选中方式动态渲染；拆出 `LoginBrandPanel`、`LoginMethodSwitch`、`PasswordLoginForm`，登录页不再是巨石文件
- `SocialQrPanel` / `SocialRedirectPanel` 支持自定义会话来源（登录 / 绑定），供绑定页复用

#### feat(auth): 账号绑定页

- 新增 `/settings/bindings` 路由与 `BindingsPage`：列出各平台绑定状态，支持绑定 / 解绑；`BindProviderDialog` 走 `bind-session` 授权
- 导航头像下拉的「个人中心（开发中）」改为「账号绑定」
- 回调页新增 `unbound` / `not_bound` / `already_bound` / `provider_occupied` 错误码文案；`withQuery` 把 `bound=provider` 带到落地页，落地页据此区分「刚绑定成功」与「直接进来看看」

## 注意事项

- **本版本推翻了 v26.56.25 的「扫码后首次登录自动创建并激活 Lawyer」策略**：现在首次使用须先用账号密码登录 → 在「个人设置 → 账号绑定」完成绑定，之后才能扫码登录
- 涉及迁移 `social_auth.0002`，部署需执行 `migrate`；若存量库已有「同一律师同平台多账号」的数据，迁移会因唯一约束失败，需先清理重复绑定
- 「一平台一账号」是刻意限制：同一平台的多个账号（个人号 + 工作号）不允许同时绑定，换绑需先解绑
