# v26.56.25

> 分支：`feat/frontend-doc-parsing`

## 后端

### 新功能

#### feat(social_auth): 飞书内嵌二维码扫码登录 + Provider 抽象支持多平台扩展

- 新增 `FeishuProvider`：基于飞书「二维码 SDK」的网页内嵌扫码登录，二维码渲染在登录页内，不跳转飞书登录页
- `providers/base.py` 引入 `LoginMode`（`redirect` / `embedded_qr`）与 `AuthorizationRequest`，把授权上下文收进单一对象并支持 session 序列化往返，为 PKCE 预留 `code_verifier` 字段；`exchange_code` 签名改为接收 request。后续接 Google / GitHub 只需新增一个 provider 文件
- `ENDPOINTS` 支持多 Host：飞书授权页走旧版 `passport.feishu.cn`（二维码 SDK 只支持旧流程）、令牌走新版 `accounts.feishu.cn/oauth/v3/token`、用户信息走 `open.feishu.cn`
- Provider 配置源从 settings 环境变量迁移到 SystemConfig（新增 `social_auth` 分类，加密存储），admin 修改即失效缓存、无需重启进程；上线换域名只需改 `SOCIAL_AUTH_FEISHU_REDIRECT_URI`
- 新增 `POST /api/v1/social/{provider}/session` 供前端获取授权 URL；`GET /social/providers` 增加 `login_mode` 字段，前端据此分流跳转或渲染二维码
- 回调视图统一 state 校验、`next_url` 开放重定向防护、多平台错误参数归一化

### 修复

#### fix(social_auth): session 端点 404 / CSRF 403

- 尾斜杠：`ApiTrailingSlashMiddleware` 会剥掉 `/api/` 路径的尾斜杠，带斜杠注册导致请求被改写后匹配不上而 404
- CSRF：session 端点原为 Django View，不享有 Ninja operation 的 `csrf_exempt`，与同前缀的 `providers` / `token-exchange` 行为分裂，导致前端 POST 命中 403。已改为 Ninja endpoint 统一行为

## 前端

### 新功能

#### feat(auth): 登录页接入飞书扫码，新增 /social-callback 回调路由

- `LoginPage` 拉取 `/social/providers`，按 `login_mode` 分流；存在内嵌二维码方式时在登录卡片内渲染二维码，账密表单保留为兜底
- `SocialQrPanel`：注入飞书二维码 SDK，`postMessage` 同时校验 `matchOrigin` 与 `matchData`（只校验其一均可被伪造登录），通过后拼接 `tmp_code` 整页导航；含 SDK 懒加载、二维码刷新、错误重试
- `SocialCallbackPage`：解析回调用一次性码换取 JWT 后跳转目标页，`ref` 防止严格模式重复兑换（临时码仅可用一次）；`redirect` 参数做开放重定向校验
- Vite 新增 `/social` 代理，确保与后端同源以正确携带 session cookie（同源下同一 OAuth state 才可校验）

## 注意事项

- 飞书 scope 取最小集 `contact:user.base:readonly`；账号唯一键使用 `union_id`（跨应用稳定）。飞书文档明确警告 email 未经实时验证，不作为登录凭据
- 上线前须在飞书开发者后台「开发配置 → 安全设置 → 重定向 URL」精确登记回调地址（不支持动态路由、`?`/`#` 后缀会被忽略），不匹配会返回 `redirect_uri unmatch`
- 涉及迁移 `core.0025`（SystemConfig 新增 `social_auth` 分类）
- 扫码后首次登录会自动创建 Lawyer 账号并激活（沿用既有策略）；如需改为白名单/审批制，改 `link_or_create_user` 即可
