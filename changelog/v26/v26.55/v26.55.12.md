### 1. fix(documents): 修复"代偿款"等本金类型不被识别导致执行事项解析为空

#### 背景

案件 361 执行依据主文包含"偿还代偿款 4376597.3 元"，点击「解析执行事项」按钮后表单无任何变化，toast 提示"未能确定本金，申请执行事项未生成。"

#### 根因

[`execution_request_parser.py`](backend/apps/documents/services/placeholders/litigation/execution_request_parser.py) 的 `principal_patterns` 仅匹配"借款"和"货款"两种本金类型，"代偿款"不在列表中 → `amounts.principal = None` → service 层因"无法确定本金"直接返回空 preview。

#### 修复

`principal_patterns` 第三条正则的本金类型列表扩展为 `借款|货款|代偿款|垫付款|赔偿款|退款|退还款`。

#### 涉及文件

| 文件 | 变更 |
|------|------|
| `backend/apps/documents/services/placeholders/litigation/execution_request_parser.py` | 扩展本金类型正则 |
| `backend/tests/ci/unit/documents/services/placeholders/litigation/test_execution_request_parser.py` | 新增"代偿款"匹配测试 |

### 2. fix(documents): 修复分段利息"日期在前+基数在后"格式解析错误

#### 背景

案件 361 主文："以 4241725.08 元为基数，自 2025 年 5 月 31 日起至 2025 年 6 月 21 日；以 4376597.3 元为基数，自 2025 年 6 月 22 日起至实际清偿之日止"。原解析结果两段利息的 start_date 都变成"2025-05-31"，丢失第二段的"6 月 22 日"和第一段的"6 月 21 日截止日"。

#### 根因

[`execution_request_clause_extractor.py`](backend/apps/documents/services/placeholders/litigation/execution_request_clause_extractor.py) 的 `date_first_pattern` 对整句用 `search` 只抓到第一个日期"2025 年 5 月 31 日"，然后给所有基数都套这个 start_date。

#### 修复

- 新增 `date_first_full_pattern`：匹配 `自{start}起...以{amount}为基数` 格式，每个分段独立提取 start_date
- 新增 `_extract_segment_end_date` 辅助函数从分段文本提取 `至{end}` 的截止日
- 放在 `date_first_pattern` 之前优先匹配

#### 验证

案件 361 实测解析结果完全正确：第一段 2025-05-31 至 2025-06-21，第二段 2025-06-22 至实际清偿之日。

#### 涉及文件

| 文件 | 变更 |
|------|------|
| `backend/apps/documents/services/placeholders/litigation/execution_request_clause_extractor.py` | 新增 `date_first_full_pattern` + `_extract_segment_end_date` |
| `backend/tests/ci/unit/documents/services/placeholders/litigation/test_execution_request_clause_extractor.py` | 新增 `test_date_first_with_independent_end_dates` 回归测试 |

### 3. fix(documents): 修复 LLM 兜底未触发 + 模型写死 + 失败静默

#### 背景

案件 361 本金为 None（最需要 LLM 兜底的场景），但 `should_try_llm_fallback` 5 个触发条件一个都不满足，导致 ollama 开关开或关都不调用 LLM。即使触发也会失败：模型名 `qwen3.5:0.8b` 不存在（Qwen 无 3.5 版本），本地 ollama 无任何模型，异常被 `except Exception` 静默吞掉。

#### 修复

- [`execution_request_llm_fallback.py`](backend/apps/documents/services/placeholders/litigation/execution_request_llm_fallback.py)：`should_try_llm_fallback` 增加"本金为 None 且无法回退"触发条件；`extract_with_ollama_fallback` 接收 `model` 参数，返回值改为 `tuple[dict | None, str]`（第二个元素是错误信息）；默认模型从 `qwen3.5:0.8b` 改为 `qwen3:0.6b`
- [`execution_request_service.py`](backend/apps/documents/services/placeholders/litigation/execution_request_service.py)：`preview_for_case_number` / `_build_execution_request` 新增 `llm_model` 参数；"未能确定本金"早期返回改为先尝试 LLM 兜底；兜底失败时把错误信息透传到 `warnings`（不再静默吞掉）

#### 涉及文件

| 文件 | 变更 |
|------|------|
| `backend/apps/documents/services/placeholders/litigation/execution_request_llm_fallback.py` | 触发条件 + model 参数 + 错误返回 + 默认模型修正 |
| `backend/apps/documents/services/placeholders/litigation/execution_request_service.py` | 接收 llm_model + 兜底优先 + 错误透传 |
| `backend/tests/ci/unit/documents/services/placeholders/litigation/test_execution_request_llm_fallback.py` | 新增触发条件测试 |
| `backend/tests/ci/unit/test_execution_request_rules.py` | 适配 service 签名变更 |

### 4. feat(cases): LLM 兜底模型从写死 ollama 开关改为动态下拉选择器

#### 背景

案件案号栏目的"解析执行事项"按钮旁原为 ollama checkbox 开关，写死只能用 ollama。当本地无 ollama 或无模型时，开关毫无意义。

#### 新功能

参考 `legal_research` 应用的「LLM 模型」选择器，改为动态 `<select>` 下拉框：
- 后端新增 `GET /admin/cases/case/llm-models/`，复用 `ModelListService().get_result()`，`is_fallback=True` 时后端不可用就返回空列表
- 前端 `fetchLLMModels()` 带内存缓存避免每行重复请求
- 空列表时 select disabled 并显示"（暂无可用 LLM 模型）"
- 用户选择的 `llm_model` 值随「解析执行事项」请求一起传给后端

#### 涉及文件

| 文件 | 变更 |
|------|------|
| `backend/apps/cases/admin/mixins/views.py` | 新增 `llm-models` endpoint + 解析透传 `llm_model` |
| `backend/apps/cases/static/cases/js/case_number_parse.js` | ollama checkbox → 动态 select + "兜底"标签 |
| `backend/apps/cases/static/cases/js/case_number_parse_utils.js` | 新增 `fetchLLMModels()` |
| `backend/apps/cases/templates/admin/cases/case/change_form.html` | switch 样式 → select 样式 |

### 5. fix(cases): 修复 Select2 destroy 控制台报错

#### 背景

案件 Admin 页面控制台报 `select2('destroy') method was called on an element that is not using Select2`。select2 4.x 在抛异常前会用 `console.error` 打日志，即使外层 try/catch 捕获了异常，控制台报错已经产生。

#### 修复

[`admin_case_form_utils.js`](backend/apps/cases/static/cases/admin_case_form_utils.js) `refreshSelect2` 在调用 `destroy` 前检查元素是否有 `data-select2-id` 属性（select2 初始化时自动添加），未初始化则跳过 destroy 直接初始化。

#### 涉及文件

| 文件 | 变更 |
|------|------|
| `backend/apps/cases/static/cases/admin_case_form_utils.js` | destroy 前检查 `data-select2-id` |
