# v27.14.4 · 修复 DB 连接池被 `thread_sensitive=False` 借空导致的 PoolTimeout

## 背景

2026-11-03 13:51，`GET /api/v1/oa-filing/session/105` 连续两次 500：

```
psycopg_pool.PoolTimeout: couldn't get a connection after 10.00 sec
```

现场（`pg_stat_activity`）有 **44 条 `idle` 连接**，不是 `idle in transaction`，
说明没有事务泄漏，而是**连接被池借走后永不归还**。且连接按
`08:27 → 09:56 → 11:26 → 12:56 → 13:56` 的节奏在数小时内单调增长——
约每 90 分钟多一条，与请求量无关，与**线程池扩容**有关。

该接口前端每 2s 轮询一次（`use-auto-run.ts` 的 `POLL_MS=2000`，上限 450 次），
单请求只做一条 `SELECT`，却能把 16 条连接的池打满。

## 根因（已复现）

**`OPTIONS["pool"]` 与 `sync_to_async(thread_sensitive=False)` 的组合必然借空池。**

四个事实叠加：

1. Django 的 `connections` 是 `thread_critical = True` 的**线程局部**对象
   （`django/db/utils.py:148`），每条线程各持一份 `BaseDatabaseWrapper`。
2. 开启 `OPTIONS["pool"]` 后连接生命周期交给 `psycopg_pool`，但「归还」只发生在
   **持有该连接的那条线程**的 `close()` 里
   （`postgresql/base.py:394 _close → pool.putconn`），而 `close` 由
   `request_finished` 信号在**请求收尾线程**触发。
3. `thread_sensitive=False` 让 asgiref 走 `executor = self._executor`（即 `None`），
   最终落到 anyio 默认线程池（`asgiref/sync.py:491`）——ORM 实际在**任意 worker 线程**
   执行。于是连接**借出在 worker 线程 W、归还在事件循环线程/另一个 worker**，
   W 上那份 wrapper 的 `connection` 永远不会 `putconn`，池里被永久借走一条。
4. anyio worker 线程会随负载扩容并长期存活，于是「每条新 worker 线程 ≈ 永久泄漏 1 条连接」。

关键点：**泄漏速率与单请求的 SQL 条数无关，只与线程池扩容速度有关**——
所以表现为「一条轻量 SELECT 的接口突然超时」，极难从业务代码定位。

## 复现与验证

新增 `backend/devtools/repro_pool_leak.py`，同 8 并发、每条只跑 `SELECT 1`：

| 配置 | 结果 |
|:--|:--|
| `DB_POOL=true` + `thread_sensitive=True` | 两批均成功，`pool_available=2` |
| `DB_POOL=true` + `thread_sensitive=False` | **第 1 批即 `couldn't get a connection after 10.00 sec`**，`pool_available=0` |
| `DB_POOL=false` + `thread_sensitive=False` | 两批均成功（无池时每线程自持有连接，不会被借空） |

第三行是关键对照：**`thread_sensitive=False` 本身不致命，致命的是它与连接池叠加**。
这也解释了为什么该问题长期潜伏——直到 `OPTIONS["pool"]` 默认在 dev 打开才爆发。

进一步验证修复方向：池 `max_size=4`、`thread_sensitive=True`、32 并发，
`connections_num=3 / requests_queued=1`，干净收敛，不耗尽。

## 影响面

- 代码里 `thread_sensitive=False` 共 **66 处**，其中 **47 处在 `api/` 层**（真实请求路径），
  横跨 17 个 app：`oa_filing` / `agent` / `automation` / `document_parsing` /
  `invoice_recognition` / `contract_review` / `evidence` / `core` / `organization` 等。
  任何一处被轮询或并发访问都能触发池耗尽。
- **生产暂未命中**：`settings.py:277` 的 `DB_POOL` 默认值是
  `_pool_env == "" and DEBUG`，而 `DEBUG = not is_production`
  （`apps/core/config/django_runtime.py:125`）——即**dev 默认开、生产默认关**。
  但这是脆的：任何人按注释「生产开启时按部署调大」设 `DB_POOL=true`，
  就会立刻踩中同一个坑。这也说明此前的注释假设「线程型 ASGI worker 复用同一组连接」
  是错的——连接是线程局部的，worker 越多泄漏越快。

## 待办（尚未修复，仅完成调查）

本次只做调查与复现，不改生产逻辑。修复方向按优先级：

1. **短期规避**：`DB_POOL` 默认值改为「仅当不存在 `thread_sensitive=False` 调用」，
   或直接默认关闭，并在 `settings.py` 池分支处写明该约束。
2. **根治**：把 `api/` 层的 47 处 `thread_sensitive=False` 收回为 `True`
   （默认值），涉及长任务的地方改为显式 `executor=ThreadPoolExecutor(...)` 并自行管理生命周期。
3. **加固**：池 `reset` 回调或中间件里在请求收尾统一 `close_all()`，
   避免「借出线程 ≠ 归还线程」的残留。
4. **可观测**：把 `pool.get_stats()` 暴露到健康检查，`pool_available` 长期为 0 时告警。
