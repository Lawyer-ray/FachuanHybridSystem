# v27.14.11 · 快递查询：PDF 里的弹窗遮罩 + 每次都要重新扫码 EMS

快递查询工具（`/admin/express_query/expressquerytool/`）两个长期毛病：**导出的 PDF
被 EMS 弹窗挡住关键轨迹**，以及**每新建一个任务都要重新扫码登录 EMS**。

本分支（`fix/ems-pdf-popup-residual`）把两件事一起修掉，并顺带把浏览器生命周期
收拢成「单次任务内启动并关闭」，消除 `asyncio.run()` 收尾永久阻塞的隐患。

---

## 后端

### 修复

#### 一、PDF 里多出一层遮罩：「电话异常反馈」弹窗被原样打印

**现象**：查一个 EMS 运单，PDF 第一页中央压着一个白底弹窗，
标题「电话异常反馈」，两个单选按钮 + 灰色提交按钮，正好盖住物流轨迹。

**根因**：这不是截图工具加的水印（我们的水印只有顶部那条黑底时间 + URL），
而是 EMS 详情页（`express_detail`）到达后才**异步弹出**的浮层。

原来的清理逻辑 `_dismiss_ems_overlays()` 只在**列表页**执行过一次，
跳转详情页之后再没调用过。而弹窗出现在「关闭弹窗之后、生成 PDF 之前」这段无人管辖
的窗口里，于是被 `page.pdf()` 原样打进了 PDF。

还有一个隐性缺陷：兜底逻辑给遮罩设的是 `pointer-events: none`——
**这只让遮罩点不到，`page.pdf()` 读的是 DOM 与样式，照样打印**。

**修复**：

1. 新增 `_close_ems_phone_feedback_dialog()`，用 `text=电话异常反馈` 精确探测，
   优先点右上角关闭，失败再试关闭类按钮，仍关不掉则 `display: none` 兜底。
2. `_dismiss_ems_overlays()` 的兜底从 `pointer-events: none` 改为 `display: none`，
   覆盖遮罩与 `position: fixed` 且 `z-index >= 100` 的顶层大弹窗（保留 300×200
   尺寸阈值，避免误伤正文卡片）。
3. 详情页展开轨迹后连续清理两次（间隔 0.5s），覆盖异步弹出窗口。
4. `service.py` 在 `page.pdf()` 之前再清一次，作为最后一道防线。

#### 二、每个任务都要重新扫码：登录态用完即弃

**根因**三层叠加：

| 层 | 位置 | 问题 |
|---|---|---|
| 1 | `profiles.py` | `express` 使用 `cdp_url=localhost:9222`，无 `user_data_dir` |
| 2 | `core/browser/__init__.py` | `create_browser_async` 走 `browser.new_context()`，**临时上下文，Cookie 不落盘**（同步版 `launch_browser` 早已支持持久化，异步版漏了） |
| 3 | `tasks.py` | 任务结束 `finally: disconnect_playwright()`，主动关掉浏览器 |

**修复**：

1. `express` profile 改为持久化 `user_data_dir` + 有头模式，目录落在
   `backend/data/browser_profiles/express`（不放 `media/`，避免被清理或备份流程带走）。
2. `create_browser_async` 补上 `is_persistent` 分支，走
   `launch_persistent_context_async`，与同步版语义对齐。这是一处**通用能力修复**，
   不止服务于快递查询。
3. `.gitignore` 排除含登录凭证的 profile 目录。

#### 三、任务永久卡在「查询中」（600s 超时）

修完上面两项后冒出两个新故障，堆栈都停在 **`asyncio.run()` 的收尾阶段**，
而非查询本身——说明业务逻辑早就跑完了，卡的是事件循环无法退出。

**第一轮错误的修复**：删掉 `tasks.py` 里的 `disconnect_playwright()`，
理由是"Cookie 已落盘，关不关无所谓"。这个判断错了一半——它忽略了该调用还承担
**让事件循环干净退出**的职责。

结果：持久化上下文仍存活，其后台任务永不结束，`asyncio.run()` 无限等待。
日志证据是 `Closed query result tab` 之后再无任何输出，且对应的 Chromium 进程
（`--user-data-dir=.../browser_profiles/express`）持续存活。

**第二轮错误的修复**：恢复清理调用，并用 `asyncio.wait_for` 给 `__aexit__` 套 15s 兜底。
这反而制造了更隐蔽的问题——**`asyncio.wait_for` 无法中断卡住的 `__aexit__`**：
`create_browser_async` 本质是 `@asynccontextmanager`（async generator），
跨 `asyncio.run()` 边界缓存它之后，关闭时底层 Playwright 连接已死，
`wait_for` 抛 `CancelledError` 试图取消，但 **Playwright 吞掉取消信号**继续等待。
超时保护失效，generator 被留在半开状态，下一次 `Runner.close()` 的
`shutdown_asyncgens()` 就永久卡住。

**最终修复——架构层面收口**：

> 浏览器生命周期必须严格落在单次 `asyncio.run()` 之内，
> 不跨边界持有任何 async generator。

- `service.query_and_save_pdf` 用 `async with create_browser_async(...)` 自包含
  「启动 → 查询 → 出 PDF → 关闭」全过程。
- 移除 `ensure_browser()` 与跨事件循环的上下文缓存（该场景下复用毫无意义，
  因为每个 Django-Q 任务都是一个全新的 `asyncio.run()`）。
- `browser_launcher.py` 退化为常量 + 兼容空操作接口，不再持有任何状态。
- `tasks.py` 直接 `asyncio.run(coro)`，不再需要 `finally` 清理。

净减少约 66 行——前两轮越修越复杂，是因为在「缓存复用」这个错误方向上打补丁。

### 测试

`tests/ci/unit/express_query/` 全套 189 项通过。覆盖重点：

- 弹窗关闭逻辑（精确选择器 + `display:none` 兜底）；
- 浏览器生命周期由 `async with` 自包含，`tasks` 不再持有 context manager
  （**这是两次故障的直接成因，重点回归点**）；
- 查询成功与失败两条路径都能正常收尾，不再依赖外部清理。

### 已知限制

- **首次仍需扫码一次**：`backend/data/browser_profiles/express/` 为空时触发；
  之后 Cookie 落盘，跨任务、跨进程重启均可复用。
- EMS 侧会话过期（通常数天到数周）后需重新扫码，属正常行为。
- 持久化 profile 只能保存一份登录态，当前按**单人使用**设计；
  若将来需要多账号，需按账号拆分 `user_data_dir`。
