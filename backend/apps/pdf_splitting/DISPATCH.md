# 材料预处理的取字调度策略（混合材料包）

> 适用：`frontend/src/features/material-prep`（阅读器自动分段）与
> `backend/apps/{pdf_splitting,document_parsing}`（取字 / 分段 / Markdown）。
> 放在本 app 下而不是 `docs/`：`docs/` 整体被 gitignore（个人分析文档），
> 落在那里等于这份设计不会被任何人读到、AI 会话也不会加载。
> 本文回答一个问题：**一个材料包里同时有扫描 PDF、电子版 PDF、图片、Word 时，
> 每份材料该走哪条取字路径，为什么不能一刀切。**

## 一、问题的本质

一个材料包（`InboxMessage`，`manual_upload` 来源）在数据模型上是「N 个附件」，
每个附件是一个 `BundleMat`。它们**互相独立**：

- 扫描件 PDF：没有文本层，取字只能 OCR / 云端视觉解析
- 电子版 PDF：有文本层，直接抽文本又快又准；但**标题层级、表格、坐标**只有版面解析能给
- 图片（jpg/png）：单页，无「页」概念上的切分需求，但需要 OCR 才能进正文
- Word/Excel：本质是富文本，应由文档解析而非 OCR 处理

**这四类的正确路径完全不同**，所以调度必须**按附件粒度**判定，而不是按「材料包」
或「这次上传」整体判定。

## 二、为什么不能整包一刀切

三种看似合理、实则都错的做法：

| 做法 | 后果 |
|---|---|
| 整包统一走云端 | 电子版 PDF 也上传云端：慢（数十秒/份）、按量计费、且把本来零成本就能拿到的文本重新识别一遍，引入不必要的识别错误 |
| 整包统一走本地 | 扫描件拿不到版面与坐标；大卷宗本地 OCR 慢到不可用（164 页全彩实测分钟级） |
| 按「上传时」判一次 | 后续 `appendPackFiles` 会往同一个包里追加不同性质的文件，一次判定必然过期 |

## 三、现有机制（已具备的部分）

好消息是**按附件粒度的调度骨架已经存在**，不需要重写：

### 3.1 前端：一附件一任务

`use-auto-split.ts` 对 `draft.mats` 逐个提交拆分任务：

```ts
const targets = pdfMats.filter(({ mi }) => canAutoSplitMat(draft, mi))
```

`canAutoSplitMat` 再按「该源是否已被人工拆分 / 跨源合并」跳过，保护律师的
手工操作不被自动结果覆盖。**这是正确的位置**——一个包里 3 份 PDF 会并发建
3 个独立 job，互不影响。

### 3.2 后端：一 PDF 内的逐页决策

`pipeline.py` 的 `PageTextExtractor.extract()` 对**同一份 PDF 内部的每一页**
独立决策，优先级：

```
PDF 文本层（is_effective_text ≥12 字）
  → OCR 页缓存（SHA-256 × 档位 × 页号）
    → 云端整本解析（MinerU / Textin，带版面块 + 表格 + 坐标）
      → 本地并行 OCR 兜底
```

关键设计：`_extract_from_text_layer_or_cache` 先扫一遍把「有文本层的页」直接
定下来，`_resolve_pending_pages` 只对**剩下的页**调云端。

**这意味着「同一个 PDF 里既有电子页又有扫描页」（最常见的混合形态）已经能
正确工作**——电子页零成本，扫描页走云端，结果合并。

## 四、已知缺口（本次要处理和要说明的）

### 缺口 1：非 PDF 材料完全不参与自动分段

`use-auto-split.ts` 只取 `mat.k === 'pdf'`；图片与 Word 被明确排除，提示
「云端识别只支持 PDF，图片 / Word 等请人工归类」。

**这是当前最实际的缺口**：客户交来的材料里，照片（拍照的证据、身份证、
票据）占比很高，全部退回人工 = 预处理没省下人力。

### 缺口 2：有文本层的 PDF 永远不拿版面 / 坐标

`is_effective_text` 只要 12 个字符就判「有文本层」，于是**电子版判决书、合同
全部走纯文本路径，layout 为空 → 没有 bbox → 无法做原文坐标对照，Markdown
也只能是「加了标题前缀的纯文本」**。

这是上一轮调研里「坐标索引对照」拿不到数据的根因。

## 五、调度策略（目标形态）

按 **附件粒度** 分四类，各自选路：

| 材料类型 | 判定依据 | 取字路径 | 产出 |
|---|---|---|---|
| 扫描 PDF | 抽样页文本层为空 | 云端整本解析 → 本地 OCR 兜底 | 文本 + 版面块 + bbox + md |
| 电子 PDF | 抽样页文本层有效 | 文本层抽字（快）**+ 可选云端补版面** | 文本；开「补版面」时同扫描件 |
| 图片 | `k === 'photo'` | RapidOCR 单页取字（前端 `ocrImage`） | 正文（无 bbox） |
| Office | `k === 'office'` | **`document_parsing` 的 `office` 后端**（本地 python-docx / openpyxl） | 文本 + md + 结构 locator |

### 为什么 Office 不用 OnlyOffice

OnlyOffice Document Server（DS）是**编辑器画布**：渲染给人看、保存时回调。
拿它抽文本要绕三处：
1. DS 在独立容器，取文件必经 `/onlyoffice/file` 签名回源 + 容器内转换，比本地读
   OOXML 慢一到两个数量级；
2. 它返回**渲染结果**，拿文字还得再 OCR 一遍——而 Word 里的字本来是结构化的，
   OCR 反而把可靠的字变成可能认错的东西；
3. 大文件要整份传给 DS（1GB 卷宗场景）纯属浪费。

结论：**OnlyOffice 负责"给人看和改"，`office` 后端负责"给机器读"**，两者不重叠。

### 关键原则

1. **判据用「抽样」，不读全文**：判定扫描 / 电子只抽首尾与中间各 1-2 页看
   `get_text()` 长度，避免为判定再扫一遍整本。
2. **失败独立降级**：某一份材料云端失败只影响它自己，其余照常写入草稿。
   前端已是 `Promise.allSettled` 语义，后端 job 也互相独立。
3. **成本可控**：电子 PDF 默认**不**上云端；需要坐标对照时由用户显式开启
   （或仅对「需要坐标的字段提取」场景开启），避免无脑烧钱。
4. **坐标统一归一化**：三家后端 bbox 坐标系不同（MinerU 千分比、Textin 绝对
   坐标 + page_width/height），必须在下发给前端前统一成 0–1，否则绿框会错位。

## 六之二、版面策略开关（layout_mode）

### 问题

默认路径里「电子页读到文本层就定稿」——快、免费、准，但**没有 bbox**（文本层
本身不带坐标/表格结构）。于是「原文坐标索引对照」对电子版 PDF 天然失效，而
电子版恰恰是判决书、合同这类最需要"指着原文说事"的材料。

### 取舍与实现

加一个显式开关，而不是改默认行为——因为两者是真正的成本/能力权衡：

| 取值 | 电子页行为 | 代价 |
|---|---|---|
| `fast_text`（默认） | 只抽文本层，不上云 | 无坐标 |
| `layout` | 也上云端拿版面块 | 这些页也按量计费、更慢 |

实现要点（`pipeline.py`）：

1. `_extract_from_text_layer_or_cache` 收到 `want_layout=True` 时**故意不拿文本层
   定稿**，把这些页留给云端。这是唯一能让电子页拿到 bbox 的办法。
2. **云端不可用/失败时必须回落文本层**（`_fill_from_text_layer`），而不是让页面
   变空、也不是丢给本地 OCR —— 文本层是机器真值，拿它去喂 OCR 等于把可靠的字
   重新猜一遍。
3. **缓存档案名带策略后缀**（`_text_v2` / `_layout_v2`）。不隔离的话，先开补版面
   再关掉，第二次仍会命中带坐标的旧缓存，开关形同虚设。
4. `summary.layout_unavailable_reason` **显式说明"开了但没生效"及其原因**。这是
   最容易让人误判成"开关有 bug"的情形，必须在数据里说清楚。

UI 放在工具栏「⋯」菜单（低频 + 直接影响费用，与「恢复初始分段」同级），
当前选中项带 ✓。策略存 `ReaderState`（随会话复位）而非 `DraftState`：它是
本次识别的成本选择，不该落进材料包草稿、也不该跨包继承。

## 七、改动前必须确认的事

1. `MAX_PAGES` 与云端超时：MinerU `POLL_TIMEOUT=360s`，164 页全彩扫描未必够。
   放宽页数前应先跑一份真实卷宗测耗时，否则表现为「任务超时」而非「跑得慢」。
2. 内存：`fetchAttachmentBytes` 会把整份附件缓存为 `ArrayBuffer`。1GB 文件
   直接吃 1GB 内存，**图片/PDF 预览路径需确认不会同时驻留多份大文件**。
3. 磁盘：收件箱附件无自动清理，1GB × N 会快速堆积；需配合备份与清理策略。
