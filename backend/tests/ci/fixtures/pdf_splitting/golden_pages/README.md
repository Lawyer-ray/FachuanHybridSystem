# golden_pages —— pdf_splitting 取字质量的最小基线集

## 一句话

7 页真实卷宗的取字快照，给 `eval_metrics.py` 当**回归基准**用：
改任何阈值（表格拆分行数、相似度门槛、归一化规则）之前先跑
`scripts/eval_baseline.py`（仓库根），比 CER / cell F1 是涨是跌。

## ⚠️ 这些不是「金标准」，是「基线」

全部 7 页 `gold_known: false`。页面的 `.txt` 是 **MinerU 的原始输出**，未经人工校对。
我没有原 PDF 的视觉裁切，无法判定「张瑞琴」还是「张瑞孝」才对。

所以本目录的用途被严格限定为：

- **能做的**：检测「改完之后变差了吗」——同一份 golden 上，CER 是涨是跌。
- **不能做的**：宣称「当前准确率是 X%」。基准本身可能就是错的，拿它当分母
  算出来的任何百分比都是自欺。`scripts/eval_baseline.py` 的报告开头也明写这一点。

**为什么还要建这批样本**：没有它，就没有任何东西能复跑。
原来的「实测 p62 首行偏差 72px」是人盯屏幕量出来的，改完代码无法证伪。
一批「可能不完全正确但固定不变」的参照，比「完全正确但不存在」有用得多。

## 样本与覆盖

| 页 | 类型 | 字数 | 表格结构 | 选它的理由 |
|---|---|---|---|---|
| p22 | 表格（押品表） | 374 | 17×4 / 68 格 / 填充率 1.000 | 注释把它当「稀疏表例外」样本，正好用来证伪 |
| p23 | 证件（身份证） | 45 | 无 | 极短文本页：只有「名称 + 盖章套话」，字段全丢 |
| p29 | 证件（结婚证内页） | 58 | 3×3 / 7 格 / 含 2 个 `<img>` 格 | 混合图片格，测 `<img>` 剥离 |
| p30 | 证件（结婚证正文） | 164 | 3×2 / 6 格 / 填充率 0.833 | 字段清晰，可人工核验 |
| p31 | 正文（收入证明） | 243 | 无 | 多行短句 + 全角标点 + 套话尾 |
| p38 | 正文（风险告知书） | 275 | 无 | 长句正文，签名行错位明显 |
| p62 | 表格（银行流水） | 3421 | 52×6 / 307 格 / 填充率 1.000 | `_TABLE_SPLIT_MAX_ROWS = 12` 的原始依据 |

三类的覆盖是齐全的：**证件页**（p23/p29/p30）、**表格页**（p22/p29/p30/p62）、
**普通正文页**（p31/p38）。

## 基线已经测出来的两件事

跑 `scripts/eval_baseline.py` 得到（详见 `/tmp/eval_baseline.md`）：

1. **p22 押品表有字率是 1.000，不是注释写的 18%**。
   `markdown_builder.py` 说「17 行 × 4 列只填了 12 格（有字率 18%）」，据此设了
   `_FILLED_CELL_RATIO_BYPASS = 0.30` 这个稀疏表例外。实测 68 格全部有字，
   **例外分支从未触发**——p22 没被拆格是走到 `_split_is_trustworthy` 的别的判据。
   这条注释支撑的阈值前提不成立。

2. **p62 的 52 行与注释一致**，但注释说「拆了也点不中」，实测确认该页走的是
   整表保留（拆块数 0）。所以 `_TABLE_SPLIT_MAX_ROWS = 12` 的行为是对的，
   只是它的**理由**（行高不等累积误差）没有在这批数据上被验证过。

## 隐私处理：做了哪些、没做哪些

**做了**：人名换成 `张三丰` / `李四光` / `王五` / `赵六` / `孙七` / `周八` / `吴九`，
身份证号换成 `110101199001011234`，**p31 的三处联系方式（电话 / 联系电话 / 单位传真）
整段换成等长的 `X` 占位**。替换保持字符数一致（`张瑞琴`→`张三丰` 同为 3 字，
电话号码连同分隔符一并等长替换），所以 CER 的长度口径不受影响。
已 `grep` 确认无真实姓名 / 真实身份证号 / 真实电话残留。

> 联系方式是后来补脱敏的：初版只登记了「人名 + 身份证」，漏了 p31 正文里的电话、
> 联系电话、传真三处。本 README 也不再转写原号码（写出来本身就是一次泄露）。
> p31 的单位名称与地址仍未脱敏（见下方「没做」一节）。
> 联系方式比地址更直接指向自然人，按同一等长规则替换，基线数字不变。

**没做（有意为之）**：

- **p62 的银行账号未脱敏**（`6223221027175157`、`3117063303100701000157`）。
  它们是 `table_cell_f1` 的主要计分对象——307 个格里绝大多数是这些数字。
  换成 `****` 会把「40 行卡号认全了没有」这个真实度量点抹掉，golden 就失去意义。
- **p31 的单位地址未脱敏**（`顺德区杏坛镇新齐宁路…`）。它在正文里，不是人名。

这批文件是**局部判据用途**（只跑 CER / F1），不进任何对外接口、不进 LLM prompt。
若将来要把它扩成「公开 benchmark」，必须先脱敏账号与地址，并重跑基线（数字会变）。

## 新增页面的规矩

1. 从上面那个备份抽页，**不要**用「MinerU 顶层 `text` 覆盖了 layout」的缓存变体；
2. 人名 / 身份证号必须替换，且**保持字符数一致**（否则 CER 口径漂移）；
3. 在 `meta.yaml` 里登记，`gold_known: false` 除非你真的逐字校对了；
4. 重跑 `scripts/eval_baseline.py`，把新数字和旧报告记在一起。
